# 기술 글 품질 체크리스트 (Quality Rubric)

ORDER가 요구한 "독자를 끝까지 이해시키는 깊은 글"을 **통과/미통과로 판정**하기 위한 루브릭이다.
`review-post`의 4축(맞춤법·개연성·테크니컬 라이팅·몰입도)이 *문장 다듬기*라면, 이 체크리스트는
*글이 ORDER의 기준선을 넘었는가*를 본다. 각 항목은 **충족 / 미흡 / 해당없음**으로 평가하고,
미흡이면 **어디서·왜·어떻게 고칠지** 한 줄 보완 지시를 남긴다.

평가는 반드시 **본문에서 근거를 인용**해서 한다(추측 금지). 인용이 안 나오면 그 항목은 미흡으로 본다.

---

## 분류와 가중치

- **필수(MUST)** — 하나라도 미흡이면 게이트 **미통과**. ORDER가 명시적으로 요구한 핵심.
- **권장(SHOULD)** — 미흡이 **2개 이하**면 통과 가능(보고에 남김). 3개 이상이면 미통과.
- **해당시(IF-APPLICABLE)** — 주제에 해당할 때만 평가. 뺐다면 "왜 뺐는지" 메모가 있어야 충족.

게이트 통과 조건: **MUST 전부 충족 + SHOULD 미흡 ≤ 2 + 해당시 항목은 충족 또는 정당한 생략 메모**.

---

## A. 독자 이해 (reader = customer)

- **[MUST] A1 점진적 공개** — 쉬운 개념 → 어려운 개념 순서로 쌓이는가. 뒤 내용이 앞에서 설명 안 한 전제에 기대지 않는가.
- **[MUST] A2 약어 풀어쓰기** — 모든 약어가 첫 등장 시 원어로 풀어쓰여 있는가("OSI(Open Systems Interconnection)").
- **[MUST] A3 미정의 용어 없음** — 비전문가가 막힐 핵심 용어가 사전 설명 없이 등장하지 않는가.
- **[SHOULD] A4 독자 약속** — 도입부가 "이 글을 읽으면 무엇을 이해/할 수 있게 되는지" 약속하는가.

## B. 해부학적 깊이 (anatomical depth)

- **[MUST] B1 "왜"의 존재** — 핵심 주장마다 "왜 그런가/왜 그렇게 설계됐나"가 붙는가. 표면 설명에서 멈추지 않는가.
- **[MUST] B2 메커니즘** — "무엇"의 나열이 아니라 "어떻게 동작하는가"(단계·상태 변화)를 보여주는가.
- **[SHOULD] B3 트레이드오프** — 설계 선택의 대안·한계·비용을 짚는가(한쪽만 칭찬하지 않는가).
- **[SHOULD] B4 건조한 덤프 없음** — 스펙/필드/표를 맥락 없이 나열한 절이 없는가(있다면 "왜 중요한가"가 앞에 있는가).

## C. 완전성 — 필수 섹션 (completeness)

- **[MUST] C1 엄밀한 정의** — 느슨한 통념 → 부족한 이유 → 엄밀한 정의 → 인접 개념 경계가 있는가.
- **[MUST] C2 핵심 원리** — 비유 → 실제 동작으로 내려가는 메커니즘 섹션이 있는가.
- **[MUST] C3 실무 시나리오** — 현실 시나리오가 **단계별**로 있고, 각 단계가 ① 원리/동작 ② 흔한 문제 ③ 진단·해결 ④ 팁/노하우를 갖췄는가.
- **[MUST] C4 오해 포인트** — "흔한 오해 → 왜 틀렸는지 → 올바른 이해" 섹션이 있는가.
- **[MUST] C5 마무리** — 핵심 재진술 + take-away + 다음 학습 거리가 있는가.

## D. 다관점 (multi-perspective)

- **[MUST] D1 다각 조명** — 최소 한 개념을 **2개 이상 관점**(정의+시뮬, 원리+시나리오 등)으로 비추는가.
- **[IF-APPLICABLE] D2 관련 장비** — 물리/논리 장비가 관여하면 역할·동작 계층·한계가 정리됐는가(없으면 생략 메모).
- **[IF-APPLICABLE] D3 관련 프로토콜·기술** — 관여 프로토콜을 "문제→해결" + 핵심 동작/필드/표준 근거로 설명했는가.
- **[IF-APPLICABLE] D4 다이어그램** — 구조/흐름이 복잡하면 그림(`[[[...]]]`) 또는 개념도가 있는가.
- **[IF-APPLICABLE] D5 React 시뮬레이션** — "조작하며 관찰"해야 이해되는 동적 개념이 있으면 시뮬이 있는가(co-located `.tsx` + `client:visible`, 본문에 조작/관찰 안내).
- **[IF-APPLICABLE] D6 실습 과제** — 손으로 확인할 과제가 목표→준비물→절차(번호)→기대 결과→관찰 포인트를 갖췄는가.
- **[IF-APPLICABLE] D7 구현/코드** — 코드가 최소 실행 가능 + 줄/블록 의미 + 흔한 실수를 갖췄는가. 맥락 없이 먼저 나오지 않는가.
- **[IF-APPLICABLE] D8 함정·안티패턴↔베스트프랙티스 결과 비교** — 코드/구현이 등장하는 실무 주제인가? 그렇다면 ❌안티패턴 ↔ ✅베스트프랙티스를(가능하면 코드로) 나란히 제시하고, **두 방식의 결과를 재현 가능한 근거로 비교**했는가. 근거 수준은 ⓐ벤치마크 수치 / ⓑ로그·실패 재현 / ⓒ정성 비교(+"왜 그런 결과인지" 원리) 중 주제에 정직한 것이면 충족(억지 수치 강요 아님).
  - **D7과의 경계**: D7은 *정상 코드 예시 한 벌*을 본다. D8은 *단순 코드 예시가 아니라 ❌접근 ↔ ✅접근의 대비와 결과 분석*에 초점이다(같은 글을 두 항목으로 중복 채점하지 않는다).
  - **언제 "해당"인가(트리거 범위)**: 독자가 *직접 코드를 작성·구현*하는 게 글의 주제일 때만 D8이 해당된다(= D7 구현/코드가 해당되는 글). **진단용 CLI 명령·로그·설정 조회만 등장하는 개념/이론 글**(예: 네트워크 계층 해설에서 `tcpdump`/`ping` 같은 확인 명령)은 D8 **해당없음** — 생략 메모만으로 충족이며, 안티패턴 코드를 억지로 끼워 넣지 말 것(오탐 방지).
  - **skip 우회 역검증(D8 한정)**: 위 트리거에 **해당하는 구현 주제인데도**(독자가 작성할 구현 코드·API 사용 코드가 본문의 핵심인데) D8을 생략 메모로 넘기면 **미흡(FAIL) 처리**한다. "✅가 더 낫다"는 주장만 있고 결과 근거가 없어도 미흡이다.

## E. 정확성·근거 (correctness)

- **[MUST] E1 모순 없음** — 앞뒤가 충돌하지 않는가(수치·정의·결론 일관).
- **[MUST] E2 사실 정확성** — 표준/버전/동작 설명이 정확한가. 근거(RFC/스펙/공식 문서)가 있거나 검증 가능한가.
- **[SHOULD] E3 시대성** — 낡았거나 폐기된 정보가 현재처럼 서술되지 않았는가.

## F. 문체·몰입 (게이트 수준)

- **[MUST] F1 비-덤프 문체** — 스펙만 건조하게 나열하지 않고 "왜 중요한지/무슨 문제를 푸는지"를 먼저 거는가.
- **[SHOULD] F2 도입 훅** — 첫 1~2문단이 독자가 겪는 실제 문제/오해로 끌어당기는가.

## G. 기술 건전성 (MDX/빌드)

- **[MUST] G1 빌드 통과** — `bun run build`가 통과하는가(JSX 문법·import 경로·frontmatter 스키마).
- **[IF-APPLICABLE] G2 시뮬 hydration** — 시뮬이 있으면 import된 컴포넌트로 `astro-island`가 생성되는가(인라인 정의 아님).
- **[SHOULD] G3 안전 가드** — 시뮬에서 `window`/`document` 접근이 `useEffect`/`typeof window` 가드 뒤에 있는가.

---

## 점수 산정 (보고용)

- MUST: `통과 X / 전체 Y` (하나라도 미흡 → 게이트 미통과)
- SHOULD: 미흡 개수 (≤2 통과)
- IF-APPLICABLE: 충족 / 정당한 생략 / 미흡

최종: **PASS** 또는 **FAIL — 보완 필요**. FAIL이면 아래 형식의 보완 지시를 함께 낸다.
