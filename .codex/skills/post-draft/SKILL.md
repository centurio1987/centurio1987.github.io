# Post Draft 스킬

`raws/`에 적어둔 아이디어/단서 메모를 읽어, **주제/제목/요약**, **3가지 플롯 후보**, 그리고 **해당 주제에서 잊지 말아야 할 주의사항**을 담은 스캐폴드 파일을 `draft/`에 `<원본파일명>-draft.md`(입력이 `.mdx`면 `.mdx`) 이름으로 생성한다.

본문 초안 작성은 이 스킬의 범위가 아니다 — 사용자가 플롯을 고른 뒤 별도로 진행한다.

## 워크플로우 상의 위치

```
raws/<메모>.md(x)   (사용자가 작성 또는 conversation-graph-mdx 산출물)
  → [post-draft]    draft/<메모>-draft.md(x)   (제목+요약 + 플롯 3개 + 주의사항)
  → 사용자가 플롯 선택 + 본문 작성
  → review-post → post-finalize → publish-post → src/content/posts/
```

## 동작 순서

### 1. 아이디어 파일 경로 확인

인자로 파일 경로가 전달된 경우 그대로 사용한다. 그렇지 않으면 `raws/` 하위를 살펴 후보를 제시하거나 사용자에게 묻는다:

> "어느 아이디어 파일을 기반으로 draft를 만들까요? (예: `raws/IDEAS.md` 또는 `raws/graph.mdx`)"

경로에 공백/한글이 포함될 수 있으므로 따옴표 처리/이스케이프에 유의한다.

### 2. 아이디어 파일 읽기 및 분석

파일 읽기 도구로 **파일 전체**를 읽는다. 들여쓰기 bullet형, heading+산문형, React 컴포넌트가 포함된 `.mdx` 등 형식이 다양하므로 끝까지 읽어 다음을 식별/생성한다:

- **생성할 글의 제목 (Title)**: 입력 내용을 바탕으로 가장 적합한 제목 생성
- **글의 추정 주제 (Topic)**: 핵심 주제 한 줄
- **한 문장 요약 (Summary)**: 이 글이 결국 무엇을 말하려 하는지
- 핵심 주장 / 하위 논점들
- 사용자가 이미 결론을 내려둔 부분과, 아직 열려 있는 분기점

`raws/IDEAS.md` 처럼 여러 주제가 섞인 메모라면, 어느 항목(주제)을 글감으로 삼을지 먼저 사용자에게 확인한다.
아이디어가 너무 빈약하면(의미 있는 본문이 5줄 미만) 그 사실을 알리고 보강 여부를 묻는다.

### 3. MDX 및 React 컴포넌트 검증 (입력 파일이 .mdx인 경우)

입력 파일이 `.mdx`이고 내부에 React 컴포넌트(예: graph 등)가 포함되어 있다면, 다음 검증 절차를 반드시 수행한다:
- **문법 및 import 확인**: 필요한 컴포넌트가 올바르게 import 되었는지, 닫는 태그나 JSX 문법 오류가 없는지 확인한다.
- **로컬 빌드 검증**: 필요시 로컬에서 `bun run build` 또는 `bun dev` 명령어를 실행하여 Astro가 해당 MDX 컴포넌트를 에러 없이 컴파일하고 렌더링할 수 있는지 검증한다.
- 오류가 발견되면 스캐폴드를 만들기 전에 사용자에게 오류를 보고하고 수정 방향을 제안한다.

### 4. 출력 경로 결정

`draft/<원본 stem>-draft.md` (입력이 `.mdx`인 경우 `.mdx` 확장자 유지)를 만든다.
예: `raws/애그리거트.md` → `draft/애그리거트-draft.md`
예: `raws/arch-graph.mdx` → `draft/arch-graph-draft.mdx`

이미 존재하면 덮어쓰기 전에 사용자에게 확인한다. 필요 시 `draft/` 디렉터리를 생성한다.

### 5. 스캐폴드 생성

`assets/DRAFT_TEMPLATE.md`를 읽어 구조를 베이스로 삼고, 아래 항목들을 채워 `apply_patch` 또는 파일 쓰기로 저장한다.

**채워야 할 항목:**

- frontmatter `source`: 입력 아이디어 파일 경로 (레포 루트 기준 상대경로)
- frontmatter `generated`: 오늘 날짜 (`YYYY-MM-DD`)
- frontmatter `category`: 아래 카테고리 슬러그 중 추정값 (확신이 없으면 비워두고 주석으로 후보 제시)
- frontmatter `title`: 위에서 생성한 제목
- `# [추정 주제 한 줄]` / `> **요약**: [한 문장 요약]`
- **Plot A / B / C**: 각 플롯은 서로 *명확히 다른* 서사 구조를 갖도록 한다. 유형 예시: 개념 정립형 / 사례 분석형 / 의사결정 가이드형 / 반례 중심형 / 진화 과정형 / Q&A형 / 비교 분석형.
  각 플롯마다: `적합한 독자/상황`, `구성 흐름`(3~6단계), `이 플롯의 강점`, `주의할 점`.
- **주의사항 / 잊지 말아야 할 점**: 이 *특정 주제*에 한정된 항목만 4~8개. 보편 글쓰기 팁("결론을 먼저 써라" 등)은 적지 않는다.
- 원본 파일의 내용 (React 컴포넌트 포함)은 적절히 본문 작성 위치에 보존하거나 주석으로 남겨둔다.
- **선택한 플롯** 섹션은 비워둔다.

### 6. 완료 안내

생성된 경로를 알린 뒤 다음 단계를 짧게 안내한다:

> "`draft/<…>-draft.md(x)` 에 스캐폴드를 만들었습니다.
> 마음에 드는 플롯을 `## 선택한 플롯`에 적고 본문을 채우신 뒤, `review-post`로 검토하세요."

## 카테고리 슬러그 (frontmatter `category` 값)

`planning`(기획) · `architecture`(아키텍처) · `strategy`(전략) · `skills`(기술) · `design`(설계) · `research`(리서치) · `quality`(품질) · `leadership`(리더십)

이 슬러그는 `src/content.config.ts`의 enum 및 `src/lib/categories.ts`와 일치해야 한다.

## 분석 시 지킬 원칙

- **3개 플롯은 겹치지 않게.** 서사 구조 자체가 달라야 한다.
- **주의사항은 토픽 특화로.** 입력에서 실제 언급됐거나 자연스럽게 따라오는 항목만.
- **한국어로 작성.** 기술 용어는 원어 그대로(DDD, Aggregate, Composition 등).
- **아이디어 파일을 끝까지 읽는다.**
- **사용자가 이미 내린 결론은 존중한다.**
