### KAN-009: 집필 AI 퍼소나(persona) 개념 정의

#### Context

지금까지 이 블로그는 "AI가 쓴 글"을 `author` frontmatter(`tony`/`ppangto`) 하나로만 구분해 왔다.
그런데 실제로는 성격이 다른 AI 집필 주체가 이미 둘 존재한다 — 기술 글을 쓰는 **빵토 연구원**(`src/lib/authors.ts`
의 `ppangto`)과, 아직 발행된 글은 없지만 인프라는 완성돼 있는 "폭신 대담" 인터뷰 시리즈의 진행자 **빵토 교수님**
(`src/lib/talk.ts`의 `TALK.interviewee`, 하드코딩된 싱글턴). 이 둘은 서로 다른 하위 시스템에 이름·아바타가
각각 흩어져 있고, 이미지도 배너도 시스템별로 다르게 다뤄진다.

이번에 사용자가 자료구조/알고리즘을 가르치는 새 목소리 **빵토 선생님**을 추가하려 하면서(새 프로필·배너 이미지
2장, 존댓말 설명체 + ascii art + before/after 도식 등 10개 규칙의 문체 가이드 제공), "퍼소나는 고유의 voice와
캐릭터 이미지를 가진다"는 개념을 명시적으로 정의해 달라고 요청했다. 목표는 세 퍼소나(연구원/교수님/선생님)를
**하나의 레지스트리**로 묶어, 앞으로 새 퍼소나를 추가하거나 기존 퍼소나의 이미지·문체를 바꿀 때 한 곳만 고치면
되게 만드는 것이다. 지금처럼 `AiBanner.astro`가 이미지 경로와 "빵토 연구원"이라는 문구를 하드코딩해 두면,
선생님 퍼소나는 정의만 되고 실제로는 절대 화면에 나타날 수 없다 — 그래서 배너 렌더링도 퍼소나별로 일반화한다.

#### 변경 사항

##### 1. 새 이미지 → `public/images/authors/`로 이동 + webp 변환

레포 루트에 있는 두 PNG(치수 확인 완료: 하나는 1254×1254 정사각 = 프로필, 다른 하나는 1672×941 와이드 = 배너):

- `ChatGPT Image 2026년 7월 22일 오후 02_10_31.png` → `public/images/authors/ppangto-teacher.webp` (프로필)
- `ChatGPT Image 2026년 7월 22일 오후 02_11_10.png` → `public/images/authors/ppangto-teacher-banner.webp` (배너)

프로젝트에 이미 있는 `convert-images-webp` 스킬(cwebp 기반, quality 82 기본값)로 변환한다. 변환 확인 후 두 PNG
원본은 삭제한다(카드에 명시된 지시).

##### 2. 빵토 선생님 문체 가이드 문서 신설

`src/lib/personas/ppangto-teacher-voice.md` 신설 — KAN-009 카드에 적힌 "문체 규칙 10" + "금지 목록"을 요약·의역
없이 원문 그대로 옮긴다(카드 본문과 1:1 대조해 옮긴 뒤 diff로 재확인). 기존 `.claude/skills/_shared/STYLE_GUIDE.md`
(빵관 토니 개인 문체 가이드, tech-deepdive·review-writing이 참조)와 같은 패턴이며, 퍼소나별로 문서를 분리해
나중에 선생님 명의로 글을 쓰는 스킬이 이 문서를 참조할 수 있게 한다.

파일명 컨벤션 `src/lib/personas/<author-id>-voice.md`을 그대로 "이 퍼소나의 voice 문서 위치"로 삼는다(예:
`ppangto-teacher-voice.md`). `authors.ts`의 `AuthorMeta`에는 별도 `voiceGuide` 필드를 추가하지 않는다 — 이 값은
빌드 타임에 렌더링에 쓰이는 데이터가 아니라 "다음에 이 퍼소나로 글 쓰는 스킬이 참조할 문서 경로"일 뿐이라, 사이트
런타임 스키마(`AuthorMeta`)에 섞기보다 파일명 컨벤션으로 분리하는 편이 "렌더 데이터 vs 집필 메타데이터"
경계가 더 명확하다.

##### 3. 퍼소나 레지스트리 확장 — `src/lib/authors.ts`

- `AuthorMeta`에 필드 추가:
  - `banner?: string` — 퍼소나 고유 상단 배너. **실제 소비처(AiBanner)가 있는 퍼소나에만** 채운다 — 죽은 데이터를
    만들지 않기 위해서다(아래 참고).
  - `bannerAlt?: string` — 배너 alt 텍스트. 생략 시 `AiBanner`가 `${author.name} 퍼소나가 집필했습니다` 같은
    일반 문구로 폴백한다. 이미지 내용과 무관한 획일적 alt를 강제하지 않기 위한 필드.
  - (`voiceGuide` 필드는 추가하지 않는다 — 아래 2번 항목의 파일명 컨벤션으로 대체. 이유는 "반영/기각 판단" 절 참고.)
- id 의미가 한눈에 안 보인다는 지적을 반영해, 배열 위에 한 줄 주석으로 `ppangto`=연구원(베이스), `ppangto-prof`=교수님,
  `ppangto-teacher`=선생님 매핑을 명시한다.
- 기존 `ppangto`(빵토 연구원) 항목에 `banner: "/images/authors/ai-banner.webp"` 추가 — 지금 `AiBanner.astro`에
  하드코딩된 이미지를 퍼소나 소유로 명시적으로 귀속.
- 신규 항목 2개 추가:
  - `ppangto-prof`(**빵토 교수님**) — avatar `/images/authors/ppangto-prof.webp`(기존 파일 재사용), isAI: true.
    **`banner` 필드는 넣지 않는다** — 대담(talk) 포스트는 `TalkLayout`을 쓰고 `PostLayout`/`AiBanner`를 거치지
    않으므로(§5 참고), 여기 banner를 넣어도 현재는 어디에서도 렌더되지 않는 죽은 데이터가 된다. 나중에 교수님
    명의로 일반 포스트(`template: default`)를 쓰게 되면 그때 추가한다.
  - `ppangto-teacher`(**빵토 선생님**) — avatar `/images/authors/ppangto-teacher.webp`, banner
    `/images/authors/ppangto-teacher-banner.webp`(1번에서 만든 신규 파일, 실제로 `AiBanner`가 소비함), isAI: true.
- `content.config.ts`의 `author` enum(`AUTHOR_IDS`)은 `AUTHORS` 배열에서 자동 파생되므로(`AUTHOR_IDS = AUTHORS.map(a => a.id)`)
  스키마 파일을 따로 고칠 필요가 없다 — 두 신규 id가 곧바로 frontmatter에서 유효해진다. (이 파생 패턴은 이미
  `tony`/`ppangto` 2개로 프로덕션에서 동작 중이므로, 항목을 더 추가해도 동일한 배열 리터럴 패턴이라 타입 리스크는
  없다 — `bun run build`로 즉시 확인된다.)

**참고 — `author` frontmatter와 "화면에 보이는 퍼소나"는 이미 분리된 개념이다.** 대담 포스트의 `author` frontmatter는
"누가 실제로 썼는가"(사람 인터뷰어 `tony`, 또는 AI 완전 집필이면 `ppangto`)를 뜻하고, 본문에 보이는 인터뷰이
캐릭터(교수님)는 `TalkLayout`이 `TALK.interviewee`를 통해 **별도로** 렌더한다 — 이 분리는 기존 설계이며 이번
변경이 새로 만드는 모호함이 아니다. 이번 변경은 그 `TALK.interviewee`의 이름·아바타 출처를 `authors.ts`
하나로 통일할 뿐, `author` frontmatter의 의미는 건드리지 않는다.

##### 4. 배너 렌더링을 퍼소나별로 일반화 — `AiBanner.astro`, `PostLayout.astro`

지금 `AiBanner.astro`는 이미지 경로(`/images/authors/ai-banner.webp`)와 alt 텍스트("...빵토 연구원이
집필했습니다")가 상수로 박혀 있어 다른 퍼소나에는 절대 못 쓴다. 이걸 고치지 않으면 선생님 퍼소나의 banner
필드는 정의만 되고 실제로는 어디에도 렌더되지 않는 죽은 데이터가 된다.

- `AiBanner.astro`를 `src`/`alt` props를 받도록 일반화(파일 존재 체크 로직 `fs.existsSync`는 경로만 prop으로 바뀔 뿐
  그대로 유지 — 기존 hero 이미지 조회에도 쓰이는 동일 패턴이라 새로운 위험이 아니다).
- `PostLayout.astro`에서 `author.isAI && author.banner`일 때만 호출하고, alt는 `author.bannerAlt`가 있으면 그 값을,
  없으면 `"${author.name} 퍼소나가 집필했습니다"` 같은 일반 문구로 폴백한다 — 퍼소나마다 다른 이미지 내용에
  획일적 alt 문구를 강제하지 않기 위함(§3의 `bannerAlt` 필드).
- 기존 `ppangto` 글(OSI/WebRTC 시리즈)은 `banner`가 그대로 `ai-banner.webp`를 가리키고 alt 문구도 기존 문구를
  `bannerAlt`로 그대로 옮기므로 시각적 변화 없음(회귀 없음).

##### 5. 대담(talk) 설정을 레지스트리에서 파생 — `src/lib/talk.ts`

`TALK.interviewee.name`/`avatar`를 하드코딩 대신 `getAuthor("ppangto-prof")`에서 가져오도록 바꿔, 빵토 교수님의
이름·아바타 데이터가 `authors.ts` 한 곳에서만 관리되게 한다(지금처럼 두 곳에 중복돼 있으면 나중에 이미지가
바뀔 때 한쪽만 고치는 drift가 생긴다). `banner`/`bannerAlt`/`handLead`/`interviewer`는 대담 시리즈 고유 문구이고
인터뷰어는 사람이라 레지스트리 대상이 아니므로 그대로 둔다.

`src/templates/talk-episode.mdx`의 `author: tony # 인터뷰어(사람)가 작성 주체. AI 완전 집필이면 ppangto` 주석은
그대로 둔다(대담 글의 "작성 주체"는 인터뷰이 페르소나가 아니라 실제로 누가 썼는지를 뜻하므로 이번 변경과 무관).

#### 검증

1. **이미지 변환 직후, 원본 삭제 전**: 변환된 webp 2개를 `file`/`sips`로 열어 치수·손상 여부를 눈으로 확인한다
   (한글 파일명 포함 경로라 쉘 quoting 실수가 나기 쉬우니 변환 스크립트 호출 시 경로를 반드시 따옴표로 감싼다).
   문제없음을 확인한 뒤에만 원본 PNG 2개를 삭제한다.
2. `bun run build` (프로젝트 CLAUDE.md 기준 CI는 bun 사용 — 로컬도 bun으로 통일해 재현성 확보) 성공 확인 — 타입/스키마 에러 없는지.
3. `bun run preview`로 로컬 확인:
   - 기존 OSI 7계층·WebRTC 글(author: ppangto) 상단 배너·하단 작가 카드가 이전과 동일하게 보이는지(회귀 체크).
   - `src/content/posts/`에 `draft: true`인 **임시 스크래치 포스트**(예: `_scratch-persona-check.md`)를 새로 만들어
     `author: ppangto-teacher`로 새 배너/프로필이 정상 렌더되는지 확인한 뒤, 기존 파일을 되돌리는 대신 **이 파일을
     통째로 삭제**한다(기존 draft를 수정 후 되돌리다 실수로 커밋에 남는 위험을 피하기 위함).
4. `git status`로 PNG 원본 2개가 삭제되고 webp 2개만 새로 생겼는지, 스크래치 포스트가 남아있지 않은지 확인.

#### 외부 검토(ChatGPT) 반영 메모

`review-plan`으로 받은 지적 중 실제로 반영한 것: `banner`/`bannerAlt` 필드 분리, `ppangto-prof`에 죽은 `banner`
데이터를 넣지 않음, `voiceGuide` 필드 대신 파일명 컨벤션 사용, id 의미 주석 추가, 이미지 검증 순서·스크래치 포스트
방식으로 검증 절차 보강. 코드베이스를 직접 확인해 기각한 지적: `AUTHORS`가 작가 목록/RSS/사이트맵/JSON-LD 등
넓은 UI에 노출될 위험(실제 소비처는 `AuthorProfile`·`PostList`·`PostLayout`·`TalkLayout`·`index.astro` 6곳뿐이며
전부 `post.data.author` 기반 조회만 하고, 별도 "작가 목록 페이지"나 RSS/사이트맵은 존재하지 않음 — grep으로 확인),
`talk.ts`↔`authors.ts` 순환 의존 위험(`authors.ts`는 다른 모듈을 import하지 않아 순환 불가), `z.enum` 파생 타입
리스크(이미 2개 항목으로 프로덕션 동작 중인 동일 패턴), 스킬 부재 가능성(`convert-images-webp`·`manage-kanban`
모두 이 환경에 설치·확인됨).
