# KAN-069-M724GH — UI 일관성을 전수 검토하여 진단 및 개선 방안에 대한 레포트를 제출해라.

## 전략
지시 원문은 `KANBAN.md` 카드의 `원문:` 블록에 있다(중복 보관하지 않음).

### 이 카드가 내는 것

**진단 리포트 한 장.** 코드를 고치는 카드가 아니다 — 원문이 "검토하여 진단 및 개선 방안에 대한
레포트를 제출해라"이고, 갭을 실제로 메우는 것은 이 리포트가 낳을 후속 카드다. 그래서 `scope` 가
`design-concept/**` 하나로 좁다(리포트 본문 + 카드/검토 문서).

원문 둘째 줄의 "**foundations, component, visual motif, wrapper, guideline 을 전부 구현한 상태여야
한다**"는 이 카드의 실행 지시가 아니라 **판정 기준선**으로 읽는다. 즉 "전부 구현됐는가"를 재고
미달분을 개선 방안으로 낸다. 이 해석은 검토 단계의 판단 항목으로 올린다.

### 두 축을 섞지 않는다

원문이 요구하는 검토는 성질이 다른 둘이고, 섞으면 둘 다 흐려진다.

| 축 | 묻는 것 | 정본 |
| --- | --- | --- |
| **A. 선언** | 스타일 가이드가 bbangto-ui 의 `StyleGuide` 인터페이스를 지켜 정의돼 있는가 | `node_modules/@centurio1987/bbangto-ui-{core,tokens}/dist/index.d.ts` |
| **B. 구현** | 블로그의 실제 지면이 그 선언을 지키는가 · 벗어난 예외는 무엇인가 | `src/**` 전체(astro 59 · tsx 88 · css 6) |

### 계약은 GitHub README 가 아니라 설치된 타입에서 뽑는다

원문은 `https://github.com/centurio1987/bbangto-ui` 를 가리키지만, 이 레포가 실제로 바인딩된 것은
**설치된 패키지 버전**이다(`bbangto-ui-core@1.1.1` · `-tokens@1.2.0` · `-style-guide-catalog@0.3.0` ·
`-visualization@0.2.0`). README 는 버전이 안 박히고 사설 레지스트리라 재현도 안 된다. 그래서 계약은
`dist/index.d.ts` 에서 뽑고, "완전히 구현된 상태"의 기준선은 카탈로그 패키지의 **51종 기성 스타일
가이드**를 실제 구현 사례로 삼아 세운다.

선행 확인으로 잡아 둔 인터페이스 골격(`core/dist/index.d.ts:61`, `tokens/dist/index.d.ts:369`):

```
StyleGuideTokens = name · description? · foundations(필수) · extendedFoundations? ·
                   foundationPresets? · defaultFoundationKey? · guidelines? · meta?
StyleGuide       = StyleGuideTokens + wrapperComponents? · wrapperBlocks? ·
                   wrapperPatterns? · patterns? · visualMotif?
```

원문이 부른 다섯 낱말을 이 필드들에 어떻게 대응시킬지가 S1 의 첫 산출물이다 — `component` 와
`wrapper` 는 인터페이스에 같은 이름의 필드가 없어 임의 대응하면 진단 전체가 흔들린다.

### 블로그 쪽 현황(선행 확인)

- 스타일 가이드 정의는 **둘**이다 — `src/lib/motion/bbangtoTonyStyleGuide.ts` (139줄) ·
  `src/lib/viz/blogVizStyleGuide.ts` (89줄).
- 앞의 것은 `foundationToStyleGuide(theme)` 로 만든다. 그 헬퍼의 문서화된 용도가
  "**foundations-only StyleGuide 로 변환**"(`core/dist/index.d.ts:80`)이라 나머지 네 층이 구조적으로
  빠져 있을 가능성이 높다. S2 에서 필드 단위로 확정한다.
- 실제 지면은 React 가 아니라 **Astro + 순수 CSS** 이고 시각 값의 단일 소스가
  `src/styles/tokens.css` 다. 그런데 `bbangtoTonyStyleGuide.ts` 는 같은 값을 TypeScript 상수로
  다시 적는다(`const PAPER = "#F3EEE4"; // --paper` 꼴). **두 곳이 같은 값을 들고 있으면 갈라진다** —
  이 드리프트가 실재하는지는 값 대조로 판정한다(S2).

### 전수는 눈이 아니라 추출로 한다

"전수 검토"를 정독으로 하면 147개 파일에서 놓치는 것이 반드시 생기고, 결과를 재현할 수도 없다.
`src/**` 에서 색·간격·radius·shadow·폰트·z-index 리터럴을 **기계 추출**해 `tokens.css` 대비로
분류하고, 그 분류에 사람이 판정을 단다. 추출기는 스크래치패드에 두고 레포에는 넣지 않는다 —
게이트로 승격하는 것은 개선 방안의 항목이지 이 카드의 산출물이 아니다.

### 버린 대안

- **웹에서 bbangto-ui README 를 읽어 계약을 세운다** — 버전이 안 박히고 사설 레지스트리라 재현 불가.
  설치된 타입이 이 레포가 실제로 지킬 계약이다.
- **브라우저로 지면을 훑어 눈으로 판정한다** — 렌더 확인은 값이 있지만 그것만으로는 전수가 안 되고
  "무엇을 봤는가"가 안 남는다. 추출 결과를 정본으로 두고 렌더 확인은 표본 검증에만 쓴다.
- **진단하면서 바로 고친다** — scope 가 `src/**` 로 번지고 리포트가 "이미 고친 것들"의 사후 설명이
  된다. 무엇을 먼저 고칠지는 리포트를 받은 뒤 유저가 정한다.

## 검증
<!-- 무엇을 실행해 무엇이 나오면 이 카드가 끝난 것인가. -->
1. **리포트 정본이 있다** — `test -f design-concept/UI_CONSISTENCY_AUDIT.md` 가 통과하고, 본문에 축 A(선언) 층별 판정표와 축 B(구현) 예외 목록, 개선 방안이 모두 있다.
2. **전수가 재현된다** — 스크래치패드의 추출기를 다시 돌려 나온 총계가 리포트에 적힌 수치와 같다. 눈으로 센 수치는 리포트에 넣지 않는다.
3. **근거가 걸려 있다** — 리포트의 모든 판정에 `파일:줄` 또는 인터페이스 필드명이 붙는다. 근거 없는 문장은 뺀다.
4. **회귀 없음** — `bun run build` 통과(리포트는 `design-concept/` 이라 빌드에 안 들어가지만, 대조 과정에서 소스를 건드리지 않았음을 확인한다). `git status --porcelain` 에 `src/` 변경이 0건.
5. **드리프트 대조가 값 쌍으로 남는다** — `tokens.css` ↔ `bbangtoTonyStyleGuide.ts` 불일치가 있으면 (토큰명, CSS 값, TS 값) 세 쌍으로 리포트에 적힌다. 없으면 "0건"이라고 적는다.
