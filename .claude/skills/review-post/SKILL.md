# review-post

작성된 마크다운 글 한 편을 4가지 축으로 자기검토하고, 일관된 포맷으로 결과를 보여준다. 사용자 승인 전에는 어떤 파일도 수정하지 않는다.

검토는 Claude가 직접 수행한다. ChatGPT/Gemini 같은 외부 모델 의견이 필요하면 별도 `review-plan` 스킬을 안내한다(이 스킬은 외부 API를 호출하지 않는다).

## 절차

1. **대상 파일 결정**
   - 사용자가 경로를 명시했으면 그것을 그대로 사용.
   - 아니면 현재 작업 디렉토리 기준으로 `docs/posts/` 하위에서 mtime 기준 가장 최신 `.md` 파일을 자동 선택. 선택한 경로를 사용자에게 한 줄로 알린다 (예: `최근 수정된 글 사용: docs/posts/.../foo.md`).
   - `docs/posts/`가 없거나 후보가 모호하면 어느 파일을 검토할지 묻는다.

2. **글 읽기**
   - `Read`로 전체 본문을 가져온다.
   - 상단의 VitePress front matter(`---` 블록)는 본문 검토 대상에서 제외한다. front matter 자체에 명백한 오류(필수 필드 누락, 잘못된 yaml)가 있으면 결과 끝에 한 줄로만 표기.

3. **4축 검토 수행 (체크리스트)**

   한 번의 패스로 아래 4축 전부를 평가한다. 각 축이 무엇을 보는지는 다음과 같다.

   ### 맞춤법/문법
   - 한국어 띄어쓰기, 조사 오류(은/는, 이/가, 을/를 혼동 등), 중복 어미
   - 외래어 표기와 영문 기술 용어 대소문자 일관성 (예: GraphQL, RDB, DDD, PostgreSQL)
   - 문장부호: 괄호/따옴표 짝 맞춤, 마침표 누락, 연속 마침표
   - 어색한 번역투(피동 남용, "~에 대하여", "~을(를) 통해")

   ### 개연성/논리
   - 주장-근거 연결: "그래서/따라서/즉" 같은 접속이 비약 없이 이어지는가
   - 정의되지 않은 개념이 사전 설명 없이 갑자기 등장하는가
   - 앞뒤 모순 (앞에서 "A는 X다"고 한 뒤 뒤에서 다르게 진술)
   - 근거 없는 일반화/단정 표현 ("모두", "항상", "절대" 등)
   - 예시가 주장을 실제로 뒷받침하는가, 아니면 옆길로 새는가

   ### 테크니컬 라이팅 기준
   - 한 문장 한 주장 / 능동태 우선 / 불필요한 수식어 제거
   - 평행 구조: 목록·표제의 형태가 일관적인가 (예: 명사형 vs 동사형 혼용)
   - 표제(heading)만 훑어도 흐름이 파악 가능한가 (scannability)
   - 독자 수준 대비 전문어가 과하거나 모자라지 않은가
   - 코드/다이어그램이 본문 설명보다 먼저 와서 문맥 없이 등장하지 않는가
   - 약어/축약어 첫 등장 시 풀어쓰기 ("DDD(Domain-Driven Design)")

   ### 몰입도
   - 도입부 훅: 첫 1–2문단이 "왜 이 글을 읽어야 하는지"를 주는가
   - 호흡: 한 단락이 너무 길거나 정보 밀도가 단조로워 지치게 만들지 않는가
   - 예시/장면: 추상만 나열하지 않고 구체 예시가 적절히 끼어드는가
   - 끝맺음: 결론이 흐지부지하지 않고 핵심을 다시 짚어주는가
   - 중복: 같은 말이 다른 표현으로 두 번 이상 반복되는가

4. **결과 출력**

   아래 구조의 마크다운으로 한 번에 보여준다.

   ```
   # 검토: <파일 경로>

   ## 🔴 반드시 수정
   - **[축]** 인용: "원문 일부"
     - 문제: <한 줄 진단>
     - 제안: "수정안" (또는 방향만)

   ## 🟡 검토 권장
   - **[축]** 인용: "..." — <지적> / 제안: "..."

   ## 🟢 잘 된 점 (축별 1줄 이내)
   - 맞춤법: ...
   - 개연성: ...
   - 테크니컬 라이팅: ...
   - 몰입도: ...

   ## 다음 단계
   (a) 직접 수정 / (b) 특정 축만 더 깊게 / (c) 그대로 두기
   ```

   - 인용은 원문에서 그대로 따올 것. 재구성 금지. 너무 길면 `…`로 축약.
   - **[축]** 자리에는 `맞춤법`, `개연성`, `테크니컬 라이팅`, `몰입도` 중 하나를 적는다.
   - 🔴는 명백한 오류(맞춤법 오타, 모순, 깨진 마크다운 등). 🟡는 개선 여지가 있는 판단성 지적.
   - 🟢 "잘 된 점"은 의례적 칭찬을 늘리지 말고 축당 한 줄 이내로 짧게.
   - 심각도가 모호하면 🟡로 분류한다.
   - 지적할 게 없는 축은 해당 항목을 비워두지 말고 "특별히 없음"으로 적는다.

5. **후속 안내**

   결과 출력 직후 다음 선택지를 한 줄로 안내한다:

   > "(a) 지적한 부분 직접 수정 / (b) 특정 축만 더 깊게 보기 / (c) 그대로 두기"

   - (a): 어떤 항목을 반영할지 사용자와 합의한 뒤에만 `Edit`로 파일을 수정한다. 전체를 한꺼번에 일괄 적용하지 말고 항목별로 확인.
   - (b): 사용자가 지정한 축만 재검토해 같은 포맷으로 다시 출력.
   - (c): 아무 변경 없이 마친다.

## 주의

- 사용자가 명시적으로 (a)에 동의한 항목만 파일을 수정한다. 그 전에는 어떤 `Edit`/`Write`도 호출하지 않는다.
- 4축 밖의 거시 피드백(예: "주제 자체를 바꿔라", "이 글은 분리해라")은 묻기 전엔 보태지 않는다. 사용자가 별도로 요청할 때만 응답.
- 외부 모델(ChatGPT, Gemini)의 의견이 필요하다고 판단되면 본 스킬에서 직접 호출하지 말고 사용자에게 `review-plan` 스킬을 안내한다.
- VitePress front matter 영역은 본문 검토와 섞지 않는다. front matter 자체의 yaml 오류는 결과 맨 끝에 한 줄로만 표기.
- 글 길이가 길면 모든 문장을 인용하려 하지 말고 가장 중요한 지적부터 위에 배치한다. 한 축에서 같은 패턴이 반복되면 첫 사례 한두 개만 인용하고 "유사 사례 N건"으로 묶는다.
