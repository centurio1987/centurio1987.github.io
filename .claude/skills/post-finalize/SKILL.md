# Post Finalize 스킬

작성 완료된 포스트 마크다운 파일에 대해 다음 세 가지 사후처리를 한 번에 수행한다.

1. 본문 내 `[[[...]]]` 자리표시자를 OpenAI `gpt-image-1` 로 생성한 webp 이미지로 치환
2. 본문에서 핵심 키워드를 뽑아 frontmatter `tags` 에 머지
3. frontmatter `series` 가 명시된 경우, 같은 series 값의 다른 포스트 링크 목록을 본문 끝에 `## 이 시리즈의 다른 글` 섹션으로 삽입

본문 자체를 새로 쓰거나 리뷰하지는 않는다 — 그 일은 각각 `post-draft`, `review-post` 의 몫이다.

## 동작 순서

### 1. 대상 파일 경로 확인

인자로 파일 경로가 전달된 경우 그대로 사용한다. 그렇지 않으면 사용자에게 묻는다:

> "어느 포스트 파일을 사후처리할까요? (예: `docs/posts/architecture/modeling/2026/애그리거트에서 엔티티가 여러 개인 경우.md`)"

확장자가 `.md` 가 아니면 중단한다. 경로에 공백이 포함될 수 있으므로 따옴표 처리/이스케이프에 유의한다.

### 2. 파일 읽기 + frontmatter 파싱

`Read` 도구로 **파일 전체**를 읽는다. 상단의 YAML frontmatter (`---` 로 감싸진 블록) 를 추출하고, 본문과 분리해서 보관한다.

- frontmatter가 없으면 빈 객체로 시작한다 (저장 시 새로 생성)
- `title` 필드가 없으면 한 번 묻는다:
  > "이 포스트의 제목을 알려주세요 (frontmatter `title` 에 들어갑니다)."
- `series` 는 없어도 무관 — 시리즈 섹션 삽입만 생략한다 (별도로 묻지 않는다)

### 3. `[[[...]]]` 이미지 자리표시자 처리

`OPENAI_API_KEY` 환경변수가 설정돼 있는지 먼저 확인한다. 없으면 빨리 알리고 사용자에게 어떻게 진행할지(이 단계 건너뛰기 vs 중단) 묻는다.

정규식 `\[\[\[([\s\S]+?)\]\]\]` 로 본문에서 자리표시자를 모두 찾는다. 등장 순서대로 1부터 번호를 매긴다.

각 매치에 대해 **순차적으로** (병렬 호출 금지):

1. 안쪽 단서 텍스트를 한국어/한문 그대로 읽고, 이미지 생성에 적합한 **영문 프롬프트로 확장**한다.
   - 단순 다이어그램 단서면 `"minimal, technical diagram, clean line art, no text labels"` 같은 스타일 힌트를 덧붙인다
   - 콘셉트/은유 단서면 `"editorial illustration, muted palette, conceptual"` 같은 톤 힌트를 덧붙인다
   - 글의 톤(딱딱한 기술 글 vs 에세이)에 맞춘다
2. 다음 명령으로 이미지를 생성한다:
   ```bash
   bun run scripts/generate-image.ts "<expanded prompt>" "docs/public/images/<post-slug>/<n>.webp"
   ```
   - `<post-slug>` 는 입력 파일명에서 확장자(`.md`)와 `-draft` 같은 접미사를 제거한 **stem 그대로** 사용 (한글 파일명이면 한글 그대로 — 기존 파일명 컨벤션과 일치)
   - 출력 디렉토리는 필요 시 자동 생성된다
3. 명령이 성공하면 매치된 `[[[...]]]` 블록 전체를 다음으로 치환한다:
   ```markdown
   ![<원본 단서 텍스트 그대로>](/images/<post-slug>/<n>.webp)
   ```
   - **참조 경로**는 `/docs/public` 을 떼고 `/images/...` 로 시작한다 (VitePress public 라우팅)
4. 명령이 실패하면 사용자에게 어느 자리표시자가 실패했는지 알리고, 해당 블록은 그대로 두고 다음 자리표시자로 넘어간다. 전체 중단하지 않는다.

### 4. 태그 추출

본문 전체(이미지로 치환된 결과 기준)를 읽고 **3~8개**의 핵심 키워드를 뽑는다.

- 글의 주제를 검색·분류할 때 누군가 칠 만한 단어를 우선
- 기술 용어는 원어 그대로 유지 (DDD, Aggregate, RDB 등)
- 한국어 개념은 한국어로 (예: "모델링", "도메인 설계")
- 너무 광범위한 단일 단어("아키텍처", "설계") 단독은 피하고 더 특화된 조합 (예: "DDD 모델링", "Aggregate 설계") 우선

기존 frontmatter에 `tags` 배열이 있으면 **머지하고 중복을 제거**한다. 없으면 신규로 추가한다.

### 5. 시리즈 섹션 삽입 (조건부)

frontmatter `series` 가 비어 있으면 이 단계는 **완전히 건너뛴다** (사용자에게 묻지 않음).

`series` 가 있으면:

1. `docs/posts/` 트리 전체를 글롭으로 훑어 같은 `series` 값을 가진 `.md` 파일을 모두 모은다 (`Glob` + 각 파일의 frontmatter 파싱)
2. 현재 파일은 제외한다
3. 정렬 기준:
   - 각 파일 frontmatter에 `order` (숫자) 가 있으면 그 값 오름차순
   - 없으면 파일명 사전순 (fallback)
4. 본문 맨 끝에 `assets/SERIES_SECTION_TEMPLATE.md` 의 형식대로 섹션을 삽입한다
5. **멱등성**: 본문에 이미 `## 이 시리즈의 다른 글` 섹션이 있으면 그 섹션을 통째로 새 내용으로 교체한다 (중복 추가 금지). 섹션 이후에 다른 내용이 있다면 그것도 보존한다 (단, 일반적으론 시리즈 섹션이 마지막에 위치).

각 항목의 링크 경로는 VitePress 라우팅 규칙에 맞춰 `/posts/...` 절대 경로로 적는다. 예:
```
/posts/architecture/modeling/2026/애그리거트에서 엔티티가 여러 개인 경우
```
(확장자 `.md` 는 뗀다.)

### 6. 저장 + 요약 보고

frontmatter + 본문을 다시 합쳐 원본 경로에 덮어쓴다. 처리 결과를 한눈에 보이게 짧게 알린다:

> "사후처리 완료:
> - 이미지 생성: 3개 (성공 3 / 실패 0) → `docs/public/images/<slug>/`
> - 태그: `DDD, Aggregate, RDB 스키마, 모델링` (frontmatter `tags`)
> - 시리즈 링크: 4개 항목 (`## 이 시리즈의 다른 글` 섹션)"

## 분석 시 지킬 원칙

- **원본 이미지 단서를 alt 텍스트로 보존.** `[[[X]]]` 의 `X` 가 그대로 alt 가 된다. 접근성과 본인의 향후 검색을 위해 임의로 줄이거나 영문화하지 않는다.
- **API 호출은 직렬화.** 동시 호출 금지. 한 이미지 생성이 끝나면 다음. rate limit 보호 + 사용자가 진행 상황을 따라가기 쉽게.
- **부분 실패 허용.** 이미지 하나가 실패해도 나머지는 계속 진행하고 실패한 자리표시자는 원본 `[[[...]]]` 그대로 둔다. 전체 작업을 중단하지 않는다.
- **frontmatter 보존.** 기존 필드(`description`, `layout`, `head`, `lastUpdated` 등)는 절대 삭제하지 말고 신규 필드만 추가/갱신한다. 키 순서도 가능한 한 유지.
- **태그 추출은 본문 기반.** 제목만 보고 뽑지 말고 본문 단락의 핵심 명사구·반복 등장 용어를 본다.
- **`OPENAI_API_KEY` 누락은 빨리 실패.** 모든 자리표시자를 시도하기 전에 환경변수 부재를 감지하고 사용자에게 알린다.
- **재실행 멱등성.** 같은 파일에 두 번 실행해도 깨지지 않아야 한다 — `[[[]]]` 가 남아 있는 것만 다시 처리하고, 시리즈 섹션은 통째로 교체하며, 태그는 중복 없이 머지한다.
- **한국어 본문 + 영문 기술 용어.** 출력 메시지도 동일한 톤을 따른다.

## 참조 파일

- `assets/SERIES_SECTION_TEMPLATE.md` — 시리즈 링크 섹션 템플릿
- `scripts/generate-image.ts` (레포 루트 기준) — OpenAI 이미지 생성 Bun 스크립트

## 사전 요건

- 환경변수 `OPENAI_API_KEY` 설정
- Bun 설치 (이 프로젝트의 패키지 매니저)

## 참고 예시 (입력 형태)

작성된 포스트의 본문 일부:

```markdown
Aggregate 루트가 여러 Entity 를 갖는 경우 RDB 스키마를 어떻게 풀어낼지가 문제다.

[[[Aggregate 루트(주문)와 두 자식 엔티티(주문항목, 배송정보)를 잇는 UML 클래스 다이어그램, 카디널리티 표기]]]

위 그림처럼 1:N 관계를 분리해도 ...
```

처리 후:

```markdown
Aggregate 루트가 여러 Entity 를 갖는 경우 RDB 스키마를 어떻게 풀어낼지가 문제다.

![Aggregate 루트(주문)와 두 자식 엔티티(주문항목, 배송정보)를 잇는 UML 클래스 다이어그램, 카디널리티 표기](/images/애그리거트에서 엔티티가 여러 개인 경우/1.webp)

위 그림처럼 1:N 관계를 분리해도 ...
```
