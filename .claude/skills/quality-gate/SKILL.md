# quality-gate 스킬

기술 글이 **ORDER의 기준선**(독자를 끝까지 이해시키는 깊이·완전성·다관점·정확성)을 넘었는지
체크리스트로 **판정**하고, 미달이면 **보완을 반복 요청**해 통과시킨다.

`review-post`가 *문장을 다듬는* 자기검토라면, 이 스킬은 *글이 합격선을 넘었는가*를 보는
**게이트 + 보완 루프**다. 둘은 보완 관계다(겹치는 항목은 게이트 관점에서만 본다).

## 워크플로우 상의 위치

```
tech-deepdive → humanize-post → review-post → review-writing → [quality-gate: 채점→보완→재채점 (≤3회)] → post-finalize → publish-post → ship-post
```

발행 오케스트레이터(`tech-article-publisher`)는 이 스킬을 **발행 전 필수 게이트**로 호출한다.
PASS 전에는 `post-finalize`/`publish-post`로 넘어가지 않는다.

## 동작 순서

### 1. 대상 글 결정
- 인자 경로가 있으면 사용. 없으면 `draft/` → `src/content/posts/`에서 mtime 최신 `.md`/`.mdx`를 골라 한 줄로 알린다.
- `Read`로 본문 전체를 읽는다. frontmatter와 `draft/` 스캐폴드 잔재(`## 플롯 후보` 등)는 채점 대상에서 제외한다.
- MDX면 import/`<Comp client:visible />`/co-located `.tsx`의 존재도 함께 확인한다(G2/G3 평가용).

### 2. 채점 (1라운드)
`assets/QUALITY_CHECKLIST.md`의 모든 항목을 순서대로 평가한다.

- 각 항목: **충족 / 미흡 / 해당없음** + **본문 인용 근거**(인용 못 하면 미흡). 해당없음은 "왜 빠졌는지 메모가 있는가"로 검증.
- 필요하면 사실성(E2/E3) 확인에 `WebSearch`/`WebFetch`를 쓴다. G1(빌드)은 MDX/코드가 있으면 `bun run build`로 실제 확인한다.
- 점수 산정 후 **PASS / FAIL** 판정.

판정 규칙(체크리스트와 동일):
> **PASS** = MUST 전부 충족 · SHOULD 미흡 ≤ 2 · IF-APPLICABLE은 충족 또는 정당한 생략 메모.
> 그 외는 **FAIL**.

### 3. 결과 출력
```
# 품질 게이트 (라운드 N): <파일>

판정: ✅ PASS  /  ❌ FAIL — 보완 필요
- MUST: 통과 X/Y   SHOULD: 미흡 K건   IF-APPLICABLE: 충족 a / 생략 b / 미흡 c

## ❌ 미흡 항목 (보완 지시)
- **[코드 Cn]** 인용: "원문 일부"
  - 문제: <기준 대비 무엇이 부족한가 한 줄>
  - 보완: <어디에·무엇을·어떻게 더할/고칠지 구체적으로>
- ...

## ✅ 충족 (요지만, 항목코드 나열)
- A1, A2, B1, ...
```
- 인용은 원문 그대로(길면 `…`). 같은 패턴 반복은 첫 사례 + "유사 N건".

### 4. 보완 루프 (FAIL일 때, 핵심)
미통과면 **기준선 통과까지 반복**한다. 무한 루프 방지를 위해 **최대 3라운드**.

1. 위 "보완 지시"를 실행한다 — 단순 문장 교정은 이 스킬이 직접 `Edit`하고,
   **누락 섹션·깊이 부족·시나리오 단계 보강처럼 새 집필이 필요한 보완은 `tech-deepdive`에 위임**한다
   (해당 섹션만 보강하도록 구체 지시 전달). 시뮬/빌드 깨짐은 `REACT_SIM_GUIDE.md` 규약으로 고친다.
2. 보완 후 **2단계로 돌아가 재채점**한다. 라운드 번호를 올린다.
3. **PASS면 종료**. 여전히 FAIL이고 3라운드를 채웠으면 **멈추고** 남은 미흡 항목 + 왜 자동 보완이 어려운지를
   사용자에게 보고한다(주제 범위·사실 확인 한계 등). 임의로 통과 처리하지 않는다.

호출 맥락에 따라:
- **오케스트레이터(`tech-article-publisher`) 안에서**: 루프를 자동으로 돌리되, 라운드마다 무엇을 고쳤는지 간단히 남긴다.
  3라운드 후에도 FAIL이면 발행을 막고 사용자 판단을 구한다.
- **사용자가 직접 호출**: 라운드 1 결과를 보여준 뒤 "(a) 기준 통과까지 자동 보완 / (b) 항목 골라 보완 / (c) 여기까지"를 묻고 진행한다.

### 5. 종료 보고
최종 판정(PASS/FAIL), 돈 라운드 수, 라운드별 핵심 보완, 남은 미흡(있으면)을 한 번에 보고한다.
PASS면 다음 단계(`post-finalize` → `publish-post`)를 안내한다.

## 참조 파일
- `assets/QUALITY_CHECKLIST.md` — 통과 판정 루브릭(MUST/SHOULD/IF-APPLICABLE, 가중치, 점수 산정)

## 주의
- **판정 근거는 본문 인용으로**. 추측으로 충족 처리하지 않는다.
- **자동 통과 금지**: 라운드를 다 써도 미통과면 그대로 보고한다. 기준을 낮춰 통과시키지 않는다.
- **위임 경계**: 새 집필이 필요한 보완은 `tech-deepdive`, 사실성 재검토는 codex/agy(`review-article.sh`)를 활용한다 — 이 스킬은 *판정과 보완 오케스트레이션*이 책임.
- `review-post`와 중복되는 문장 단위 지적은 게이트(합격선) 관점으로만 다룬다 — 세부 교정은 `review-post`에 맡긴다.
- 빌드(G1)·hydration(G2)은 추측하지 말고 실제 `bun run build`/`astro-island` 마크업으로 확인한다.
