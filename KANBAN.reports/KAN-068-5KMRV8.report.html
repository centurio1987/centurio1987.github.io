이 카드가 무엇을 끝내려는가

홈 화면에서 맨 위 메뉴 줄의 왼쪽 끝과 그 아래 본문의 왼쪽 끝을 눈으로 이어 보면 두 선이 어긋나 있습니다. 유저가 이 카드에 적어 준 지적 두 줄 중 하나가 그것이고요. 다른 하나는 홈의 본문 폭과 블로그 탭(글 목록)의 본문 폭이 서로 다르다는 것입니다.

용어부터 정하고 가겠습니다. KAN-068-5KMRV8 은 칸반 보드가 카드마다 붙이는 고유 번호이고, 뒤의 여섯 글자는 같은 번호가 두 번 나오지 않게 붙는 꼬리입니다. GNB(Global Navigation Bar)는 모든 페이지 맨 위에 같은 모양으로 얹히는 메뉴 줄이고요. 그 GNB 와 맨 아래 푸터를 묶어 셸이라고 부르겠습니다. 어느 지면으로 가도 따라오는 껍데기라는 뜻입니다.

KAN-068-5KMRV8
└──┬──┘ └──┬─┘
   │       └ 꼬리 여섯 글자 — 같은 번호가 두 번 나오지 않게 붙는다
   └ 카드 번호

셸 = GNB + 푸터.  어느 지면으로 가도 따라온다
      ─── GNB ───
          본문       <- 지면마다 달라지는 쪽
      ── 푸터 ──

지금 홈에서 벌어지는 일을 폭만 남겨 그리면 이렇습니다.

지금 (/ 홈)
  GNB · 푸터  |------- 720 -------|
  본문        |---------- 1100 ----------|      <- 두 선이 안 맞는다

끝난 뒤 (/ 홈)
  GNB · 푸터  |---------- 1100 ----------|
  본문        |---------- 1100 ----------|

이 카드가 끝나면 달라지는 것은 셋입니다.

  • 페이지 폭이 숫자가 아니라 이름으로 정해집니다. 읽는 판 720px 과 넓은 판 1100px, 둘뿐입니다.
  • 셸이 그 지면의 폭을 따라갑니다. 한 화면 안에서 GNB 와 본문의 좌우 끝이 같은 선에 섭니다.
  • 그 규칙이 디자인 정본 문서에 적히고, 같은 일이 다시 생기면 잡아내는 검사가 남습니다.

솔직하게 남는 것도 하나 적어 둡니다. 홈은 1100px, 글 목록은 720px 로 여전히 다릅니다. 지적 두 줄 중 첫 줄은 값을 맞추는 방식으로 닫히지 않습니다. 규칙으로 닫히죠. 왜 그런지는 바로 다음 절에서 풉니다.

끝난 뒤에도 값은 다르다 — 어긋나지 않을 뿐이다

  / 홈                      /posts 글 목록
   GNB  |---- 1100 ----|     GNB  |-- 720 --|
   본문 |---- 1100 ----|     본문 |-- 720 --|
        한 화면 안에서 같은 선    한 화면 안에서 같은 선

그리고 이 리포트 아래쪽 「루트 독립성」 절은 다른 카드와 경로가 겹치지 않는다고 적어 줄 텐데, 그 문장은 조건을 달고 읽어야 합니다. 조건이 무엇인지는 「막힐 만한 지점」에서 숫자와 함께 말씀드리겠습니다.

왜 이 접근인가

지적이 두 줄이라 문제도 둘로 보이지만, 뿌리는 하나입니다. 페이지 컨테이너의 폭을 정하는 토큰이 --content-max: 720px 하나뿐인데(src/styles/tokens.css:42), 세 지면이 그 토큰을 안 쓰고 숫자를 CSS 에 직접 적어 두었습니다. 토큰(CSS 커스텀 프로퍼티)은 값에 이름을 붙여 한 곳에서 고칠 수 있게 하는 장치입니다.

숫자가 직접 적힌 자리는 셋입니다. 홈의 히어로 영역과 최근 글 영역이 각각 1100px(src/pages/index.astro:162 · :274), 글 지도가 960px(src/pages/graph.astro:410). 반대로 셸은 토큰을 그대로 읽습니다(Header.astro:35 · Footer.astro:54). 그래서 홈에서는 셸 720 대 본문 1100 이 되고, 홈과 블로그 탭 사이에서는 1100 대 720 이 됩니다. 같은 원인이 지면 안에서 한 번, 지면 사이에서 한 번 드러난 것이죠.

토큰을 읽는 쪽                      숫자를 직접 적은 쪽
  Header.astro:35   720            index.astro:162   1100
  Footer.astro:54   720            index.astro:274   1100
        ↑                          graph.astro:410    960
  --content-max: 720px                    ↑
  (tokens.css:42)                  토큰을 안 거친다 — 그래서 셸과 어긋난다

전수로 확인한 결과이기도 합니다. grep -rnE 'max-width: *[0-9]{3,}px' src/ 로 훑어 페이지 컨테이너에 숫자가 적힌 자리는 위 셋이 전부였습니다. /design/* 카탈로그가 1180px 을 쓰지만 검색 엔진 색인에서 제외되는(noindex) 내부 문서라 이 카드의 범위 밖입니다.

잠깐 확인 하나만 해 볼까요. 두 지적이 하나의 원인에서 나온다면, 고칠 것은 "폭 값"일까요 "폭을 정하는 방법"일까요? 이 카드가 고른 답은 뒤쪽입니다.

값을 고치는 길    720 이냐 1100 이냐를 고른다  ->  선택되지 않은 쪽 지면이 망가진다
방법을 고치는 길  폭에 이름을 붙인다          ->  지면이 자기 이름을 고른다

접근 — 폭 토큰 둘을 두고, 셸이 지면을 따라가게 합니다. 유저가 2026-08-24 에 고른 방식입니다.

BaseLayout width="wide"   ->  --shell-max: var(--wide-max)     (1100)
BaseLayout (기본 "read")  ->  --shell-max 를 아예 안 깐다
                                        |
Header / Footer:  max-width: var(--shell-max, var(--content-max))
                                                    ^ 없으면 720 이 쓰인다

여기서 가장 중요한 줄은 var(--shell-max, var(--content-max)) 입니다. 쉼표 뒤가 폴백(fallback), 즉 앞의 값이 없을 때 대신 쓰는 값이에요. 이 폴백이 있어서 width 를 안 넘긴 지면 여덟 곳은 지금과 한 픽셀도 달라지지 않습니다. 폴백을 빼면 그 여덟 지면의 셸에서 폭 제한이 사라집니다. 새 규칙을 넣으면서 기존 지면을 안 건드리는 장치가 이 한 줄입니다.

토큰 쪽 배분은 이렇습니다. --content-max: 720px 는 그대로 두고 읽는 판이라는 역할을 줍니다. 글 목록 · 카테고리 · 글 상세 · 폭신 대담 · 404 가 여기에 속하죠. --wide-max: 1100px 를 새로 만들어 넓은 판으로 쓰고, 홈과 글 지도가 여기에 들어옵니다. 글 지도의 960px 도 1100px 로 흡수해서, 폭의 종류를 셋에서 둘로 줄입니다.

폭에 붙는 이름은 둘뿐이다

  읽는 판  --content-max   720px  ─ 글 목록 · 카테고리 · 글 상세 · 폭신 대담 · 404
  넓은 판  --wide-max     1100px  ─ 홈 · 글 지도  (글 지도의 960 을 여기로 흡수)

버린 대안 둘. 두 안 모두 첫 번째 지적을 글자 그대로 해결하지만, 실측해 보면 값이 지면을 망가뜨립니다.

전부 720px 로 통일하는 안부터 봅시다. 홈 히어로는 1fr 1fr 두 열 그리드입니다. 720 에서 좌우 패딩 48px 씩 96 을 빼면 624 가 남고, 열 사이 간격 36 을 빼면 588, 반으로 나누면 한 열이 294px 입니다. 그 좁아진 열에 회전한 폴라로이드가 들어가야 하는데 회전한 상태의 바운딩 폭이 141px 이고, index.astro 에 남아 있는 실측 주석은 769px 에서 여백 129px · 964px 에서 166px 입니다. 폭을 줄이면 이 여백은 129px 보다 더 좁아지죠. 카드는 타이틀 우측 여백이 사라진다고 적고 있습니다. 글 지도도 960 에서 720 으로 줄면 노드가 밀집합니다.

720 − 좌우 패딩 48×2(=96)  = 624
624 − 열 사이 간격 36      = 588
588 ÷ 2                    = 294px   <- 히어로 한 열

  이 294px 안에 회전한 폴라로이드(바운딩 폭 141px)가 들어가야 한다
  실측 주석: 769px 에서 여백 129px · 964px 에서 166px  -> 더 줄이면 더 좁아진다

전부 1100px 로 통일하는 안은 방향이 반대인데 대가는 더 큽니다. 디자인 정본 design-concept/DESIGN_CONCEPT.md:106 의 720px 이 "포스트 본문"에 붙은 값이라, 이 안을 고르면 정본을 뒤집는 것부터 해야 합니다. 그다음이 실제 작업이고요. 글 목록의 한 행은 날짜 160px · 제목 · 화살표로 짜여 있는데 이게 1100px 로 벌어지고, 글 상세의 히어로와 PostNav · SeriesEpisodes 카드가 전부 커집니다. 읽는 지면 여덟 곳을 다시 디자인하는 일입니다.

정본이 이 접근을 지지한다는 점도 짚어 둘 만합니다. 같은 문서 90~96행은 홈 히어로를 1fr 1fr 두 열 그리드에 마스코트를 얹는 구조로 따로 규정합니다. 정본은 이미 지면마다 폭이 다르다는 것을 전제하고 있고, 홈의 1100px 을 금지한 곳도 없고요. 없던 것은 값이 아니라 규칙이었습니다.

DESIGN_CONCEPT.md:106     "포스트 본문" max-width 720px   <- 글 지면 하나에 붙은 값
DESIGN_CONCEPT.md:90~96   홈 히어로 = 1fr 1fr 두 열 + 마스코트  <- 홈은 따로 규정
                          정본은 이미 "지면마다 폭이 다르다"를 전제한다

여기서 헷갈리기 쉬운 지점을 하나 짚겠습니다. 일관성을 모든 지면이 같은 값을 갖는 상태로 읽으면, 이 계획은 첫 번째 지적을 안 푼 것처럼 보입니다. 그런데 같은 값으로 맞추는 순간 히어로 한 열이 294px 로 줄고 폴라로이드 자리가 사라지죠. 즉 값을 맞추는 쪽이 오히려 지면을 못 쓰게 만듭니다.

값을 맞추는 것이 아니라 규칙을 맞춥니다. 한 화면 안에서는 같게, 지면 사이에서는 역할대로.

무엇을 어떤 순서로

work 는 실행 계획에 S1~S5 로 번호가 붙은 한 줄, 즉 이 카드가 쪼갠 최소 실행 단위입니다. 다섯 개 전부 아직 미착수라 진행은 0/5 입니다. 하나씩 무엇을 하는 단계인지 보겠습니다.

S1 은 규칙을 만드는 단계입니다. --wide-max 토큰을 만들고, 셸이 --shell-max 를 읽게 배선하고, BaseLayout 에 width prop(컴포넌트에 넘기는 설정값)을 답니다. 특이한 점 하나. 이 단계가 끝나도 화면에는 아무 변화가 없어요. 그리고 그게 오히려 완료 기준입니다 — 폴백 덕에 읽는 판 여덟 곳의 셸 폭이 720px 그대로여야 하니까요.

S1 만 들어간 뒤, 읽는 판 여덟 지면

  변경 전   GNB |-- 720 --|   본문 |-- 720 --|
  변경 후   GNB |-- 720 --|   본문 |-- 720 --|   <- 한 픽셀도 안 움직인다

S2 는 홈에서 1100 이라는 숫자 둘을 걷어내고 넓은 판이라고 선언하는 단계입니다. 두 번째 지적이 여기서 사라집니다. 홈의 GNB · 히어로 · 최근 글 · 푸터가 전부 같은 1100px 선에 서게 되죠.

S3 은 글 지도의 960px 을 넓은 판으로 흡수합니다. 이 단계를 지나야 폭의 종류가 720 · 960 · 1100 셋에서 둘로 줄어듭니다.

폭의 종류
  S3 앞   720 · 960 · 1100   (셋)
  S3 뒤   720 · 1100         (둘)

S4 는 만드는 단계가 아니라 재는 단계입니다. 푸터가 720 에서 1100 으로 넓어지면 그 안의 저자 라인업이 같이 벌어지는지 실제로 재고, 벌어졌으면 라인업에만 상한을 줍니다. 셸 폭은 되돌리지 않습니다. 되돌리면 두 번째 지적이 그대로 되살아나니까요.

S4 에서 칸이 벌어졌을 때
  고치는 곳     AuthorLineup 에만 현행 렌더 폭 상한 + 중앙 정렬
  안 고치는 곳  셸 폭 (되돌리면 두 번째 지적이 그대로 살아난다)

S5 는 규칙을 정본에 적고 검사를 남기는 단계입니다. 이 단계가 없으면 다음에 새 지면을 만드는 사람이 또 숫자를 직접 적게 됩니다. 같은 카드가 나중에 다시 올라오는 것을 막는 자리가 여기예요.

순서에는 이유가 있습니다. S2 와 S3 는 S1 이 만든 토큰과 prop 이 있어야 성립하므로 S1 이 무조건 먼저입니다. S4 는 넓은 판 두 지면의 푸터를 나란히 재는 일이니 S2 와 S3 가 둘 다 끝나야 하고요. S5 가 마지막인 것은 S4 에서 라인업 상한값이 나올 수 있고, 그 값도 정본에 함께 적어야 하기 때문입니다. 아래 그림의 대괄호가 배치 — 한 번에 끊어서 수행하는 work 묶음이고, 번호는 수행하는 차례를 뜻합니다.

S1 ─┬─ S2 (홈)      ─┐
    └─ S3 (글 지도)  ─┴─ S4 (푸터 실측) ── S5 (정본 · 재발 검사)

    [------- 배치1 -------]   [--------- 배치2 ---------]

두 가지 수행안

먼저 사실 하나를 적어 둡니다. 배치1 문서는 S2 와 S3 를 순차로 두면서 병렬로 나누는 관점을 이미 버렸고, 그 근거로 dist/ 충돌을 적어 두었습니다. 다만 어느 쪽으로 수행할지는 이 리포트를 읽고 정하는 몫이라, 아래 둘을 같은 항목으로 나란히 적습니다.

배치의 크기 기준이 시간이 아니라 work 개수라는 점부터 짚고 가겠습니다 — 이 프로젝트는 work 3~4개를 한 세션 예산의 절반으로 봅니다. 이 카드는 배치1 에 S1 · S2 · S3 셋, 배치2 에 S4 · S5 둘을 담았습니다. 두 배치 모두 상태는 「계획」이고 진행은 0 이고요. 배치2 가 기준보다 작은 것은 S4 가 S2 · S3 를 둘 다 요구해서 앞으로 당길 수 없기 때문입니다.

단일 에이전트 수행

  • 어떻게 도는가: 한 세션이 S1 → S2 → S3 를 순서대로 끝내고(배치1), 끊었다가 S4 → S5 를 끝냅니다(배치2). 브랜치는 KAN-068-5KMRV8 하나입니다.
  • 이 카드의 의존 구조에서는: 의존이 거의 전부 직렬이라 계획 순서를 그대로 따라가면 됩니다. 서로 의존하지 않는 것은 S2 와 S3 한 쌍뿐입니다.
  • 얻는 것: 중간에 멈춰도 사이트는 정상으로 그려집니다. S1 의 폴백이 그 보증이고, work 마다 bun run build 와 bun run deco:verify 가 자기 완료 기준에 붙어 있습니다. 되돌릴 대상은 배치1 기준 파일 여섯 개입니다.
  • 감수하는 것: S2 와 S3 를 동시에 진행하지 못합니다. 다만 이 카드에서 병렬로 벌 수 있는 구간이 그 한 쌍뿐이라, 내주는 것도 그 한 쌍입니다.

오케스트레이션 수행

  • 어떻게 도는가: 병렬 서브에이전트에 work 를 나눠 주고, 동시에 도는 분량의 합이 세션 예산 절반을 넘지 않게 끊습니다. 이 카드에서 나눌 수 있는 것은 S2 와 S3 한 쌍입니다.
  • 이 카드의 의존 구조에서는: S1 이 둘의 선행이라 혼자 먼저 끝나야 하고, S4 는 S2 · S3 가 둘 다 끝나야 성립하며, S5 는 S4 뒤입니다. 병렬 구간은 가운데 한 칸입니다.
  • 얻는 것: S2 는 index.astro, S3 는 graph.astro 라 파일이 겹치지 않습니다. 소스만 놓고 보면 동시에 진행해도 서로의 편집을 덮지 않습니다.
  • 감수하는 것: 두 work 모두 완료 기준에 bun run build 와 deco:verify 가 있는데, 같은 워크트리(작업 폴더 한 벌)에서 병렬로 돌리면 두 실행이 같은 빌드 결과 폴더 dist/ 에 동시에 씁니다. 그래서 워크트리를 따로 떼야 하고, 그 준비가 병렬 한 칸을 위한 것이 됩니다. 배치1 문서가 이 관점을 버린 근거로 적어 둔 줄이 그것입니다.

막힐 만한 지점

되돌리기부터 보면 이 카드는 가벼운 편입니다. 배치1 이 되돌릴 대상으로 세는 파일은 여섯 개이고, S1 은 폴백을 갖고 있어 단독으로 들어간 상태에서도 읽는 판 여덟 지면이 한 픽셀도 안 움직입니다. 배치1 중간에 멈춰도 화면은 지금 그대로라는 뜻이죠.

실질 위험은 푸터 한 곳입니다. 푸터 안의 저자 라인업은 width: 100% 에 grid-template-columns: repeat(var(--n), minmax(0,1fr)) 로 짜여 있어서(AuthorLineup.astro:173 · :176), 푸터가 720 에서 1100 으로 넓어지면 저자 컷아웃 칸이 그만큼 비례해서 벌어집니다. 데코 좌표 쪽은 괜찮습니다 — deco.css 에서 폭에 걸린 좌표는 grep 결과 0건이라 입력이 바뀌지 않습니다. 벌어지는 것은 라인업 자체예요. 배치1 에서는 이걸 고치지 않고 관찰만 합니다. 판정과 대응이 S4 이기 때문이고, deco:verify 가 먼저 잡으면 그 자리에서 배치2 를 당깁니다.

AuthorLineup.astro:173  width: 100%
                 :176  grid-template-columns: repeat(var(--n), minmax(0,1fr))

  푸터 720   [저자][저자] …
  푸터 1100  [ 저자 ][ 저자 ] …   <- 칸 폭이 푸터 폭에 비례해 벌어진다

되돌리기 어려운 자리는 배치2 쪽에 둘 있습니다. S4 가 라인업에 상한을 주게 되면 그 값은 실측이어야 합니다. DECO_KIT.md 8절의 컷아웃 규격과 어긋나는 값을 눈대중으로 넣으면 조용히 어긋나고요. 판정은 눈이 아니라 deco:verify 로 합니다. S5 는 디자인 정본을 고치는 일이지만 새 절을 더하는 것이지 :106 을 뒤집는 것이 아니라서, 방향이 바뀌어도 마크다운 한 절을 되돌리면 됩니다.

예산 쪽은 배치1 문서가 초과 지점 없음으로 봤습니다. 세 work 가 전부 CSS 몇 줄 교체와 빌드 확인이어서입니다. 배치2 는 work 가 둘인데 S4 가 새 CSS 를 부를 수 있어, 크기는 작아도 판단이 들어가는 쪽입니다.

배치1  work 3개   CSS 몇 줄 교체 + 빌드 확인      -> 초과 지점 없음 (배치1 문서 판단)
배치2  work 2개   S4 가 새 CSS 를 부를 수 있다    -> 크기는 작고, 판단이 들어간다

마지막이 루트 독립성입니다. 루트는 다른 카드의 하위가 아닌 최상위 카드를 말하고, 독립성 검사는 두 루트가 같은 파일 경로를 건드리는지 봅니다. 이 카드의 검사 결과는 겹침 0건이에요. 그런데 그 0 이 겹치지 않는다는 뜻은 아닙니다.

검사는 카드가 scope 를 적었을 때만 성립합니다. scope 는 그 카드가 손댈 파일 경로 목록이고요. 지금 미완료 루트는 15개인데, 그중 scope 가 적혀 있는 것은 이 카드 하나뿐이고 나머지 14개는 빈칸입니다. 이 카드는 이번에 일곱 경로를 적었습니다 — tokens.css · BaseLayout.astro · Header.astro · Footer.astro · index.astro · graph.astro · DESIGN_CONCEPT.md. 비교할 상대가 없어서 0 이 나온 것이지, 겹치지 않는다고 확인된 것이 아니죠. 지금 상태를 정확히 적으면 판정 불가입니다.

검사가 보는 것 = 두 루트의 scope 가 같은 경로를 건드리는가

  KAN-068-5KMRV8   scope 7 경로  ─┐
  나머지 루트 14개  scope 빈칸    ─┴─ 맞대 볼 상대가 없다 -> 겹침 0건
                                     (겹치지 않는다 != 판정했다)

제목으로 보면 닿을 가능성이 있는 카드가 눈에 띕니다. KAN-069 「UI 일관성을 전수 검토하여 진단 및 개선 방안에 대한 레포트를 제출해라」와 KAN-061 「홈 배경 모션 아일랜드(AmbientAurora/Waves)가 끌고 오는 JS ~130KB 재검토」는 같은 지면을 다룰 수 있는 카드입니다. 다만 둘 다 scope 가 비어 있어 지금 말할 수 있는 것은 여기까지입니다. 아래 「루트 독립성」 절은 병렬로 수행해도 충돌하지 않는다고 적어 줄 텐데, 그 문장은 이 조건 위에서 읽어 주세요.

무엇이 되면 끝인가

넷이 전부 초록이면 끝난 것입니다. 순서대로 무엇을 실행해 무엇을 보면 되는지 적습니다.

첫 항목, 빌드와 검사가 회귀 없이 통과합니다. bun run build · bun run deco:verify · bun run viz:verify 셋을 돌립니다. 하나라도 비0으로 끝나면 그 상태는 나가지 못합니다.

bun run build        ─┐
bun run deco:verify  ─┼─ 셋 다 0 으로 끝나야 한다
bun run viz:verify   ─┘   (하나라도 비0 -> 통과가 아니다)

두 번째 항목, 페이지 컨테이너에 직접 적힌 숫자가 0건입니다. grep -rnE 'max-width: *[0-9]{3,}px' src/ | grep -v 'src/pages/design/' 를 돌려 .hero-inner · .recent · .graph-page · .header-inner · .footer-inner 가 한 건도 안 나오면 통과입니다. 여기서 오해하기 쉬운 지점이 있어 미리 짚습니다. 컴포넌트 내부 상한은 대상이 아닙니다 — AuthorProfile 의 440px, TalkLayout 화자 카드의 520px, 히어로 이미지의 380/500px 은 페이지 컨테이너가 아니라 부품 안쪽 치수라 이 규칙이 겨냥하는 것이 아닙니다.

세 번째 항목, 한 지면 안에서 셸과 콘텐츠 폭이 같습니다. bun run preview 로 띄우고 브라우저 콘솔에서 .header-inner · .hero-inner · .recent · .graph-page · .post-page · .footer-inner 의 getBoundingClientRect().width 를 잽니다. / 와 /graph 에서는 잰 값이 전부 1100 이어야 하고, /posts · /categories/<slug> · 글 상세 · 대담 · /404 에서는 전부 720 이어야 합니다.

잰 값이 한 지면 안에서 같은 숫자여야 한다

  /  ·  /graph                        .header-inner · .hero-inner · .recent
                                      · .graph-page · .footer-inner  -> 전부 1100
  /posts · 카테고리 · 글 상세 · 대담 · /404   .header-inner · .post-page
                                      · .footer-inner              -> 전부 720

마지막 항목, 기본값이 무해합니다. width prop 을 안 넘긴 읽는 판 여덟 지면이 변경 전과 같은 720px 로 그려집니다. --shell-max 의 폴백이 그 보증이고, 세 번째 항목의 720 쪽 측정이 그대로 이 항목의 증거가 됩니다.

세 번째 항목에서 지면마다 다른 숫자가 나오는 것이 정상이라는 점을 마지막으로 남깁니다. 이 카드는 "모든 지면을 같은 폭으로" 만드는 일이 아니라 "한 화면 안에서 어긋나지 않게" 만드는 일입니다. 두 지적 중 첫 줄은 값이 아니라 규칙으로 닫히고, 그 조건을 알고 고른 선택이라는 기록이 남아 있어야 같은 지적이 다시 올라왔을 때 처음부터 다시 따지지 않아도 됩니다.

전략

지시 원문은 KANBAN.md 카드의 원문: 블록에 있다(중복 보관하지 않음).

진단 — 지적 두 건은 같은 뿌리다. 페이지 컨테이너 폭 토큰이 하나(--content-max: 720px, src/styles/tokens.css:42)뿐인데 세 지면이 그것을 안 쓰고 값을 박아 뒀다.

| 지면 | 폭 | 근거 | | --- | --- | --- | | GNB(헤더) · 푸터 | --content-max 720px | Header.astro:35 · Footer.astro:54 | | 홈 히어로 · 최근 글 | 1100px 하드코딩 | index.astro:162 · index.astro:274 | | 글 지도 | 960px 하드코딩 | graph.astro:410 | | 글 목록 · 카테고리 · 글 상세 · 대담 · 404 | --content-max 720px | posts/index.astro:85 · [category].astro:57 · PostLayout.astro:171 · TalkLayout.astro:148 · 404.astro:18 |

지적 1(홈 ≠ 블로그 탭)은 1100 대 720이고, 지적 2(홈에서 GNB ≠ 콘텐츠)는 같은 판에서 720 대 1100이다. 전수 확인 결과 페이지 컨테이너 하드코딩은 위 세 곳이 전부다(grep -rnE 'max-width: *[0-9]{3,}px' src/). /design/* 카탈로그(1180px, noindex)는 독자용이 아니라 범위 밖이다.

접근 — 두 폭 토큰 + 셸이 지면을 따라간다 (유저 선택, 2026-08-24).

디자인 정본이 근거다. design-concept/DESIGN_CONCEPT.md:106의 720px은 "포스트 본문"에 붙은 값이고, 같은 문서 90~96행은 홈 히어로를 1fr 1fr 2열 그리드 + 마스코트로 따로 규정한다. 정본은 이미 "지면마다 폭이 다르다"를 전제하며 홈 폭 1100px을 금지한 곳은 없다. 정본에 없는 것은 그 규칙이고, 실제로 깨진 것은 둘이다 — 규칙이 토큰에 없다는 것, 그리고 셸이 그 규칙을 안 따른다는 것(지적 2). 그래서 값을 통일하는 대신 규칙을 토큰과 문서에 박는다.

  • --content-max: 720px 유지 = 읽는 판 (글 목록 · 카테고리 · 글 상세 · 대담 · 404)
  • --wide-max: 1100px 신설 = 넓은 판 (홈 · 글 지도). 글 지도 960px도 여기로 흡수한다
  • Header/Footer는 var(--shell-max, var(--content-max))를 읽고, BaseLayout의 width="wide"가 --shell-max: var(--wide-max)를 깐다 → 셸이 지면 폭을 따라간다. 폴백을 둔 이유는 prop을 안 넘긴 지면 8곳이 지금과 한 픽셀도 달라지지 않아야 하기 때문이다

버린 대안 둘. 둘 다 지적 1을 문자 그대로 풀지만 실측 비용이 지면을 망가뜨린다.

  • 720px 단일 통일 — 히어로 2열이 열당 294px(720 − 패딩 48×2 = 624, gap 36 제외)로 줄고, 폴라로이드 회전 바운딩 141px이 들어갈 타이틀 우측 여백이 사라진다(index.astro 실측 주석: 769px에서 129px · 964px에서 166px). 글 지도 캔버스도 960→720으로 노드가 밀집한다.
  • 1100px 단일 통일 — DESIGN_CONCEPT.md:106을 뒤집어야 하고, 글 목록 행(날짜 160px | 제목 | 화살표)이 1100px로 벌어지며 글 상세 히어로·PostNav·SeriesEpisodes 카드가 전부 커진다. 읽는 지면 8곳 재디자인이다.

남는 것 하나 — 지적 1은 값으로 풀리지 않는다. 홈 1100 ≠ 블로그 탭 720이 그대로 남고, 일관성은 "같은 값"이 아니라 "같은 규칙"으로 성립한다. 유저가 그 조건을 알고 고른 선택이다.

회귀 위험은 푸터가 넓어지는 쪽 하나다. AuthorLineup은 width:100% + grid-template-columns: repeat(var(--n), minmax(0,1fr))이라(AuthorLineup.astro:173·:176) 푸터가 720→1100이 되면 저자 컷아웃 칸이 그만큼 벌어진다. deco.css에 폭에 걸린 좌표는 없지만 (grep 0건) 라인업 자체는 폭에 비례한다 — S4에서 실측하고, 벌어지면 라인업에만 현행 렌더 폭 상한을 주고 중앙 정렬한다.

경로 겹침은 신호이지 판정이 아닙니다. DB 스키마·환경변수·패키지 매니페스트·공유 API 계약처럼 경로에 드러나지 않는 의존은 여기 잡히지 않습니다.

검증 기준

아래 넷이 전부 초록이면 끝난 것이다.

1. 지면 안에서 셸과 본문 폭이 같다 (지적 2) — 이것이 정본 판정이다

bun run width:verify

scripts/verify-widths.ts 가 지면마다 .header-inner · 페이지 컨테이너 · .footer-inner 의 렌더 폭을 재서 셋이 한 값인지 본다. 어느 값이어야 하는지는 안 본다 — 홈 1100 과 글 목록 720 은 설계대로 다르고, 판정하는 것은 지면 안의 일치다. 비0 이면 그 화면은 못 나간다.

기대:

| 지면 | 기대 | | --- | --- | | / · /graph | 셋 다 1100 | | /posts · /404 · 글 상세 | 셋 다 720 |

눈으로 하지 않는 이유는 역검증으로 확인했다 — graph.astro 에서 width="wide" 만 떼면 CSS 에 숫자가 없어 grep 은 0건인데 width:verify 는 header-inner=720 · graph-page=1100 으로 잡는다. 홈과 글 지도가 어긋난 채 오래 남아 있던 것이 정확히 이 방향이다.

2. 빌드·기존 게이트 회귀 없음

bun run build
bun run deco:verify
bun run viz:verify
bun scripts/check-emphasis.ts && bun scripts/check-emphasis.ts --dist
bun scripts/check-post-markers.ts

3. 페이지 컨테이너 하드코딩 0건 (보조 검색)

grep -rnE 'max-width: *[0-9]{3,}px' src/ | grep -v 'src/pages/design/' | grep -v '@media'

.hero-inner · .recent · .graph-page · .header-inner · .footer-inner 가 한 건도 안 나와야 한다. 남는 것은 컴포넌트 내부 상한뿐이며 대상이 아니다 — AuthorProfile 440px · 글 삽화 Shot 562px · TalkLayout 화자 카드 520px · 홈 히어로 이미지 380/500px.

4. 푸터 저자 라인업이 판 폭에 안 끌려간다

넓은 판(/ · /graph)과 읽는 판(/posts · /404)에서 라인업 판 폭과 액자 사이 간격이 같아야 한다. 실측 기대값은 판 624px · 액자 102×117 · 액자 사이 54px 이다(뷰포트 1440·1024 둘 다).

5. 정본에 규칙이 있다

design-concept/DESIGN_CONCEPT.md 「6. 레이아웃 → 폭 체계」 절에 읽는 판/넓은 판 표, 배선 셋, 푸터 라인업 예외, 그리고 width:verify 가 판정한다는 사실이 적혀 있다.
