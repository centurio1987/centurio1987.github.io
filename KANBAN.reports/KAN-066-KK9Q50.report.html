이 카드가 무엇을 끝내려는가

이 일이 끝나면 대화 원본을 던져 넣는 것만으로 폭신 대담 에피소드 한 편이 나옵니다.

지금은 그 길이 없어요. 대담 레이아웃도, <QA> 컴포넌트도, 에피소드 템플릿도 다 만들어져 있지만 거기에 넣을 내용을 어디에 어떤 모양으로 두는지가 안 정해져 있습니다. 그래서 대담 에피소드가 아직 0편입니다.

카드 KAN-066-KK9Q50(칸반 보드의 카드 번호입니다)이 요구한 것은 셋이에요. ① 대화 원본을 받아 데이터 구조와 파일 형식을 정형화해 저장할 것 ② 그 과정에서 톤앤매너·비문·맞춤법을 교정할 것 ③ 나중에 방향이 바뀌면 다시 만들 수 있도록 원문을 따로 보존할 것.

루트 독립성은 깨지지 않았습니다 — 다른 최상위 카드와 작업 경로가 겹치지 않아요. 다만 짚어 둘 것이 하나 있습니다. 이 저장소는 공개이고 raws/ 도 함께 커밋됩니다. 대화 원본에는 시스템 프롬프트가 통째로 들어 있으니, 무엇을 걸러 낼지를 첫 단계에서 규칙으로 정하겠습니다.

왜 이 접근인가

먼저 입력의 실물을 재 봤습니다. 지금 저장소에 있는 유일한 대화 원본 raws/ddd-transaction-account-discussion.mdx 를 파서로 열어 세어 본 값이에요.

파일 전체              100,125 B   노드 51개
├─ 사람 질문            2,859 B    6개   ← 남길 것
├─ 모델 답변           20,592 B    5개   ← 남길 것 (빈 껍데기 11개는 뺀 수)
├─ 시스템 프롬프트     38,190 B   15개   ← 버릴 것
└─ 도구 호출·기타      나머지     20개   ← 버릴 것

남는 발화 11개 = 23,451 B = 파일의 23.4%

대담이 될 부분은 4분의 1도 안 됩니다. 나머지 4분의 3은 시스템 프롬프트와 도구 호출이에요. 이 상태로는 집필자가 매번 100KB 를 통째로 읽어야 하고, 같은 원본에서 같은 결과가 두 번 나오지도 않습니다.

반대편 끝, 즉 도착지는 이미 정해져 있습니다. 폭신 대담 명세(polssin-daedam)가 글의 골격을 셋으로 못박아 뒀거든요 — 대담 설정 · 질문과 답변 · 정수 한 문장. 그리고 그 명세의 원칙 넷은 전부 기계가 검사할 수 있는 것입니다. 질문 번호가 1부터 빠짐없이 이어지는가, 인용구가 한두 개인가, 시리즈와 회차가 채워졌는가, 저자가 인터뷰어로 적혔는가. 사람이 손으로 지킬 규칙이 아니라 빌더가 지켜 줄 규칙이라는 뜻이에요.

그래서 층을 셋으로 나눕니다.

  L1 원문        받은 그대로. 아무도 안 고친다
      │          raws/talks/<slug>/source/ + source.json (sha256)
      │  ← 스킬: 노이즈 제거 · 질문 재구성 · 톤앤매너·비문·맞춤법 교정
      ▼
  L2 정형본      사람이 계속 손보는 정본
      │          raws/talks/<slug>/talk.md  (Zod 스키마로 계약)
      │  ← 스크립트: 계약 검사 + 치환뿐
      ▼
  L3 발행물      파생물. 손대지 않는다
                 src/content/posts/talk-<slug>.mdx

카드는 "원문/교정본 2계층"을 요구했는데 하나를 더 얹었습니다. 왜냐하면 2계층이면 교정본이 곧 발행물이 되기 때문이에요. 발행물에 오타 하나만 손으로 고쳐도 그 순간 원문과 발행물 사이의 연결이 끊어지고, 카드가 요구한 ③(다시 만들기)이 죽습니다. L3 를 파생물로 못박아야 ③ 이 삽니다.

경계선을 여기 그은 이유도 같습니다. L1→L2 는 "무엇이 잡음이고 무엇이 대담인가"를 판단하는 일이라 사람 또는 AI 가 해야 하고, L2→L3 는 정해진 검사와 치환뿐이라 스크립트가 해야 해요. "스킬로 만들까 스크립트로 만들까"는 둘 중 하나를 고르는 문제가 아니라 이 선을 어디에 긋는가의 문제였습니다.

버린 대안 셋

  • 원본을 그대로 두고 집필자가 읽어 쓴다 (지금 방식) — 위에서 잰 대로 100KB 중 76.6% 가 잡음이고, 재현이 안 됩니다.
  • 원본에서 곧장 MDX 를 만든다 (2계층) — 다시 만들기가 불가능해집니다. 카드 요구사항 ③ 을 정면으로 어겨요.
  • 정형본을 JSON 이나 YAML 로 둔다 — 기계는 편하지만 긴 한국어 답변이 이스케이프와 블록 스칼라에 갇혀 사람이 못 고칩니다. 정본은 사람이 계속 고칠 물건이에요.

무엇을 어떤 순서로

작업 단위 일곱 개(S1~S7, 실행 계획의 단계 번호입니다)는 규격 → 기계 → 입구 순으로 흐릅니다. 옆의 간트 차트가 그 순서를 그림으로 보여 줘요.

앞의 셋(S1·S2·S3)은 규격입니다. 원본에서 무엇을 버릴지 정하고(S1), 원문을 어디에 어떻게 봉인할지 정하고(S2), 정형본의 문법과 검사기를 만듭니다(S3). 이 셋이 끝나면 코드가 읽고 쓸 형식이 전부 확정돼요. 되돌리기 가장 비싼 결정이 여기 몰려 있는 대신, 여기까지만 하고 멈춰도 규격 문서와 파서가 남습니다.

가운데 둘(S4·S5)은 기계입니다. 정형본을 발행물로 굽는 빌더와, 그 결과가 어긋나지 않았는지 보는 검증기예요. 검증기가 보는 것은 셋입니다 — 원문 해시가 그대로인가, 정형본이 스키마를 통과하는가, 발행물을 다시 구웠을 때 같은 것이 나오는가. 세 번째가 곧 "발행물을 손으로 고치지 않았는가"입니다.

뒤의 둘(S6·S7)은 사람이 부르는 입구입니다. talk-ingest 스킬이 원본 투입부터 굽기까지를 한 흐름으로 잇고, 마지막으로 CLAUDE.md · init-post 스킬 · authoring 경로 설정 세 곳에 접점을 적습니다. 문서를 맨 뒤에 두는 이유는 실제로 도는 것을 확인한 뒤에 써야 하기 때문이에요. 안 그러면 문서가 계획을 적게 되고, 그건 다음 사람을 속입니다.

교정을 스킬이 직접 하지 않는다는 점도 미리 말씀드릴게요. 톤앤매너·비문·맞춤법은 authoring-kit 이 소유한 규칙이고, 이 스킬은 그쪽에 위임만 합니다. 이 저장소는 같은 규칙을 여러 곳이 각자 들고 있다가 갈라진 적이 있어서, 규칙을 다시 복제하지 않습니다.

두 가지 수행안

두 안 모두 작업 단위 일곱 개를 다 합니다. 다른 것은 묶는 방식뿐이에요.

안 A — 단일 에이전트 순차

한 세션이 처음부터 끝까지 순서대로 갑니다. 묶음(배치)은 셋이에요 — 규격 셋, 기계 둘, 입구 둘. 동시에 도는 작업은 없습니다.

  • 묶음 수: 3 (작업 3개 / 2개 / 2개)
  • 동시 실행 폭: 1
  • 되돌리기: 묶음마다 태그가 붙어 통째로 되돌릴 수 있습니다
  • 강점: 묶음이 끝날 때마다 결과를 보고 다음 묶음을 조정할 수 있어요. 표본이 하나뿐이라 첫 묶음에서 규칙이 흔들릴 여지가 있는데, 그때 방향을 틀 자리가 생깁니다
  • 약점: 묶음이 하나 더 많습니다. 안 B 라면 겹쳐 돌았을 작업이 순서대로 기다려요

안 B — 오케스트레이션 병렬

첫 묶음에서 S1 과 S2 를 나란히 돌리고, 둘째 묶음에서 기계 갈래와 스킬 갈래를 동시에 갑니다. 묶음은 둘이에요.

  • 묶음 수: 2 (작업 3개 / 4개)
  • 동시 실행 폭: 2
  • 되돌리기: 둘째 묶음은 두 갈래가 얽혀 부분 되돌리기가 어렵습니다
  • 강점: 묶음이 하나 줄어듭니다. 규격이 흔들리지 않는다면 더 빨리 끝나요
  • 약점: 스킬 갈래가 빌더의 호출 규약을 미리 알아야 합니다. 첫 묶음 끝에 그 규약을 문서로 못박아야 하고, 그게 나중에 바뀌면 스킬 쪽이 재작업입니다

옆의 비교 차트가 두 안의 묶음 크기와 동시 실행 폭을 나란히 보여 줍니다.

추천은 안 A 입니다. 이유는 하나예요 — 대화 원본 표본이 1건뿐입니다. 다른 도구의 내보내기 형식이 오면 첫 단계의 규칙이 흔들리는데, 안 B 는 그 흔들림이 스킬 갈래까지 번집니다. 표본이 서너 건 쌓인 뒤라면 안 B 가 나은 선택이 될 거예요.

막힐 만한 지점

첫째, 표본이 하나입니다. 이게 이 계획에서 가장 큰 위험이에요. 지금 잰 51개 노드의 분류는 한 도구의 내보내기 형식 하나를 본 결과입니다. 다른 형식이 오면 첫 단계의 규칙이 그대로 통하지 않아요. 그래서 파서를 형식별 어댑터로 나누고, 모르는 형식은 추측해서 읽지 않고 실패시킵니다. 조용히 잘못 읽는 것보다 멈추는 편이 낫거든요.

둘째, 원본이 이미 잘려 있을 수 있습니다. 모델 답변 5개의 바이트 수를 재 보니 4,116 · 4,117 · 4,119 · 4,120 · 4,120 이었어요. 글자 수는 2,205 자에서 2,709 자까지 제각각인데 바이트만 거의 같습니다. 우연으로 보기 어려운 수치예요 — 내보내기 쪽에 상한이 걸려 있을 가능성이 있습니다. 다섯 개 모두 문장 끝에서 깔끔하게 끝나서 육안으로는 안 보였고요. 첫 단계에서 이것부터 확인하겠습니다. 잘린 원본을 정본으로 봉인하면 그 뒤 전부가 헛일이니까요.

셋째, 첫 단계 자체가 예산을 먹을 수 있습니다. 100KB 를 통째로 컨텍스트에 올리면 그것만으로 세션이 기웁니다. 그래서 본문을 다 읽지 않고 (출처, 종류, 길이) 표만 먼저 뽑아 보고, 실제 본문은 표본 몇 개만 엽니다 — 위에 적은 숫자들이 그렇게 나온 값이에요.

넷째, 되돌리기가 비싼 자리는 디렉터리 구조입니다. 두 번째 단계에서 정하는 레이아웃 위에 나머지 전부가 섭니다. 다행히 첫 묶음은 기존 파일을 고치지 않고 새 파일만 만들어요. 되돌릴 때 충돌이 날 여지가 적습니다.

다섯째, 공개 저장소입니다. 첫 단계의 필터가 약하면 시스템 프롬프트와 경로가 그대로 커밋됩니다. 필터 규칙을 명시하고, 두 번째 단계에서 표본을 실제로 앉힐 때 눈으로 확인하겠습니다.

무엇이 되면 끝인가

표본 raws/ddd-transaction-account-discussion.mdx 를 실제 입력으로 넣어서 아래가 전부 초록이면 끝난 것으로 봅니다. 하나라도 비0으로 끝나면 미완이에요.

bun run talk:verify        # 원문 해시 · 정형본 스키마 · 발행물 일치
bun scripts/build-talk.ts raws/talks/<slug>/talk.md   # 다시 구워도 같은가
bun run build              # 대담 글이 포함된 채로 전 페이지 빌드
bun scripts/check-post-markers.ts
bun scripts/check-emphasis.ts && bun scripts/check-emphasis.ts --dist
bunx tsc --noEmit

그리고 스크립트가 판정 못 하는 것 셋은 눈으로 봅니다.

  1. 구워진 글을 미리보기로 열었을 때 대담 레이아웃이 뜨는가 — 배너, 화자 둘, 그리고 질문 목차가 질문문에서 자동으로 생기는가.
  2. 정형본의 한 문장만 고치고 다시 구웠을 때 그 문장만 바뀌는가.
  3. 원문 파일의 해시가 파이프라인 전 구간에서 안 바뀌는가.

3번이 이 카드의 핵심입니다. 원문이 한 바이트라도 움직이면, 이 계획이 세운 세 층 구조가 첫 회에 무너진 것이거든요.

전략

입력의 실물을 먼저 봤다. raws/ddd-transaction-account-discussion.mdx 가 유일한 대화 원본 표본이고 93KB 다. 그 안은 중첩 JSON 그래프({id, step_index, source, type, content, tool_calls, children})이며 source 는 USER_EXPLICIT · MODEL · SYSTEM, type 은 USER_INPUT · CONVERSATION_HISTORY · EPHEMERAL_MESSAGE 등으로 갈린다. 사람의 발화보다 시스템 프롬프트 · 도구 호출 · 플래너 잡음이 훨씬 많다. 이 상태로는 <QA n q> 골격에 못 넣고, 매번 집필자 컨텍스트에 93KB 를 통째로 올려야 한다.

목적지도 이미 정해져 있다. .claude/authoring/specs/polssin-daedam/spec.json 의 sections 가 frontmatter · qa(repeat) · pullquote 셋이고, 원칙 SP1(n 은 1부터 연속) · SP4(PullQuote 는 요약이 아닌 도달점, 1~2개) · SP5(template: talk · series · order) · SP6(author 는 인터뷰어)은 전부 기계가 검사할 수 있는 계약이다. 즉 발행물은 사람이 손으로 쓸 것이 아니라 구워야 할 것이다.

3계층으로 나눈다

카드가 요구한 "원문/교정본 2계층"에 발행물 1계층을 더해 3계층으로 간다. 2계층으로 끝내면 교정본이 곧 발행물이 되어, 발행물에 손을 대는 순간 "다시 굽기"가 깨지기 때문이다.

| 층 | 무엇 | 어디 | 누가 고치나 | |---|---|---|---| | L1 원문 | 받은 그대로. 불변 | raws/talks/<slug>/source.<ext> + source.json | 아무도 | | L2 정형본 | 노이즈 제거 + 교정된 정본 | raws/talks/<slug>/talk.md | 사람 · AI | | L3 발행물 | 파생. 손대지 않는다 | src/content/posts/talk-<slug>.mdx | 빌더만 |

L1→L2 는 판단이 드는 일(무엇이 질문이고 무엇이 잡음인가, 톤앤매너·비문·맞춤법)이라 스킬이 맡는다. L2→L3 는 계약 검사와 치환뿐이라 스크립트가 맡는다. "스킬로 만들지 스크립트로 만들지"는 양자택일이 아니라 이 경계선의 문제였다.

굳힌 판단 넷

  1. L2 는 markdown 이다 (JSON·YAML 아님). 대담 정본은 사람이 계속 손볼 물건인데 긴 한국어 답변을 JSON 이스케이프나 YAML 블록 스칼라에 가두면 편집이 무너진다. 대신 형식이 흐물해지지 않도록 Zod 파서로 계약을 잡는다 — src/lib/viz/schema.ts 가 ``viz`` 블록에 쓴 것과 같은 방식이다.
  2. 저장 위치는 raws/talks/<slug>/ 다. raws/README.md 가 raws 를 "사용자가 직접 작성하는 공간"으로 정의하고 raws/_proceeded/ 로 봉인하는 관례가 이미 있다. 별도 루트 디렉터리를 새로 파면 유저 입력의 입구가 둘이 된다.
  3. init-post --talk 와 합치지 않는다. 그쪽은 원본 없이 바로 쓰는 빈 스켈레톤 경로이고 이쪽은 내용이 찬 것을 굽는 경로다. 진입점이 다르므로 둘 다 남기고, src/templates/talk-episode.mdx 를 두 경로의 단일 소스로 공유한다.
  4. L3 는 사람이 안 고친다. 고치고 싶으면 L2 를 고쳐 다시 굽는다. 이 규약이 없으면 카드가 요구한 "개선 방향이 바뀔 때 다시 굽는다"가 첫 수정에서 죽는다.

버린 대안 셋

  • 원본을 raws 에 그대로 두고 집필자가 읽어 쓴다(현행) — 93KB 노이즈를 매번 올려야 하고, 같은 원본에서 같은 결과가 두 번 나오지 않는다.
  • 원본 → MDX 직행(2계층) — 교정본이 곧 발행물이라 재생성이 불가능하다. 카드 요구사항 ③ 을 정면으로 어긴다.
  • L2 를 JSON/YAML 로 — 기계 친화적이지만 사람이 못 고친다. 정본은 사람이 고치는 물건이라는 전제와 충돌한다.

열린 위험 둘

  • 표본이 1건이다. 다른 export 형식(ChatGPT · Claude · 평문 붙여넣기)이 오면 S1 의 정규화 규칙이 흔들린다. 그래서 파서를 형식별 어댑터로 나누고, 모르는 형식은 추측하지 않고 실패시킨다.
  • KAN-067 과 맞물린다. 그 카드의 대담 준비 노트가 어디에 앉을지가 정해지면 raws/talks/<slug>/ 안에 prep.md 로 들어올 수 있다. 지금은 자리만 비워 둔다.

루트 독립성

이 카드가 속한 루트는 다른 루트와 경로가 겹치지 않습니다. 병렬로 수행해도 충돌하지 않습니다.

경로 겹침은 신호이지 판정이 아닙니다. DB 스키마·환경변수·패키지 매니페스트·공유 API 계약처럼 경로에 드러나지 않는 의존은 여기 잡히지 않습니다.

bunx tsc --noEmit
