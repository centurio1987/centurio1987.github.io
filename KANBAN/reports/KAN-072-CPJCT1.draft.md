## 끝난 뒤의 상태 — 리터럴 한 줄이 그 자리에서 걸린다

먼저 수준을 맞추고 갈게요. `KAN-072-CPJCT1` 은 이 블로그 저장소의 칸반 카드에 붙은 번호입니다. 앞의 `KAN-072` 가 카드 번호이고 뒤의 `CPJCT1` 은 카드마다 하나씩 붙는 꼬리표예요. 이 카드가 상대하는 것은 검사 명령 하나입니다 — `bun run tokens:verify`. 색·글씨 크기·모서리 둥글기·간격 같은 시각 값이 `src/styles/tokens.css` 에 정의된 토큰을 쓰는지 훑어서, 안 쓰는 자리를 세어 주는 게이트죠.

그 게이트가 지금 세고 있는 수는 이렇습니다.

```
갈래  색 · 글자 · radius · 간격 · 선 굵기 · 모션 · 그림자 · z-index · 기타 · 잡음
  ×  판정  위반 · 드리프트 · 준수 · 판정 불가
  =  값이 들어 있는 칸 22개   (검사한 파일 152개)

      위반     1,305
      드리프트     90
      ─────────────
      무는 합   1,395   ← 이 수가 0 이 되는 것이 이 카드의 끝
```

판정 넷 중에서 게이트가 **무는 것은 앞의 둘**입니다. 「준수」는 토큰을 제대로 쓴 자리라 셀 이유가 없고, 「판정 불가」는 규칙도 토큰도 없어서 애초에 대상 밖인 히트예요. 890건이 여기 있습니다(간격 444 · 글자 247 · 그림자 132 · 잡음 50 · z-index 17). 이 카드는 890 을 건드리지 않습니다.

여기서 헷갈리기 쉬운 곳이 있어요. **「무는 칸이 0」과 「히트가 0」은 다른 말입니다.** 이 카드가 끝나도 게이트는 여전히 890건을 보고합니다. 목표는 그 890 을 지우는 것이 아니라, 위반과 드리프트 칸을 전부 비우는 것이에요.

```
게이트가 무는 것      위반 1,305 + 드리프트 90 = 1,395   ← 이 수를 0 으로 만든다
게이트가 안 무는 것   준수      1,304                    ← 이미 토큰을 쓴 자리
                     판정 불가   890                     ← 규칙도 토큰도 없다
```

「드리프트」가 어떤 판정인지는 두 번째 배치에서 눈으로 볼 수 있습니다. 선 굵기 토큰이 서면 `1px` 리터럴 129건이 「위반」에서 「드리프트」로 옮겨 가요. 판정 이름만 바뀌고 무는 합은 그대로입니다 — 값을 실제로 치환하는 일은 뒤쪽 구획이 하니까요.

그럼 이 일이 끝나면 무엇이 달라지느냐. 게이트가 지금 **하드월이 아니라 래칫**이라는 데서 출발합니다. 래칫은 한 방향으로만 도는 장치의 이름인데, 게이트가 그 이름을 쓰는 이유는 늘어나는 쪽만 막기 때문이에요. 커밋된 기준선(`scripts/tokens-baseline.json`)보다 늘면 실패하고, 줄거나 같으면 통과합니다.

```
지금        기준선 = 1,395
            1,396 → 실패      1,394 → 통과      1,395 → 통과
            새 리터럴을 넣어도 다른 자리에서 그만큼 지우면 지나간다

끝난 뒤     기준선 = 0
            1 → 실패
            새 리터럴 한 줄이 그 자리에서 걸린다
```

지금은 부채가 1,395건 깔려 있어서 그 위에 한 줄을 더 얹어도 눈에 안 띕니다. 기준선이 0 이 되면 그럴 여지가 사라져요. 이 카드가 만들려는 상태가 그것입니다. 다만 게이트를 하드월로 승격시키는 일은 이 카드가 하지 않습니다 — 게이트 코드는 `KAN-070` 소유이고, 이 카드는 0 으로 수렴했다는 사실만 넘깁니다.

착수 전에 확인해 둘 것이 하나 더 있어요. **루트 독립성**입니다. 칸반에서 「루트」는 위에 아무 카드도 없는 최상위 카드를 말하고, 독립성은 두 루트가 같은 파일을 건드리는지를 봅니다. 이 카드는 겹침 0건이에요. 다만 그 0 이 무엇에 근거한 0인지는 밝혀 두는 편이 낫습니다.

- 루트 카드는 15장인데, 건드릴 경로 목록(`scope`)을 선언한 것은 **두 장뿐**입니다 — `KAN-071-6361MY` 와 이 카드.
- 나머지 13장은 `scope` 가 빈 배열이라 애초에 대조할 경로가 없습니다. 겹침이 없다고 확인된 것이 아니라, 확인할 대상이 없는 상태예요.
- 선언한 두 장 사이에는 겹치는 경로가 실제로 없습니다. 이 카드가 `src/lib/viz/` 에서 가져가는 것은 `Comparison.tsx`·`PosterHero.tsx`·`ProcessSteps.tsx`·`layout.ts` 넷이고, `KAN-071` 이 선언한 `blogVizStyleGuide.ts` 는 가져가지 않습니다.

```
루트 15장
   scope 선언 2장   KAN-071-6361MY · KAN-072-CPJCT1   → 대조했고 겹침 0
   scope 미선언 13장                                  → 대조할 경로가 없다
```

이 리포트를 끝까지 읽으면 두 수행안 중 하나를 고를 수 있게 됩니다. 왜 이 순서로 자르는지, 어느 배치가 무거운지, 어디서 되돌리기 어려워지는지를 차례로 보겠습니다.

## 왜 갈래가 아니라 파일로 자르나

이 카드의 핵심 판단은 하나입니다. 감사 문서(`design-concept/UI_CONSISTENCY_AUDIT.md`)가 자른 단위는 그대로 받되, **실행 단위를 게이트 갈래에서 파일 구획으로 뒤집었어요.** 「갈래」는 위 그림의 세로줄입니다 — 색·글자·radius·간격 같은 분류죠. 「구획」은 파일 묶음이고요.

갈래로 자르는 쪽이 자연스러워 보입니다. 색은 색끼리, 글자는 글자끼리 고치면 되니까요. 실제로 세어 보면 그렇지 않습니다.

```
갈래로 자르면 — 같은 파일을 여러 세션이 동시에 연다

  무는 1,395건의 파일 81개 중 73개(90%)가 두 갈래 이상
      2갈래 17 · 3갈래 37 · 4갈래 11 · 5갈래 6 · 6갈래 2 = 73
      한 갈래만 무는 파일은 8개    8 + 73 = 81

  글자 갈래 36파일 ─ 그중 35파일이 간격 갈래 안에 있다
                     차집합은 components/deco/Tape.astro 한 파일

  가장 심한 두 파일이 여섯 갈래씩 문다
      src/pages/design/frame-picks.astro
      src/components/graph/GraphExplorer.tsx
```

글자를 맡은 세션과 간격을 맡은 세션을 따로 열면 35파일에서 부딪힙니다. 두 세션이 같은 파일을 동시에 여는 상황이 서른다섯 번 생기는 거예요. 무는 갈래가 색·간격·선 굵기·글자·radius·기타·모션 일곱인데, 그중 여섯을 한꺼번에 무는 파일이 둘 있습니다. 이 두 파일은 어느 갈래를 맡든 거의 항상 따라옵니다.

파일로 자르면 반대 결과가 나옵니다.

```
파일로 자르면 — 갈린다

  posts/** 안   색 위반 322 (색 위반 368 중 87%)
                글자 위반   0
                radius 위반 0

  posts/** 밖   색 위반  46
                글자 위반 151
                radius 위반 67
```

글자 갈래 위반 151건과 radius 갈래 위반 67건이 발행 글 폴더 안에 **하나도 없습니다.** 그래서 `posts/**` 밖을 먼저 훑으면 그 두 갈래가 거기서 완결돼요. 남는 것은 색이 대부분인 발행물이고, 그건 시리즈 단위로 뒤에 갑니다. 구획 경계가 곧 세션 경계라 두 세션이 같은 파일을 여는 일이 없습니다. 덧붙이면, 방금 본 파일 81개는 무는 히트가 하나라도 있는 파일 전부이고 이 수는 기준선 파일 맵의 항목 수와 같아요. 아래에서 볼 구획 열셋의 파일 합도 81입니다 — 구획이 그 81개를 빠짐없이 덮는다는 뜻이죠.

두 번째 판단은 순서입니다. **첫 수는 치환이 아니라 게이트 인식층입니다.** 왜 그런지는 코드를 봐야 알 수 있어요.

```
scripts/lib/tokens/color.ts:54   COLOR_TOKENS — 토큰 이름 18개가 하드코딩된 Set
                          :64   if (name.includes("radius")) return "radius";
                          :66   if (name === "--stroke") return "stroke";   ← 정확 일치
scripts/lib/tokens/docrule.ts:66  SPACING_SCALE = {0,4,8,12,16,24,32,48,64,96}  상수
                            :79  FONT_ROLES    = {60,38,36,28,26,20,18,13,12}  상수
```

이 카드가 새로 세울 토큰은 6종입니다 — 종이 흰색 · `--stroke-hair` · `--state-*` · `--space-*` · `--text-*`, 그리고 radius 토큰. 그중 **게이트가 자동으로 자기 갈래에 넣는 것은 radius 하나뿐**이에요. `:64` 한 줄만 이름 규칙을 데이터로 보고 있어서 이름에 `radius` 가 들어가면 그냥 인식합니다. 나머지 다섯은요? 이름이 Set 에 없고 정확 일치도 아니라 전부 `기타` 갈래로 샙니다. 그러면 어떻게 되느냐. 뒤 구획에서 리터럴을 아무리 토큰으로 바꿔도 게이트가 그 토큰을 색으로도 간격으로도 안 읽으니까, 색 칸과 간격 칸의 수가 안 줄어듭니다. **인식층을 안 열면 뒤 열세 구획이 전부 헛돕니다.** 그래서 첫 work 가 치환이 아니라 인식층이고, 그 work 는 위반을 한 건도 줄이지 않아요.

```
S1 을 건너뛰면

  S3 ~ S15 에서 리터럴을 토큰으로 바꾼다
        ↓
  게이트는 그 토큰을 기타 갈래로 읽는다
        ↓
  색 칸도 간격 칸도 안 줄어든다   ← 열세 구획이 헛돈 자리
```

버린 대안은 셋입니다.

- **갈래별 병렬** — 감사 문서 §5 의 사슬을 그대로 세션에 매핑하는 방식이에요. 위에서 본 81개 중 73개 겹침 때문에 그 자리에서 깨집니다.
- **파일 구획 카드로 재편** — 카드 자체를 파일 단위로 다시 쪼개는 방식입니다. 완료 판정이 게이트 칸과 안 맞아요. `files` 맵은 실패했을 때 어느 파일이 늘었는지 지목하는 진단용이라, 「이 파일들의 모든 갈래가 0」이라는 판정을 게이트에서 뽑을 수 없습니다. 하위 카드 6장에 쌓인 브리프와 메모 근거도 옮겨 적어야 하고요.
- **게이트 코드를 이 카드 범위로 흡수** — 하위 카드 하나가 토큰 데이터와 판정 코드를 동시에 소유하게 되면서 `KAN-070` 이 세운 분리가 깨집니다. 그래서 게이트 코드 범위는 하위 카드 `KAN-072.7-D6DCXJ` 하나가 집니다.

결론은 이렇게 정리됩니다. **카드는 갈래로 두고, 배치가 파일을 나눕니다.** 카드 완료 판정이 게이트 칸과 1:1 로 맞아야 하니 카드는 갈래를 유지하고, 실행 단위만 파일 구획으로 바꾸는 거예요. 대가는 카드 완료가 뒤쪽 웨이브에 몰리는 것이고, 그 사이 진행 상황은 게이트 카운트가 보여 줍니다.

## work 16개가 무엇을 하나

work 는 카드를 쪼갠 실행 단위이고 `S1` 부터 `S16` 까지 번호가 붙어 있습니다. 열여섯이 다 같은 종류는 아니에요.

```
S1              게이트 인식층 열기      하위 카드 KAN-072.7
S2              토큰 신설               하위 카드 KAN-072.2
S3 ~ S15        파일 구획 13개
S16             수렴 판정

16 = 2 + 13 + 1
```

앞의 둘은 구획이 아닙니다. `S1` 은 방금 본 인식층이고, `S2` 는 토큰을 실제로 세우는 일이에요. `S2` 에서 radius 위반 25건(`50%` 로 적힌 자리)이 토큰 한 줄로 닫힙니다 — `color.ts:64` 가 이름에 `radius` 가 든 토큰을 자동으로 인식하니까요. 같은 자리에서 `1px` 리터럴 129건이 「위반」에서 「드리프트」로 재분류되고요.

`S2` 에는 판단이 다섯 개 몰려 있습니다. 여기서 정하지 않으면 뒤 구획 전부가 멈춰요.

```
S2 에서 정할 다섯
   종이 흰색의 정본 값
   토큰을 둘 파일
   --space-*  명명
   --text-*   명명과 clamp 처리
   --state-*  매핑

같은 자리에서 함께 볼 것
   tokens.css        변수 44개 중 --cat-* 는 8개
   categories.ts     카테고리는 9개
                     차이 = learning #6A6FB3 이 토큰에 없다
   hex 표기          categories.ts 는 대문자 · tokens.css 는 소문자
```

가운데 열셋이 파일 구획입니다. 무게는 고르지 않고, 파일 수와 건수가 같이 가지도 않아요.

```
무거운 쪽   카탈로그  216건 / 3파일     ← frame-picks.astro 가 여기 있다
            글 컴포넌트·레이아웃  209건 / 13파일
            데코      157건 / 18파일
            osi-7-layers EP4~6  137건 / 6파일

가벼운 쪽   마스코트   34건 / 1파일

파일 하나에 81건 ─ 그래프 구획의 GraphExplorer.tsx
파일 18개에 157건 ─ 데코 구획
```

순서는 무게가 아니라 갈래가 정합니다. `posts/**` 밖 여섯 구획(카탈로그 · 그래프 · 데코 · 글 컴포넌트·레이아웃 · 페이지·셸 · viz·전역 스타일)이 먼저 가는 이유는, 글자와 radius 가 거기서 완결되기 때문이에요. 그 여섯이 끝나면 남은 것은 색이 대부분인 발행물이고, 그때부터는 시리즈별로 잘라 나갑니다. osi-7-layers 를 EP1~3(118)과 EP4~6(137)으로 쪼갠 것도 한 구획이 255건으로 부풀지 않게 하려는 것이고요.

마지막 두 개는 성격이 또 다릅니다. `S15` 마스코트는 치환이 아니라 **기록**이에요. 캐릭터 고유색(볼 `#F4A6BE` · 털 `#7A4A38` · 잎 `#8CC2A0` · 눈 흰자 `#FFFFFF` · 외곽선 `#1C1B18`)은 UI 토큰으로 옮길 값이 아닌데, 그 팔레트가 어디에도 안 적혀 있어서 규칙대로 위반으로 세어졌습니다. 팔레트를 문서와 토큰에 적으면 닫히는 34건이죠. `S16` 은 수렴 판정이고요 — 기준선의 무는 칸이 전부 0이고 하위 카드 6장이 각자 완료 판정을 받는지 확인하는 자리입니다.

```
구획 13개 합계   파일 81개 · 1,395건
                 = scripts/tokens-baseline.json 의 files 맵 총계

  → 구획끼리 겹치지 않고, 빠진 파일도 없다
```

## 두 수행안 — 배치 7개와 배치 9개

용어부터 정리할게요.

```
work      카드를 쪼갠 실행 단위        S1 ~ S16
배치      한 세션이 한 번에 잡는 work 묶음
          이 카드의 배치 크기 대역은 work 3~4개  ← 개수 기준이지 시간 기준이 아니다
병렬 폭   그 배치를 동시에 여는 세션 수
웨이브    오케스트레이션 안에서 배치 하나가 도는 한 판
```

### 오케스트레이션 안 — 배치 7개

카드가 고른 쪽입니다. work 하나 = 파일 구획 하나이고, 구획마다 그 파일의 모든 갈래를 한 세션이 처리합니다.

- **배치 수** — 7개. 병렬 폭은 배치1·2·7 이 1, 배치3~6 이 3입니다.
- **어느 배치가 무엇을 닫나** — 배치1 은 인식층만 열고 위반을 0건 줄입니다. 배치2 는 radius 위반 25건을 닫고 `1px` 129건을 재분류해요. 그다음부터 실제로 줄어듭니다 — 배치3 이 454건, 배치4 가 315건, 배치5 가 357건, 배치6 이 235건, 배치7 이 34건. 더하면 1,395 로 전체와 같습니다.
- **가장 무거운 자리** — 배치3(454)입니다. 카탈로그 216 · 그래프 81 · 데코 157 을 한 판에 돌리거든요. 그다음이 배치5(357)인데, 여기가 발행물에 처음 들어가는 자리이기도 합니다.
- **이 안이 나은 점** — 배치5 에서 이득이 가장 큽니다. 그 배치의 세 구획(osi-7-layers EP1~3 · EP4~6 · vpn-anatomy)은 파일도 글도 안 겹치고, `astro preview` 조작 확인도 구획별로 따로 나거든요.
- **이 안이 지는 부담** — 세 세션이 한 브랜치로 커밋을 밀어 넣습니다. 래칫이 칸별로 물기 때문에 **커밋마다** 게이트 초록을 확인해야 해요. 웨이브 끝에 몰아서 보면 어느 세션이 어느 칸을 늘렸는지 가를 수 없습니다.

### 단일 에이전트 안 — 배치 9개

같은 work 열여섯을 한 세션이 순차로 처리하는 방식입니다.

- **배치 수** — 9개. 일곱 자리를 순서대로 세면 1 · 1 · 2 · 1 · 2 · 1 · 1 이고, 병렬 폭은 전 구간 1입니다.
- **어느 배치가 무엇을 닫나** — 닫는 건수는 오케스트레이션 안과 같습니다. 같은 work 를 같은 순서로 처리하니까요. 인식층이 먼저 열리고, radius 위반 25건이 닫히고, 454 · 315 · 357 · 235 · 34 가 차례로 줄어듭니다. 달라지는 것은 한 판에 몇 개를 함께 잡느냐뿐이에요.
- **가장 무거운 자리** — 454건과 357건은 한 세션이 한 판에 담기엔 커서, 그 둘이 배치 2개씩으로 늘어납니다. 나머지 다섯 자리는 한 세션으로도 배치 1개예요.
- **이 안이 나은 점** — 커밋 순서를 조율할 일이 없습니다. 「어느 세션이 칸을 늘렸나」를 물을 일도 없고요. 커밋하는 쪽이 하나뿐이라, 게이트가 붉게 나오면 직전 커밋이 곧 원인입니다. 리스크가 반대 방향으로 움직이는 거예요. 배치4 와 배치6 은 한 세션으로도 배치 1개라, 그 두 자리에서는 오케스트레이션의 이득이 가장 작습니다.
- **이 안이 지는 부담** — 배치3 과 배치5 를 각각 두 판에 나눠 담아야 합니다. 배치5 의 구획별 `astro preview` 확인도 한 세션에 순서대로 쌓이고요. 배치가 둘 늘어난다는 것은 착수·재개 지점이 그만큼 늘어난다는 뜻이기도 합니다.

### 두 안이 갈리는 자리

배치 수는 9 대 7이고, **차이가 나는 곳은 배치3 과 배치5 둘뿐입니다.** 나머지 다섯 자리(배치1 · 배치2 · 배치4 · 배치6 · 배치7)는 두 안의 배치 수가 같아요. 배치1 과 배치2 는 work 가 하나씩이라 애초에 나눌 것이 없고, 배치7 은 두 work 가 순서로 묶여 있어 병렬 폭이 1입니다.

잠깐 확인 하나만 해 볼까요? 그러면 두 안의 진짜 차이는 무엇일까요. 닫는 건수도 같고 순서도 같으니, 갈리는 것은 **두 자리에서 세션을 셋으로 열 것이냐 하나로 둘 것이냐**입니다. 셋으로 열면 커밋 규율이 따라붙고, 하나로 두면 그 규율이 사라지는 대신 배치가 둘 늘어납니다.

## 막힐 만한 자리

### 래칫은 합계를 보지 않는다

가장 먼저 알아야 할 제약입니다. 게이트는 갈래와 판정, 두 축을 교차시킨 칸을 **하나씩** 비교해요.

```
scripts/lib/tokens/baseline.ts:121-127

  칸마다   n > b   이면 실패        n = 이번 값, b = 기준선 값
  줄어든 칸은 down++ 로 세기만 하고 이 비교에 끼지 않는다
```

여기서 가장 중요한 것은 `n > b` 한 줄입니다. 이 비교에 합계가 안 들어가요. 줄어든 칸을 세는 `down++` 는 보고용이지 상쇄에 쓰이지 않습니다.

그래서 이런 일이 생깁니다.

```
                  Before      After          판정
                  (기준선)    (이번 커밋)
  간격 / 위반       570   →     470  (-100)   통과
  색   / 위반       368   →     369  (  +1)   실패  ← 이 칸 하나로 커밋 전체가 실패
```

100 을 줄이고 1 을 늘린 커밋이 실패합니다. 없던 칸이 새로 생기는 경우도 같아요 — 기준선에 그 칸이 0 이니까 1 만 생겨도 걸립니다.

> 래칫은 합계를 보지 않습니다. 칸을 하나씩 봅니다.

이것이 병렬 수행에 주는 제약이 앞 절의 커밋 규율이에요. 세 세션이 동시에 커밋하는데 웨이브가 끝난 뒤에 한 번 확인하면, 어느 세션이 어느 칸을 늘렸는지 가려낼 방법이 없습니다.

### 기준선 갱신이 게이트를 비켜 간다

되돌리기가 가장 어려운 자리입니다.

```
bun run tokens:verify                    자가검사 · 예외 검사 · 기준선 비교 전부 돈다
bun run tokens:verify --update-baseline   verify-tokens.ts:98-102 에서 먼저 빠져나간다
                                          자가검사와 예외 검사에 닿기 전에 exit 0
```

게이트가 죽은 채로 기준선을 갱신하면 0 에 가까운 수가 파일에 박히고, 그게 곧 「다 갚았다」로 보입니다. 그리고 래칫은 줄어든 것을 통과로 읽으니, **죽은 게이트와 다 갚은 게이트가 화면에서 같은 모양**이에요. 그래서 갱신 전에는 반드시 맨몸으로 한 번 돌립니다.

여기에 하나가 더 붙습니다. CI 는 `push: main` 트리거라 브랜치에서는 돌지 않아요. 병합 전까지 로컬 확인이 유일한 그물입니다.

### 예외 등록이 값을 못 가른다

`color.ts:229-230` 의 `exceptionFor(hit.file, axis)` 는 파일 단위로 걸립니다. 걸리면 그 파일의 색 히트가 통째로 「정당한 예외」로 내려가요. 「이 파일의 이 3색만」은 지금 구조로 불가능합니다.

이 제약이 실제로 무엇을 막는지 보이는 자리가 마스코트예요. 예외로 등록하면 34건이 한 번에 사라집니다. 대신 그 파일에 다섯 번째 분홍이 새로 들어와도 아무도 모르게 되죠. 그래서 예외 등록이 아니라 팔레트를 문서와 토큰에 적는 쪽으로 갑니다.

### 배치마다 다른 자리

- **배치1** — 자가검사가 판정 문구를 문자열로 매칭합니다(`selftest.ts` 의 `reason.includes(want)`). 판정 문구를 건드리면 게이트가 자기를 죽여요. 결함이 아니라 그물이니 걸리면 픽스처를 함께 고칩니다. 규칙을 넓히다 판정이 헐거워질 수도 있는데, 색을 「값이 색이면 색 갈래」로 바꾸면 `--hatch`(그라디언트)와 `--deco-shadow`(rgba 를 품은 그림자)가 색 갈래로 새어 들어옵니다. 그래서 이 배치의 완료 기준이 「판정 수가 안 바뀐다」예요 — 줄면 규칙이 헐거워진 것입니다.
- **배치2** — 판단 다섯이 여기 몰려 있습니다. 정하지 않으면 뒤 구획 전부가 멈춰요.
- **배치3** — 여섯 갈래를 무는 파일 둘이 여기 다 들어옵니다. `frame-picks.astro` 는 카탈로그 구획에, `GraphExplorer.tsx` 는 그래프 구획에 있어요. 한 갈래를 고치다 다른 갈래를 늘리기 가장 쉬운 자리입니다. 데코 좌표(`top`·`left`·`width`·`height`)는 게이트 관할 밖이라 대상이 아닌데, 「간격처럼 보이는 값」을 함께 스냅하려는 유인이 있어요. `deco.css` 의 fallback 은 죽은 값이 아니라 실제로 발동합니다 — 값을 틀리면 그 지면에서 다른 색이 뜹니다.
- **배치4** — `TalkLayout`(폭신 대담)은 자기 시각 언어를 가진 지면이에요. 색감이 바뀌면 부채 청산이 아니라 디자인 변경입니다. `global.css` 는 전 페이지에 깔려서, 여기서 잘못 옮기면 한 지면이 아니라 사이트 전체가 바뀝니다.
- **배치5·6** — 발행된 글의 부품입니다. 감사가 준수율 3.6% 로 잰 구획이고 색 위반의 87% 가 여기 있어요. React 시뮬의 fallback 값은 `var(--토큰, 값)` 의 값이 토큰 값과 **정확히 같아야** 합니다 — 어긋나면 fallback 칸이 새로 늘어 그 커밋이 그 자리에서 실패해요. 시뮬이 `${cond ? "#fff" : "#000"}` 꼴로 색을 고르면 정규식은 리터럴만 잡고 어느 상태에서 쓰이는지는 안 남습니다. 그래서 `astro preview` 조작 확인이 완료 기준에 추가로 붙어요. `posts/**` 의 지배값 넷은 `#6b6357`(73) · `#302d28`(69) · `#fffdf8`(65) · `#c9c1b1`(60) 인데, 앞 둘은 본문 잉크가 두 벌이라는 자리입니다 — 사이트는 코발트 남색 `--ink #20264a` 를 쓰고 여기는 따뜻한 먹색을 씁니다. 배치6 에는 하나가 더 붙습니다. `PermissionGate.tsx:57` 은 `REACT_SIM_GUIDE.md` 규칙 6이 좋은 예로 인용하는 줄이라, 줄이 움직이면 그 문서의 인용이 어긋나요.
- **배치7** — 마스코트 팔레트 기록과 수렴 판정입니다. 위에서 본 「죽은 게이트와 다 갚은 게이트가 같은 모양」이 실제로 판정되는 자리예요.

되돌리기는 대체로 쉽습니다. 배치1 은 게이트 코드만 건드리므로 `git revert` 하나로 원상복구되고 `src/**` 는 안 건드립니다. 배치3 이후는 구획별 커밋이라 구획 하나만 되돌릴 수 있고, 발행물 구획은 시리즈별 커밋이라 글 하나 단위로 되돌릴 수 있어요. 되돌리기 어려운 것은 코드가 아니라 위에서 본 기준선 갱신 하나입니다.

## 무엇이 되면 끝인가

카드가 정한 검증은 여섯입니다. 순서에 뜻이 있어요.

1. **게이트가 0 을 낸다.** `bun run tokens:verify` 가 위반·드리프트 전 칸 0 을 보고하고 exit 0 으로 끝납니다. `scripts/tokens-baseline.json` 이 그 수로 커밋돼 있어야 하고요.
1. **게이트가 살아 있다.** 자가검사 6종이 각자 다른 사유로 걸리고, 리터럴 한 줄을 일부러 더한 워킹트리에서 게이트가 비0 으로 끝나면서 그 `파일:줄` 을 지목합니다. 그 줄을 지우면 다시 0 이고요.
1. **회귀가 없다.** `bun run build` · `bun scripts/check-post-markers.ts` · `bun scripts/check-emphasis.ts`(`--dist` 포함) · `bun run viz:verify` · `bun run deco:verify` · `bun run width:verify` · `bun run talk:verify` · `bun run graph:verify` · `tsc --noEmit` 이 전부 통과합니다. `bun run gen:motion` 을 돌린 뒤 `git diff --exit-code -- src/styles/motion.css` 도 통과해야 하고요.
1. **발행물이 안 깨졌다.** `posts/**` 를 건드린 글을 `astro preview` 로 열어 시뮬 인터랙션이 도는 것을 확인합니다. 빌드만으로는 안 잡히는 부분이에요.
1. **화면이 안 바뀐 것이 확인됐다.** 홈 · 글 목록 · 글 상세 · 글 지도 · 대담 · `/design/deco` 를 웨이브 전후로 대조합니다. 바뀐 자리는 왜 바뀌었는지가 수행 내역에 적혀 있어야 해요. 「화면 변화 0」이 목표지만 스케일 스냅은 값을 움직이는 일이라 0 을 단정하지는 않습니다.
1. **다음 리터럴이 막힌다.** 리터럴을 넣은 브랜치에서 `tokens:verify` 가 무는 것을 봅니다. CI 는 `push: main` 트리거라 브랜치에서 안 도니 로컬로 확인해요.

```
Before   기준선 1,395 · 무는 칸 11개 · 게이트는 래칫
After    기준선     0 · 무는 칸  0개 · 게이트는 여전히 래칫
                                       하드월 승격은 KAN-070 이 한다
```

**카드는 2번을 1번보다 먼저 봅니다.** 이유는 앞에서 본 그대로예요 — 래칫은 「줄었다」를 통과로 읽으니, 게이트가 조용히 죽어도 0 이 나옵니다. 1번만 보고 끝내면 다 갚은 상태와 게이트가 죽은 상태를 구별할 수 없어요. 2번이 그 둘을 갈라 줍니다.

여섯 중 5번만 성질이 다릅니다. 나머지 다섯은 명령을 돌려서 판정되는데, 5번은 사람이 눈으로 대조하고 그 결과를 글로 남기는 항목이에요. 스케일 스냅은 값을 실제로 움직이는 일이라 「안 바뀐다」를 기계로 증명할 수 없기 때문입니다. 그래서 이 항목의 합격 조건은 「변화 0」이 아니라 「바뀐 자리마다 이유가 적혀 있다」입니다.

```
1 · 2 · 3 · 6    명령을 돌리면 판정된다
4                astro preview 로 사람이 조작해 확인한다
5                사람이 눈으로 대조하고 그 결과를 수행 내역에 적는다
```

마지막으로 하나. 여섯을 다 통과해도 게이트는 여전히 래칫입니다. 하드월 승격은 `KAN-070` 이 소유한 일이고, 이 카드는 0 으로 수렴했다는 사실만 그쪽으로 넘깁니다.
