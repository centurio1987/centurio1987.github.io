### KAN-006 수행 — "WebRTC 해부" 시리즈 2편 집필

#### Context

`KANBAN.md`의 진행 중 카드 `KAN-006`(WebRTC 이해와 최적 활용 사례)은 3부작 시리즈로 쪼개져 있고, 1편(`src/content/posts/webrtc-1.mdx`)은 이미 발행되어 있다. 1편 본문 말미(`## 이 시리즈의 다른 글`, line 199-203)에 이미 다음 두 편의 주제가 예고되어 있다:

- 2편 — 미디어 파이프라인과 품질: RTP/RTCP, jitter buffer, 혼잡제어, simulcast
- 3편 — 토폴로지와 최적 활용 (mesh/SFU/MCU 등, KAN-006 카드 제목의 "최적 활용 사례"에 대응)

사용자 확인 결과 이번 요청은 **2편 집필**이다. 목표는 1편과 동일한 깊이·형식(RFC 근거, 인터랙티브 React 시뮬레이션, 구조형 정보 이미지)을 갖춘 2편을 리서치→집필→검토→발행→푸시까지 끝내는 것.

#### 접근 방식

1편은 리서치 단계를 건너뛰지 않았다 — `~/blog-research/raws/002-webrtc-connection.md` + angle 페이지(`~/blog-research/wiki/angles/webrtc-connection-three-axes.md`)를 근거로 집필됐다. `tech-deepdive`/`tech-article-publisher` 스킬 문서 모두 리서치 스킵은 "순수 코드 튜토리얼·개인 회고"에만 허용된다고 명시하므로, "저자가 도메인을 잘 안다"는 이유로 2편의 리서치를 스킵하지 않는다 — 1편과 동일하게 리서치부터 다시 돌린다.

**중심 질문으로 스코프를 좁힌다**: 2편 전체를 관통하는 질문은 "연결된 경로 위에서, 패킷 손실·지연·대역폭 변동 속에서도 WebRTC는 어떻게 미디어 품질을 지키는가"로 고정한다. RTP/RTCP·jitter buffer·혼잡제어·simulcast 네 개념을 독립 소재로 나열하지 않고, 이 중심 질문에 각각을 종속시켜 순서대로 배치한다: RTP/RTCP(측정·피드백) → jitter buffer(지연 흡수) → 혼잡제어(대역폭 적응) → simulcast(다중 품질 계층). 이 순서·중심 질문을 `tech-deepdive` 프롬프트에 명시적으로 전달한다.

전체 파이프라인은 `tech-article-publisher` 오케스트레이터 에이전트(`.claude/agents/tech-article-publisher.md`)에 위임한다. 이 에이전트가 자체적으로:

1. `research` — "WebRTC 미디어 파이프라인과 품질: RTP/RTCP, jitter buffer, 혼잡제어(congestion control), simulcast" 주제로 신뢰 소스를 모은다. 최소 확인 후보 소스를 프롬프트에 명시한다:
   - RTP/RTCP: [RFC 3550](https://www.rfc-editor.org/rfc/rfc3550) (RTP), [RFC 3551](https://www.rfc-editor.org/rfc/rfc3551) (A/V 프로파일), [RFC 4585](https://www.rfc-editor.org/rfc/rfc4585) (AVPF)
   - 혼잡제어: WebRTC 표준 혼잡제어인 [Google Congestion Control (GCC), IETF draft](https://datatracker.ietf.org/doc/html/draft-ietf-rmcat-gcc), [Transport-Wide CC(TWCC)](https://datatracker.ietf.org/doc/html/draft-holmer-rmcat-transport-wide-cc-extensions) — REMB는 GCC의 구형 피드백 경로였고 TWCC로 대체돼 온 이력이 있으므로, "현재 주요 브라우저(Chrome/libwebrtc)가 실제로 쓰는 방식이 무엇인지"를 리서치 단계에서 반드시 확인·명기한다(오래된 REMB 설명만으로 끝내지 않는다).
   - simulcast/SVC: [W3C WebRTC 1.0 — simulcast](https://www.w3.org/TR/webrtc/), [RFC 8853 (simulcast SDP)](https://www.rfc-editor.org/rfc/rfc8853)
   - W3C [WebRTC-STATS](https://www.w3.org/TR/webrtc-stats/) (jitter buffer 관련 `getStats()` 지표 근거)
2. `tech-deepdive` — 위 angle + 중심 질문·순서를 입력으로 `draft/webrtc-2-draft.mdx` 집필.
   - frontmatter 템플릿은 1편(`webrtc-1.mdx`)을 그대로 따른다: `title`(2편 제목), `description`, `pubDate`, `category: skills`, `author: ppangto`, `tags`(RTP/RTCP, jitter buffer, 혼잡제어, simulcast 등), `series: "WebRTC 해부"`, `order: 2`, `draft: false`. `publish-post` 단계에서 Astro 콘텐츠 스키마(`src/content.config.ts`)에 맞는지 다시 확인한다.
   - **인터랙티브 컴포넌트는 1개로 제한**한다 — 후보 중 "jitter buffer 지연/재정렬 시각화"를 핵심 데모로 선정(가장 손으로 조작해볼 가치가 큰 개념). 혼잡제어와 simulcast는 정적 구조형 이미지(다이어그램/비교표)로 대체해 구현·검증 부담을 줄인다. 1편 패턴 참고: 토글형 `IceTraversalLab`, 스테퍼형 `SdpNegotiationStepper`. 신규 컴포넌트는 `src/components/posts/webrtc-2/` 아래 별도 디렉토리에 두고(1편 컴포넌트와 공유하지 않음), MDX에서 상대경로 import + `client:visible`(브라우저 API 불필요 시) 방식은 1편과 동일하게 따른다. figcaption에 "교육용 단순화 모델"임을 명시하고, 실제 RFC/브라우저 구현과 다른 지점을 별도로 표기한다(1편 `IceTraversalLab`의 디스클레이머 패턴 재사용).
   - 구조형 이미지(비교표·다이어그램·hero)는 1편의 `public/images/webrtc-1/` 자산 패턴(hero 1개 + 설명 다이어그램 3~4개)을 참고해 make-image에 위임하되, RTP/RTCP 흐름도·혼잡제어 개념도·simulcast 레이어 구조도처럼 기술적으로 틀리기 쉬운 다이어그램은 초안 생성 후 리서치 소스(위 RFC/문서)와 대조해 화살표·용어가 정확한지 별도로 확인한다.
   - 3편(토폴로지와 최적 활용)과의 경계: simulcast는 "인코더가 여러 화질 계층을 보낸다"는 클라이언트 관점까지만 다루고, "SFU가 그 계층을 어떻게 라우팅/선택하는가"는 3편 소재로 남겨 명시적으로 위임한다(중복 방지).
3. `review-post` → `review-writing` → `quality-gate` (통과까지 반복). `quality-gate`/`review-post` 단계에 "RFC 인용·용어 정의가 실제 근거 문서와 일치하는지", "표준(RFC/W3C 스펙)과 특정 브라우저의 구현 관행을 구분해서 서술했는지"를 명시적 체크 항목으로 추가 요청한다.
4. `post-finalize` (개념 이미지/태그/시리즈 링크)
5. `publish-post` → `src/content/posts/webrtc-2.mdx`
6. `ship-post` (빌드 재검증 + git commit&push) — **push 직전에 `git diff --stat`으로 변경 파일 목록을 사용자에게 보여주는 체크포인트를 하나 추가**한다(대량 자산 diff를 사람이 훑어본 뒤에만 push 진행).

에이전트가 시작 시 "자동 진행 / 단계별 개입" 여부를 한 번 묻는데, 이는 에이전트 자신의 몫이므로 이 플랜에서 미리 답하지 않는다.
