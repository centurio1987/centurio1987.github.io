# GraphQL을 써야 할 때와 쓰지 말아야 할 때

> GraphQL은 API 기술 선택지가 아니라, 클라이언트 다양성·데이터 조합 방식·운영 복잡도를 함께 평가해야 하는 아키텍처 선택이다.

## 플롯 후보

### Plot A: 의사결정 체크리스트형
- **적합한 독자/상황**: REST와 GraphQL 중 무엇을 선택해야 할지 판단해야 하는 백엔드/플랫폼 팀
- **구성 흐름**:
  1. GraphQL을 "좋은 API"가 아니라 "좋은 조건에서 빛나는 API"로 정의한다.
  2. 유리한 조건을 정리한다: 다양한 클라이언트, 화면별 데이터 조합, over-fetching/under-fetching 문제, BFF 확산 억제.
  3. 불리한 조건을 정리한다: 단순 CRUD, 캐싱 중심 API, 팀의 schema 운영 역량 부족, 권한/성능 통제 난이도.
  4. 판단 질문 목록으로 기술 선택 기준을 만든다.
  5. GraphQL 도입 여부보다 도입 범위가 더 중요하다는 결론으로 닫는다.
- **이 플롯의 강점**: 글을 읽은 뒤 바로 의사결정에 사용할 수 있다.
- **주의할 점**: GraphQL을 REST의 상위 호환처럼 보이게 쓰면 논지가 약해진다.

### Plot B: 실패 사례에서 출발하는 반례 중심형
- **적합한 독자/상황**: GraphQL 도입 후 복잡도가 늘어난 경험이 있거나 도입을 경계하는 팀
- **구성 흐름**:
  1. "GraphQL을 도입했는데 더 복잡해졌다"는 상황에서 시작한다.
  2. 복잡도의 원인을 나눈다: N+1, 권한 체크 분산, schema versioning 착시, 클라이언트 쿼리 폭주.
  3. 이 문제가 GraphQL 자체의 결함인지, 운영 모델 부재인지 구분한다.
  4. GraphQL이 유리했던 반대 사례를 제시한다.
  5. 실패 조건과 성공 조건을 비교표로 정리한다.
- **이 플롯의 강점**: 기술 도입의 현실적 비용을 드러낼 수 있다.
- **주의할 점**: 경험담이 부족하면 추상적 경고문처럼 보일 수 있다.

### Plot C: API 아키텍처 진화 과정형
- **적합한 독자/상황**: REST, BFF, GraphQL의 관계를 구조적으로 이해하고 싶은 독자
- **구성 흐름**:
  1. 단일 클라이언트와 단순 REST API에서 출발한다.
  2. 클라이언트가 늘어나며 endpoint와 BFF가 증가하는 과정을 보여준다.
  3. GraphQL이 클라이언트별 데이터 조합 문제를 어떻게 흡수하는지 설명한다.
  4. 대신 schema governance와 resolver 운영이라는 새 비용이 생긴다는 점을 설명한다.
  5. GraphQL은 진화의 끝이 아니라 특정 병목을 해결하는 한 단계라는 결론을 낸다.
- **이 플롯의 강점**: 기술 선택의 맥락과 비용 이동을 설명하기 좋다.
- **주의할 점**: REST를 낡은 방식으로 단순화하지 않아야 한다.

## 주의사항 / 잊지 말아야 할 점

- GraphQL의 장점은 "필요한 필드만 받는다"보다 "클라이언트별 데이터 조합을 schema로 통제한다"에 가깝다.
- 단순 CRUD API나 서버 주도 캐싱이 핵심인 시스템에서는 GraphQL이 과한 선택일 수 있다.
- Resolver 성능, N+1, query depth 제한, persisted query 같은 운영 이슈를 빼면 실무 판단 글이 되기 어렵다.
- 권한 모델이 필드 단위로 내려갈 때 복잡도가 급격히 커질 수 있다.
- REST와 GraphQL은 배타적 선택이 아니라 경계별 병행 선택도 가능하다.
- 팀이 schema를 제품 계약으로 관리할 준비가 되어 있는지 따져야 한다.
