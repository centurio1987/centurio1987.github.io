# 모델은 속성이 아니라 내러티브로 나뉜다

> 같은 속성을 가진 두 대상이 같은 모델인지는 이름이나 필드가 아니라 생명주기·행위·사용 맥락이 만드는 내러티브로 판단해야 한다.

## 플롯 후보

### Plot A: 개념 정립형
- **적합한 독자/상황**: 모델을 필드 묶음이나 명사 정의로만 판단하는 습관을 점검하고 싶은 독자
- **구성 흐름**:
  1. "속성이 우연히 같다고 같은 모델이 아니다"라는 문장으로 시작한다.
  2. 사전적 의미와 도메인 내러티브의 차이를 설명한다.
  3. 같은 속성을 가진 두 개념이 다른 생명주기와 행위를 가질 수 있음을 설명한다.
  4. 모델 동일성을 판단하는 기준을 이름, 속성, 행위, 생명주기, 문맥으로 나눈다.
  5. 모델링은 분류가 아니라 이야기의 경계를 긋는 일이라는 결론으로 닫는다.
- **이 플롯의 강점**: 짧지만 철학적 중심 문장을 선명하게 만들 수 있다.
- **주의할 점**: 원본 메모가 짧으므로 예시를 보강하지 않으면 추상론에 머무를 수 있다.

### Plot B: 반례 중심형
- **적합한 독자/상황**: 공통 필드를 발견하면 즉시 공통 모델을 만들고 싶은 개발자
- **구성 흐름**:
  1. 두 객체가 같은 필드를 가진다는 이유로 하나의 모델로 합쳐지는 상황을 제시한다.
  2. 시간이 지나며 서로 다른 행위와 변경 이유가 드러나는 문제를 보여준다.
  3. 이름의 사전적 의미가 같아도 실제 사용자/업무 내러티브가 다를 수 있음을 설명한다.
  4. 공통화가 모델링을 단순하게 만드는지, 오히려 의미를 흐리는지 판단하는 질문을 제시한다.
  5. 우연한 유사성과 본질적 동일성을 구분해야 한다는 결론을 낸다.
- **이 플롯의 강점**: "공통화 본능"을 비판하는 글로 읽기 쉽다.
- **주의할 점**: 지나치게 공통화 자체를 부정하는 글이 되지 않도록 해야 한다.

### Plot C: 모델링 리뷰 체크리스트형
- **적합한 독자/상황**: 모델 분리/통합을 리뷰하는 팀
- **구성 흐름**:
  1. 모델이 같다고 판단하기 전에 던질 질문을 소개한다.
  2. 속성 동일성, 이름 동일성, 생명주기 동일성, 행위 동일성, 변경 이유 동일성을 각각 점검한다.
  3. 하나라도 다르면 무조건 분리하라는 뜻이 아니라, 비용과 의미 훼손을 비교해야 한다고 설명한다.
  4. 코드/DB 설계로 옮길 때 흔한 실수를 정리한다.
  5. 리뷰 체크리스트로 마무리한다.
- **이 플롯의 강점**: 짧은 원본 메모를 실용적인 글로 확장하기 좋다.
- **주의할 점**: 체크리스트가 일반론에 머물지 않도록 예시가 필요하다.

## 주의사항 / 잊지 말아야 할 점

- 속성의 우연한 동일성과 모델의 본질적 동일성을 구분해야 한다.
- 어구의 사전적 의미보다 도메인 안에서 어떤 이야기를 수행하는지가 더 중요하다.
- 생명주기, 행위, 변경 이유, 사용하는 사람/업무 맥락을 모델 판단 기준으로 삼아야 한다.
- 공통화는 중복 제거가 아니라 의미 결합이므로 비용을 따져야 한다.
- DB 테이블 통합이나 클래스 상속 같은 구현 선택이 모델 동일성을 역으로 정당화하게 두면 안 된다.
- 원본 아이디어가 짧으므로 본문 작성 전에 구체 예시를 하나 정하는 것이 필요하다.
