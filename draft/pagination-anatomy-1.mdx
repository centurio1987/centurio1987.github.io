목록을 내리다 방금 지나친 글을 또 만납니다. 새로고침하고 다시 내려 보면 이번엔 분명히 있던 글 하나가 사라져 있어요. 프론트 코드를 아무리 뒤져도 중복 제거 쪽에는 잘못된 곳이 없습니다.

버그가 아닙니다. 서버에 "네 번째 자리부터 세 개 주세요"라고 물었는데, 묻는 사이에 맨 앞으로 새 글이 하나 올라왔을 뿐이에요.

```text
 1페이지를 받았다         F  E  D │ C  B  A
                          └ 봤다 ┘

 그 사이 G 가 올라온다    G  F  E  D │ C  B  A
                          └ 3칸 건너 ┘
 2페이지를 요청하면               D  C  B
                                  └ D 를 또 받는다
```

자리 번호는 데이터를 가리키는 게 아니라 **줄 서 있는 순서**를 가리킵니다. 앞줄이 한 명 길어지면 뒷사람 번호가 전부 밀려요. 그러니 이건 프론트가 고칠 문제가 아니라, 서버가 다음 구간을 **무엇으로 지목했는가**의 문제입니다.

그런데 여기서 대부분의 논의가 곧장 엉킵니다. 이런 되물음이 따라 나오거든요.

> 그럼 무한 스크롤로 바꾸면 되나요?

무한 스크롤은 이 문제와 아무 상관이 없습니다. 애초에 같은 저울에 올릴 물건이 아니거든요.

```text
 잘못 묶인 질문   offset 이냐 무한 스크롤이냐
                  └ 서버가 무엇으로 지목하는지와 화면이 어떻게 보이는지를 한 저울에 올렸다

 갈라 놓은 질문   offset 이냐 keyset 이냐
                  무한 스크롤이냐 페이지 번호냐
                  └ 두 질문은 따로 묻고 따로 답한다
```

왜 갈라야 하는지, 갈라 놓고 나면 무엇이 보이는지를 정하는 것이 이 글의 첫 일입니다.

이 편에서 정하고 갈 것은 셋입니다.

- **전략과 표현을 가르는 선** — 무한 스크롤과 페이지 번호는 전략이 아닙니다
- **네 갈래의 명세** — 요청 파라미터·응답 형태·정렬 요구·안정성·총 개수·임의 점프·비용
- **조건에서 선택으로 가는 규칙** — 어느 조건에서 어느 갈래를 고르는가

레이어별 구현은 이 편에서 다루지 않습니다. 세 편으로 나눠 놨거든요.

```text
 1편  전략과 명세                                          ← 지금 이 글
 2편  바깥쪽 — 프론트 상태·URL·복원 · 컨트롤러 계약·커서 인코딩
 3편  안쪽  — 서비스 경계·정렬 키 소유 · 인덱스와 실행 계획
```

대신 1편에서 고른 것이 뒤 두 편에 무엇을 청구하는지는 그때그때 걸어 두겠습니다. 선택이 비용을 부르는 자리가 어디인지 미리 보여야 선택이 실감 나니까요.

## 한눈에 보기 — 섞여 있던 세 갈래

먼저 무엇이 무엇인지 갈라 둡니다. 흔히 페이지네이션 방식이라는 이름 하나로 뭉뚱그리는 것들이 실은 **서로 독립인 세 층**입니다.

```text
 ① 서버가 다음 구간을 무엇으로 지목하는가  ── 전략
    ├─ offset   몇 번째 자리부터   ?page=3&size=20
    └─ keyset   어떤 값 다음부터   ?after_ts=...&after_id=1042

 ② 그 지목값을 클라이언트에 어떻게 넘기는가  ── 계약
    ├─ 그대로 노출    숫자와 값이 URL 에 그대로 보인다
    ├─ cursor        불투명한 문자열 하나로 감싼다        (Relay Connections)
    └─ page token    불투명한 문자열 + 서버가 수명을 쥔다  (Google AIP-158)

 ③ 그 구간을 화면에 어떻게 내놓는가  ── 표현
    └─ 페이지 번호 · 이전/다음 · 더 보기 · 무한 스크롤
```

세 층이 서로를 강제하지 않는다는 게 요점이에요. ①에서 offset 을 고르고 ②에서 불투명 커서를 씌우고 ③에서 무한 스크롤을 쓰는 조합이 그냥 성립합니다.

이제 ①과 ②에 있는 네 갈래를 명세 일곱 항목으로 갈라 봅시다. 아래 표가 이 글의 등뼈입니다.

| 명세 항목 | offset/limit | keyset(seek) | cursor 계약 | page token |
| --- | --- | --- | --- | --- |
| 요청 파라미터 | `page`+`size` 또는 `offset`+`limit` | 마지막 행의 정렬 키 값 전부 | `first`/`after`, `last`/`before` | `page_size`+`page_token` |
| 응답 형태 | 배열 (+ 총 개수·총 페이지) | 배열 + 다음 경계값 | `edges[].node`/`cursor` + `pageInfo` | 배열 + `next_page_token` |
| 정렬 요구 | 고유 순서를 만드는 `ORDER BY` | 위 조건 + 비교 방향이 정렬 방향과 일치 | 앞·뒤 방향의 순서 일치만 | 이 사양이 다루지 않는다 |
| 안정성(중복·누락) | 앞이 밀리면 둘 다 난다 | 지나온 경계는 안 밀린다 | 안쪽 지목 방식이 정한다 | 안쪽 지목 방식이 정한다 |
| 총 개수 제공 | 별도 질의로 가능 | 별도 질의로 가능 | 사양에 필드가 없다 | `total_size` 로 열려 있다 |
| 임의 페이지 점프 | 된다 | 안 된다 | 안 된다 | 안 된다 |
| 비용 특성 | 건너뛴 깊이에 비례 | 깊이와 무관 | 안쪽이 정한다 | 안쪽이 정한다 |

여기서 가장 중요한 줄은 아래에서 넷째, **안정성**입니다. 오른쪽 두 칸이 나란히 "안쪽 지목 방식이 정한다"라고 적혀 있죠. 이게 우연이 아니라는 것 — 그러니까 cursor 와 page token 은 offset·keyset 과 **같은 줄에 세울 수 있는 물건이 아니라는 것**이 다음 절의 내용입니다.

## 엄밀한 정의 — 전략·계약·표현

용어를 정하고 갑니다. 여기서 정한 뜻을 글 끝까지 그대로 쓸 거예요. **페이지네이션 전략**은 서버가 다음 구간을 **무엇으로 지목하는가**입니다. 자리 번호로 지목하면 offset, 마지막으로 본 행의 값으로 지목하면 keyset 이에요. 갈래는 이 둘뿐입니다.

**계약**은 그 지목값을 **클라이언트에 어떤 모양으로 넘기는가**입니다. 숫자와 값을 그대로 노출할 수도 있고, 불투명한 문자열 하나로 감쌀 수도 있어요.

**표현**은 받은 구간을 **화면이 어떻게 내놓는가**입니다. 페이지 번호를 깔든 무한 스크롤로 잇든, 서버가 받은 질문은 똑같습니다.

두 축을 교차시키면 네 칸이 나오고, **네 칸이 전부 실재합니다.**

```text
                        ┌─────────── 계약(노출 방식) ────────────┐
                        │  그대로 노출        불투명하게 감싼다   │
 ┌── 전략(지목 방식) ───┼────────────────────┬──────────────────┤
 │ offset 으로 지목     │ ?page=3&size=20    │ 커서 안에         │
 │                      │                    │ offset 을 넣는다  │
 ├──────────────────────┼────────────────────┼──────────────────┤
 │ keyset 으로 지목     │ ?after_id=1042     │ 커서 안에         │
 │                      │ &after_ts=...      │ 정렬 키를 넣는다  │
 └──────────────────────┴────────────────────┴──────────────────┘
```

여기가 헷갈리기 쉬운 포인트입니다. **"커서 기반"과 "keyset"을 같은 말로 쓰는 습관** 말이에요.

두 단어는 격자의 서로 다른 변을 가리킵니다. 커서는 오른쪽 열의 이름이고, keyset 은 아래 행의 이름이에요. 실무에서 "커서 기반 페이지네이션"이라 부르는 것 대부분이 오른쪽 아래 칸, 그러니까 **불투명 커서 + keyset 질의**의 조합이라서 둘이 붙어 다닐 뿐입니다. 오른쪽 위 칸도 멀쩡히 존재해요. 커서를 열어 보면 `offset=60` 한 줄만 들어 있는 API 는 흔합니다.

> 기억법: **커서는 봉투고, keyset 은 그 안에 넣는 편지입니다.** 봉투만 보고 편지를 알 수 없어요.

이제 세 번째 갈래를 겹칩니다. 표현은 전략을 거의 가리지 않습니다.

```text
 전략            표현
 ──────────      ────────────────────────────────────────────
 offset  ──────▶ 페이지 번호 · 이전/다음 · 더 보기 · 무한 스크롤
 keyset  ──────▶              이전/다음 · 더 보기 · 무한 스크롤
                 └ 페이지 번호만 못 잇는다(경계값을 모르니까)
```

무한 스크롤은 offset 위에서도 그대로 돌아갑니다. 잘 돌아가지 않는 것처럼 보였다면 그건 무한 스크롤 탓이 아니라 **offset 이 밀린 탓**이고, 무한 스크롤이 그 밀림을 유난히 잘 보이게 만들었기 때문이에요. 페이지 번호를 눌러 이동하는 UI 에서는 사용자가 앞 페이지를 이미 닫아서 중복을 눈치채지 못할 뿐입니다.

잠깐, 확인 하나만 해 볼까요? "무한 스크롤이라 총 개수는 못 보여 준다"는 말은 맞을까요?

틀렸습니다. 총 개수는 **전략**이 정하는 항목이고 무한 스크롤은 **표현**이에요. offset 이든 keyset 이든 총 개수는 별도 질의로 낼 수 있습니다. 실제로 총 개수를 안 주는 서비스가 많은 건 못 줘서가 아니라 그 질의의 비용이 커서죠. 못 하는 것과 안 하는 것은 다릅니다.

## 핵심 원리 — 네 갈래의 명세

이제 갈래마다 일곱 항목을 채웁니다. 표에 적힌 한 칸이 왜 그 값인지를 여기서 팝니다.

### offset/limit — 자리 번호로 지목합니다

가장 흔하고, 가장 자주 틀립니다. 그런데 이 갈래를 한물간 것으로 여기고 밀어 두면 뒤에서 반드시 되돌아옵니다. 다른 갈래가 못 주는 것을 하나 쥐고 있거든요.

```text
 요청   GET /posts?page=3&size=20          (또는 ?offset=40&limit=20)

 응답   {
          "items": [ ...20건... ],
          "page":  3,
          "size":  20,
          "total": 1043
        }
```

**정렬 요구**부터 봅시다. `ORDER BY` 는 있으면 좋은 게 아니라 없으면 안 되는 것입니다. PostgreSQL 문서가 이렇게 적고 있어요.

> "When using `LIMIT`, it is important to use an `ORDER BY` clause that constrains the result rows into a unique order. Otherwise you will get an unpredictable subset of the query's rows."
>
> (`LIMIT` 을 쓸 때는 결과 행을 **고유한 순서**로 묶어 주는 `ORDER BY` 절을 쓰는 것이 중요하다. 그러지 않으면 예측할 수 없는 부분집합을 받게 된다.)

핵심은 **고유한 순서**입니다. 정렬만 걸면 되는 게 아니라 동점이 남지 않아야 해요. 같은 문서가 그 이유를 이렇게 잇습니다.

> "Thus, using different `LIMIT`/`OFFSET` values to select different subsets of a query result _will give inconsistent results_ unless you enforce a predictable result ordering with `ORDER BY`."

MySQL 도 같은 말을 자기 문장으로 적어 둡니다 — "If multiple rows have identical values in the `ORDER BY` columns, the server is free to return those rows in any order." 동점 행의 순서는 실행 계획에 따라 달라진다는 뜻이에요. 그래서 `ORDER BY created_at DESC` 만 걸린 목록은 같은 시각에 만들어진 글들 사이에서 조용히 흔들립니다.

그러니 SQL 에서 가장 중요한 줄은 이겁니다.

```sql
ORDER BY created_at DESC, id DESC
```

`id DESC` 가 tie-breaker 예요. 이 한 칸이 빠지면 위 두 인용이 말하는 "예측할 수 없는 부분집합"이 그대로 나옵니다.

**안정성**은 실제로 재현해 봅시다. 글 여섯 건이 있고 페이지 크기가 3 입니다.

```sql
-- 1페이지
SELECT id, created_at, title FROM post
ORDER BY created_at DESC, id DESC
LIMIT 3 OFFSET 0;
```

```text
 id │    created_at    │ title
 ───┼──────────────────┼───────
  6 │ 2026-08-01 14:00 │ F
  5 │ 2026-08-01 13:00 │ E
  4 │ 2026-08-01 12:00 │ D
```

여기서 새 글 G 가 하나 들어옵니다. 그리고 2페이지를 요청해요.

```sql
INSERT INTO post VALUES (7, '2026-08-01 15:00', 'G');

-- 2페이지
SELECT id, created_at, title FROM post
ORDER BY created_at DESC, id DESC
LIMIT 3 OFFSET 3;
```

```text
 id │    created_at    │ title
 ───┼──────────────────┼───────
  4 │ 2026-08-01 12:00 │ D     ← 1페이지에서 이미 받은 행
  3 │ 2026-08-01 11:00 │ C
  2 │ 2026-08-01 10:00 │ B
```

D 가 두 번 왔습니다. 반대 방향도 재현됩니다. 삽입 대신 맨 앞의 F 를 지우고 2페이지를 요청하면 `B A` 두 건만 돌아와요. **C 가 통째로 사라집니다.**

```text
 Before  삽입     G 가 앞에 끼어든다  →  경계가 뒤로 밀린다  →  D 중복
 After   삭제     F 가 앞에서 빠진다  →  경계가 앞으로 당겨진다 → C 누락
```

두 경우 모두 원인이 같습니다. offset 은 **행을 가리키는 게 아니라 줄 서 있는 자리를 가리킨다**는 것 하나예요.

**비용 특성**으로 갑니다. 여기에도 널리 퍼진 설명이 하나 있어요.

> OFFSET 이 느린 건 정렬 때문이다.

절반만 맞습니다. PostgreSQL 문서를 그대로 읽어 봅시다.

> "The rows skipped by an `OFFSET` clause still have to be computed inside the server; therefore a large `OFFSET` might be inefficient."
>
> (`OFFSET` 절이 건너뛴 행도 서버 안에서는 여전히 **계산되어야 한다.** 그래서 큰 `OFFSET` 은 비효율적일 수 있다.)

정렬을 인덱스로 해결해서 `Sort` 노드를 없애도, 건너뛴 행은 계산됩니다. MySQL 쪽 문장도 같은 방향이에요 — "If a filesort must be done, all rows that match the query without the `LIMIT` clause are selected, and most or all of them are sorted, before the first _row_count_ are found." 산술만 보겠습니다.

```text
 페이지 크기 20, 1,000 페이지째 요청
   → OFFSET 19980 LIMIT 20
   → 서버가 만드는 행 20,000 건
   → 그중 버리는 행     19,980 건
   → 돌려주는 행            20 건
```

이건 측정값이 아니라 문서에 적힌 동작에서 나온 산술입니다. 한 행을 만드는 비용이 몇 밀리초인지는 여러분 테이블의 폭·인덱스·버퍼 적중률이 정하니까, 그 숫자는 직접 재셔야 해요. 다만 **깊이에 비례해서 늘어난다는 성질**은 어디서 재도 같습니다.

**총 개수**는 이 갈래의 자산입니다. `COUNT(*)` 한 번이면 총 개수와 총 페이지 수가 나오죠. 정확값의 비용이 크면 근사값으로 내려갈 길도 있습니다. PostgreSQL 의 `pg_class.reltuples` 가 그것인데, 문서가 성격을 분명히 적어 둬요.

> "Number of live rows in the table. This is only an estimate used by the planner."

플래너용 추정치고 `VACUUM`·`ANALYZE` 때 갱신됩니다. 그러니 필터가 걸린 목록의 개수로는 못 씁니다. 전체 행 수를 대충 보여 주는 자리에만 쓰세요.

**임의 페이지 점프**가 이 갈래의 존재 이유입니다. 47페이지로 바로 뛰는 것, "마지막 페이지" 버튼을 다는 것 — offset 만 자연스럽게 할 수 있어요. 다음 갈래가 이걸 못 준다는 사실이 선택의 절반을 정합니다.

### keyset(seek) — 마지막으로 본 값으로 지목합니다

자리 번호 대신 **값**으로 지목하면 밀림이 사라집니다. Before/After 로 나란히 봅시다.

```text
 Before (offset)   ORDER BY created_at DESC, id DESC
                   LIMIT 3 OFFSET 3
                   └ "앞에서 3칸 건너뛰고 3개"

 After  (keyset)   WHERE (created_at, id) < ('2026-08-01 12:00', 4)
                   ORDER BY created_at DESC, id DESC
                   LIMIT 3
                   └ "이 값보다 뒤에 오는 것부터 3개"
```

여기서 가장 중요한 줄은 `WHERE` 한 줄입니다.

```sql
WHERE (created_at, id) < (?, ?)
```

이게 keyset 의 전부예요. 왼쪽 괄호에 든 것은 `ORDER BY` 에 적은 열과 **같은 순서로 같은 열**이고, 오른쪽 괄호에 든 것은 **직전 페이지 마지막 행의 그 열 값들**입니다. 두 괄호의 열 목록이 어긋나면 그 순간 조용히 틀립니다.

행 값 비교가 어떻게 계산되는지는 PostgreSQL 문서에 적혀 있습니다.

> "For the `<`, `<=`, `>` and `>=` cases, the row elements are compared left-to-right, stopping as soon as an unequal or null pair of elements is found."
>
> (`<`, `<=`, `>`, `>=` 의 경우 행의 원소를 **왼쪽에서 오른쪽으로** 비교하며, 값이 다르거나 null 인 쌍을 만나는 즉시 멈춘다.)

사전 순서와 같습니다. `created_at` 이 다르면 거기서 판정이 끝나고, 같을 때만 `id` 로 내려가요.

**정렬 요구**가 offset 보다 한 단계 더 셉니다. 마지막 열이 **고유해야** 합니다. 왜 그래야 하는지는 말로 설명하는 것보다 반례를 하나 놓고 보는 편이 훨씬 빠르니까, `created_at` 하나만으로 keyset 을 했다고 해 봅시다.

```text
 같은 시각에 만들어진 행이 셋   (12:00, D1)  (12:00, D2)  (12:00, D3)
 1페이지에서 D1 까지 받았다     D2 · D3 는 아직 못 받았다
 경계값으로 쥔 것 = '12:00'

 WHERE created_at <  '12:00'   →  D2 · D3 를 건너뛴다   (누락)
 WHERE created_at <= '12:00'   →  D1 을 다시 받는다     (중복)
```

빠져나갈 방법이 없어요. `id` 같은 고유 열을 마지막에 붙이는 이유가 이겁니다. tie-breaker 는 취향이 아니라 **정확성 요건**이에요.

> 기억법: **정렬 키의 마지막 칸은 반드시 고유해야 한다.** 아니면 누락이거나 중복이다.

**안정성**을 같은 조건에서 재현해 봅시다. 아까와 똑같이 G 를 삽입한 뒤 2페이지를 요청합니다.

```sql
INSERT INTO post VALUES (7, '2026-08-01 15:00', 'G');

SELECT id, created_at, title FROM post
WHERE (created_at, id) < ('2026-08-01 12:00', 4)
ORDER BY created_at DESC, id DESC
LIMIT 3;
```

```text
 id │    created_at    │ title
 ───┼──────────────────┼───────
  3 │ 2026-08-01 11:00 │ C
  2 │ 2026-08-01 10:00 │ B
  1 │ 2026-08-01 09:00 │ A
```

중복이 없습니다. 앞에서 F 를 지우는 시나리오로 바꿔도 결과는 `C B A` 그대로예요. 새 글은 어차피 경계값보다 **앞**에 놓이니 뒤쪽 구간을 건드리지 않고, 앞에서 지워진 글도 마찬가지입니다.

여기서 범위를 정확히 해 두겠습니다. keyset 이 보장하는 것은 **경계값이 밀리지 않는다**는 것 하나입니다. 행이 두 번 안 나온다가 아니에요. 정렬 키로 쓴 열의 값이 바뀌면 그 행은 다시 나타나기도 하고 건너뛰어지기도 합니다.

```text
 keyset 이 보장하는 것    경계값이 밀리지 않는다
 보장하지 않는 것         행이 경계를 넘어 이동하지 않는다
                           └ 정렬 키 값이 변하면 넘어 다닌다
```

`updated_at` 이나 좋아요 수로 정렬할 때 벌어지는 일인데, 이 조건이 걸리면 선택의 결이 완전히 달라집니다. 뒤의 네 번째 장면에서 다시 봅니다.

**비용 특성**이 이 갈래의 자산입니다. 인덱스가 정렬을 만족하면 깊이와 무관해요. PostgreSQL 문서가 이 성질을 정면으로 적어 둡니다.

> "An important special case is `ORDER BY` in combination with `LIMIT n`: an explicit sort will have to process all the data to identify the first _n_ rows, but if there is an index matching the `ORDER BY`, the first _n_ rows can be retrieved directly, without scanning the remainder at all."
>
> (`ORDER BY` 와 `LIMIT n` 이 함께 쓰인 경우가 중요한 특수 사례다. 명시적 정렬은 첫 _n_ 행을 찾기 위해 데이터 전체를 처리해야 하지만, `ORDER BY` 에 맞는 인덱스가 있으면 첫 _n_ 행을 **나머지를 전혀 훑지 않고** 바로 꺼낼 수 있다.)

keyset 은 `WHERE` 로 시작점을 옮기고 `LIMIT` 으로 개수를 자릅니다. 인덱스가 `ORDER BY` 와 맞아떨어지면 1페이지든 1,000페이지든 읽는 행 수가 같아요. offset 이 깊이에 비례해 늘어나던 그 자리에서, keyset 은 평평합니다.

다만 인덱스가 `ORDER BY` 와 맞아떨어져야 한다는 전제는 공짜가 아닙니다. MySQL 은 행 값 비교를 `AND` 와 섞으면 인덱스를 덜 써요. 문서에 이렇게 적혀 있습니다 — "The optimizer is less likely to use available indexes if the row constructor columns do not cover the prefix of an index." 그래서 같은 문서가 등가 전개형을 권합니다.

```sql
-- 행 값 비교
WHERE c1 = 1 AND (c2, c3) > (1, 1)

-- MySQL 이 인덱스를 더 쓰는 등가 형태
WHERE c1 = 1 AND (c2 > 1 OR (c2 = 1 AND c3 > 1))
```

같은 조건인데 실행 계획이 다릅니다. **어느 형태를 쓸지는 DB 가 정하지 이론이 정하지 않아요.** 이 갈림길을 제대로 파는 건 3편 몫입니다.

**임의 페이지 점프**는 안 됩니다. 47페이지의 경계값을 모르니까요. 이전 페이지는 갈 수 있는데, 비교 방향과 정렬 방향을 **둘 다** 뒤집고 받은 결과를 되뒤집어야 합니다. 한쪽만 뒤집으면 엉뚱한 구간이 옵니다.

**총 개수**는 커서와 무관한 별도 질의입니다. keyset 을 쓴다고 총 개수를 못 주는 게 아니에요. 앞에서 한 번 짚은 그 구분입니다.

### cursor 계약 — 지목값을 봉투에 넣습니다

왜 굳이 감싸야 할까요? `after_id=1042` 가 뭐가 문제죠? 문제는 값이 아니라 **그 값이 계약이 된다는 것**입니다. 파트너 20곳의 코드에 `after_id` 가 박히고 나면, 우리는 정렬 키를 못 바꿉니다. 최신순을 인기순으로 바꾸는 순간 그 파라미터의 뜻이 달라지는데 이미 남의 코드에 들어가 있으니까요.

그래서 GraphQL Cursor Connections 사양은 커서를 이렇게 규정합니다.

> "The result of this field should be considered opaque by the client, but will be passed back to the server as described in the "Arguments" section below."
>
> (이 필드의 결과는 **클라이언트가 불투명한 것으로 취급해야** 하며, 다만 아래 "Arguments" 절에 서술된 대로 서버로 되돌려 보내진다.)

문장의 주어를 보세요. 서버더러 암호화하라는 말이 아니라 **클라이언트더러 뜯어보지 말라**는 말입니다. 그러니 불투명함을 만드는 것은 인코딩이 아니라 문서에 적은 이 한 줄이에요. base64 로 감싸도 파트너는 5초면 열어 봅니다.

응답 형태는 사양이 정해 뒀습니다 — "Connection types must have fields named `edges` and `pageInfo`."

```text
 Connection
   ├─ edges  [ Edge ]
   │           ├─ node    실제 데이터
   │           └─ cursor  이 행을 가리키는 문자열
   └─ pageInfo
        ├─ hasNextPage
        ├─ hasPreviousPage
        ├─ startCursor
        └─ endCursor
```

요청 쪽은 방향마다 두 개씩입니다. 앞으로 갈 때 `first`+`after`, 뒤로 갈 때 `last`+`before`. 둘을 섞는 것에 대해 사양은 금지가 아니라 이렇게 적습니다 — "Including a value for both `first` and `last` is strongly discouraged, as it is likely to lead to confusing queries and results." **금지가 아니라 강한 비권장**이고, 둘 다 왔을 때의 동작도 알고리즘으로 정의돼 있어요.

이제 이 절에서 가장 중요한 대목입니다. `hasNextPage` 를 계산하는 알고리즘을 그대로 옮깁니다.

```text
 HasNextPage(allEdges, before, after, first, last)
   1. first 가 set 이면
        ApplyCursorsToEdges 결과가 first 개보다 많으면 true, 아니면 false
   2. before 가 set 이면
        "서버가 before 뒤에 원소가 더 있음을 효율적으로 판정할 수 있으면" true
   3. false 를 반환한다
```

2번 줄을 다시 보세요. 사양이 **"efficiently determine"** 이라고 적고 있습니다. 어떻게 알아내는지를 정하지 않을 뿐 아니라, **못 알아내면 그냥 false 를 돌려줘도 된다**고 허용해요. 다음 페이지가 있는지조차 구현에 맡기는 문서가 지목 방식을 정할 리 없습니다.

이것이 앞의 표에서 cursor 열을 안쪽 지목 방식에 넘긴 이유입니다. 커서 계약은 봉투의 규격이지 편지의 내용이 아니에요.

덤으로 실무에서 어긋나기 쉬운 자리가 하나 딸려 옵니다. 3번 줄 때문에 **`first` 없이 `last`/`before` 로 역방향 페이징을 할 때 `hasNextPage` 는 false 가 정답**입니다. 그 값을 뒤에 더 없다는 뜻으로 읽으면 틀려요.

```text
 앞으로 읽을 때   first + after    →  hasNextPage 를 본다
 뒤로 읽을 때     last  + before   →  hasPreviousPage 를 본다
                                       hasNextPage 는 false 가 정상이다
```

총 개수는 어떨까요? `totalCount` 는 **사양에 없습니다.** 문자열 자체가 문서에 한 번도 나오지 않아요. 생태계가 관행으로 붙인 필드고, 근거는 Connection Types 절의 재량 조항입니다 — "They may have additional fields related to the connection, as the schema designer sees fit."

정렬에 대해 사양이 요구하는 것도 딱 한 줄뿐입니다.

> "The ordering of edges should be the same when using `first`/`after` as when using `last`/`before`, all other arguments being equal."

앞으로 읽든 뒤로 읽든 순서가 같아야 한다는 것. 그 순서가 안정적인지, 동점을 어떻게 깨는지는 **이 사양이 다루지 않습니다.**

### page token — 봉투의 수명까지 서버가 쥡니다

Google AIP-158 이 정의하는 page token 은 커서와 모양이 비슷한데, 계약이 한 겹 더 두껍습니다. 응답 한 조각을 먼저 봅시다.

```text
 요청   GET /v1/publishers/123/books?page_size=50&page_token=CgQIARAB

 응답   {
          "books": [ ... 50건 이하 ... ],
          "next_page_token": "CgQIARAC",
          "total_size": 1043
        }
```

두꺼워진 대목이 넷입니다. 규범 강도가 저마다 다르니 표로 먼저 정리해 두고 하나씩 확인해 봅시다.

| 두꺼워진 대목 | 사양의 규범 강도 |
| --- | --- |
| `page_size` 는 최댓값이지 정확한 개수가 아니다 | `may` return fewer |
| 토큰은 불투명해야 한다 | `must` be opaque |
| 서버가 토큰을 만료시킬 수 있다 | `may` expire |
| 다른 인자가 바뀌면 거절한다 | `should` send `INVALID_ARGUMENT` |

**`page_size` 는 정확한 개수가 아니라 최댓값입니다.**

> "The API may return fewer results than the number requested (including zero results), even if not at the end of the collection."
>
> (API 는 요청한 수보다 **적게** 반환할 수 있다. **0건도 포함**되며, 컬렉션의 끝이 아니어도 그렇다.)

그래서 종료 판정을 개수로 하면 안 됩니다. 사양이 종료를 정의하는 문장은 따로 있어요 — "If the end of the collection has been reached, the `next_page_token` field must be empty."

```text
 Before  종료 판정을 개수로 한다
           받은 건수 < page_size  →  끝났다고 본다
           └ 0건이 와도 끝이 아닐 수 있다. 여기서 목록이 잘린다.

 After   종료 판정을 토큰으로 한다
           next_page_token 이 빈 문자열  →  끝
           └ 개수는 보지 않는다
```

**토큰의 불투명함은 의무입니다.**

> "Page tokens provided by APIs must be opaque (but URL-safe) strings, and must not be user-parseable."

Relay 가 클라이언트에게 `should` 로 부탁한 자리를 AIP-158 은 API 에게 `must` 로 지웁니다. 흔히 인용되는 base64 proto 는 그보다 훨씬 약해요.

> "For page tokens which do not need to be stored in a database, and which do not contain sensitive data, an API may obfuscate the page token by defining an internal protocol buffer message with any data needed, and send the serialized proto, base-64 encoded."

`may` 인 데다 조건이 둘 붙습니다. 그리고 사양이 고른 동사가 `encrypt` 가 아니라 **`obfuscate`(난독화)** 예요. 감춘 게 아니라 읽기 불편하게 만든 것입니다.

```text
 must   토큰은 불투명해야 한다          ← 지켜야 하는 의무
 may    base64 proto 로 감싼다          ← 그 의무를 이행하는 한 가지 방법
          조건 ① DB 에 저장할 필요가 없다
          조건 ② 민감 데이터를 담지 않는다
```

**수명은 서버가 쥡니다.**

> "APIs may expire page tokens a reasonable time after they have been sent, in order not to needlessly store large amounts of data that is unlikely to be used."

이 한 문장이 page token 을 별도의 층으로 만듭니다. `after_id=1042` 를 그대로 노출하면 만료라는 개념을 아예 쓸 수가 없어요 — 그 값은 행이 살아 있는 한 영원히 유효하니까요. 봉투를 씌워야 비로소 수명을 말할 수 있습니다. 그래서 한 겹입니다.

```text
 값을 그대로 노출   after_id=1042        행이 살아 있는 한 유효
                                         → 만료를 말할 자리가 없다

 봉투를 씌움        page_token=CgQIARAB  봉투에 유효 기간을 새긴다
                                         → 한 시간 뒤 거절할 수 있다
```

**토큰은 질의 전체를 대표합니다.**

> "The user is expected to keep all other arguments to the RPC the same; if any arguments are different, the API should send an `INVALID_ARGUMENT` error."

필터를 바꾸고 토큰만 이어 쓰면 거절하라는 뜻입니다. 커서가 몇 번째 행이 아니라 **어떤 질의의 어디쯤**을 가리킨다는 선언이에요.

```text
 토큰 하나가 대표하는 것
   정렬 기준  +  필터 조건  +  어디까지 읽었는가
   └ 셋 중 하나라도 바뀌면 그 토큰은 다른 질의의 것이다
```

2편에서 커서에 무엇을 담아야 하는지 다룰 때 이 그림이 설계의 출발점이 됩니다.

총 개수는 열려 있습니다. 다만 성격을 정확히 읽어야 해요.

> "Response messages for collections may provide an `int32 total_size` field, providing the user with the total number of items in the list. This total may be an estimate (but the API should explicitly document that)."

`may` 이고 **추정치여도 됩니다.** 대신 추정치라면 그 사실을 문서에 적으라고 요구하죠. 앞에서 본 `pg_class.reltuples` 같은 값을 그대로 실을 수 있는 길이 사양 안에 열려 있는 셈입니다.

마지막으로 JSON:API 를 짧게 얹습니다. 이쪽은 커서를 파라미터가 아니라 **링크**로 넘깁니다.

```text
 "links": {
   "first": "/articles?page[number]=1",
   "prev":  null,
   "next":  "/articles?page[number]=2",
   "last":  "/articles?page[number]=47"
 }
```

네 키는 사양이 `MUST` 로 고정합니다. 그런데 그 링크 안에 무엇이 들어가는지는 정하지 않아요.

> "JSON API is agnostic about the pagination strategy used by a server, but the `page` query parameter family can be used regardless of the strategy employed."
>
> (JSON API 는 서버가 쓰는 페이지네이션 **전략에 대해 불가지론**이며, `page` 쿼리 파라미터 family 는 어떤 전략을 쓰든 사용할 수 있다.)

`page[number]` 든 `page[after]` 든 사양 위반이 아닙니다. 참고로 `first`·`last`·`next`·`prev` 는 IANA 링크 관계 레지스트리에 등록된 이름이라, 헤더로 옮겨도 그대로 통합니다.

세 사양이 각자의 어법으로 같은 말을 하고 있습니다.

> 기억법: **계약은 봉투의 규격만 정한다. 편지는 안쪽에서 고른다.**

## 실무 시나리오 워크스루

이제 조건이 선택을 어떻게 정하는지 장면으로 봅니다. 각 장면에서 무엇이 결정을 내렸는지에 주목해 주세요.

### 장면 1 — 관리자 콘솔의 주문 검색

운영자가 기간과 상태로 필터를 걸었더니 3,400건이 나왔습니다. 한 페이지에 20건씩 깔리니 170페이지네요. 운영자는 "마지막 페이지"를 눌러 가장 오래된 건부터 확인합니다.

```text
 요구사항으로 올라온 것
   · 총 3,400건이라고 보여 줘야 한다        → 총 개수
   · 47페이지로 바로 뛸 수 있어야 한다       → 임의 점프
   · "마지막 페이지" 버튼이 있어야 한다      → 임의 점프
   · 이 화면을 보는 사람은 사내 운영자 5명   → 계약 수명이 짧다
```

앞의 명세표에서 **임의 페이지 점프 행에 된다고 적힌 열은 offset 하나뿐**입니다. 위 네 줄 중 둘이 그 칸을 직접 가리키고 있어요. 여기서 keyset 을 고르면 요구사항을 못 냅니다.

깊이 문제는 어떻게 하냐고요? 이 화면에서는 **필터가 깊이를 눌러 줍니다.** 기간을 필수로 받으면 결과 집합이 수천 건에서 멈추고, 마지막 페이지의 `OFFSET 3380` 정도는 문제가 되지 않아요. 문제가 되는 건 필터 없이 수천만 행을 페이징할 때입니다.

**offset 을 고릅니다.** 그리고 이건 타협이 아니라 정확한 선택이에요.

### 장면 2 — 앱 홈의 타임라인

초당 수십 건의 글이 올라오는 피드입니다. 사용자는 무한 스크롤로 20페이지쯤 내려가고, 화면 어디에도 총 개수나 페이지 번호가 없습니다.

```text
 조건
   · 쓰기가 잦다              → 세션 중에 앞이 계속 밀린다
   · 세션이 길다              → 밀림이 누적된다
   · 깊이에 상한이 없다        → OFFSET 이 계속 자란다
   · 임의 점프 요구 없음       → offset 의 자산이 여기선 쓸모없다
```

offset 을 쓰면 앞에서 실측한 그 중복과 누락이 화면에 그대로 나옵니다. 초당 수십 건이면 사용자가 한 페이지를 읽는 몇 초 사이에 경계가 몇십 칸씩 밀려요.

**keyset 을 고릅니다.** 정렬 키도 마침 좋은 조건이에요 — 생성 시각은 한 번 정해지면 바뀌지 않고, `id` 를 tie-breaker 로 붙이면 전순서가 완성됩니다.

여기서 1편이 2·3편에 청구서를 하나 씁니다. keyset 을 골랐으니 프론트는 "지금 어디까지 봤는가"를 페이지 번호가 아니라 **경계값으로** 들고 있어야 하고(2편), 서버는 `(created_at, id)` 순서를 그대로 따라가는 인덱스를 갖고 있어야 합니다(3편).

### 장면 3 — 서드파티에 여는 공개 API

파트너 20곳이 붙어 있고, 우리는 6개월 뒤 이 목록의 저장소를 바꿀 계획이 있습니다.

이 장면의 결정 요인은 성능이 아니라 **바꿀 자유**입니다.

```text
 값을 그대로 노출한 경우
   파트너 코드:  GET /items?after_id=1042
   6개월 뒤:     정렬을 바꾸고 싶다 → after_id 의 뜻이 달라진다
                 파트너 20곳이 전부 고쳐야 한다 → 못 바꾼다

 봉투를 씌운 경우
   파트너 코드:  GET /items?page_token=CgQIARAB
   6개월 뒤:     봉투 안을 바꾼다 → 파트너 코드는 그대로
```

**page token 을 고릅니다.** 만료와 무효화까지 계약에 적어 두면 저장소 교체 시점에 옛 토큰을 정리할 길도 생겨요. AIP-158 이 만료 조항과 `INVALID_ARGUMENT` 조항을 함께 둔 이유가 이겁니다.

주의할 점 하나. 봉투를 씌우는 것과 안쪽을 keyset 으로 하는 것은 **따로 결정합니다.** 이 장면에서 계약은 page token 으로 정해졌지만, 안쪽을 offset 으로 둘지 keyset 으로 둘지는 장면 1·2의 기준으로 다시 판단해야 해요.

### 장면 4 — 사용자가 정렬을 고르는 상품 목록

최신순·가격순·인기순 토글이 있습니다. 인기순의 정렬 키는 좋아요 수인데, 이 값은 초 단위로 바뀝니다.

여기서는 keyset 의 보장이 닿지 않습니다. 왜 그런지 손으로 따라가 봅시다.

```text
 1페이지 마지막 행:  좋아요 120, id 55   →  경계 (120, 55)

 그 사이에 id 90 짜리 상품이 좋아요 200 으로 뛴다
   · id 90 이 1페이지 구간으로 올라간다
   · 그런데 우리는 이미 1페이지를 지나왔다      → 이 상품은 영영 안 보인다

 반대로 id 40 짜리가 좋아요 300 에서 100 으로 떨어진다
   · 1페이지에서 이미 봤는데
   · 경계 (120, 55) 뒤로 내려온다              → 2페이지에서 또 나온다
```

keyset 이 보장한 것은 **경계값이 밀리지 않는다**였지 행이 제자리에 있다가 아니었어요. 정렬 키가 변하면 행이 경계를 넘어 다닙니다.

여기서는 **어느 갈래도 공짜로 안정성을 주지 않습니다.** 선택지는 셋인데, 셋 다 페이지네이션 바깥의 결정이에요.

- 랭킹 값을 주기적으로 굳혀 **읽기 전용 스냅샷 열**을 따로 둔다 — 그 열로 keyset 을 한다
- 순서를 세션에 고정한다 — 첫 요청에서 순서를 확정해 커서에 실어 보낸다
- 안정성을 포기한다 — offset 에 깊이 상한을 걸고 "정렬이 바뀌면 순서도 바뀝니다"를 UI 에 적는다

정렬 키가 변한다는 조건이 걸리면 문제가 전략 선택에서 **정렬 키 소유**로 올라갑니다. 누가 그 값을 정하고 언제 굳히는가 — 3편에서 서비스 경계와 함께 다룹니다.

## 오해하기 쉬운 포인트

여기 모은 일곱 가지는 두 갈래의 병에서 나옵니다. 갈래를 섞어서 생기는 것과, 보장의 범위를 넘겨 읽어서 생기는 것.

### 갈래를 섞어서 생기는 오해

**오해 1. 커서 기반과 keyset 은 같은 말이다.**
커서는 계약 갈래, keyset 은 전략 갈래입니다. 커서를 열면 `offset=60` 한 줄만 들어 있는 API 가 실제로 흔해요.

**오해 2. 무한 스크롤이라 총 개수를 못 준다.**
표현과 전략을 섞은 말입니다. 총 개수는 별도 질의로 언제든 낼 수 있고, 안 주는 이유는 대개 비용이에요.

**오해 3. base64 로 감싸면 불투명해진다.**
base64 는 인코딩이지 은닉이 아닙니다. AIP-158 도 그 동작을 `obfuscate` 라고 부르지 `encrypt` 라고 부르지 않아요. 불투명함을 만드는 것은 **문서에 적은 계약**입니다.

```text
 섞이기 쉬운 자리 세 곳

   커서(계약)          ↔  keyset(전략)
   무한 스크롤(표현)   ↔  총 개수(전략의 명세 항목)
   base64(인코딩)      ↔  불투명함(계약이 만드는 성질)
```

### 보장의 범위를 넘겨 읽어서 생기는 오해

**오해 4. keyset 이 언제나 낫다.**
임의 점프와 총 페이지 수가 요구사항이면 keyset 은 그 요구를 못 냅니다. 장면 1이 그 자리예요. 성능이 아니라 **요구사항이 갈래를 정하는 경우**가 실무에 흔합니다.

**오해 5. keyset 이면 중복이 절대 없다.**
정렬 키 값이 고정된 동안에만 그렇습니다. `updated_at` 이나 좋아요 수처럼 값이 변하는 열로 정렬하면 장면 4의 일이 벌어져요.

**오해 6. OFFSET 이 느린 건 정렬 때문이다.**
정렬을 인덱스로 없애도 건너뛴 행은 계산됩니다. PostgreSQL 문서가 "still have to be computed inside the server" 라고 적은 그대로예요. 정렬은 원인의 일부지 전부가 아닙니다.

**오해 7. 페이지 크기만큼 안 왔으니 마지막 페이지다.**
AIP-158 은 끝이 아니어도 0건을 돌려줄 수 있다고 명시합니다. 종료는 토큰이 비었는지로만 판정하세요.

## 그래서 무엇을 고르나

조건에서 선택으로 가는 길을 한 장으로 접습니다.

```text
 임의 페이지 점프·총 페이지 수가 진짜 요구사항인가?
   │
   ├─ 예 ──▶ offset
   │          깊이 상한을 함께 건다(필수 필터 · 기간 · 최대 페이지)
   │
   └─ 아니오
        │
        정렬 키에 고유 tie-breaker 를 붙일 수 있는가?
          │
          ├─ 아니오 ──▶ 정렬 키부터 손본다
          │              못 손대면 offset + 깊이 상한
          │
          └─ 예
               │
               정렬 키 값이 페이징 도중에 변하는가?
                 │
                 ├─ 예 ──▶ 순서를 먼저 고정한다(스냅샷 열 · 세션 고정)
                 │          그 다음에 아래로 내려온다
                 │
                 └─ 아니오
                      │
                      계약을 나중에 바꿀 여지가 필요한가?
                        │
                        ├─ 아니오(사내 전용) ──▶ keyset, 값을 그대로 노출
                        │
                        └─ 예(공개 API)  ──▶ keyset + 불투명 커서
                                              수명·무효화까지 정하면 page token
```

표로 다시 접으면 이렇습니다.

| 고르게 되는 조건 | 고를 것 | 대가로 내주는 것 |
| --- | --- | --- |
| 임의 점프·총 페이지가 요구사항 · 결과 집합을 필터로 누를 수 있다 | **offset** | 깊이 비용 · 쓰기 중 중복·누락 |
| 깊이 무제한 · 쓰기 잦음 · 정렬 키가 불변이고 고유 tie-breaker 있음 | **keyset** | 임의 점프 · 총 페이지 수 |
| 계약을 오래 유지해야 함 · 안쪽을 바꿀 여지가 필요함 | **불투명 커서** | 디버깅 난이도 · 인코딩 층 하나 |
| 위에 더해 수명·무효화·질의 동일성까지 서버가 쥐어야 함 | **page token** | 서버 측 상태 관리 부담 |
| 정렬 키 값이 페이징 도중 변함 | **어느 것도 그냥은 안 됨** | 순서를 먼저 고정하는 비용 |

마지막 줄이 이 표에서 제일 중요합니다. 조건이 그 줄에 걸리면 전략을 고르기 전에 **데이터 모델을 먼저 손봐야** 해요. 그걸 모르고 keyset 으로 갈아탄 뒤 왜 아직도 중복이 나오는지 몰라 며칠을 버리는 일이 실제로 자주 벌어집니다.


## 직접 해보기

sqlite3 하나면 앞의 실측을 손으로 재현할 수 있습니다. 행 값 비교는 sqlite 3.15.0(2016-10-14)부터 들어가 있어서 그대로 돌아가요.

1. **표를 만들고 offset 으로 밀어 봅니다.**

   ```sql
   CREATE TABLE post (id INTEGER PRIMARY KEY, created_at TEXT, title TEXT);
   INSERT INTO post VALUES
     (1,'2026-08-01 09:00','A'),(2,'2026-08-01 10:00','B'),
     (3,'2026-08-01 11:00','C'),(4,'2026-08-01 12:00','D'),
     (5,'2026-08-01 13:00','E'),(6,'2026-08-01 14:00','F');

   SELECT title FROM post ORDER BY created_at DESC, id DESC LIMIT 3 OFFSET 0;
   INSERT INTO post VALUES (7,'2026-08-01 15:00','G');
   SELECT title FROM post ORDER BY created_at DESC, id DESC LIMIT 3 OFFSET 3;
   ```

   관찰 포인트: 두 번째 결과의 첫 행이 첫 번째 결과의 마지막 행과 같습니다.

2. **삭제 쪽도 재현합니다.** `INSERT` 대신 `DELETE FROM post WHERE id = 6;` 을 넣고 같은 2페이지를 요청해 보세요. 이번엔 **돌아오는 행 수부터** 다릅니다. 몇 건이 오는지, 어느 글이 사라졌는지 확인해 보세요.

3. **keyset 으로 바꿔 같은 조건을 겁니다.**

   ```sql
   SELECT title FROM post
   WHERE (created_at, id) < ('2026-08-01 12:00', 4)
   ORDER BY created_at DESC, id DESC LIMIT 3;
   ```

   관찰 포인트: 1·2번에서 무슨 짓을 했든 결과가 같습니다.

4. **tie-breaker 를 일부러 빼 봅니다.** 같은 `created_at` 값을 가진 행을 셋 만들고, `WHERE created_at < ?` 만으로 페이징해 보세요. `<` 로 했을 때와 `<=` 로 했을 때 무엇이 각각 어떻게 망가지는지 직접 확인하시면 tie-breaker 가 왜 정확성 요건인지 몸으로 남습니다.

## 스스로 점검하기

1. 어떤 API 가 `?cursor=eyJvZmZzZXQiOjYwfQ` 를 씁니다. 이 API 는 keyset 을 쓰고 있을까요? 판단에 필요한 정보가 무엇인지 대 보세요.
2. `ORDER BY updated_at DESC, id DESC` 로 keyset 페이징을 합니다. tie-breaker 도 붙었고 인덱스도 맞췄어요. 그런데도 같은 글이 두 번 나옵니다. 왜일까요?
3. 관리자 화면에 "마지막 페이지" 버튼이 있고 데이터는 5천만 행입니다. keyset 으로 바꾸자는 제안이 들어왔을 때 먼저 되물어야 할 것은 무엇일까요?
4. GraphQL API 를 `last`/`before` 로 역방향 페이징하는데 `hasNextPage` 가 계속 false 입니다. 사양에 비추어 이게 버그일까요?

1. **알 수 없습니다.** 커서를 디코드하면 `{"offset":60}` 이 나오니 안쪽은 offset 일 가능성이 큽니다. 하지만 커서의 내용은 계약이 아니라 구현이고, 서버가 그 값을 어떻게 쓰는지는 응답을 관찰해야 압니다. 판단하려면 **쓰기가 일어나는 동안 연속 페이지를 받아 중복·누락이 나는지**를 봐야 해요.
2. 정렬 키인 `updated_at` 의 **값이 변하기 때문**입니다. 경계값보다 앞에 있던 글이 갱신되면 경계 뒤로 내려오고, 그러면 다음 페이지에서 다시 잡힙니다. tie-breaker 와 인덱스는 이 문제를 못 막아요 — 장면 4의 그 조건입니다.
3. **"마지막 페이지" 버튼이 진짜 요구사항인지**를 먼저 물어야 합니다. 그 버튼이 남아 있는 한 keyset 으로는 못 갑니다. 요구사항이 진짜라면 방향은 전략 교체가 아니라 **결과 집합을 줄이는 필수 필터**를 거는 쪽입니다.
4. **버그가 아닙니다.** `HasNextPage` 알고리즘은 `first` 가 set 이 아니고 `before` 뒤의 원소를 효율적으로 판정할 수 없으면 3번 스텝으로 내려가 false 를 반환합니다. 역방향 페이징에서 봐야 할 값은 `hasPreviousPage` 예요.

## 마무리 — 1편이 남긴 계약

한 문장으로 줄이면 이렇습니다.

> **전략을 고르는 일은 무엇을 얻을지 고르는 일이 아니라, 무엇을 포기할지 고르는 일이다.**

offset 은 임의 점프를 주는 대신 안정성을 잃고 깊이 비용을 집니다. keyset 은 안정성과 평평한 비용을 주는 대신 임의 점프를 포기해요. 커서와 page token 은 바꿀 자유를 주는 대신 디버깅 편의와 서버 측 부담을 떠안습니다. 공짜로 주는 갈래는 없습니다.

그래서 이 편의 결론은 keyset 을 쓰라는 것이 아닙니다. **요구사항 목록을 명세 일곱 항목에 겹쳐 보라**는 것이에요. 겹쳐 보면 대개 한 칸이 먼저 걸립니다. 장면 1에서는 임의 점프 행이었고 장면 2에서는 안정성 행이었죠. 장면 4는 달랐습니다. 어느 칸도 답을 주지 못하고, 문제가 페이지네이션 바깥의 정렬 키 자체로 넘어가 버렸으니까요.

그리고 고른 순간 청구서가 두 장 발행됩니다.

```text
 offset 을 골랐다면
   2편 ▶ 페이지 번호를 URL 에 어떻게 싣고 뒤로가기로 어떻게 복원하나
   3편 ▶ 깊이 상한을 어디서 강제하나 · COUNT 를 얼마나 자주 떠도 되나

 keyset 을 골랐다면
   2편 ▶ 경계값을 프론트 어디에 보관하나 · 커서를 무엇으로 인코딩하나
   3편 ▶ (정렬 키, tie-breaker) 순서의 인덱스를 누가 소유하나

 커서·page token 을 씌웠다면
   2편 ▶ 잘못된 커서를 컨트롤러가 어떻게 거절하나
   3편 ▶ 필터·정렬까지 담은 토큰이 서비스 경계를 어떻게 넘나
```

2편은 바깥쪽부터 엽니다. 프론트가 "지금 어디까지 봤는가"를 어디에 두는지, 그 상태가 뒤로가기와 새로고침을 어떻게 견디는지, 컨트롤러가 커서를 받아 무엇을 검증하는지. 3편은 안쪽으로 내려가 정렬 키의 소유권과 인덱스, 실행 계획을 봅니다.

목록 하나 내려받는 일에 이렇게 많은 결정이 걸려 있다는 게 처음엔 과해 보일 수 있어요. 그런데 처음에 본 그 중복된 글 하나는 **이 결정들 중 어느 하나가 조용히 미뤄진 자리**에서 나옵니다. 미룬 결정은 사라지지 않고 버그로 돌아옵니다.

## 근거와 더 읽을 거리

본문의 SQL 실행 결과는 **2026-08-04 에 sqlite 3.51.0 으로 직접 실행해 얻은 값**입니다. PostgreSQL·MySQL 에서 재실행한 값이 아니라는 점을 밝혀 둡니다 — 두 DB 의 동작은 아래 공식 문서 인용으로 갈음했어요. 인용한 사양 문장은 모두 같은 날 각 원문 페이지에서 확인했습니다.

- PostgreSQL Documentation, [LIMIT and OFFSET](https://www.postgresql.org/docs/current/queries-limit.html) — 건너뛴 행도 서버에서 계산된다 · 고유 순서를 만드는 `ORDER BY` 요구
- PostgreSQL Documentation, [Row Constructor Comparison](https://www.postgresql.org/docs/current/functions-comparisons.html) — 행 값 비교의 왼쪽에서 오른쪽 평가
- PostgreSQL Documentation, [Indexes and ORDER BY](https://www.postgresql.org/docs/current/indexes-ordering.html) — `ORDER BY` + `LIMIT n` 에서 나머지를 훑지 않는 경우
- PostgreSQL Documentation, [pg_class](https://www.postgresql.org/docs/current/catalog-pg-class.html) — `reltuples` 는 플래너용 추정치
- MySQL 8.4 Reference Manual, [LIMIT Query Optimization](https://dev.mysql.com/doc/refman/8.4/en/limit-optimization.html) — 동점 행 순서의 비결정성 · filesort 와 `LIMIT`
- MySQL 8.4 Reference Manual, [Row Constructor Expression Optimization](https://dev.mysql.com/doc/refman/8.4/en/row-constructor-optimization.html) — 인덱스 접두어를 덮지 않을 때의 한계와 등가 전개형
- [GraphQL Cursor Connections Specification](https://relay.dev/graphql/connections.htm) — `edges`/`pageInfo` 필수 · 커서 opacity · `HasNextPage` 알고리즘. 문서에 버전 라벨이 없어 소스 파일 최종 갱신(2022-10-28)으로 시점을 갈음합니다
- Google API Improvement Proposals, [AIP-158: Pagination](https://google.aip.dev/158) — `page_size` 는 최댓값 · 토큰 opacity 는 `must` · 만료와 `INVALID_ARGUMENT`
- [JSON:API v1.1 — Pagination](https://jsonapi.org/format/#fetching-pagination) — `page` family 예약 · 링크 키 4종 · 전략 불가지론
- [IANA Link Relation Types](https://www.iana.org/assignments/link-relations/link-relations.xhtml) — `first`·`last`·`next`·`prev` 등록. `first`/`last` 는 RFC 8288, `next`/`prev` 는 HTML 사양을 참조로 갖습니다
- SQLite, [Row Values](https://www.sqlite.org/rowvalue.html) — 3.15.0(2016-10-14) 도입 · 비교 연산자 목록
