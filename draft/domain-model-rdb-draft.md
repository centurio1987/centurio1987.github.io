# 도메인 모델과 RDB는 어디서 어긋나는가

> 도메인 모델과 ER 모델은 서로를 베끼는 산출물이 아니라, 독립적으로 정합성을 세운 뒤 차이가 발생하는 지점을 비교·조정해야 하는 두 설계다.

## 플롯 후보

### Plot A: 비교 분석형
- **적합한 독자/상황**: DDD 모델을 RDB 스키마로 옮기며 1:1 대응이 깨지는 지점을 고민하는 개발자
- **구성 흐름**:
  1. 도메인 모델링과 ER 모델링을 독립적으로 수행해야 한다는 전제를 세운다.
  2. Aggregate와 테이블이 어긋나는 경우를 검토 신호로 정의한다.
  3. 외래키가 필요한 신호를 도메인 서비스와 Read model 관점에서 나눈다.
  4. Value Model, 상속/Composite, 거대 Aggregate를 각각 RDB에 표현하는 선택지를 비교한다.
  5. "정답 매핑"이 아니라 "정합성 훼손을 감지하는 비교 절차"가 핵심이라는 결론을 낸다.
- **이 플롯의 강점**: 원본 메모의 모든 논점을 가장 균형 있게 담을 수 있다.
- **주의할 점**: 항목이 많아 산만해질 수 있으므로 각 섹션마다 판단 기준을 명확히 둬야 한다.

### Plot B: 사례 분석형
- **적합한 독자/상황**: 주문/결제/상품 같은 구체 도메인을 놓고 스키마 설계를 따라가고 싶은 독자
- **구성 흐름**:
  1. 하나의 Aggregate 예시를 만들고 기본 테이블 대응을 잡는다.
  2. Value가 단일 값, 1:n 리스트, 거대 리스트로 바뀔 때 DB 표현이 어떻게 달라지는지 보여준다.
  3. 참조 Aggregate가 등장할 때 외래키와 도메인 의존성을 분리한다.
  4. 상속/Composite가 들어오면서 단일 테이블, 분리 테이블, json 선택지를 비교한다.
  5. 예시를 통해 설계 변경 신호를 정리한다.
- **이 플롯의 강점**: 추상적인 모델링 논의를 구체적인 schema 판단으로 연결하기 좋다.
- **주의할 점**: 예시 도메인을 새로 만들 때 원래 메모의 전제를 흐리지 않아야 한다.

### Plot C: 의사결정 가이드형
- **적합한 독자/상황**: 모델-테이블 매핑에서 선택지를 빠르게 좁혀야 하는 실무자
- **구성 흐름**:
  1. "이 관계는 Aggregate 내부인가, 참조인가?"라는 첫 질문으로 시작한다.
  2. Value인지 Entity인지에 따라 플래트닝, json, 별도 테이블 선택지를 나눈다.
  3. 상속/Composite가 나타날 때 속성 편차와 쿼리 빈도를 기준으로 선택한다.
  4. Aggregate가 거대해질 때 설계 재검토와 Lazy Loading 대안을 배치한다.
  5. 각 선택지의 위험 신호를 체크리스트로 마무리한다.
- **이 플롯의 강점**: 글 자체가 설계 리뷰 체크리스트로 기능한다.
- **주의할 점**: 판단 분기를 너무 기계적으로 만들면 도메인 맥락이 사라질 수 있다.

## 주의사항 / 잊지 말아야 할 점

- 도메인 모델과 ER 모델은 독립적으로 정합성을 세운 뒤 비교해야 한다는 전제를 글 초반에 분명히 둔다.
- Aggregate와 table의 1:1 불일치를 즉시 오류로 단정하지 말고 검토 신호로 표현한다.
- Value는 식별성이 없다는 점을 유지해야 하며, 별도 테이블로 분리하더라도 id 부여를 당연시하지 않는다.
- json은 영속화 편의와 쿼리 복잡도 사이의 교환임을 명확히 적는다.
- delete & insert 전략은 Value 리스트의 논리적 동일성과 변경 감지를 함께 설명해야 설득력이 생긴다.
- 상속/Composite의 DB 표현은 sparse table 문제와 상위 개념 쿼리 성능을 함께 비교해야 한다.
- 거대 Aggregate는 DB 최적화 이전에 도메인 설계 재검토 신호라는 점을 놓치지 않는다.
