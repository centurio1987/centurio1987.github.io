# 상속보다 Composite를 먼저 의심해야 하는 이유

> 도메인 모델에서 상속은 강한 의미 결합을 만들기 쉬우므로, 대부분의 변화 가능성은 Composite와 Value 중심으로 먼저 검토하는 편이 안전하다.

## 플롯 후보

### Plot A: 의사결정 가이드형
- **적합한 독자/상황**: 모델링 중 상속과 Composite 사이에서 선택해야 하는 개발자
- **구성 흐름**:
  1. 상속과 Composite를 "코드 재사용"이 아니라 "변화에 대한 결합 방식"으로 비교한다.
  2. 대부분의 도메인 관계가 깔끔한 상속으로 고정되지 않는 이유를 설명한다.
  3. Composite가 Value 형태로 나타날 때 변경과 배제가 쉬워지는 점을 설명한다.
  4. 상속을 고려할 수 있는 기능 집약적 로직의 조건을 분리한다.
  5. 선택 질문 목록으로 마무리한다.
- **이 플롯의 강점**: 실무 설계 판단으로 바로 사용할 수 있다.
- **주의할 점**: "상속 금지"처럼 단정하면 원본 메모의 균형이 무너진다.

### Plot B: 진화 과정형
- **적합한 독자/상황**: 초기에는 상속이 좋아 보였지만 도메인이 변하면서 어려움을 겪은 팀
- **구성 흐름**:
  1. 처음에는 속성과 행위가 비슷해 상속이 자연스러워 보이는 상황을 제시한다.
  2. 시간이 지나며 예외 속성, 다른 생명주기, 다른 문맥이 나타나는 과정을 보여준다.
  3. 상속 depth, super 참조, generic 타입 복잡도가 늘어나는 문제를 설명한다.
  4. Composite로 바꿨을 때 모델 배제와 변경 격리가 쉬워지는 점을 설명한다.
  5. 진화 가능성이 큰 도메인에서는 Composite 우선이라는 결론으로 닫는다.
- **이 플롯의 강점**: 왜 처음의 설계가 나중에 부담이 되는지 설득하기 좋다.
- **주의할 점**: 구체 예시 없이 쓰면 상속 일반론으로 흐를 수 있다.

### Plot C: 문맥 레이어와 코드 구조 분리형
- **적합한 독자/상황**: 도메인 개념의 상하 관계와 OOP 상속을 혼동하는 개발자
- **구성 흐름**:
  1. 컨텍스트 상의 관계와 코드 구조상의 상속은 다른 층위라고 선언한다.
  2. Root를 부모 클래스로 확장하는 접근이 왜 혼란을 만드는지 설명한다.
  3. Root는 독립적인 Entity, 바운더리, 생명주기를 가진다는 점을 강조한다.
  4. 공통 개념이 필요하면 별도 추상화를 만들고 Root가 그것을 구현/상속하는 방향을 설명한다.
  5. 상위 개념 사용 시나리오는 하위 개념 설계 이후 확장적으로 다룬다는 결론을 낸다.
- **이 플롯의 강점**: 도메인 모델링과 OOP 구현의 층위 차이를 선명하게 만들 수 있다.
- **주의할 점**: 너무 추상적으로 쓰면 Composite의 실무 장점이 약해질 수 있다.

## 주의사항 / 잊지 말아야 할 점

- 속성과 행위가 비슷하다는 이유만으로 상속 관계를 만들면 변화에 취약해질 수 있다.
- 상속은 더 강한 관계성을 만들며, 실무 도메인은 그 관계가 깔끔하게 유지되지 않는 경우가 많다.
- Composite는 모델을 배제하거나 교체하기 쉬운 구조를 제공한다.
- 기능 집약적 로직에서는 추상화의 의미가 커질 수 있으므로 상속 가능성을 완전히 배제하지 않는다.
- Root를 부모 클래스로 삼는 확장은 도메인 바운더리와 생명주기를 흐릴 수 있다.
- 컨텍스트의 관계와 OOP의 상속 관계를 같은 것으로 취급하지 않는다.
- 상위 개념 사용 시나리오 때문에 초기 설계를 과도하게 일반화하지 않는다.
