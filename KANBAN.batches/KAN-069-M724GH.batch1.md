이 배치는 **판정을 하지 않는다.** 계약(S1)과 사실(S2·S3)만 모은다. 판정과 개선안은 배치2다 —

## 1. 작업 패키지

### WP1 · `S1` 계약 확정 — 다섯 낱말을 인터페이스 필드에 건다

원문이 부른 다섯(`foundations` · `component` · `visual motif` · `wrapper` · `guideline`)을
`StyleGuide` 필드에 대응시킨다. 셋은 이름이 그대로 있다(`foundations` · `visualMotif` ·
`guidelines`). **`component` 와 `wrapper` 는 그렇지 않다** — 인터페이스에는
`wrapperComponents` · `wrapperBlocks` · `wrapperPatterns` · `patterns` 넷이 있고, 어느 것이 원문의
`component` 이고 어느 것이 `wrapper` 인지 임의로 정하면 진단 전체가 그 위에 선다. 카탈로그
51종이 실제로 무엇을 채우는지를 세어 대응을 **관찰로** 정한다.

**완료 기준**: (a) 층↔필드 대응표 1개 — 대응이 안 서는 층은 "안 선다"고 적고 검토 판단 항목으로
올린다. (b) 카탈로그 51종의 층별 구현 카운트 1개 — "완전히 구현한 상태"가 실제로 몇 종이나
되는지가 기준선이다.

### WP2 · `S2` 선언 층 진단(축 A)

`src/lib/motion/bbangtoTonyStyleGuide.ts`(139줄) · `src/lib/viz/blogVizStyleGuide.ts`(89줄)를
WP1 대응표에 걸어 층별로 판정한다. 앞의 것은 `foundationToStyleGuide` 로 만드는데 그 헬퍼의
문서화된 용도가 "foundations-only StyleGuide 로 변환"(`core/dist/index.d.ts:80`)이라, 네 층이
구조적으로 빠졌을 가능성이 높다 — **가능성이 아니라 필드 유무로** 확정한다.

같은 WP 에서 **값 드리프트**를 전량 대조한다. `bbangtoTonyStyleGuide.ts` 는 `tokens.css` 의 값을
TS 상수로 다시 적는다(`const PAPER = "#F3EEE4"; // --paper`). 두 곳이 같은 값을 들면 갈라진다.

**완료 기준**: 층별 판정표(구현 · 부분 · 없음 + 근거 `파일:줄`) + 드리프트 대조 결과
(일치/불일치 건수, 불일치는 (토큰명, CSS 값, TS 값) 세 쌍).

### WP3 · `S3` 구현 층 전수 스캔(축 B)

`src/**` 의 astro 59 · tsx 88 · css 6 에서 색 · 간격 · radius · shadow · 폰트 · z-index 리터럴을
기계 추출해 `tokens.css` 대비로 분류한다. **정독으로 하지 않는다** — 147개 파일에서 눈은 반드시
놓치고, 놓친 것은 재현도 안 된다. 추출기는 스크래치패드에 두고 레포에 넣지 않는다(게이트 승격은
개선 방안의 항목이지 이 카드의 산출물이 아니다).

**완료 기준**: 파일별 리터럴 목록(추출기 + 출력 JSON)이 스크래치패드에 남고, 재실행으로 총계가
그대로 재현된다.

## 2. 의존과 순서

- `S1` → `S2` **하드 의존.** 대응표 없이 층을 판정할 수 없다.
- `S1` → `S3` **약한 의존.** 추출 자체는 대응표와 무관하지만, 무엇을 토큰 위반으로 볼지의 기준이
  `tokens.css` 이므로 S1 에서 파운데이션 층의 정본을 확정한 뒤가 안전하다.
- `S2` ⟂ `S3` **독립.** 축이 다르다(선언 vs 구현). 병렬 가능 지점은 여기 하나뿐이다.
- 배치 밖 의존 없음. `dep-check` 위반 0건(미완료 루트 14개 중 13개가 `scope` 미기재라 경로로는
  판정 불가 — 다만 이 카드는 `design-concept/**` 만 쓰고 소스를 안 고치므로 실제 충돌 여지가 없다).

## 3. 두 관점 — 유저가 고른다

| | **단일 에이전트 수행** | **오케스트레이션 수행** |

| 배치 수 | 2 (S1·S2·S3 / S4·S5·S6) | 2 (같음) |
| 병렬 폭 | 1 | **2** — S1 이 끝난 뒤 S2·S3 을 서브에이전트 둘로 |
| 실질 이득 | — | S2·S3 구간만. S1 은 뒤 전부를 정하므로 병렬 불가, S4~S6 은 종합이라 병렬이 해롭다 |
| 리스크 | 없음 | S2·S3 이 **같은 계약 문서를 각자 읽어** 미묘하게 다른 기준으로 판정할 수 있다. 그러면 배치2 의 종합에서 두 축이 안 맞는다 |

**추천은 단일 에이전트다.** 병렬로 벌 수 있는 구간이 6 work 중 2개뿐이고, 그 둘조차 S3 의
실제 무게는 추출기 실행(기계 작업)이라 에이전트를 붙여도 대기 시간이 안 줄어든다. 반면 두 축이
기준을 달리 읽을 위험은 배치2 전체를 오염시킨다.

## 4. 리스크

- **`component` · `wrapper` 대응 실패(S1).** 임의 대응하면 진단이 통째로 흔들린다 → 안 서면 안
  선다고 적고 검토 판단 항목으로 올린다. 추측으로 메우지 않는다.
- **추출기의 오탐/누락(S3).** 정규식이 `#RRGGBB` 만 잡고 `rgb()` · `hsl()` · 이름 색을 놓치면
  "위반 0건"이라는 틀린 안심이 나온다 → 추출 패턴을 리포트에 명시하고, 알려진 미포함 항목을
  "이 스캔이 안 본 것"으로 적는다.
- **되돌리기**: 이 배치는 `src/` 를 한 글자도 안 고친다. 되돌릴 것은 카드/배치 문서뿐이다.
