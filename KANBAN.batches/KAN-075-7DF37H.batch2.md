## 1. 작업 패키지

### WP1 · `S3` 새 기준선

**자가검사 생존을 먼저 확인한 뒤** `bun scripts/verify-tokens.ts --update-baseline`.
래칫이 `0 → 29`(드리프트 21 + 위반 8)로 선다.

순서가 규약이다 — 래칫은 「줄었다」를 통과로 읽으므로 죽은 게이트와 다 갚은 게이트가
화면에서 같은 모양이다. 살아 있음을 먼저 증명해야 새 기준선이 뜻을 갖는다.

**완료 기준**: `bun run tokens:verify` exit 0, `scripts/tokens-baseline.json` 이
`--update-baseline` 산출물과 바이트 단위로 같다(손으로 안 고쳤다).

### WP2 · `S4` 문서

- `design-concept/UI_CONSISTENCY_AUDIT.md` §6 11항에 **정정 블록** — 「옛 정규식을 고쳐야
  해서 원자료 대조가 깨진다」가 **사실이 아니었다**(별도 인식기로 열면 옛 히트가 안 움직인다).
  실측 54건과 감사가 적은 47의 차이는 **원인을 못 짚었다**는 사실까지 적는다(그 수를 낸
  판정기가 KAN-073 스크래치패드에만 있었고 레포에 안 남았다).
- `CLAUDE.md` 토큰 게이트 절 — 「아직 안 연 갈래 셋」이 **둘**(KAN-076 선 굵기 ·
  KAN-077 상수 승격)로 줄고, 이 카드가 지킨 「옛 히트 불변」과 그 방법(별도 인식기 + 가드 셋)을 적는다.
- **수는 안 적는다.** 문서에 박은 수는 반드시 낡는다(이 자리가 실제로 그랬다).

**완료 기준**: 두 문서가 갱신되고 `git status --porcelain src/ public/` 가 **비어 있다**.

## 2. 의존과 순서

`S3` → `S4` 직렬. `S4` 가 인용하는 「남은 갈래 둘」은 `S3` 의 결과와 무관하지만,
정정 블록이 「기준선이 29 로 섰다」를 사실로 적으려면 `S3` 이 먼저다.

**`S1`~`S4` 는 한 커밋이다.** 게이트는 `main.yml` 의 `build` 잡에서 `astro build` 앞에 돌고
`deploy` 가 `needs: build` 로 물려 있다 — 인식층과 기준선을 나누면 그 사이 푸시에서
사이트 배포가 멈춘다.

## 3. 리스크

- **기준선을 자가검사보다 먼저 갱신하면** 게이트가 죽은 채로 초록이 된다. 순서가 곧 안전장치다.
- 정정 블록이 감사 문서의 §0 표를 건드리면 안 된다 — 그 표는 「기록이지 장부가 아니다」로
  동결돼 있다(KAN-074).
