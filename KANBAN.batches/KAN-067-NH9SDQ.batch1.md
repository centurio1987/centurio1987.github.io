## 1. 작업 패키지

### WP1 · `S1` 주제① — 대시보드 대량 aggregated 조회의 반응성

`research` 스킬로 수집한다. 훑을 축은 둘이고, 각 축 안에서 갈래를 나눈다.

**성능축**

- 전송량 축소 — 사전 집계·롤업, 컬럼 프루닝, 다운샘플링, 바이너리 직렬화(Arrow IPC·Protobuf), 전송 압축(gzip·br·zstd)
- 요청 분할 — 시각화 단위 분해, 뷰포트·우선순위 기반 지연 로드, HTTP/2·HTTP/3 멀티플렉싱에서 요청 수가 실제로 비용인지
- 서버 주도 전달 — SSE·WebSocket, chunked·NDJSON 스트리밍, 부분 결과 조기 렌더
- 캐시 계층 — HTTP 캐시(`ETag`·`Cache-Control`·`stale-while-revalidate`), Service Worker + IndexedDB, 서버측 결과 캐시

**UX축**

- skeleton · spinner · progressive rendering 의 체감 차이에 대한 **실증 근거**(추정이 아니라 측정된 것만)
- 지각 성능(perceived performance) 연구와 Core Web Vitals(LCP·INP) 기준선
- 부분 데이터로 먼저 그릴 때 생기는 레이아웃 이동(CLS)과 그 대가

**완료 기준**: `~/blog-research/raws/NNN-<slug>.md` 원본 1건 + 위키 topic 페이지 + 집필에 넘길 angle 경로. 모든 주장에 출처가 붙어 있다.

### WP2 · `S2` 주제② — 영속성 조회에 지배되는 성능

같은 방식으로 수집한다. 사용자의 전제("자료구조를 쓰려면 데이터를 버퍼 위에 올리는 수밖에 없다")를 **검증 대상으로 두고**, 반대 방향(알고리즘을 DB 안으로 내리는 길)까지 함께 본다.

- 사전 계산 — materialized view, 롤업 테이블, 큐브, 증분 갱신 주기와 정합성 대가
- 엔진의 자료구조 — 인덱스 종류별 성립 조건(B-tree·해시·GIN·BRIN·bitmap), 커버링 인덱스, 컬럼 스토어와 벡터화 실행
- 근사 자료구조 — HyperLogLog, t-digest, Count-Min sketch, Roaring bitmap. **DB 확장으로 엔진 안에서 도는 것**과 앱에서 도는 것의 차이
- 데이터를 올리는 길 — 인메모리 열 지향(DuckDB·Arrow), 캐시 계층, 스트리밍 집계(로그 → 집계 저장소)
- 알고리즘을 내리는 길 — UDF·저장 프로시저·DB 확장, 그리고 그것이 운영에서 치르는 비용

**완료 기준**: WP1 과 동일.

## 2. 의존과 순서

`S1` 과 `S2` 는 서로 독립이다 — 다른 주제이고 다른 소스를 읽는다. 다만 **캐시 계층과 사전 집계는 두 주제가 같이 만지는 자리**라, 뒤에 하는 쪽이 앞의 결과를 참조하면 중복 수집을 줄인다. 배치 밖 의존은 없다.

## 3. 리스크

- **예산.** 이 배치가 이 카드에서 제일 무겁다. 웹 수집은 팬아웃 폭에 따라 비용이 선형으로 늘어난다. 소주제를 넓게 잡으면 배치 하나가 세션 예산의 절반을 넘긴다 — 축을 위 목록으로 고정해 넓히지 않는다.
- **출처 없는 수치.** 성능 글은 "N배 빨라졌다" 류의 근거 없는 수치가 많다. 측정 조건이 없는 값은 **적지 않는다**(L0 `evidence`).
- **되돌리기.** 산출물이 `~/blog-research/` 쪽이라 이 레포에는 아무것도 안 남는다. 되돌릴 것이 사실상 없다.

## 4. 착수 시점 판단

**2026-08-18 착수.** 유저가 고른 수행안은 **혼합 — 배치1만 병렬**이다. `S1`·`S2` 를
`research-gatherer` 워커 둘에 동시에 맡기고, 배치2·3 은 한 세션이 순차로 한다. 병렬의
이득이 웹 수집에 몰려 있고 메인 컨텍스트도 거기서 가장 크게 오염되는 반면, 판정(`S3`)은
두 주제를 다 본 하나가 해야 두 노트의 용어와 판정이 안 갈리기 때문이다.

**두 work 를 다음 배치로 미루지 않는다** — 배치1 은 원래 둘뿐이고, 하나만 하면 `S3` 이
반쪽 입력으로 시작한다.

**병렬 때문에 추가로 통제하는 것 셋.** 두 워커가 같은 저장소(`~/blog-research/`)에 쓰므로
공유 파일에서 부딪힐 수 있다. 그래서 워커에게 이렇게 나눠 준다.

- raws 번호와 slug 를 **미리 못 박아 준다**(`012-dashboard-bulk-aggregated-fetch`,
  `013-db-bound-query-performance`). 각자 최대값+1 을 계산하면 둘 다 `012` 를 집는다.
- **`index.md`·`log.md` 는 워커가 손대지 않는다.** 둘 다 파일 끝에 붙이는 구조라
  동시에 쓰면 한쪽이 지워진다. 두 결과가 다 온 뒤 이 세션이 한 번에 반영한다.
- **push 도 워커가 하지 않는다.** 커밋 하나로 묶어야 "이 리서치는 여기까지"가 한 지점에 남는다.
