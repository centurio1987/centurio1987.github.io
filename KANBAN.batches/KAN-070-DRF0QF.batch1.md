## 1. 작업 패키지

### WP1 · `S1` 감사 판정기와 출력 JSON 을 레포로 옮긴다

세션 스크래치패드의 19개 파일을 `scripts/fixtures/tokens/reference/` 로 **한 바이트도 안 고치고**
옮긴다. `.py` 넷(`s3-scan` · `s4-classify` · `s4-fallback` · `s4-docrules`)과 그 출력 `.json`,
그리고 단계별 판정 기록 `.md` 다섯이 함께 간다.

**완료 기준**
- `cmp` 로 원본과 19/19 바이트 동일.
- 출력 JSON 의 sha256 이 검토서 verify 절 값과 일치한다 —
  `s4-classify f278448e106d83eb` · `s4-fallback 568ff12229198f08` · `s4-docrules 2d588fc5edd10f4c` ·
  `s3-scan e5e69a55331207dc`.
- 회수본을 설명하는 `README.md` 가 함께 있고, 거기에 **왜 레포에 있는지**와
  **감사 문서 부록 A 의 s3-scan 해시가 낡았다는 사실**이 적혀 있다.

## 2. 의존과 순서

**이 배치가 다른 배치 전부의 선행이다.** 배치3 의 축 모듈 셋은 각자 자기 참조 JSON 과
히트 단위로 대조해 완료를 판정하는데, 그 JSON 이 여기서 들어온다. 없으면 배치3 은
"돌아는 가는데 맞는지 모르는" 상태로 끝난다.

배치 안에서는 WP 가 하나뿐이라 순서가 없다.

## 3. 리스크

- **`/private/tmp` 는 재부팅에 지워진다.** 이 배치가 늦어지는 만큼 그대로 위험이다.
  회수 자체는 이미 작업 트리에 끝나 있으므로 **남은 위험은 커밋 전 유실 하나**다.
- **s3-scan 해시가 감사 문서와 다르다.** 회수 실패가 아니라 문서 쪽이 낡은 것이다 —
  S3 종료 시점 값(`76ec13fd`, `KANBAN.cards/KAN-069-M724GH.md:112`)이 부록 A 에 실렸고,
  그 뒤 S4 보강에서 스캔이 다시 돌아 값이 바뀌었다. 검토서 verify 절이 새 값을 적었다.
  **이 사실을 모르면 다음 사람이 회수가 틀렸다고 판단한다.** 부록 A 정정은 `S5` 로 넘긴다.
- 되돌리기: 파일 추가뿐이라 `git rm -r` 하나로 원상복구된다.
