- [x] 도메인 모델과 RDB
  - draft: `draft/domain-model-rdb-draft.md`
  - 전제
    - 도메인 모델링과 ER 모델링은 독립적으로 이뤄진 후, 비교·조정해야 각각의 정합성을 해치지 않는다.
    - 이 논의는 두 설계를 비교했을 때 어떤 부분에서 차이가 발생할 수 있는지를 미시적으로 고민한 내용이다.
  - 외래키 작성을 위한 신호
    - 도메인 서비스에서 동시에 나타나는 Aggregate
    - Read model에서 같이 나타나는 table
  - 상속, 합성이 나타날 때 테이블 표현 방식
    - 가장 단순한 솔루션: 하나의 테이블에 통합
    - 테이블이 sparse 해질 가능성 증가
    - 비슷한 Aggregate가 많아진다면 Knowledge Level로 도메인 설계 개선을 검토
  - Aggregate와 테이블 대응
    - Aggregate와 테이블이 1:1 대응하지 않으면 검토 신호가 될 수 있음
  - Value Model의 DB 표현
    - Value는 식별성이 없으므로 하나의 테이블에 플래트닝한다.
    - 1:n인 경우에도 기본적으로 플래트닝한다.
    - Value 리스트 수가 많은 경우 json을 사용한다.
      - 모델링과 영속화가 쉬워진다.
      - 쿼리가 복잡해진다.
      - 리스트 단위로 불러와 programmable하게 처리하거나 view 테이블을 만드는 것도 방법이다.
    - Value 리스트 수가 많은 경우 별도 테이블로 분리한다.
      - Value는 여전히 id가 없는 것이 논리적으로나 관리 측면에서 바람직하다.
      - 변경이 발생하면 부모 id를 참조하는 레코드를 전부 지우고 다시 삽입한다.
      - 최적화를 위해 변경이 발생했을 경우에만 delete & insert를 수행한다.
      - 변경 여부 판단을 위해 리스트를 hashing하여 부모 테이블 컬럼에서 관리하는 것도 방법이다.
  - 상속이나 Composite가 있을 경우
    - 속성 편차가 작으면 하나의 테이블로 처리할 수 있다.
    - 상위 개념을 쿼리에서 더 자주 사용하면 성능에서도 유리할 수 있다.
    - 그러나 table이 sparse 해진다는 근원적 문제가 있다.
  - Aggregate가 거대한 경우
    - 포함하는 모델 자체가 많거나 소속 Entity가 많으면 설계 관점에서 다시 생각한다.
    - 특히 composition 관계가 아닌 경우를 주의 깊게 본다.
    - 불가피하면 Lazy Loading 패턴을 사용한다.
    - 1:1인데 속성이 많은 경우 Value 패턴을 고려하여 Root를 재구성하고 테이블을 분화한다.
    - Value는 프록시나 데코레이터를 사용해 값에 접근하는 시점에 로딩하도록 구현한다.
    - Collection이 문제가 되는 경우에도 테이블을 별도로 구성하여 같은 방식으로 구현한다.

- [x] DDD에서 Composition과 Aggregation
  - draft: `draft/ddd-composition-aggregation-draft.md`
  - Composition
    - Composition으로 연관된 모델은 의존적 생명주기를 가지므로 Aggregate에 소속된다.
  - Aggregation
    - Aggregation은 결국 '참조'다.
    - DB에서는 참조 가능한 Aggregate의 key 칼럼을 포함한다.
    - 도메인에서까지 참조를 드러낼 필요는 없다.
    - 참조 목적이 기능 수행 시 데이터가 필요한 것이라면, 키를 DAO로 구하여 참조 Aggregate의 정보를 가져와 도메인 메서드의 파라미터로 전달할 수 있다.
    - Aggregation은 연관되는 모델의 생명주기가 연관을 가지는 Aggregate 바깥에서 발생한다.

- [x] 상속이냐 Composite냐
  - draft: `draft/inheritance-vs-composition-draft.md`
  - 기본 판단
    - 대부분은 Composite 관점에서 설계하는 것이 좋다.
    - 상속은 더 강한 관계성을 가지고 있고, 실 사례에서는 깔끔하게 맞아떨어지는 상속 관계가 잘 나타나지 않는다.
    - Evolving 과정에서 관계에 변형이 생기는 경우가 많다.
    - Composite로 구현한 경우 해당 모델을 배제할 수 있어서 관리가 편하다.
    - Composite은 Value의 형태로 나타난다.
    - Value의 구현 사항과 독립적으로 변경이 발생할 공산이 크다.
    - 상속의 경우 super를 참조하게 되면 변경 고려사항이 커진다.
    - 제네릭 타입을 사용하는 경우에도 상속은 depth가 나타나 구현상 어려움이 있다.
  - 상속을 고려할 수 있는 상황
    - 기능 집약적 로직에서는 추상화가 가지는 의미적 절대성이 더 크기 때문에 상속 고려에 조금 더 가중치를 줄 수 있다.
  - Evolving 관점
    - A class가 target인 경우 method 구현 규모가 크다면 상속은 단시간에 확장할 수 있는 이점을 준다.
    - 이미 사용하던 Root를 부모 클래스로 사용하도록 확장하는 접근은 권장하기 어렵다.
    - Root는 이미 컨텍스트에 등장하는 별도의 Entity다.
    - 코드 상에서나 DB 상에서나 독립적인 바운더리와 생명주기를 가지고 있다.
    - OOP 관점의 상속 관계는 컨텍스트 상에서 존재하지 않는 관계적 개념이라 혼란을 야기한다.
    - 실제로는 컨텍스트 상에서 서로 상호작용하는지만 관측하면 된다.
    - 상속이 필요하다면 문맥 레이어가 아닌 코드 구조 관점에서 고려해야 한다.
    - 공통 개념을 추상화하여 별도로 빼고 Root도 해당 추상 개념을 상속받도록 구현한다.
    - Composite의 경우에도 공통 Value를 정의하고 기존 Root가 Value를 사용하도록 확장한다.
    - 상위 개념 사용 시나리오 때문에 설계를 과도하게 복잡하게 만들 필요는 없다.
    - 하위 개념 기준으로 설계하되, 상위 개념 사용 시나리오가 나타나면 확장적으로 고려한다.
    - Aggregate 단위 관계일 때는 도메인 서비스에서 다형성을 사용한다.
    - Aggregate 하위 Entity 단위 관계일 때는 Root의 도메인 메서드에서 다형성을 사용한다.
    - Composite의 경우 Value를 사용하는 공통 로직을 각각 구현하되, 그에 대한 인터페이스를 정의한다.
