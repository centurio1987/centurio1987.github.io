# 사례별 pagination 전략과 최적 구현

> 글감 메모. 2026-08-04 사용자 지시.
> 이 문서는 **집필 입력**이지 집필 결과가 아니다. 여기 적힌 것은 다뤄야 할 범위이고,
> 사실 확인과 구현 검증은 집필 단계에서 한다.

## 요구사항 (사용자 원문)

- 사례별 pagination 전략과 최적 구현
- pagination 전략에는 **어떤 갈래가 있고 각 전략별 명세**를 서술
- **레이어별**(프레젠테이션(React 등의 프론트) · 컨트롤러 · 서비스 · infra)로
  고려해야 할 부분과 **실제 최적 구현 예시와 그에 대한 설명**

## 이 글이 답해야 하는 것

**"어떤 페이지네이션을 쓸 것인가"는 취향이 아니라 조건이 정한다.**
그 조건이 무엇이고, 조건마다 어느 전략이 왜 맞는지가 이 글의 뼈대다.

전략을 나열하는 글은 이미 많다. 이 글의 차별점은 **한 전략을 골랐을 때 네 레이어가
각각 무엇을 떠안는가**이다 — 프론트의 상태 관리, 컨트롤러의 계약, 서비스의 경계,
인프라의 인덱스까지 한 줄로 꿰는 것.

## 다뤄야 할 갈래 (집필 시 확정·보강)

메모 수준이다. 실제 목록과 명세는 집필 단계에서 1차 자료로 확인한다.

- **offset / limit** — 가장 흔하고 가장 자주 틀린다
- **cursor 기반** — 커서에 무엇을 담는가가 전부다
- **keyset(seek)** — 커서 기반의 한 형태인지 별개인지부터 정리해야 한다
- **page token** — 커서를 불투명하게 감싸는 층
- **무한 스크롤 vs 페이지 번호** — 이건 전략이 아니라 **표현**이다. 섞이면 논의가 흐려진다

각 전략의 **명세**로 적어야 할 것: 요청 파라미터 · 응답 형태 · 정렬 요구 · 안정성
(중복·누락) · 총 개수 제공 가능 여부 · 임의 페이지 점프 가능 여부 · 비용 특성.

## 레이어별 관심사

| 레이어 | 이 전략이 여기에 무엇을 요구하는가 |
| --- | --- |
| 프레젠테이션 (React 등) | 상태 보관 형태 · 뒤로가기/새로고침 복원 · 낙관적 갱신과의 충돌 · URL 반영 |
| 컨트롤러 | 요청·응답 계약 · 커서 인코딩 · 잘못된 커서 처리 · 캐시 헤더 |
| 서비스 | 정렬 키의 소유 · 필터와의 상호작용 · 권한 경계를 넘는 항목 처리 |
| 인프라 (DB) | 인덱스 설계 · 실행 계획 · 대용량에서의 비용 · 복합 정렬 키 |

## 유의

- **"최적"은 조건부다.** 무조건 keyset 이 낫다는 식으로 쓰면 이 글은 실패다.
  각 전략을 고르게 되는 조건을 명확히 적는다.
- 코드 예시는 **실제로 도는 것**이어야 한다. 의사코드로 얼버무리지 않는다.
- 수치(성능 비교 등)는 실측하거나, 못 재면 **가정임을 정하고 산술만 보인다.**

## 참고 확인 대상 (집필 시)

PostgreSQL 문서(`LIMIT`/`OFFSET`, 인덱스 스캔), MySQL 문서, Relay Cursor Connections
사양, Google AIP-158(page token), JSON:API 페이지네이션 프로파일.
