# 로직이 안 쓰는 id 를 Entity 에 두어야 하나 — 대화 원문 보관

이 파일은 폭신 대담의 L1 원문이다. 준비 노트(`raws/talks/_prep/entity-identity-necessity.md`)의 질문 순서·전제 판정·되받기를 글쓴이 발화로 삼아, 교수님 역할의 AI(Claude Code 세션, Claude Fable 5.1)가 답했다. 글쓴이가 직접 자판을 친 대화가 아니다. 글쓴이 쪽 발화는 준비 노트와 KAN-081 원문에 적힌 것 밖으로 나가지 않도록 했고, 답변은 이 세션에서 새로 생성됐다. 문답의 흐름을 보존하기 위해 시간 순서로 기록한다.

## 사용자 · 원 질문

entity는 식별성이 있어야 한다. 그래서 id가 있어야 하는데, 실제 로직에서는 사용하지 않는 값이다. 그렇다면 굳이 entity에 id가 있어야 할 필요가 있나.

이번엔 회의를 하나 들고 왔다. 안 쓰는 값을 왜 드느냐는 것이다. 낱말부터 갈라 두고 싶다. 식별성(identity)과 식별자(identifier)는 같은 말인가. Entity 정의가 요구하는 것은 둘 중 무엇인가.

## 답변 · 식별성과 식별자

같은 말이 아닙니다. 그리고 그 둘을 가르는 것이 이 회의를 어디까지 밀 수 있는지를 정합니다.

Evans 의 Entity 정의를 원문으로 보죠. "Some objects are not defined primarily by their attributes. They represent a thread of identity that runs through time and often across distinct representations." 어떤 객체는 속성으로 정의되지 않고, 시간을 가로지르며 여러 표현을 가로지르는 정체성의 실을 나타낸다. 여기서 identity 는 성질입니다. 속성이 바뀌어도 같은 것으로 남는다는 성질이요.

그다음에 Evans 가 요구하는 것이 무엇인지 보세요. "Define a means of distinguishing each object regardless of its form or history." 형태나 이력과 무관하게 각 객체를 구별하는 수단을 정의하라. 그리고 "Define an operation that is guaranteed to produce a unique result for each object." 각 객체에 대해 유일한 결과를 내는 연산을 정의하라. 요구된 것은 수단이고 연산입니다. id 필드가 아니에요. id 필드는 그 수단을 구현하는 한 방법이고, 속성 조합으로 구별할 수도 있고 밖에서 온 기호로 구별할 수도 있습니다.

그러니 "식별성이 있어야 하니까 id 가 있어야 한다"는 문장은 앞 절반이 맞고 뒤로 건너가는 대목이 헐겁습니다. 식별성은 Entity 의 선택 사양이 아닙니다. Entity 는 "distinguished by its identity, rather than its attributes" 로 정의되고, Value Object 항목은 "Don't give a value object any identity" 로 반대편을 긋습니다. 여기까지는 단단해요. 헐거운 것은 "그래서 id" 입니다. 식별성은 필수이고, 식별자는 그것을 담는 그릇 중 하나입니다.

동시에 방어되는 대목도 있습니다. 그 그릇이 시스템이 만든 임의값이어도 된다고 원문이 명시하거든요. "This means of identification may come from the outside, or it may be an arbitrary identifier created by and for the system." 그러니 "로직이 안 쓰는 임의값"이라는 사실만으로는 그 id 의 정당성이 깎이지 않습니다. 깎는 조건은 따로 있고, 바로 그 문장의 뒷부분입니다. 다음 질문이 거기일 것 같은데요.

## 사용자 · 그 조건

맞다. "but it must correspond to the identity distinctions in the model." 모델의 식별 구분에 대응해야 한다는 조건이 실무에서 무엇을 요구하는가. 임의값이어도 된다면 이 조건은 무엇을 거르는 장치인가.

## 답변 · 그 id 가 말하는 같음과 업무가 말하는 같음

그 조건은 값을 거르는 장치가 아니라 같음을 거르는 장치입니다.

바로 옆 문장이 실마리입니다. "The model must define what it means to be the same thing." 모델이 "같은 것"이 무엇을 뜻하는지 정의해야 한다. 업무에는 이미 같음의 기준이 있습니다. 어떤 고객이 이름을 바꿔도 같은 고객인지, 주문을 취소하고 다시 넣으면 같은 주문인지 다른 주문인지. 그 기준을 모델이 명시적으로 정해야 하고, 식별자는 그 기준에 맞아야 한다는 겁니다.

그러니 이 조건이 거르는 것은 "그 id 가 같다고 하는 것"과 "업무가 같다고 하는 것"이 어긋나는 경우입니다. 예를 들어 볼게요. 업무는 "같은 사람이면 같은 고객"이라고 하는데, 시스템은 가입 폼이 제출될 때마다 새 id 를 만든다고 합시다. 한 사람이 두 번 가입하면 id 는 둘이고 업무는 하나입니다. 이 id 는 모델의 식별 구분에 대응하지 않아요. 임의값이라서가 아니라, 그 임의값이 그리는 경계가 업무의 경계와 다르기 때문입니다. 반대로 생성 시점에 붙인 UUID 라도, 업무의 같음이 "그때 만들어진 그것이 어떻게 바뀌든 그것"이라면 그 UUID 는 대응합니다.

그래서 판정선은 "로직이 이 값을 읽는가"가 아닙니다. "이 값이 말하는 같음이 업무가 말하는 같음과 일치하는가"입니다. 이 자리에서 확정하고 싶으신 것이 이거였다면, 저는 이렇게 확정하겠습니다. 로직이 안 읽어도 일치하면 정당하고, 로직이 읽어도 안 일치하면 잘못된 식별자입니다.

## 사용자 · 안 쓴다는 관찰

그러면 "로직이 안 쓴다"는 내 관찰이 검증된 것인지 물어야겠다. 도메인 메서드에는 안 나온다. 그 말고 그 값을 쓰는 자리가 정말 없는가. 어디를 봐야 확인되는가.

## 답변 · 소비자 넷

"로직"이 무엇을 가리키는지부터 봐야 합니다. 도메인 메서드만 보고 계셨다면 아직 검증된 관찰이 아닙니다.

id 가 도메인 메서드에 한 번도 안 나타나도 실제로는 네 자리 중 어딘가가 쓰고 있는 경우가 대부분입니다. 어디를 봐야 하는지와 함께 하나씩 말씀드리죠.

동일성 판정이 첫 자리입니다. equals 와 hashCode 가 무엇으로 구현돼 있는지 보세요. id 로 구현돼 있으면 컬렉션의 중복 제거와 정렬, Set 에 넣고 빼는 모든 자리가 그 값을 씁니다. 도메인 메서드에 id 가 안 보여도 contains 한 번에 쓰이는 거예요. 이걸 없애면 속성 전체 비교로 바뀌고, 그 순간 그 객체는 Value Object 가 됩니다.

영속화가 두 번째 자리입니다. PK 와 FK, ORM 의 identity map 과 dirty checking. identity map 은 한 세션 안에서 같은 행을 같은 객체 하나로 유지하는 장치이고, dirty checking 은 로딩 시점 스냅샷과 비교해 바뀐 필드를 찾는 방식인데 둘 다 행을 식별할 키가 있어야 돌아갑니다. 매핑 설정을 보시면 됩니다.

외부 참조가 세 번째 자리입니다. 다른 Aggregate 가 이 객체를 id 로 가리키는지. Vernon 의 세 번째 규칙이 "Reference Other Aggregates By Identity" 입니다. 다른 Aggregate 는 객체 참조가 아니라 식별자로 가리킨다는 것인데, 참조되는 쪽에 id 가 없으면 이 규칙 자체가 성립하지 않아요. 다른 Aggregate 의 필드를 보시면 됩니다. 여기에 걸리면 id 는 협상 대상이 아닙니다.

시스템 경계가 네 번째 자리입니다. API 응답, 로그, 이벤트에서 그 객체를 지칭하는 자리. 클라이언트가 "그 주문"을 다시 가리켜야 하면 무언가로 가리켜야 하고, 그 무언가가 id 입니다. 응답 스키마와 이벤트 페이로드를 보시면 됩니다. 여기도 걸리면 협상 대상이 아니에요.

세 번째와 네 번째에 해당하는지가 먼저입니다. 둘 중 하나라도 걸리면 이 대화는 여기서 끝나도 됩니다. 안 걸리면 첫 번째와 두 번째가 남는데, 그 둘은 성격이 달라서 따로 봐야 합니다. 동일성 판정은 도메인의 요구이고 영속화는 영속화의 요구예요. 다음 질문이 아마 거기로 갈 것 같습니다.

## 사용자 · 세어 보겠다, 그리고 두 id

넷 중 무엇에 해당하는지는 돌아가서 세어 보겠다. 그러면 지금 말한 두 번째 갈래를 묻겠다. 영속화가 요구하는 id 와 도메인이 요구하는 id 는 같은 것인가. 다르다면 지금 내가 보고 있는 그 필드는 어느 쪽인가. ORM 이 요구하니까 두는 거라면 그건 도메인의 식별자가 아니지 않나.

## 답변 · 존재가 아니라 노출

같은 것이 아닙니다. 그리고 "ORM 이 요구하니까 둔다"가 사실이라면 문제는 그 id 의 존재가 아니라 노출입니다.

Vernon 이 Implementing Domain-Driven Design 5장에서 식별자 생성 전략 넷을 다룹니다. 사용자가 제공하는 것, 애플리케이션이 만드는 것, 영속화 메커니즘이 만드는 것, 다른 Bounded Context 가 할당하는 것. 그리고 그것과 별도로 surrogate identity, 대리 식별자를 다루는 절을 따로 둡니다. ORM 이 원하는 식별자와 도메인이 원하는 식별자가 충돌하니까 둘을 나누고, 대리 식별자 쪽은 Layer Supertype 에 실어 가시성을 제한해 감춘다는 것이 그 절의 요지로 알려져 있습니다. 여기서 단서를 달아야 합니다. 저는 그 장의 본문을 1차로 확보하지 못했습니다. 목차와 2차 요약으로만 압니다. 그러니 "Vernon 이 두 식별자를 분리하는 절을 따로 두었다"는 사실까지만 말씀드리고, 그 절의 문구를 인용하지는 않겠습니다.

그 사실만으로도 답은 나옵니다. 지금 보고 계신 필드가 ORM 의 자동 증가 값이고 도메인의 어떤 구별에도 대응하지 않는다면, 그것은 도메인 모델의 식별자가 아니라 영속화 관심사가 도메인 객체 안으로 새어 들어온 것입니다. 그러면 할 일은 없애는 것이 아니라 감추는 것이에요. ORM 은 여전히 그 값을 필요로 하니까 없앨 수 없고, 도메인은 그 값을 볼 이유가 없으니 보이면 안 됩니다.

반대로 그 필드가 애플리케이션이 만든 값이고 두 번째 답변의 조건, 업무의 같음에 대응한다면 그것은 도메인의 식별자입니다. 로직이 안 읽는 것과 무관하게요. 그리고 하나가 둘 다인 경우도 있습니다. 애플리케이션이 만든 UUID 를 도메인 식별자로도 쓰고 PK 로도 쓰는 구성이요. 이때는 나눌 것이 없습니다.

그러니 "ORM 이 요구하니까 두는 겁니다"는 반론이 아니라 진단입니다. 그 말이 맞다면 그 필드는 영속화 층의 것이고, 도메인 객체의 공개 표면에 나와 있는 것 자체가 설계 문제입니다.

## 사용자 · Aggregate 안쪽

Aggregate 안쪽 Entity 에도 같은 요구가 걸리는가. 밖에서 참조되지 않는 객체의 식별자는 무엇까지 만족하면 되는가.

## 답변 · 안쪽이면 요구가 약해진다

요구가 걸리기는 하는데 약해집니다. 무엇이 약해지는지를 정확히 해 두죠.

Aggregate 의 규칙을 다시 보면, 밖에서는 루트만 참조하고 트랜잭션은 경계를 넘지 않습니다. Fowler 의 정리가 그렇고 Evans 의 Reference 도 같습니다. 그러니 Aggregate 안쪽의 Entity 는 밖에서 id 로 가리켜질 일이 없어요. 앞에서 본 소비자 넷 중 세 번째, 외부 참조가 정의상 빠집니다. 네 번째인 시스템 경계도 대개 루트를 통해 가리키니까 약해지고요.

남는 것은 안에서의 구별입니다. 주문 안의 주문 항목 둘을 서로 구별해야 하면 그건 여전히 식별성이고, Entity 입니다. 다만 그 식별자는 Aggregate 안에서만 유일하면 됩니다. 전역에서 유일할 필요가 없어요. 커뮤니티에서는 이걸 local identity 라고 부르고, "aggregate id 더하기 local id 가 global id" 라는 식으로 정식화합니다. 순번이어도 되고 작은 정수여도 됩니다.

여기도 단서가 있습니다. local identity 라는 표현은 2015 Reference 에 없습니다. dddcqrs 그룹 토론이나 튜토리얼 같은 2차 출처에서 굳은 말이에요. 그러니 이걸 Evans 의 것으로 인용하면 안 되고, "커뮤니티에서 굳은 구분"으로 말해야 합니다.

이 질문이 왜 중요하냐면, 지금 보고 계신 id 가 "안 쓰인다"고 느껴지는 이유가 여기 있을 수 있어서입니다. 그 객체가 안쪽 Entity 라면 구별은 부모가 하고 있고, 그 객체의 id 필드는 전역 식별자의 모양을 하고 있으면서 실제로는 부모 안에서의 위치 정도만 뜻할 수 있습니다. 그러면 요구는 그 위치를 유일하게 하는 것까지이고, 그 이상은 아닙니다.

## 사용자 · 셋 다 아니라면

넷을 세어 봤는데 아무 데도 안 걸리고, 안쪽 Entity 라서 부모가 구별하는 것도 아니라면. 그러면 그것은 Entity 가 맞는가. 즉 이 질문은 "id 를 뺄까"가 아니라 "분류가 틀렸나"로 되돌아가는 것인가.

## 답변 · 질문이 바뀌는 자리

되돌아갑니다. 그리고 그것이 이 대화의 전환점입니다.

아무도 그 객체를 구별하지 않고, 아무도 가리키지 않고, 시간을 가로질러 추적할 일도 없다면, 식별성이 하는 일 둘, 구별과 연속이 둘 다 비어 있는 겁니다. 그러면 물을 것은 id 가 아니라 Entity 라는 분류입니다. Vernon 이 판정 기준을 한 문장으로 적어 두었어요. "First ask whether that part must itself change over time, or whether it can be completely replaced when change is necessary. If instances can be completely replaced, it points to the use of a value object rather than an entity." 그 부분이 시간에 따라 스스로 바뀌어야 하는지, 아니면 바꿀 일이 생기면 통째로 교체해도 되는지를 먼저 물으라는 겁니다. 통째로 교체할 수 있으면 Value Object 신호입니다. Khorikov 도 같은 기준을 씁니다. 속성 집합이 같은 다른 인스턴스로 안전하게 바꿔치기할 수 있으면 Value Object 라고요.

여기서 성급해지면 안 되는 지점이 있습니다. "그럼 Value Object 로 만드세요"가 자동으로 따라 나오는 게 아니에요. 판정 기준은 "id 를 쓰느냐"가 아니라 추적 필요성입니다. 속성이 바뀐 뒤에도 그것을 다른 것과 구별해 추적해야 하는 물건이면, id 를 아무 메서드가 안 읽어도 Entity 입니다. 그 id 가 곧 추적이니까요. 반대로 추적할 일이 없으면 Entity 가 아니고, 그러면 id 는 분류와 함께 빠집니다. id 를 뺄지 말지는 독립된 결정이 아니라 분류의 결과입니다.

실측에 가까운 이야기를 하나 드릴 수는 있는데 조건을 붙여야 합니다. Vernon 이 같은 글에서 전하기를, 한 프로젝트에서 Aggregate 의 약 70% 가 루트 Entity 하나에 값 타입 속성만으로 이루어졌고 나머지 30% 도 Entity 가 두셋에 그쳤다고 합니다. 조건은 Qi4j 프레임워크, 금융 파생상품 도메인, Niclas Hedhman 한 사람의 보고이고, Vernon 본인이 "모든 도메인 모델이 70/30 이라는 뜻은 아니다"라는 단서를 달았습니다. 원자료의 측정 방식과 표본은 저도 확인하지 못했습니다. 이 수치에서 가져갈 것은 비율이 아니라 방향입니다. Entity 로 세울 일은 생각보다 드물 수 있고, "안 쓰는 id" 가 그 드묾을 알려 주는 표시일 수 있다는 것.

그러니 질문은 처음부터 "id 를 뺄까"가 아니었습니다. "이게 Entity 인가" 였고, id 는 그 답을 따라갑니다.

## 사용자 · 거꾸로, 두는 쪽의 비용

거꾸로 묻겠다. id 를 두는 쪽의 비용은 무엇인가. 안 쓰는 id 를 그냥 두면 그만 아닌가. 원문에 적힌 대가가 있는가.

## 답변 · 원문이 적어 둔 대가

있습니다. 그리고 그 대가를 적은 사람이 Evans 본인이라는 점이 이 회의를 지지해 줍니다.

Value Object 항목입니다. "Tracking the identity of entities is essential, but attaching identity to other objects can hurt system performance, add analytical work, and muddle the model by making all objects look the same." Entity 의 식별성을 추적하는 것은 필수이지만, 다른 객체에 식별성을 붙이면 성능을 해치고 분석 부담을 늘리고 모든 객체를 똑같아 보이게 만들어 모델을 흐린다. 대가가 셋 적혀 있고, 이 질문에 걸리는 것은 마지막입니다.

모든 객체에 id 가 있으면 모델을 읽는 사람이 무엇이 추적되는 것이고 무엇이 교체되는 것인지 구분할 수 없습니다. Entity 와 Value Object 의 구분이 코드에서 사라지는 거예요. 그 구분은 장식이 아니라 "이 객체는 바뀌어도 같은 것으로 따라가야 한다"는 업무의 판단을 코드에 남기는 방법입니다. 안 쓰는 id 를 습관처럼 두면 그 판단이 지워집니다.

그러니 "안 쓰는 값을 왜 드나"는 회의는 틀린 본능이 아닙니다. Evans 의 경고 그대로예요. 다만 처방이 다릅니다. 사용 횟수를 세어 0 이면 지우는 것이 아니라, 분류를 다시 묻고 그 답에 따라 두거나 빼는 겁니다. 두는 경우에도 그것이 대리 식별자라면 감추고, 도메인 식별자라면 업무의 같음에 대응하는지 확인합니다.

마지막으로 제가 모르는 것 하나를 남기겠습니다. JPA 의 Embeddable 컬렉션이나 EF Core 의 owned entity type 처럼 프레임워크가 식별자 없는 객체를 어디까지 허용하는지는 제품마다 다르고, 이번에 확인하지 않았습니다. "프레임워크가 id 없는 엔티티를 허용 안 합니다"라는 반론을 만나시면 어느 프레임워크의 어느 기능인지부터 물으셔야 합니다.
