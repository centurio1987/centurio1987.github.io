## Q. backend 가 따로 있고 room 역할을 하는 worker 를 별도로 띄운다고 하면, 클라이언트가 그 room 에 연결되게 하는 방법은 어떤 것들이 있습니까?

설계를 시작하기 전에 그림 한 장을 같이 두고 보죠. 이 시스템에는 성격이 다른 흐름이 둘 있습니다.

```
 [클라이언트]
     │
     │ ① 제어 경로 (HTTPS, 짧고 드물다)
     │    "이 문서는 누가 맡고 있습니까"
     ▼
 [backend]───────────────┐
  인증 · 권한 · 배치     │ 조회·갱신
                         ▼
                   [공유 저장소]
                    소유권 · 변경 로그 · 체크포인트
                         ▲
     ┌───────────────────┘ 검증된 쓰기
     │
 [room worker A]   [room worker B]
  문서1 · 문서2      문서3
     ▲
     │ ② 데이터 경로 (WebSocket, 길고 잦다)
     │    편집 · 병합 · 전파
 [클라이언트]
```

**제어 경로**는 짧고 드뭅니다. 접속할 때 한 번, 서버가 바뀔 때 한 번. **데이터 경로**는 길고 잦습니다. 글자를 칠 때마다 흐르죠. 이 둘을 같은 통로로 밀어 넣으면 backend 가 모든 편집 메시지의 중계자가 되면서 병목이 그리로 옮겨 갑니다. 그래서 갈라 둡니다. 이 전제 위에서 연결 방법을 하나씩 펴 볼게요.

### 갈래 1 — 이미 열린 연결을 worker 에게 넘긴다

가장 먼저 떠오르는 방법이고, 가장 먼저 지워야 하는 방법입니다.

일반적인 WebSocket 과 브라우저 API 로는 이미 맺어진 연결을 다른 호스트의 서버에게 투명하게 넘기는 방법이 제공되지 않습니다. 같은 호스트 안에서 소켓 핸들을 자식 프로세스로 전달하는 것과는 다른 문제예요. 그건 커널이 파일 기술자를 넘겨 주는 얘기이고, 다른 기계로 보내는 건 TCP 연결 상태와 TLS 세션을 통째로 옮기는 얘기입니다.

특수한 런타임이나 네트워크 계층을 동원하면 비슷한 효과를 낼 수는 있습니다. 다만 그건 "일반적인 웹 스택에서 된다"와는 다른 말입니다. 표준 구성에서는 안 된다고 보고 설계를 시작하시는 편이 낫습니다.

### 갈래 2 — 목적지를 먼저 묻고 그 서버에 직접 연결한다

연결을 옮길 수 없다면 순서를 뒤집습니다. 옮길 일이 생기기 전에 목적지를 정하는 거죠.

```
클라이언트                backend              worker C2
    │                       │                     │
    │ ① POST /rooms/{id}/route                    │
    │──────────────────────>│                     │
    │                       │ ② 권한 확인         │
    │                       │ ③ 소유권 조회/배치  │
    │                       │────── activate ────>│
    │                       │                     │ ④ 복원
    │                       │<───── ready ────────│
    │ ⑤ { url, ticket }     │                     │
    │<──────────────────────│                     │
    │                                             │
    │ ⑥ new WebSocket(url) + ticket               │
    │────────────────────────────────────────────>│
    │ ⑦ 동기화 시작                               │
    │<───────────────────────────────────────────>│
```

클라이언트가 HTTPS 로 접속 경로를 묻습니다. backend 는 권한을 확인하고, 이 문서를 맡고 있는 worker 가 있으면 그 주소를, 없으면 새로 정해서 그 주소를 돌려줍니다. 함께 주는 티켓은 문서·권한·만료 시각에 묶인 짧은 수명의 증표입니다. 클라이언트는 그 주소로 **새 연결**을 엽니다.

여기엔 조건이 하나 붙습니다. 그 주소로 들어온 연결이 지정된 worker 에 실제로 도착해야 합니다. 앞단의 부하 분산기가 아무 서버로나 뿌려 버리면 이 설계는 성립하지 않아요. worker 별 경로를 프록시에 등록해 고정 라우팅을 잡아 두셔야 합니다. 그리고 그 주소는 공개 TLS 종단이어야 합니다. 내부 IP 를 그대로 돌려주면 안 되고요.

대가는 서버가 교체될 때 클라이언트가 재접속을 해야 한다는 겁니다.

### 갈래 3 — 고정 게이트웨이가 중계한다

재접속이 곤란한 요구사항이라면 이 갈래를 봅니다. 클라이언트는 언제나 게이트웨이에 붙고, 게이트웨이가 내부에서 담당 worker 에게 메시지를 전달합니다. worker 가 바뀌어도 바깥에서는 연결이 끊기지 않죠.

```
[클라이언트]──WSS──>[게이트웨이]──내부 전달──>[worker A]
                          │
                          └────재배치 후────>[worker B]
                       (바깥 연결은 그대로)
```

깔끔해 보이지만 복잡도가 사라지는 게 아니라 옮겨 갑니다. 게이트웨이 자체를 확장해야 하고, worker 가 바뀔 때 게이트웨이가 내부 연결을 다시 맺고 그동안의 메시지를 어떻게 다룰지 정해야 합니다. 그리고 모든 편집 메시지가 한 층을 더 지나갑니다.

**연결 유지가 계약 수준의 요구사항일 때** 고르는 갈래입니다. "재접속이 좀 거슬려서"가 이유라면 비용이 큽니다.

### 갈래 4 — 주소를 계산해서 찾는다

배치 정보를 어디에 묻지 않고 클라이언트나 프록시가 직접 계산하는 방법도 있습니다. 문서 식별자를 해시해서 서버 목록에 매핑하는 방식이죠. 일관 해시를 쓰면 서버가 늘고 줄 때 옮겨 가는 문서의 비율을 줄일 수 있습니다.

조회가 없으니 빠르고, 배치를 기록할 곳도 필요 없습니다. 대신 **특정 문서를 특정 서버에 두는 선택권이 사라집니다.** 무거운 문서 둘이 같은 서버로 떨어져도 옮길 수가 없어요. 서버 목록이 바뀌는 순간 여러 문서가 동시에 이사를 가고요.

문서마다 부하 편차가 작고 재배치 요구가 없는 시스템이면 가장 단순한 답입니다. 편차가 크면 맞지 않습니다.

### 갈래 5 — 서브도메인이나 경로를 분리해 DNS 로 가른다

worker 마다 별도 호스트명을 주는 방법입니다. 프록시 설정 대신 DNS 가 가르는 거죠. 인증서와 CORS 설정이 늘어나고, DNS 전파 시간 때문에 배치 변화가 즉시 반영되지 않습니다. worker 집합이 거의 고정된 환경이 아니면 권하지 않습니다.

### 조건에 따라 무엇을 고르나

| 조건 | 맞는 갈래 |
| --- | --- |
| 일반적인 웹 스택, 재접속 허용 | 갈래 2 (목적지 선조회) |
| 연결 유지가 계약 조건 | 갈래 3 (게이트웨이) |
| 문서별 부하 편차가 작고 재배치 불필요 | 갈래 4 (해시 라우팅) |
| worker 집합이 거의 고정 | 갈래 5 (DNS 분리) |
| 어떤 조건에서도 | 갈래 1 은 제외 |

기본값으로 갈래 2 를 권합니다. 다만 "권한다"와 "이것만 맞다"는 다른 말입니다. 연결 유지 요구가 실제로 있으면 갈래 3 이 정답이고, 그때 갈래 2 를 고집하면 요구사항을 설계로 덮는 셈이 됩니다.

## Q. 그러면 그 worker 는 backend 가 직접 띄웁니까, 아니면 미리 pool 을 만들어 놓고 씁니까?

"room 이 독립 단위다"와 "room 마다 프로세스가 하나여야 한다"를 먼저 갈라 두죠. 앞은 논리의 문제이고 뒤는 자원의 문제입니다. 논리 단위를 그대로 자원 단위로 옮기면 방 하나 열 때마다 프로세스 하나가 떠야 하는데, 방 대부분은 대부분의 시간 동안 한가합니다.

room 을 무엇으로 볼지부터 정의하고 갑니다. **room 은 worker 프로세스 안에 있는 상태 객체와 작업 큐입니다.** CRDT 문서 하나, 참여자 목록, 그 문서에 대한 요청을 순서대로 처리하는 큐. 프로세스가 아닙니다.

```
 [worker 프로세스]
  ├─ room W17/D8  : CRDT 문서 · 참여자 3 · 작업 큐
  ├─ room W17/D9  : CRDT 문서 · 참여자 1 · 작업 큐
  └─ room W22/D1  : CRDT 문서 · 참여자 8 · 작업 큐
```

이 정의 위에서 자원 전략이 넷으로 갈립니다.

### 전략 A — 요청이 올 때 인스턴스를 띄운다

첫 접속이 오면 backend 가 컨테이너나 프로세스를 하나 만들고, 그것이 뜨면 주소를 돌려줍니다.

격리가 확실합니다. 한 방이 메모리를 다 써도 이웃이 안 다치고, 방마다 자원 상한을 따로 걸 수 있죠. 대신 첫 접속 경로에 **인스턴스 시작 시간이 통째로 들어갑니다.** 컨테이너 이미지를 받고 런타임이 뜨고 애플리케이션이 초기화되는 시간이 사용자 대기 시간이 돼요. 그리고 한가한 방들이 각자 자원을 쥐고 있습니다.

문서 하나가 세션 하나만큼 무겁고 동시 문서 수가 적은 시스템, 예를 들면 문서마다 무거운 계산이 붙는 경우에 맞습니다.

### 전략 B — 상시 worker 풀에 논리 room 을 배치한다

worker 프로세스들을 미리 띄워 두고, 방이 열리면 그중 하나에 배치합니다. 배포 시스템이 복제본 수를 유지하고, 지표에 따라 수를 조절하죠.

첫 접속에서 인스턴스 시작 시간이 빠집니다. 남는 건 문서를 복원하는 시간뿐이에요. 자원도 뭉쳐 쓰니 한가한 방 백 개가 프로세스 백 개를 잡고 있지 않습니다.

대신 한 프로세스 안에서 방들이 이웃이 됩니다. 한 방이 이벤트 루프를 오래 잡으면 옆방 사용자의 입력이 밀려요. 그래서 방 하나가 쓸 수 있는 시간과 메모리에 상한을 걸고, 무거운 계산은 별도 스레드 풀로 뺍니다.

여기서 "풀"이 무엇인지 헷갈리기 쉬운데, **미리 만들어 둔 빈 방들의 집합이 아니라 실행 중인 worker 프로세스들의 집합입니다.** 방은 필요할 때 그 안에서 생겨납니다.

### 전략 C — 상시 풀을 기본으로 두고 무거운 방만 격리한다

대부분의 방은 풀에서 살고, 특정 방이 일정 기준을 넘으면 전용 프로세스로 옮깁니다. 기준은 메모리, 참여자 수, 초당 변경량 같은 것이 되겠죠.

두 전략의 좋은 쪽을 가져오지만 배치 규칙이 둘이 되고 "언제 옮기나"를 판정하는 로직이 생깁니다. **처음부터 이걸로 시작하지 마십시오.** 전략 B 로 운영하다가 실제로 무거운 방이 이웃을 방해하는 것을 관측한 뒤에 도입하는 순서가 맞습니다.

### 전략 D — 쓰지 않으면 0 으로 내린다

트래픽이 없으면 worker 를 모두 내리고, 요청이 오면 그때 올립니다. 비용이 가장 적게 듭니다.

첫 접속에 콜드 시작이 붙는다는 걸 받아들여야 하고, 그 대기가 사용자에게 보입니다. 사내 도구처럼 사용 시간대가 뚜렷하고 첫 접속이 몇 초 걸려도 되는 시스템이면 합리적인 선택입니다.

### 조건표

| 조건 | 전략 |
| --- | --- |
| 문서 수가 적고 문서마다 무겁다 · 격리가 중요 | A |
| 문서가 많고 대부분 가볍다 · 첫 접속 지연에 민감 | B |
| B 로 운영 중 특정 방이 이웃을 방해한다 | C |
| 사용 시간대가 뚜렷하고 비용이 우선 | D |

그리고 전략과 무관하게 지켜야 할 것이 하나 있습니다. **방이 살아 있는 시간과 프로세스가 살아 있는 시간을 같은 것으로 보지 마십시오.** 마지막 참여자가 나가도 방을 즉시 버리지 않고 짧은 유예를 둡니다. 새로고침으로 잠깐 나갔다 오는 경우가 흔하니까요. 대신 유예 시간과 함께 유지할 방의 총 메모리 예산을 걸어 두어야 무제한으로 쌓이지 않습니다.

## Q. pool 을 만든다면 worker 를 제어하는 controller 인스턴스가 필요합니까? 필요하다면 구체적으로 어떤 역할을 하고 어떤 기능을 구현합니까?

역할은 반드시 필요합니다. 전용 인스턴스는 선택입니다. 이 둘을 갈라 놓고 답하겠습니다.

먼저 무슨 일을 해야 하는지부터 세어 보죠. worker 풀을 굴리려면 누군가는 이 일들을 해야 합니다.

### 제어 역할이 해야 하는 일 여섯

**하나, 레지스트리.** 지금 어떤 worker 가 살아 있고 새 방을 받을 수 있는지 압니다. worker 가 뜨면 자신의 내부 주소와 외부 경로를 등록하고, 준비가 끝나면 상태를 보고합니다. 여기서 값 하나를 더 받아 두십시오. **논리적인 서버 이름과 이번 프로세스 실행을 구분하는 값을 따로 둡니다.** 같은 이름의 worker 가 재시작되면 메모리에 있던 방은 전부 사라졌는데, 이름만 보고 이전 소유권을 물려받으면 없는 방을 있다고 여기게 됩니다.

**둘, 배치.** 새 방을 어느 worker 에 둘지 정합니다. 준비 상태이고 최근에 살아 있다고 보고했으며 여유가 있는 worker 중에서 고릅니다.

**셋, 임대 관리.** 배치한 방에 기한을 겁니다. 담당 worker 는 주기적으로 기한을 연장하고, 연장이 끊기면 그 방은 주인이 없는 것으로 간주됩니다.

여기서 두 신호를 갈라 두셔야 합니다.

| | heartbeat | lease |
| --- | --- | --- |
| 단위 | worker 하나 | 방 하나 |
| 뜻 | "나 살아 있고 여유 이만큼" | "이 방은 지금 내 담당" |
| 용도 | 배치 대상 선택 | 소유권 판정 |

worker 가 살아 있다는 보고 하나로 그 worker 가 가진 모든 방의 권한을 자동 연장하면 안 됩니다. 프로세스는 살아 있는데 특정 방의 처리가 멈춘 경우를 못 걸러 내거든요.

**넷, 세대 관리.** 방의 담당자가 바뀔 때마다 번호를 올립니다. 이 번호가 나중에 장애 처리의 핵심이 됩니다. 뒤에서 다시 다루죠.

**다섯, 복구.** 배치는 커밋됐는데 활성화 요청이 중간에 끊긴 방, 임대가 만료된 채 남아 있는 방, 예약만 잡히고 쓰이지 않은 자리를 주기적으로 찾아 정리합니다.

**여섯, 용량 조절.** 전체 여유가 부족하면 worker 를 늘리도록 요청합니다. 이건 보통 배포 시스템의 확장 기능에 맡깁니다.

### 그 역할을 어디에 두나 — 네 가지 배치

이 여섯을 어디에 구현하느냐가 갈립니다.

**배치 1 — backend 안의 모듈.** backend 복제본 어디서든 실행되는 모듈로 두고, 경쟁 조정은 공유 DB 에 맡깁니다.

새 프로세스가 늘지 않고, 배포와 감시 대상도 늘지 않습니다. backend 가 이미 인증과 권한을 하고 있으니 배치 판단에 필요한 정보도 가까이 있고요. **시작점으로 이걸 권합니다.**

"복제본이 둘인데 같은 문서의 첫 요청이 동시에 도착하면 둘 다 방을 만들지 않느냐"가 당연한 의문일 텐데, 그건 DB 가 막습니다.

```
BEGIN;
  -- 행이 없을 수 있으니 먼저 만든다. 없는 행은 잠글 수 없다.
  INSERT INTO room_ownership(room_id) VALUES (:room_id)
    ON CONFLICT DO NOTHING;
  -- 이제 잠근다. 다른 트랜잭션은 여기서 기다린다.
  SELECT * FROM room_ownership WHERE room_id = :room_id FOR UPDATE;
  -- 유효한 담당자가 이미 있으면 그대로 쓰고 끝낸다.
  -- 없으면 worker 를 고르고, 그 worker 의 예약 수를 같은 트랜잭션에서 올린다.
  -- 담당자 · 실행 식별자 · 세대+1 · 상태 loading · 기한을 기록한다.
COMMIT;
-- 커밋한 다음에 활성화 요청을 보낸다. 재시도 가능하게 만든다.
```

순서에 두 가지가 들어 있습니다. 없는 행은 잠글 수 없으니 생성 경쟁은 기본 키 충돌로 정리하고, 잠금을 잡은 뒤에는 조건을 **다시** 확인합니다. 기다리는 동안 상황이 바뀌었을 수 있으니까요. 그리고 네트워크 호출을 트랜잭션 안에서 기다리지 않습니다. 소유권을 먼저 커밋하고 그다음에 활성화를 요청합니다.

**배치 2 — 전용 controller 프로세스 하나.** 배치 판단을 한 곳에 모읍니다.

상태를 한 프로세스가 들고 있으니 판단이 빠르고 규칙이 복잡해져도 다루기 쉽습니다. 대신 그 프로세스가 단일 장애점이 됩니다. 죽으면 새 방 배치가 멈춰요. 이중화하면 다시 "둘 중 누가 진짜인가"를 풀어야 하고, 결국 배치 1 이 DB 에게 맡긴 문제를 직접 풀게 됩니다.

**메모리를 정본으로 삼지 마십시오.** controller 를 분리하더라도 배치 결과는 공유 저장소에 남아야 합니다. 그래야 재시작 후에도 이어집니다.

**배치 3 — 분산 조정 시스템에 맡긴다.** 임대와 리더 선출을 제공하는 외부 시스템을 쓰는 방법입니다. 검증된 도구를 쓰는 셈이지만, 운영해야 할 시스템이 하나 늘고 그 시스템의 장애 모드를 새로 배워야 합니다. 이미 쓰고 있다면 자연스러운 선택이고, 이것 때문에 도입하는 거라면 먼저 DB 로 될지 따져 보시는 게 좋겠습니다.

**배치 4 — controller 없이 계산으로.** 앞서 나온 해시 라우팅입니다. 배치 주체가 아예 없죠. 대신 배치를 조정할 수 없고 재배치도 못 합니다.

| 배치 | 언제 |
| --- | --- |
| 1. backend 모듈 | 시작점. 대부분 여기서 충분하다 |
| 2. 전용 프로세스 | 배치 규칙이 복잡해지고 API 부하와 수명이 달라졌을 때 |
| 3. 외부 조정 시스템 | 이미 운영 중일 때 |
| 4. 없음 (해시) | 부하 편차가 작고 재배치가 필요 없을 때 |

배치 1 에서 2 로 옮길 때 계약을 그대로 유지하면 옮기는 일이 가벼워집니다. 처음부터 인터페이스를 갈라 두시면 좋겠습니다.

### 소유권을 기록하는 자리의 실체

"소유권 디렉터리"라고 부르면 제품 이름 같지만, 테이블 몇 개와 그걸 갱신하는 규칙이 전부입니다.

| 테이블 | 무엇을 담나 |
| --- | --- |
| `collab_servers` | worker 실행 하나하나. 주소 · 상태 · 최근 생존 보고 · 여유 |
| `room_ownership` | 방마다 담당자 · 실행 식별자 · 세대 · 상태 · 기한 · 마지막 로그 위치 |
| `room_updates` | 영속화된 변경분. 방별 순번과 중복 방지 키 |
| `room_checkpoints` | 복구 지점. 상태 바이트와 그 시점의 로그 위치 |

```
room_ownership
  room_id          'W17/D8'
  owner_server_id  'C2'          ← 논리 이름
  owner_boot_id    (실행별 UUID)  ← 이번 프로세스 실행
  epoch            12            ← 담당자가 바뀔 때마다 +1
  state            'ready'       ← idle | loading | ready | draining
  lease_until      (만료 시각)
  last_sequence    4821
```

`epoch` 는 방이 비어 idle 로 돌아가도 초기화하지 않습니다. 세대는 계속 올라가기만 합니다. 이유는 다음 질문에서 드러납니다.

## Q. room 을 담당하던 worker 가 교체됐을 때 구체적인 시스템 시나리오는 어떻게 됩니까?

교체에는 결이 다른 경우가 넷 있습니다. 하나씩 따라가 보죠.

### 시나리오 1 — 갑자기 죽는다

가장 먼저 정할 것은 **언제 죽었다고 판정하는가**입니다. 소켓이 끊겼다는 이유만으로 즉시 다른 worker 에게 방을 넘기면 위험합니다. 실은 살아 있는데 네트워크만 잠깐 막힌 경우에 한 방에 주인이 둘이 되거든요.

```
 t0  C2 가 방 W17/D8 을 담당 (epoch 12, 기한 t0+30s)
 t1  C2 의 소켓이 끊긴다. 아직 아무 일도 하지 않는다
 t2  기한이 지난다
 t3  제어 역할이 소유권 행을 잠그고 C3 / epoch 13 을 기록
 t4  C3 이 체크포인트 + 이후 로그를 복원
 t5  C3 이 준비 완료를 보고, 상태가 ready 로
 t6  클라이언트가 경로를 다시 조회해 C3 에 연결
 t7  클라이언트가 확인 못 받은 변경을 다시 보낸다
 t8  C2 가 되살아나 epoch 12 로 쓰기를 시도 → 거부
```

t1 과 t2 사이의 기다림이 설계 결정입니다. 짧게 잡으면 복구가 빠르지만 멀쩡한 worker 를 죽었다고 오판할 확률이 올라가고, 길게 잡으면 그 반대죠. 이 값은 네트워크 특성을 보고 정하셔야 합니다. 제가 숫자를 드릴 수는 없습니다.

t8 이 이 시나리오의 핵심입니다. 죽은 줄 알았던 이전 담당자가 뒤늦게 깨어나 자기가 들고 있던 변경을 쓰려고 하는 상황이요. 그걸 **저장소가** 막습니다.

```
BEGIN;
  SELECT * FROM room_ownership WHERE room_id = :room_id FOR UPDATE;
  -- 호출자가 보낸 담당자 · 실행 식별자 · 세대가 지금 값과 전부 일치하는가
  -- 기한이 아직 유효한가 · 상태가 ready 인가
  -- 하나라도 어긋나면 ROLLBACK
  -- 같은 변경 식별자가 이미 있으면 내용을 대조하고 기존 결과를 돌려준다
  -- 새 변경이면 순번을 올려 기록한다
COMMIT;
-- 이 커밋 뒤에만 저장 확인을 보낸다
```

판정이 backend 가 아니라 **데이터가 실제로 쌓이는 자리**에 있어야 합니다. 그래야 우회로가 없습니다. worker 에게 임의 쓰기 권한을 주지 말고 이 검사를 포함한 제한된 함수만 열어 두십시오.

> [!정수]
> CRDT 는 복제본끼리 결국 같은 상태로 수렴하게 해 줍니다. 그런데 저장소에 뒤늦게 도착한 옛 주인의 쓰기까지 막아 주지는 않습니다. 그건 다른 층에서 풀어야 하는 문제입니다.

여기서 번호가 셋 나왔으니 정리하고 갑니다. 서로 대신 쓸 수 없습니다.

| 번호 | 무엇을 가리키나 | 언제 올라가나 |
| --- | --- | --- |
| `sequence` | 저장 로그에서의 위치 | 변경이 영속화될 때마다 |
| `epoch` | 담당 worker 의 세대 | 담당자가 바뀔 때마다 |
| 상태 벡터 | CRDT 복제본이 어디까지 알고 있는지 | 편집이 병합될 때마다 |

### 시나리오 2 — 계획하고 옮긴다

배포나 축소처럼 미리 아는 교체입니다. 절차가 다릅니다.

```
 ① C2 를 신규 배치 대상에서 제외한다
 ② 방별로 새 편집 수락을 멈춘다 (draining)
 ③ 이미 받은 변경을 전부 저장한다
 ④ 정말 멈췄는지 확인한다
 ⑤ 소유권을 C3 / epoch 13 으로 바꾼다
 ⑥ C3 이 복원하고 준비를 마친다
 ⑦ C2 가 남은 연결을 끊는다 → 클라이언트가 재조회·재접속
```

④ 가 중요합니다. 확인이 안 되면 억지로 진행하지 말고 시나리오 1 의 기한 만료 경로를 타게 두십시오. 확인 없이 소유권을 넘기면 계획된 이동이 오히려 주인 둘을 만듭니다. 그리고 ⑦ 에서 메모리 객체나 소켓을 통째로 보내려 하지 않습니다. 앞에서 정한 대로 연결은 옮기지 않고 다시 맺습니다.

### 시나리오 3 — 부하 때문에 옮긴다

한 방이 뜨거워져 이웃이 느려지는 경우입니다. 여기서 한 가지를 분명히 해야 합니다. **담당 worker 가 자기 판단으로 소유권을 다른 worker 에게 넘기면 안 됩니다.** 부하 상황을 보고하고 이동을 요청하되, 결정은 제어 역할이 합니다. 그렇지 않으면 두 worker 가 서로에게 방을 떠넘기는 상황이 생길 수 있어요.

이동 절차 자체는 시나리오 2 와 같습니다. 옮겨도 한 방의 한계를 넘는다면 그때는 구독 범위를 좁히거나 문서를 나누는 쪽을 봐야 합니다. **worker 를 늘린다고 방 하나가 저절로 병렬화되지는 않습니다.**

### 시나리오 4 — 제어 쪽이 멈춘다

worker 가 아니라 backend 나 저장소가 문제일 때입니다.

backend 복제본 하나가 죽으면 다른 복제본이 이어받습니다. 배치를 커밋한 직후에 죽었다면 활성화 요청이 전달되지 않은 채 `loading` 상태의 방이 남는데, 다음 경로 조회나 주기적 점검 작업이 같은 세대로 활성화를 다시 보냅니다. 그래서 활성화 요청은 **여러 번 와도 같은 결과여야** 합니다. 같은 방과 같은 세대에 대한 중복 요청은 이미 진행 중인 작업을 돌려주도록 만드십시오.

임대 연장 경로가 통째로 멈추면 기한이 지난 방들은 쓰기를 중단해야 합니다. 저장소에 쓸 수 없으면 저장 확인을 보낼 수 없고, 클라이언트는 확인 못 받은 편집을 로컬에 들고 기다립니다. 여기서 화면에 "저장됨"을 띄우면 안 됩니다.

## Q. CRDT 를 쓸 때 데이터 영속화 전략과 그 구체적인 설계는 어떻게 됩니까?

먼저 CRDT 가 무엇을 해 주고 무엇을 안 해 주는지 갈라 두죠. CRDT(Conflict-free Replicated Data Type)는 여러 복제본이 각자 편집해도 병합 결과가 같아지는 자료구조입니다. 병합은 이것이 풀어 줍니다. **"언제 디스크에 쓸 것인가"는 병합 문제가 아닙니다.** 그건 내구성 문제이고 답이 따로 있어야 합니다.

### 전략 가 — 마지막 세션이 닫힐 때 저장한다

구현이 가장 단순합니다. 방이 살아 있는 동안은 메모리에서만 돌고, 마지막 참여자가 나갈 때 한 번 씁니다.

문제는 그 이벤트가 **실행되지 않는 경우**입니다. 프로세스가 강제 종료되거나 배포로 교체되거나 네트워크가 끊긴 채 세션이 정리되면 저장 코드는 아예 돌지 않습니다. 그러면 마지막 저장 이후의 전부를 잃습니다. 접속이 길수록 잃는 범위가 커지고요.

**잃어도 되는 데이터일 때만** 고를 수 있습니다. 임시 메모나 실시간 화이트보드 낙서처럼요. 복구가 필요한 문서에는 맞지 않습니다.

### 전략 나 — 주기적으로 전체 상태를 덮어쓴다

일정 시간마다 문서 상태 전체를 저장합니다. 가 보다 낫고 여전히 단순합니다.

손실 범위가 주기만큼으로 줄어듭니다. 주기를 짧게 잡으면 손실이 줄지만 큰 문서를 자주 통째로 쓰게 되죠. 그리고 두 번의 저장 사이에 있던 편집은 순서 정보 없이 사라집니다.

문서가 작고 편집 빈도가 낮으면 이걸로 충분합니다.

### 전략 다 — 변경 로그를 쌓고 주기적으로 체크포인트를 잡는다

편집이 들어올 때마다 변경분을 덧붙여 기록하고, 로그가 길어지면 그 시점까지의 상태를 통째로 저장해 앞쪽 로그를 정리합니다.

```
 변경 로그   [1][2][3][4][5][6][7][8][9]...
                          ▲
             체크포인트 (여기까지의 상태 + 위치 7)
 복구 = 체크포인트 + 8번 이후 로그
```

손실 범위가 확인받지 못한 마지막 몇 건으로 줄어듭니다. 순서가 남으니 되감기도 가능하고요. 대신 저장 횟수가 늘고, 체크포인트와 로그 정리의 순서를 정확히 지켜야 합니다.

**복구가 필요한 협업 문서의 기본값입니다.** 구체적인 설계를 펴 보죠.

로그 한 줄에 들어갈 것은 넷입니다. 방 식별자, 방 안에서의 순번, 이 변경의 고유 식별자, 그리고 변경분 자체. 고유 식별자가 필요한 이유는 **재전송 때문**입니다. 클라이언트가 저장 확인을 못 받고 다시 보내면 같은 변경이 두 번 도착하는데, 식별자가 같으면 이미 처리한 것으로 보고 같은 결과를 돌려줍니다. 내용까지 다르면 거부해야 하고요.

체크포인트는 방의 직렬 처리 구간 안에서 잡습니다. 상태 바이트와 **그 상태에 실제로 반영된 마지막 로그 위치**를 함께 기록해야 해요. 이 둘이 어긋나면 복구가 조용히 깨집니다. 그리고 체크포인트가 내구성 있게 확정된 **다음에만** 그 위치 이하의 로그를 지웁니다. 순서를 바꾸면 체크포인트 쓰기가 실패했을 때 로그도 없고 체크포인트도 없는 상태가 됩니다.

그리고 여기, 자주 틀리는 자리가 하나 있습니다. **문서 상태를 JSON 같은 일반 형식으로 바꿔 저장한 뒤 나중에 그걸로 CRDT 를 새로 만들면 안 됩니다.** 본문 글자가 같아도 CRDT 내부의 식별 정보와 인과 관계가 달라지거든요. 기존 클라이언트와 이어서 동기화하려면 복원 가능한 CRDT 형식 그대로 보존하셔야 합니다.

### 전략 라 — 외부 로그 시스템에 맡긴다

변경 로그를 DB 가 아니라 전용 로그 시스템에 쌓는 방법입니다. 쓰기 처리량이 DB 의 한계에 닿았을 때 보는 갈래죠.

처리량은 올라가지만 **세대 검사와 로그 쓰기가 원자적이어야 한다는 요구는 그대로 남습니다.** 소유권은 DB 에 있고 로그는 다른 시스템에 있으면, 두 곳을 한 번에 검사하고 쓰는 방법을 따로 마련해야 해요. 이게 생각보다 까다롭습니다. 먼저 DB 로 재 보고, 실제로 부족할 때 옮기십시오.

### 전략 마 — 클라이언트 쪽 저장을 함께 쓴다

앞의 전략들과 배타적이지 않습니다. 보내지 못한 변경을 브라우저에 보관해 두는 거죠.

새로고침을 견뎌야 한다면 메모리가 아니라 내구성 있는 로컬 저장소를 써야 합니다. 그리고 **확인받지 못한 편집을 확정된 것으로 표시하지 마십시오.** 재인증에 실패했거나 권한이 사라진 편집이 있을 수 있습니다.

### 저장과 화면 사이의 순서

전략을 골랐으면 순서를 정해야 합니다. 기본값은 이겁니다.

```
 로컬 즉시 반영 → 서버 검증 → 로그 커밋 → 전파 → 저장 확인
      (내 화면)                              (남의 화면)  (저장됨 표시)
```

이 순서에서는 다른 참여자에게 보이는 시점에 저장 지연이 포함됩니다. 측정해 보니 그 지연이 문제라면 전파를 먼저 할 수 있어요. 다만 그때는 **전파된 변경이 아직 저장 안 됐을 수 있다**는 걸 받아들이는 겁니다. 어느 쪽이 맞는지는 시스템이 정합니다. 문서 편집기면 앞이, 커서가 실시간으로 움직이는 화이트보드면 뒤가 맞을 수 있죠.

그리고 **"보였다"와 "저장됐다"를 화면에서 갈라 표시하십시오.** 이건 전략과 무관하게 지켜야 합니다.

커서나 접속자 표시 같은 것은 본문 로그에 넣지 않습니다. 잃어도 되는 정보라 별도 휘발성 채널로 다루고, 너무 잦으면 합쳐 보내거나 버려도 됩니다. 본문 변경은 조용히 버리지 않고요.

### 조건표

| 조건 | 전략 |
| --- | --- |
| 잃어도 되는 임시 데이터 | 가 |
| 문서가 작고 편집이 드물다 | 나 |
| 복구가 필요한 협업 문서 | 다 (기본값) |
| 다 로 운영 중 쓰기 처리량이 한계 | 라 |
| 오프라인 편집이나 새로고침을 견뎌야 한다 | 마 (다른 전략과 함께) |

### 첫 접속이 느린 문제

영속화 설계는 첫 접속 속도와 직결되니 같이 봅니다. 첫 접속에서 시간이 흐르는 자리는 넷입니다.

```
 [실행 환경 준비] [저장소 읽기] [CRDT 복원] [전송·클라이언트 적용]
       ↑                ↑            ↑
   전략 A·D 에서만   체크포인트로   스레드 풀로
   발생한다         줄인다        뺄 수 있다
```

뭉뚱그려 "로딩이 느리다"고 보면 엉뚱한 곳을 고치게 됩니다. 접속할 때마다 인스턴스를 띄우는 설계라면 첫 칸이 통째로 붙는데 정작 저장소부터 의심하게 되거든요.

같은 방에 두 사람이 동시에 들어오는 경우를 미리 정해 두십시오. 복원을 두 번 돌리지 않고 하나의 작업을 공유하게 합니다. 그리고 여러 방이 동시에 깨어날 때를 대비해 동시 복원 수에 상한을 겁니다. 없으면 저장소와 CPU 가 같이 넘어갑니다.

재방문 사용자는 로컬 캐시를 먼저 그려 화면을 즉시 띄울 수 있습니다. 다만 캐시를 보여 주는 것과 서버 동기화가 끝난 것은 다른 사건이에요. 캐시가 없는 첫 방문에는 이 이점이 아예 없고요.

마지막으로 틈 하나. **초기 상태를 내려 주는 일과 실시간 변경 구독을 시작하는 일 사이에 틈이 있으면 그 틈에 들어온 편집을 놓칩니다.** 방의 직렬 처리 구간 안에서 구독을 먼저 걸고 초기 상태를 잡거나, 로그 위치를 기준으로 그 이후 변경을 재생하십시오. 서버 상태를 일방적으로 내려 주고 끝내지 말고, 클라이언트에 남아 있던 오프라인 편집도 합쳐야 합니다.

> [!정수]
> 마지막 퇴장은 저장을 시작하라는 신호가 아닙니다. 이제 메모리를 회수해도 된다는 신호입니다.

### 무엇을 재고 나서 정할 것인가

여기까지가 조건별로 갈리는 지점들이고, 어느 쪽을 고를지는 숫자가 정합니다. 저는 그 숫자를 모릅니다. 재 보셔야 하는 것들만 적어 두죠.

| 상황 | 재는 것 | 그 결과로 정해지는 것 |
| --- | --- | --- |
| 큰 문서 첫 접속 | 동기화 준비 시간 · 복원 CPU · 전송량 | 체크포인트 간격 · 문서 경계 |
| 같은 방 동시 접속 | 복원이 한 번만 도는가 · 초기 동기화 중 누락 | 복원 공유 · 구독 경계 |
| 여러 방 동시 활성화 | 복원 큐 · 저장소 부하 · 이벤트 루프 지연 | 동시 복원 상한 · 풀 크기 |
| 커밋 전후 강제 종료 | 확인된 변경의 복구 · 재전송 결과의 일관성 | 저장 확인 경계 |
| 이전 담당자의 뒤늦은 복귀 | 옛 세대의 쓰기가 거부되는가 | 저장소 검사의 정확성 |
| 해제 직전 새 접속 | 살아 있는 방이 버려지지 않는가 | 세션·작업·해제의 직렬화 |

도입 순서를 권한다면 이렇습니다. 단일 worker 에서 방·로그·복구를 먼저 검증하고, 그다음 소유권과 다중 worker 배치를 붙이고, 부하를 재고 나서 CPU 분리와 무거운 방 격리를 봅니다. 한 번에 다 세우려고 하면 어느 층이 문제인지 가려낼 수가 없습니다.

## 마치며

처음에 저는 room 을 하나의 덩어리로 보고 있었습니다. 방이 열리고, 사람이 들어오고, 마지막 사람이 나가면 닫히면서 저장되는. 그 그림이 깔끔해서 의심하지 않았어요.

깨진 지점은 "마지막 사람이 나갈 때 저장한다" 였습니다. 그 문장이 성립하려면 마지막 사람이 나가는 사건이 항상 일어나야 하는데, 서버는 그런 예의를 지키지 않고 죽더군요. 방이 살아 있는 시간, 저장이 일어나는 시점, 프로세스가 살아 있는 시간을 갈라 놓고 나니 연결도 배치도 교체도 각자의 자리를 찾았습니다.

조건표를 다섯 개 만들었는데, 채워 넣을 숫자는 아직 하나도 없습니다. 다음은 재는 일입니다.
