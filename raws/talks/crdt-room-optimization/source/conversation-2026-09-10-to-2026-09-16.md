# CRDT room 최적화 설계 — 대화 원문 보관

이 파일은 폭신 대담의 L1 원문이다. 문답의 흐름을 보존하기 위해 사용자 질문과 답변을 시간 순서로 기록한다. 보고서 HTML은 같은 디렉터리의 `artifacts/`에 원본 그대로 보관한다.

## 사용자 · 첫 질문

나는 workspace 단위로 room을 만들어서, socket과 crdt로 소통하는 전략을 방향성으로 잡았다. 첫 세션 접속 시 관련 데이터가 DB에서 로드되고, 마지막 세션이 닫힐 때 DB에 저장한다. 첫 세션은 데이터 로드 때문에 지연 시간이 생길 것 같은데 어떻게 극복할 수 있는지 궁금하다. 여러 workspace에서 많은 세션들이 접속하면 단일 서버로 병목이 생길 것이다. room별로 worker를 띄우는 게 좋을 것 같은데 실제 그런지, 그렇다면 어떤 식으로 구현되어야 하는지 궁금하다. 백엔드가 worker 생성 요청을 하여 실제 인스턴스가 올라가더라도 클라이언트가 worker와 소통하도록 커넥션을 인계할 수는 없을 것 같다.

## 답변 · 첫 번째 설계 논의

workspace를 room으로 묶는 방향은 합리적이다. 다만 room의 수명, 데이터를 저장하는 시점, 서버 인스턴스의 수명을 분리해야 한다. 마지막 세션 종료만을 저장 시점으로 삼으면 비정상 종료 시 작업을 잃을 수 있으므로, 편집 중 변경분을 내구성 있는 저장소에 기록하고 주기적으로 스냅샷을 정리해야 한다. 마지막 퇴장은 저장 시작보다 메모리 회수 조건에 가깝다.

초기 로딩은 실행 환경 준비, DB 읽기, CRDT 복원, 클라이언트 전송·적용으로 나눠야 한다. 스냅샷과 그 이후 변경분을 사용하고, 같은 room의 동시 접속은 하나의 복원 작업을 공유한다. 재방문 사용자는 로컬 캐시를 먼저 보여줄 수 있지만 캐시 표시와 서버 동기화 완료는 구분한다.

room마다 프로세스나 컨테이너를 띄우기보다 한 서버가 여러 room을 맡는 서버 풀로 시작한다. 세션 수가 아니라 문서 크기, 업데이트 빈도, CRDT 적용 시간, 전파량을 측정한다. 연결을 다른 서버로 넘기는 것을 기본으로 삼지 않고, 접속 전에 room 담당 서버를 결정해 클라이언트가 처음부터 해당 서버에 연결한다. 대안으로 고정 게이트웨이가 내부 room 서버를 중계할 수 있지만 게이트웨이 자체의 확장과 재동기화가 필요하다.

## 사용자 · 전략 상세화 요청

전제에 따라 전략이 달라진다면 각 전략을 다 보여 달라. 전략에 대한 자세한 설명이 필요하다. 코드와 시각화, 과정 설명을 포함해 달라.

## 답변 · 전략별 비교

문서 경계에 따라 네 전략을 비교했다. A는 workspace 전체를 하나의 CRDT 문서로 두는 방식, B는 workspace의 문서를 분리하고 열린 문서만 로드하는 방식, C는 문서는 분리하되 권한·소속처럼 엄격한 규칙은 서버 명령과 DB 트랜잭션으로 처리하는 방식, D는 하나의 초대형 문서를 구역으로 나누는 방식이다. 기본 권장은 문서별 논리 room, 여러 room을 맡는 서버 풀, 변경 로그와 체크포인트, 접속 전 목적지 결정이다.

Yjs의 상태 벡터를 통한 차이 동기화, subdocument의 지연 로딩, 바이너리 update 병합을 설명했다. 저장은 세션 중에 수행하고 ACK는 내구성 커밋 뒤에 보낸다. room 소유권에는 서버 세대(epoch)를 두어 장애 뒤 이전 서버의 쓰기를 차단한다. worker thread는 CPU 집약 작업이 실제 병목일 때 풀로 쓰며 room마다 thread를 만들지 않는다.

## 사용자 · HTML 보고서 요청

내가 생각하는 최적 설계에 대해 HTML 보고서로 작성해 달라. 시각화를 활용해 직관적으로 이해되도록 하고, 별도로 최적화 설계와 비교했을 때 내 아이디어에서 무엇이 적용됐고, 무엇이 보완됐으며, 무엇이 적용 불가능했는지 이유와 함께 설명해 달라.

## 답변 · 첫 HTML 보고서 작성

`reports/crdt-design/index.html`에 독립적으로 열 수 있는 HTML 보고서를 작성했다. 권장 구조, 접속·저장·퇴장·장애 복구 시각화, 원안의 적용·보완·미채택·적용 불가 비교, TypeScript 의사코드와 검증 기준을 포함했다. 문서별 논리 room과 서버 풀을 기본안으로 삼았고, 기존 보고서에서 새 세부 보고서로 연결할 수 있도록 구성했다.

## 사용자 · 세부 실물 시나리오 요청

협업 서버의 구성 방식, backend가 협업 서버 인스턴스를 띄우는지 독립적으로 운영되는 서버의 주소만 알고 있는지, 협업 서버가 room을 변경하면 backend API를 호출해 backend의 room 정보를 바꾸는지, room pool을 운영할 때 별도 관리 인스턴스가 필요한지 구체적으로 서술해 달라. workspace 첫 접근 세션 요청에서 pool의 어느 서버에 room을 만들지 파악하고 주소를 넘겨줘야 하는 점과 소유권 디렉터리의 구체적 실체를 포함해 달라.

## 답변 · 협업 서버 구성과 소유권 디렉터리

권장 구성은 backend와 협업 서버를 논리적으로 분리하는 것이다. 인프라 제어기가 협업 서버 프로세스들을 띄우고, backend에는 인증과 RoomAllocator 모듈을 둔다. 처음부터 단일 관리 인스턴스를 만들 필요는 없다. 여러 backend 복제본이 같은 공유 DB의 트랜잭션과 조건부 갱신을 사용해 경쟁을 조정하고, 관리 부하가 커질 때만 RoomAllocator를 별도 서비스로 분리한다.

소유권 디렉터리는 특별한 마법의 제품이 아니라 `collab_servers`, `room_ownership`, `room_updates`, `room_checkpoints` 같은 공유 DB 테이블과 그 갱신 규칙이다. 서버에는 논리 server_id와 프로세스 실행별 boot_id를 함께 기록한다. room에는 owner_server_id, owner_boot_id, epoch, state, lease_until, last_sequence를 둔다. epoch는 재할당 때 증가하며, 저장소가 현재 owner·boot_id·epoch를 검사해 이전 서버의 쓰기를 막는다.

첫 접근에서는 클라이언트가 backend에 route 요청을 보낸다. backend는 권한을 확인하고 room 소유권 행을 잠근 뒤 ready 상태이고 수용량이 남은 서버를 선택한다. 소유권을 `loading`으로 커밋한 뒤 선택된 협업 서버에 activate RPC를 보낸다. 서버가 체크포인트와 후속 로그를 복원하고 `ready`를 보고하면, backend는 짧은 수명의 문서별 티켓과 WSS 경로를 반환한다. 클라이언트는 그 주소로 새 WebSocket을 연다. 기존 소켓을 다른 서버로 넘기지 않는다.

본문 CRDT 변경은 협업 서버가 제한된 DB 쓰기 함수로 저장하고 참여자에게 전파한다. room 복원 완료·lease 연장·해제·이동 같은 수명 변화는 내부 API를 통해 보고한다. 본문 입력마다 backend의 room 메타데이터를 갱신하지 않는다. room 이동은 계획적으로 draining하고 새 epoch를 발급한 뒤 새 서버가 복원하며 클라이언트는 재접속한다.

장애 시 lease가 만료되면 RoomAllocator가 새 서버와 새 epoch를 할당한다. 늦게 돌아온 이전 서버는 저장소의 epoch 검사에서 거부된다. PostgreSQL의 행 잠금과 기본 키 충돌, 조건부 갱신으로 두 backend가 같은 room을 동시에 배치하지 않게 한다. heartbeat는 서버 선택용 생존 정보이고 lease는 특정 room의 권한이므로 분리한다.
