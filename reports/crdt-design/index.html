01 / DECISION

현재 정보에서 가장 균형 잡힌 기본안

무조건 가장 빠른 설계라는 뜻은 아니다. 문서 크기·편집 빈도·동시 접속·허용 지연이 아직 주어지지 않았으므로, 필요한 데이터만 로드하면서 복구 가능성과 운영 단순성을 확보하는 설계를 기본값으로 택했다. 성능 수치나 인스턴스 크기를 측정 없이 확정하지 않는다.

문서별 논리 room

workspace는 권한과 목록의 경계. 실제 협업 문서마다 room을 둔다. workspace 전체가 하나의 작은 문서라면 room도 하나다.

여러 room을 맡는 서버 풀

접속은 기존 서버의 room을 활성화한다. 전체 자원이 부족할 때 서버를 늘린다. room마다 컨테이너를 생성하지 않는다.

변경 로그 + 체크포인트

편집 중에 변경분을 영속화한다. 마지막 퇴장은 저장의 유일한 계기가 아니라 메모리 회수의 계기다.

선택한 연결 방식: 접속 API가 권한을 확인하고 담당 서버의 외부 WebSocket 주소와 짧은 수명의 접속 티켓을 반환한다. 클라이언트는 그 목적지에 새로 연결한다. 서버 교체 시에는 경로 재조회와 재동기화를 수행한다.

기본 전제는 사용자가 workspace 안의 일부 문서만 연다는 것이다. 모든 데이터를 함께 편집한다면 문서 하나로 시작하고, 한 문서 자체가 한계에 도달하기 전에는 내부 구역 분할을 도입하지 않는다. 엄격한 권한·소속 변경은 CRDT 본문과 분리한 서버 명령으로 처리한다.

디렉터리는 논리적인 역할이다. 처음부터 별도 서비스 여러 개로 분리할 필요는 없다. 초기 구현은 관계형 DB의 소유권 테이블과 변경 로그를 이용할 수 있다. 데이터 쓰기 시점에 소유권을 원자적으로 확인할 수 있어야 한다.

데이터 경로

본문 변경은 클라이언트와 담당 협업 서버 사이를 흐른다. 접속 API는 모든 편집 메시지를 중계하지 않으므로 중앙의 메시지 병목을 줄인다.

제어 경로

배치·권한·서버 준비 상태를 관리한다. 프로세스가 만들어졌다는 사실만으로 주소를 반환하지 않고, 연결을 수락할 준비가 됐는지 확인한다.

03 / LIFECYCLE

첫 접속, 편집, 퇴장, 장애를 같은 규칙으로 처리한다

    시나리오 상세는 아래 접속·저장·확장 설명에 포함된다. 대화형 시나리오는 HTML에서 확인할 수 있다.

    1목적지 결정권한 확인과 소유권 조회
    2필요한 문서 복원체크포인트 + 후속 로그
    3양방향 동기화서버·클라이언트의 빠진 변경 교환
    4편집 중 저장내구성 ACK와 화면 반응 구분
    5유예 후 해제세션과 처리 중 작업 재확인

    초기 동기화와 실시간 업데이트 구독 사이에 빈틈이 있으면 변경을 놓친다. room의 직렬 처리 구간에서 구독을 먼저 등록하고 초기 상태를 잡거나, 로그 커서 이후의 변경을 재생하는 방식으로 그 틈을 막는다. 서버 상태만 내려주는 단방향 로딩으로 끝내지 않고, 클라이언트에 남은 오프라인 변경도 합친다.

    04 / FIRST LOAD

    첫 방문을 빠르게 하는 것과, 재방문을 빠르게 하는 것은 다르다

    라우팅담당자 확인
    DB 읽기필요한 문서
    복원체크포인트 + 로그
    전송필요한 차이
    브라우저 적용동기화 상태 반영
    개념도이며 칸 너비는 측정된 시간 비율이 아니다. 전용 인스턴스를 접속 때 생성하면 별도의 시작 대기 시간이 추가된다.
    첫 방문
    열린 문서만 로드한다. 긴 로그는 체크포인트로 줄인다. 같은 room의 동시 접속은 하나의 복원 Promise를 공유한다. 복원 동시성에 상한을 두어 DB와 CPU를 보호한다.
    재방문
    로컬 캐시를 먼저 표시하고, 서버와 차이를 동기화한다. 로컬 표시를 최신 상태 또는 저장 완료로 표시하지 않는다. 캐시가 없는 첫 방문에는 이 이점이 없다.
    짧은 이탈
    세션이 0이 되어도 바로 폐기하지 않고 제한된 유예 시간 동안 유지한다. 유예 시간과 총 warm room 메모리 예산을 함께 두어 무제한 보관을 막는다.
    큰 문서
    전송 압축만 보지 말고 복원 CPU와 브라우저 메모리를 측정한다. 페이지·독립 문서 단위 분리를 먼저 검토하고 내부 구역 분할은 후순위로 둔다.

    Yjs의 상태 벡터 기반 교환은 상대에게 부족한 변경을 계산한다. 삭제 정보까지 포함하는 실제 동기화 프로토콜을 사용해야 하며, 상태 벡터가 같다는 이유만으로 모든 동기화를 생략하지 않는다. Yjs 업데이트 API

    DB JSON에서 매번 새 CRDT를 만들지 않는다. 본문 텍스트만 같아도 CRDT 식별·인과 정보가 달라질 수 있다. 기존 클라이언트와 이어서 동기화하려면 복원 가능한 CRDT 상태를 보존한다.
    05 / DURABILITY

    “보였다”와 “저장됐다”를 분리한다

    권장 기본값은 로컬 즉시 반응 → 서버 검증 → 변경 로그 커밋 → 서버 반영·전파 → 저장 ACK다. 다른 참여자에게 보이는 시점에는 저장 지연이 포함된다. 측정 결과 이 지연이 문제가 되면 전파를 먼저 할 수 있지만, 그때는 전파된 변경도 아직 미저장 상태일 수 있다.

    변경 로그

    roomId, sequence, updateId, payload를 저장한다. 같은 updateId 재전송은 같은 결과로 처리하고 내용이 다르면 거부한다. ACK 전에 연결이 끊겨도 미확인 변경을 다시 보낼 수 있다.

    체크포인트

    room의 직렬 처리 구간에서 상태 바이트와 포함된 로그 위치 N을 함께 잡는다. 체크포인트를 내구성 있게 확정한 뒤에만 N 이하의 로그를 정리한다. 복구는 체크포인트 + N 이후 로그다.

    세 가지 다른 번호: sequence는 저장 로그의 위치, epoch는 담당 서버의 세대, CRDT state vector는 복제 상태다. 서로 대신 사용할 수 없다.

    기본 저장소는 내구성 커밋이 가능한 관계형 DB로 시작할 수 있다. 복제 설정과 장애 범위에 따라 ACK의 보장 범위가 달라지므로 “저장 완료”의 의미를 배포 설정과 일치시킨다. 로그 쓰기가 병목이면 짧은 묶음 커밋을 측정하되, 묶음이 커밋되기 전에 ACK하지 않는다.

    커서·접속자 표시 같은 presence는 별도 휘발성 채널로 다룬다. 필요 이상의 움직임은 합쳐 보내거나 버릴 수 있지만, 본문 변경은 조용히 버리지 않는다. 느린 소비자의 송신 큐는 상한을 두고 재동기화로 복구한다.

    06 / SCALE & OWNERSHIP

    room은 늘리고, 실행 자원은 묶어서 관리한다

    일반 room

    한 프로세스가 여러 room의 상태와 연결을 관리한다. 문서별 작업 큐로 수명 전환과 저장 순서를 명확히 한다. 접속 수뿐 아니라 메모리·이벤트 루프 지연·전파 바이트·복원 큐를 보고 배치한다.

    뜨거운 room

    다른 서버로 옮겨 이웃 room에 미치는 영향을 줄인다. 그래도 단일 room 한계를 넘으면 구독 범위 축소나 문서 내부 분할을 검토한다. 서버 수 증가만으로 단일 room이 자동 병렬화되지는 않는다.

    worker thread는 CRDT 복원·인코딩 등 CPU 작업이 실제 병목일 때 풀로 도입한다. 일반 비동기 I/O를 위해 room마다 thread를 만들지는 않는다. Node.js worker threads

    1장애 감지소켓 종료·임대 만료
    2새 세대 할당원자적 소유권 갱신
    3이전 쓰기 차단저장소가 epoch 검사
    4복원커밋된 변경 재생
    5재접속미확인 변경 재전송

    임대는 장애 판단에, epoch는 뒤늦게 돌아온 이전 서버의 쓰기 차단에 사용한다. 갱신을 못 한 서버는 편집 수락을 중단해야 한다. 새 소유권 부여와 로그 추가가 서로 모순되게 통과하지 않도록 같은 직렬화 규칙으로 검사한다. CRDT의 수렴 성질만으로 저장소의 오래된 쓰기를 막을 수는 없다.

    직접 연결의 대가는 서버 교체 시 재접속이다. 연결 주소는 공개 TLS endpoint이며 내부 IP를 반환하지 않는다. 티켓은 문서·권한·만료에 묶고 연결 서버에서도 재검증한다. 권한이 철회되면 활성 세션에도 반영한다. 서버 준비가 늦거나 경로가 오래됐다면 제한된 재시도와 무작위 지연으로 경로를 다시 조회한다.

    07 / YOUR IDEA → RECOMMENDED DESIGN

    원안에서 무엇을 살렸고, 무엇을 바꿨는가

    원안의 핵심인 room으로 상태를 모으고 활성 세션에 맞춰 자원을 사용한다는 방향은 유지했다. 바뀐 부분은 room의 크기, 저장 시점, 실행 자원의 배치, 연결의 시작 순서다. “불가능”과 “구현 가능하지만 채택하지 않음”을 구분한다.

    사용자의 아이디어판정권장안의 반영 방식이유와 적용 조건
    workspace 단위 room조건부 적용 · 보완workspace는 권한·목록의 경계로 유지. 본문은 협업 문서별 room.안 여는 문서까지 복원하지 않기 위해서다. workspace 자체가 작은 단일 문서면 원안 그대로 room 하나로 적용한다.
    socket과 CRDT로 소통적용WebSocket으로 전달하고 CRDT로 병합한다.전송과 병합의 역할이 맞다. 재접속·영속화·권한 검사는 추가로 필요하다.
    첫 세션에서 DB 로드적용 · 보완콜드 room의 첫 요청이 필요한 문서만 복원. 동시 요청은 복원 작업 공유.지연을 완전히 없앨 수는 없다. 체크포인트와 짧은 로그, 제한된 미리 로드로 실제 대기량을 줄인다.
    마지막 세션 종료 시 DB 저장유일한 저장 시점으로 미채택접속 중 변경 로그 저장. 퇴장 시 필요하면 체크포인트 후 유예 해제.구현 자체는 가능하다. 그러나 비정상 종료 시 이벤트가 실행되지 않고 장기 접속 중 손실 범위가 커져, 복구 가능한 편집 서비스의 저장 정책으로는 부족하다.
    여러 workspace·세션에 대비한 분산적용room을 여러 서버에 배치하고 전체 부하로 서버 풀 확장.단일 서버의 CPU·메모리·네트워크 한계에 대응한다. 실제 병목은 세션 수만으로 결정되지 않는다.
    room마다 worker 생성논리 단위 적용 · 자원 단위 보완room 객체와 작업 큐는 독립. 프로세스·컨테이너·thread는 여러 room이 공유.room마다 인스턴스 생성은 가능하지만 시작 지연과 자원 낭비가 생긴다. 큰 room의 전용 격리는 측정 후 적용할 수 있다.
    백엔드가 인스턴스 생성 요청확장 제어로 보완접속 API는 기존 담당자를 할당. 용량 부족 시 확장 관리자가 서버를 추가.접속 경로에서 매번 인스턴스 준비를 기다리지 않게 한다. scale-to-zero를 택하면 콜드 시작 대기를 받아들여야 한다.
    열린 소켓을 새 worker에 인계하기 어렵다문제 인식 적용목적지를 먼저 찾은 뒤 처음부터 담당 서버에 연결. 이동 시 재접속.일반 WebSocket/브라우저 API로 다른 호스트의 서버에 기존 연결을 투명하게 넘기는 것은 기본 제공되지 않는다.
    기존 연결을 다른 호스트로 그대로 이전일반 구성에서 적용 불가이 설계에서는 연결 이전을 요구하지 않는다.특수 런타임·네트워크 계층은 별도다. 같은 호스트의 소켓 핸들 전달도 일반적인 서버 간 이전과 다르다. 외부 연결 유지가 필요하면 메시지 게이트웨이가 대신 중계해야 한다.
    원안에 대한 핵심 평가: room을 중심으로 생각한 것은 그대로 유효하다. 다만 room의 활성화와 인스턴스 생성, 세션 종료와 데이터 영속화를 각각 분리해야 지연·확장·복구를 함께 다룰 수 있다.

    코드보다 먼저 고정할 계약

    다음은 핵심 순서를 드러내는 TypeScript 의사코드다. 실제 DB·provider·오류 복구 구현을 생략했으며, 실행 가능한 완성 서버 코드는 아니다.

    async function receive(room, session, message) {
  return room.queue.run(async () => {
    await authorize(session, room.id);
    await validateBoundedUpdate(message); // 형식·크기·자원 상한

    const row = await storage.appendIfCurrentOwner({
      roomId: room.id,
      epoch: room.epoch,
      updateId: message.id,
      payload: message.bytes,
    }); // 원자적 소유권 검사 + 중복 확인 + 내구성 커밋

    try {
      Y.applyUpdate(room.doc, row.payload, "remote");
    } catch (error) {
      await room.stopAndRecover(error);
      throw error; // 저장 성공 뒤 적용 실패를 숨기지 않는다
    }
    // checkpoint 경계는 실제 적용한 연속 로그 위치로 관리한다.
    room.markApplied(row.sequence);
    room.broadcast(row.payload);
    session.ack(message.id); // 저장소 커밋 이후에만
  });
}

    직렬 작업 큐를 쓰더라도 입구의 큐 길이와 바이트 수에 상한을 둔다. 악성·비정상 업데이트를 저장한 뒤에야 발견하지 않도록 디코딩 및 자원 제한을 먼저 적용한다. 업무 의미의 유효성까지 필요하면 임의 CRDT 업데이트에 기대지 말고 서버 명령 경로를 둔다.

    복원과 체크포인트

    읽기 도중 로그 정리가 일어나도 복구 묶음이 일관돼야 한다. 체크포인트의 N은 연속적으로 반영된 로그 위치이며, 중복 재전송에서 받은 오래된 sequence로 되돌리지 않는다. 일반 JSON 변환은 복구 형식을 대신하지 않는다.

    로컬 변경의 보존

    전송 대기 변경은 ACK까지 로컬에 보관한다. 새로고침을 견뎌야 하면 내구성 있는 로컬 저장소를 사용한다. 재인증에 실패한 편집은 서버에 확정된 것으로 표시하지 않는다.

    현재는 도입하지 않는 선택지

    바이너리 중계 전용 서버는 내용 해석이 필요 없고 복원 CPU가 병목일 때 검토한다. Yjs의 바이너리 병합은 삭제 정보의 GC를 대신하지 않는다. 다중 문서를 한 소켓에 태우는 게이트웨이는 동시 구독 수가 많아졌을 때 검토한다. 두 선택 모두 초기 구현의 필수 요소는 아니다. 업데이트 처리의 범위
