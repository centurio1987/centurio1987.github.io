01 · 권장안: 원본 + 재생성 가능한 집계

기본안은 원본 DB, 비동기 집계 작업자, 조회 API, 대용량 내보내기 작업자다. 처음부터 모두 별도 서버로 배포할 필요는 없다. 집계는 DB의 버킷 요약으로 시작하고, 긴 범위의 읽기 비용이 확인되면 계층 요약을 추가한다.

전제: 집계에 짧은 지연을 허용하고, 원본은 정확하게 보존한다. 지연 허용치는 아직 합의되지 않았다. 즉시 일치가 필수면 03의 동기 경로를 선택한다. 부하·데이터 크기 실측이 없으므로 이 가이드는 절대적인 최적해가 아니라 검증 가능한 출발점이다.

원본 조회를 집계 트리로 우회시키지 않는다. sum·count·max는 원본의 전체 필드를 보존하지 않으며, K개 레코드를 반환하는 작업은 적어도 K개의 출력이 필요하다. 여러 불연속 범위를 하나로 합쳐 집계한다면 먼저 겹치는 구간을 합쳐 중복 계산을 막는다.

02 · 데이터의 기준을 먼저 고정한다

조회 범위는 UTC 기준 [begin,end)로 정한다. 하루·월 같은 달력 버킷은 업무 시간대와 일광절약시간 규칙을 별도로 명시한다. 같은 일시에 여러 행이 있을 수 있으므로 정렬 키에 ID를 붙인다.

events
  series_id, event_id, occurred_at, value, payload, revision
  PRIMARY KEY (series_id, event_id)
  INDEX (series_id, occurred_at, event_id)

aggregate_nodes
  series_id, partition_id, level, slot
  sum, count, max
  PRIMARY KEY (series_id, partition_id, level, slot)

outbox
  change_id, series_id, event_id, revision, before, after

projection_checkpoint
  partition_id, applied_position

count는 행 개수이며 distinct count가 아니다. 값이 NULL일 때 sum·max에서 제외할지, count에 포함할지 계약으로 정한다. 평균은 평균끼리 더하지 않고 sum / non_null_count로 계산한다. 금액은 decimal 또는 최소 화폐 단위 정수를 쓰고, sum의 오버플로 범위를 정한다.

시계열 외에 고객·상품·지역 필터를 지원한다면 그 차원도 집계 키에 포함돼야 한다. 버려진 차원을 조회 시 되살릴 수 없다. 모든 차원 조합을 사전 계산하면 저장량이 폭증하므로 자주 쓰는 조합만 요약하고 나머지는 원본/분석 엔진으로 보낸다.

03 · 변경은 한 번 기록하고, 재전달에 견디게 한다

원본 저장 성공 후 메시지 전송이 실패하는 틈을 없애기 위해 원본과 outbox를 같은 트랜잭션에 기록한다. 전달은 중복될 수 있다. 작업자는 상태 변경과 처리 위치 저장을 같은 트랜잭션에 묶어 재시도해도 합계가 두 번 증가하지 않게 한다.

// 개념 의사코드: 실제 DB의 잠금·재시도 구현 필요
transaction {
  old = lockEvent(series, id)
  next = applyCommand(old, command)
  saveEvent(next)
  appendOutbox(uniqueChangeId, old, next)
}

// 파티션별 순서가 보장되는 소비 경로
transaction {
  checkpoint = lockCheckpoint(partition)
  if (alreadyApplied(change.position, checkpoint)) return
  applyProjection(change.before, change.after)
  saveCheckpoint(change.position)
}

revision만 보고 중간 변경을 건너뛰면서 차분을 적용하면 합계가 틀릴 수 있다. 순서대로 적용하거나, 최신 원본으로 해당 버킷 전체를 다시 계산하는 전략을 선택한다. 이벤트 시간과 전달 순서는 다르다. 단순한 event time은 변경 체크포인트가 아니다.

원본은 최신인데 집계는 아직 과거인 상태를 숨기지 않는다. 집계 응답에 projectionVersion 또는 파티션별 체크포인트와 생성 시각을 싣는다. 여러 파티션에 임의의 단일 숫자를 붙여 전역 일관성을 주장하지 않는다.

쓰기 직후 읽기 일치가 필요하면 쓰기 응답의 토큰까지 집계가 따라올 때 제한 시간 동안 기다린다. 시간 초과 시 원본 SQL로 계산하거나 명시적인 미반영 응답을 준다. 동일 시점의 원본과 집계가 모두 필요하면 동기 트랜잭션 또는 원본의 과거 버전 조회까지 설계해야 한다.

04 · 구간 구조는 하나, 집계 상태는 묶어서

각 노드는 (sum,count,max)를 갖는다. 연산별 트리 세 개를 만들기보다 탐색 구조와 병합 규칙을 분리한다. 동일한 데이터·경계·갱신 주기를 공유한다면 한 번 읽어 세 값을 계산할 수 있다.

type Stats = { sum: bigint; count: bigint; max: number | null };
const empty = (): Stats => ({ sum: 0n, count: 0n, max: null });
function merge(a: Stats, b: Stats): Stats {
  return {
    sum: a.sum + b.sum,
    count: a.count + b.count,
    max: a.max === null ? b.max :
         b.max === null ? a.max : Math.max(a.max, b.max)
  };
}

위 타입은 정수 집계 예제다. sum·count의 BigInt는 JSON 응답에서 문자열 등으로 명시적으로 변환한다. max 값은 JavaScript의 안전 정수 범위라고 가정한다.

DB 왕복 없이 필요한 노드 키를 계산하기

// 정렬된 고정 리프 슬롯 [l,r)을 2의 거듭제곱 구간으로 분해
function cover(l: number, r: number, size: number): number[] {
  const ids: number[] = [];
  for (l += size, r += size; l < r; l = Math.floor(l/2), r = Math.floor(r/2)) {
    if (l % 2) ids.push(l++);
    if (r % 2) ids.push(--r);
  }
  return ids;
}
// 0 ≤ l ≤ r ≤ size, size는 2의 거듭제곱. 입력 검증은 호출부 책임.
const ids = cover(1, 7, 8);
const states = await readNodesInOneSnapshot(ids);
const answer = states.reduce(merge, empty());

size·슬롯 매핑·파티션 버전을 조회 동안 고정한다. DB 노드를 포인터처럼 하나씩 따라가거나 트리 전체를 매 요청 복원하지 않는다. 고정 슬롯의 단일 구간은 O(log N)개 요약을 선택하지만, DB 페이지 읽기·여러 파티션 병합 비용은 별도다.

분 단위 리프에 12:00:30 경계가 들어오면 분 전체 요약은 정확하지 않다. 완전히 포함되는 내부 구간만 요약으로 읽고, 양 끝의 불완전한 버킷은 원본으로 계산한다. 겹치지 않는 세 영역을 같은 기준 시점에서 병합한다.

05 · 삭제는 최대값의 약점을 드러낸다

한 버킷에 여러 행이 있다면 리프를 빈 상태로 만드는 것으로 끝나지 않는다. 최대였던 행이 삭제됐을 때 버킷의 남은 원본을 재집계하거나, 값 정렬 인덱스에서 다음 최대값을 찾는다. 실제 갱신 비용은 리프 상태 복구 + 조상 갱신이다.

일시 자체가 바뀌면 이전 버킷에서 빼고 새 버킷에 넣는다. 두 버킷과 상위 요약을 함께 확정하거나, 비동기 투영의 불완전한 중간 상태가 노출되지 않도록 게시 단위를 둔다. 원본 삭제를 로그·내보내기 파일 보존 정책에도 어떻게 적용할지 정한다.

모든 쓰기가 같은 루트를 잠그면 경합이 커진다. 시계열·시간 파티션으로 나누고 짧은 배치에서 중복된 조상 갱신을 묶는다. 초고빈도 쓰기에서는 단순 버킷 집계가 정교한 트리보다 유리할 수 있다.

06 · 수정이 없다면 과거를 확정한다

시간순 추가만 발생하는 확정 구간에서는 누적합 두 개를 빼서 범위 합계를 얻는다. max는 차분이 불가능하므로 계층 요약을 유지한다. 누적합의 O(1)은 경계 위치를 이미 알고 있는 메모리 접근 기준이며 DB의 경계 검색 비용까지 없애지는 않는다.

values = [3, 1, 4, 9, 2, 6, 5, 8]
prefix = [0, 3, 4, 8, 17, 19, 25, 30, 38]
sum(1, 7) = prefix[7] - prefix[1] = 27

늦은 이벤트가 들어올 수 있는 동안은 버킷이 확정되지 않았다. 업무상 마감 규칙을 정하고, 마감 뒤 정정은 새 버전으로 재작성한다. “과거는 불변”을 단순한 시간 경과로 가정하지 않는다. 확정된 과거는 압축 파일·요약·캐시를 함께 버전별로 재사용할 수 있다.

07 · 전체 데이터는 커서와 스냅샷으로 읽는다

SELECT occurred_at, event_id, value, payload
FROM events
WHERE series_id = :series
  AND occurred_at >= :begin AND occurred_at < :end
  AND (occurred_at, event_id) > (:last_time, :last_id)
ORDER BY occurred_at, event_id
LIMIT :page_size;

첫 페이지는 마지막 커서 조건을 생략한다. 커서는 범위·필터·정렬·권한 맥락과 결합하고 변조를 막는다. OFFSET이 커질수록 앞부분을 건너뛰는 비용이 쌓이는 패턴을 피한다. 전체 범위 대량 읽기에서는 DB가 순차 스캔을 선택할 수도 있으므로 인덱스를 강제하지 않는다.

커서 페이지네이션은 스냅샷이 아니다. 페이지 사이에 행의 시간 키가 이동하거나 삭제되면 결과가 달라진다. 화면 탐색은 최신 상태를 허용할 수 있지만, 완전한 내보내기는 같은 DB 스냅샷에서 읽거나 원본 이력/고정 파일 버전을 사용한다.

장시간 DB 스냅샷은 버전 정리와 연결 점유에 영향을 준다. HTTP 연결을 오래 붙잡기보다 내보내기 작업이 스냅샷을 읽어 임시 파일을 완성하고, 검증된 파일만 공개하는 경로를 기본으로 둔다. 실패 후 같은 스냅샷을 복구할 수 없다면 새 작업으로 시작한다.

08 · 대용량은 비동기 파일, 중간 크기는 압축 스트림

사용 목적응답 전략지켜야 할 의미
집계 숫자작은 JSON집계 반영 시점 표시
목록 탐색커서 페이지정렬·필터 고정
중간 크기 원본압축 NDJSON 스트림부분 파싱·취소·완료 표식
대량 전체 내보내기비동기 파일고정 스냅샷·행 수·체크섬
차트해상도에 맞는 버킷전체 데이터 API와 구분

“중간”과 “대량”은 임의의 MB 경계로 고정하지 않는다. 실측한 생성 시간·요청 제한 시간·동시 다운로드 수·메모리 예산으로 결정한다. 전체 데이터를 요청한 사용자에게 다운샘플링을 몰래 적용하면 요구사항을 위반한다.

// Node.js 예제의 핵심 흐름: rows는 제한된 DB 커서
await pipeline(
  Readable.from(encodeNDJSON(rows), { objectMode: false }),
  createGzip(),
  response,
  { signal }
);

사용자의 Accept-Encoding을 협상하고 Content-Encoding·Vary를 설정한다. 소비자가 느려지면 읽기도 느려져야 한다. 연결 종료는 DB 취소까지 전달하고 커서는 finally에서 닫는다. gzip은 매 행마다 새로 만들지 않으며, flush 주기는 첫 결과 지연과 압축률을 함께 측정해 정한다. 중간 프록시의 버퍼링도 확인한다.

NDJSON은 레코드 경계가 줄바꿈일 뿐 네트워크 청크가 한 줄이라는 뜻이 아니다. 클라이언트는 UTF-8 증분 디코더와 미완성 줄 버퍼를 사용한다. 스트림 마지막에 완료 레코드와 행 수를 보내고, 그것이 없으면 성공한 전체 결과로 취급하지 않는다. 파일은 완료 이후 ready로 게시하고 체크섬·행 수·스냅샷 식별자를 제공한다.

가상 산술 예: 100만 행 × 직렬화 후 평균 500바이트 = 약 500MB. 압축 후 25%라고 가정하면 약 125MB이며, 실효 10MB/s 회선에서는 전송만 약 12.5초다. 압축률·속도는 예시 가정이며 벤치마크 결과가 아니다.

09 · 쿼리 서버 분리는 병목에 맞춰 한다

원본 DB가 느린데 중계 서버만 늘리면 DB 요청도 늘어난다. 반대로 자주 읽는 집계 상태가 메모리에 상주하거나 파티션 병합 CPU가 크면 별도 쿼리 서버의 가치가 생긴다. 압축이 병목이면 집계 서버보다 내보내기 작업자를 먼저 분리한다.

DB 네이티브 집계를 지원하는 분석 엔진도 후보지만, 쓰기 트리거형 사전 집계가 원본의 모든 UPDATE·DELETE를 자동으로 되돌린다고 가정하지 않는다. 제품별 정정 의미를 확인하고 SQL 기준 결과와 비교한다.

캐시와 복구를 함께 설계한다

캐시 키는 시계열·범위·필터·집계 종류·투영 버전을 포함한다. 같은 요청은 합쳐 처리하고 메모리 상한을 둔다. 시간만 지난다고 최신이 된다고 보지 않는다. 투영은 원본 스냅샷에서 새 세대로 재구축하고, 그 스냅샷과 연결된 변경 로그 위치 이후를 재생한다. 따라잡은 뒤 읽기 포인터를 원자적으로 바꾼다.

스냅샷과 로그 시작 위치 사이에 누락 구간이 있으면 복구가 틀린다. 재구축 중에도 필요한 로그가 보존되도록 하고, 파티션별 체크포인트를 저장한다. 원본의 물리 삭제로 재구축할 수 없는 정보가 필요한지 보존 정책과 함께 확인한다.

10 · 도입 순서와 통과 기준

  1. 정확성: 무작위 범위·경계·빈 결과를 원본 SQL과 대조한다. 중복 전달·순서 문제·수정·삭제·일시 이동·늦은 입력을 포함한다.
  2. 장애: 원본 커밋 직후, 집계 적용 도중, 체크포인트 저장 전후를 중단시켜 유실·중복을 검사한다.
  3. 일관성: 변경 중인 여러 노드를 읽어도 하나의 투영 스냅샷인지 확인한다. 비동기 집계와 최신 원본의 차이를 API가 드러내는지 본다.
  4. 성능: 짧은/긴 범위, 낮은/높은 결과 수, 동시 읽기·쓰기에서 p50/p95/p99, 읽은 행·바이트, 잠금 대기, 투영 지연을 잰다.
  5. 전송: 느린 클라이언트·취소·프록시 경로에서 메모리 상한, DB 커서 해제, 부분 결과 실패 판정을 검사한다.
  6. 운영: 재구축 소요 시간·로그 보존량·내보내기 만료·사용자별 동시 작업 제한을 정한다.

목표 지연·허용 투영 지연·처리량은 실제 요구사항을 받은 뒤 수치화한다. 검증 기준을 만족하는 가장 단순한 단계에서 멈춘다. 이 설계가 줄이는 읽기 비용보다 쓰기·운영 비용이 더 커지면 계층 트리를 도입하지 않는 것이 올바른 결과다.

설계 근거와 추가 확인
  • PostgreSQL — 정렬 인덱스와 LIMIT
  • PostgreSQL — 트랜잭션 스냅샷과 격리
  • ClickHouse — 병합 가능한 집계 상태
  • Node.js — 스트림·pipeline·백프레셔
  • Node.js — 압축 스트림

폭신 대담 진행 중 작성한 설계 가이드. 최종 대담 포스트와 별개의 보조 문서다. 도식 8개는 프로젝트의 bbangto-ui viz 컴포넌트와 블로그 스타일 가이드로 생성했다. HTML에 도식과 스타일을 포함해 외부 스크립트 없이 읽을 수 있다.
