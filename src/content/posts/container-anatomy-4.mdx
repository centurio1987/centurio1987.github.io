"도커 대신 뭘 쓰는 게 좋을까요?"

이 질문에는 답할 수가 없습니다. 무례해서가 아니라 **정보가 빠져 있어서**입니다. 이렇게 되물어야 해요 — **"도커의 어느 부분을 바꾸시려고요?"**

지난 세 편에서 우리는 "도커"가 단일 프로그램이 아니라 층층이 쌓인 조립품이라는 걸 봤습니다. 그렇다면 대안도 층마다 따로 있는 게 당연합니다.

```text
 Podman   은 엔진을 바꾸고
 crun     은 저수준 런타임을 바꾸고
 gVisor   는 격리 모델을 바꾸고
 Buildah  는 빌드 도구를 바꾼다
```

넷은 경쟁 관계가 아닙니다. **서로 다른 층에 있고, 실제로 동시에 쓸 수도 있습니다.** Podman으로 Buildah를 불러 이미지를 만들고 crun으로 실행하는 조합이 그냥 성립해요.

이 마지막 편에서는 층별로 선택지를 갈라 보고, 상황에 따라 무엇을 고르면 되는지까지 정리하겠습니다. 그리고 **지금은 고르면 안 되는 것** 하나도 짚고 가겠습니다.

## 먼저 지도를 다시 그립니다

EP1~EP3에서 본 것을 "바꿀 수 있는 자리" 관점으로 다시 그리면 이렇습니다.

```text
 ┌─ 빌드 도구 ──────────  이미지를 만든다
 │     BuildKit · Buildah · (Kaniko)
 │
 ├─ 사람이 쓰는 엔진 ───  손으로 부린다
 │     Docker · Podman
 │
 ├─ 쿠버네티스 런타임 ──  kubelet 이 CRI 로 부린다
 │     containerd · CRI-O
 │
 ├─ 저수준 런타임 ─────  실제로 컨테이너를 세운다
 │     runc · crun · youki
 │
 └─ 격리 모델 ─────────  얼마나 단단히 가둘 것인가
       namespace/cgroup · gVisor · Kata
```

두 번째와 세 번째 층을 나눈 게 보이시나요? 흔히 "컨테이너 엔진"으로 뭉뚱그리지만 **쓰는 주체가 다릅니다.** Docker·Podman은 사람이 터미널에서 부리는 도구고, containerd·CRI-O는 kubelet이 CRI로 부리는 부품입니다. 이 구분을 안 하면 뒤에 나올 "CRI-O로 로컬 개발하면 되나?" 같은 질문에서 길을 잃습니다.

(EP1에서 본 대로 **Docker도 안쪽에서 containerd를 씁니다.** 층이 겹치는 게 아니라, 사람이 쓰는 엔진이 그 아래 런타임을 품고 있는 구조예요.)

그리고 층 사이를 이어 주는 게 표준입니다 — EP2의 **OCI(Open Container Initiative)** 런타임 스펙 덕에 저수준 런타임을 갈아 끼워도 위층이 그대로고, EP3의 **CRI(Container Runtime Interface)** 덕에 쿠버네티스 런타임을 바꿔도 kubelet이 그대로입니다.

다만 정확히 해 두면, **모든 층이 표준으로 맞물린 건 아닙니다.** 격리 모델(gVisor·Kata)은 독립된 표준 층이라기보다 **OCI 런타임이나 shim 자리에 끼어드는 구현**이고, 빌드 도구는 서로 교체되는 규격이 있다기보다 **결과물이 같은 이미지 포맷**일 뿐입니다. 그래도 "바꿔 끼울 수 있다"는 결론은 같습니다.

> 기억법: **뭘 바꿀지 정하려면, 먼저 어느 층인지부터 정한다.**

이제 층별로 하나씩 열어 보겠습니다. **위 지도의 아래쪽부터 거꾸로 올라갑니다** — 아래층이 위층의 전제라서, 밑에서부터 쌓는 편이 이해가 빠릅니다. 그래서 여기서 말하는 "1층"은 지도의 맨 아래(저수준 런타임)입니다.

## 1층 — 저수준 런타임: runc를 뭘로 바꾸나

가장 아래부터 갑니다. EP2에서 본 그 자리 — 번들을 받아 `create`/`start`/`kill`/`delete`/`state`를 구현하는 프로그램입니다.

| 런타임 | 언어 | 성격 | 버전(2026-07-27) |
| --- | --- | --- | --- |
| **runc** | Go | OCI 참조 구현. Docker가 기증한 원본 | v1.5.1 |
| **crun** | C | containers 조직(Podman·CRI-O 계열) | 1.28 |
| **youki** | Rust | runc **드롭인 대체**를 지향 | v0.7.0 |

셋 다 **같은 OCI 런타임 스펙을 구현**합니다. 그래서 위층이 바뀔 필요가 없어요. 언어가 다르다는 게 왜 의미가 있냐면, 컨테이너 하나 띄울 때마다 이 프로그램이 새로 실행되기 때문입니다. 시작 비용과 메모리 사용량이 곱해집니다.

다만 **언어만 보고 고르시면 안 됩니다.** "C라서 가볍다", "Rust라서 안전하다"는 출발점일 뿐이고, 실제로 봐야 할 건 따로 있습니다.

```text
 · cgroup v2 와 systemd 드라이버 지원 성숙도   (EP3 의 그 함정)
 · rootless 지원 수준
 · seccomp · AppArmor · SELinux 연동
 · 쓰는 배포판이 패키지로 제공하는가
 · CVE 가 나왔을 때 대응이 빠른가
```

특히 마지막 둘이 실무에서 큽니다. 배포판 패키지로 안 오면 직접 빌드·배포·업데이트를 떠안아야 하거든요. Docker 문서도 youki를 소개하며 성능·메모리 이점을 **"주장한다(claims)"**는 표현으로 적습니다 — 검증된 수치가 아니라 프로젝트의 주장이라는 뜻이죠.

### 도커에서 실제로 바꿔 끼우기

방법이 두 가지인데, EP1의 shim 이야기가 여기서 되돌아옵니다.

**① containerd shim API를 구현한 런타임** — 데몬 설정 없이 바로 지정합니다.

```bash
docker run --runtime io.containerd.kata.v2 hello-world
```

EP1에서 배운 이름 규칙 기억하시나요? 점을 하이픈으로 바꾸고 마지막 두 요소를 취해 `containerd-shim-`을 붙이면 `containerd-shim-kata-v2`. 도커가 그 바이너리를 찾습니다.

**② runc 드롭인 대체 런타임** — `/etc/docker/daemon.json`에 등록합니다.

```json
{
  "runtimes": {
    "youki": { "path": "/usr/local/bin/youki" }
  }
}
```

두 방법이 갈리는 이유가 뭘까요? **끼어드는 자리가 다르기 때문**입니다. ①은 shim 자리를 통째로 바꾸는 것이고, ②는 shim은 그대로 두고 **그 아래 저수준 런타임만** 바꾸는 겁니다.

```text
 ① shim 자리 교체        containerd → [다른 shim] → 그 shim 이 알아서
 ② 저수준 런타임 교체     containerd → containerd-shim-runc-v2 → [youki]
```

Kata가 ①로 들어가는 이유가 여기 있습니다. VM을 띄우는 일은 "번들 받아서 프로세스 만들기"와 성격이 아예 달라서, runc 자리에 그대로 꽂을 수가 없어요. 그래서 shim 층부터 자기 것으로 바꿔 끼웁니다. 반면 crun·youki는 runc와 **하는 일이 같으니** ② 자리에 그대로 들어갑니다.

## 2층 — 엔진과 쿠버네티스 런타임: 데몬을 없앤다는 것

### Podman

Podman의 소개 문구는 **데몬리스(daemonless)**입니다. 상주 데몬 없이 **명령마다 프로세스를 fork/exec**하는 모델이죠.

EP1의 그림과 비교하면 차이가 선명합니다.

```text
[Docker]
  docker CLI ──REST──▶ dockerd (상주 데몬, 보통 root)
                          └─▶ containerd ─▶ shim ─▶ runc

[Podman]
  podman  ──직접 fork/exec──▶ conmon ─▶ runc/crun
     └─ 명령을 받아 줄 상주 데몬이 없다
```

여기서 딸려오는 것들이 있습니다.

- **유휴 자원이 낮습니다.** 아무것도 안 돌 때 상주하는 관리 데몬이 없으니까요.
- **rootless가 기본입니다.** 공식 문서 표현으로 **"setuid 바이너리를 요구하지 않고 일반 사용자로 실행"**할 수 있고, **"실행하는 사용자가 갖지 않은 권한은 전혀 없는 잠긴 컨테이너"**를 돌립니다. user namespace로 자기 권한 수준에 가두는 방식이에요.
- **파드를 압니다.** 이름 자체가 POD MANager예요. 로컬에서 파드 단위로 묶어 볼 수 있습니다.
- **conmon**이 컨테이너를 감시합니다. EP1의 shim과 같은 자리의 역할이고, **CRI-O도 같은 conmon을 씁니다.**

전환 비용도 낮은 편입니다. Docker 문법 CLI를 제공하고, **Docker 호환 REST API**까지 갖췄습니다.

### 다만 "데몬리스"를 오해하면 안 됩니다

여기가 헷갈리기 쉬운 포인트입니다. **데몬리스는 "프로세스가 전혀 상주하지 않는다"는 뜻이 아닙니다.**

- 컨테이너가 도는 동안에는 **`conmon`이 그 옆에 상주**합니다. 누군가는 로그와 종료 코드를 챙겨야 하니까요. EP1에서 shim이 하던 그 일입니다.
- **Docker 호환 REST API를 쓰려면** `podman.sock`을 여는 서비스를 띄워야 합니다. Docker socket을 전제로 만들어진 도구를 붙이는 순간, 결국 **상주 프로세스가 하나 생깁니다.**

없어진 건 **"모든 명령을 중앙에서 받아 처리하는 root 데몬"**이지 프로세스 전부가 아닙니다.

그리고 데몬이 없다는 건 **중앙에서 상태를 관리해 주는 주체도 없다**는 뜻입니다. 부팅 시 자동 시작 같은 건 systemd에 맡겨야 하고(그래서 Podman이 systemd 연동을 강조합니다), 도커 데몬을 전제로 만들어진 도구들 — Compose, 테스트 라이브러리, IDE 연동, CI 플러그인 — 과의 호환은 **각각 확인이 필요합니다.** "API가 호환된다"와 "내가 쓰는 그 도구가 그대로 돈다"는 다른 이야기예요.

트레이드오프지 우열이 아닙니다.

### CRI-O

CRI-O는 성격이 다릅니다. **범용 엔진이 아니라 쿠버네티스 전용**이에요.

EP3에서 봤듯 "OCI 호환 런타임을 쓸 수 있게 하는 CRI 구현"이고, **버전을 쿠버네티스에 맞춥니다**(2026-07-27 기준 v1.36.2). 구성 부품도 목적이 뚜렷합니다.

```text
 CRI-O
   ├─ conmon            컨테이너 감시 · 로깅 · OOM 감지
   ├─ runc(기본)/Kata   OCI 런타임
   ├─ CNI               파드 네트워킹 (Container Network Interface)
   ├─ containers/storage  레이어와 rootfs
   └─ containers/image    레지스트리에서 이미지 pull
```

**로컬 개발용으로 CRI-O를 고르는 건 잘못된 선택입니다.** 사람이 손으로 쓰라고 만든 물건이 아니에요. `docker run` 같은 UX를 기대하시면 안 됩니다.

## 3층 — 격리 모델: 커널을 어떻게 할 것인가

여기가 이 편에서 가장 재미있는 층입니다. EP1의 마지막 문장 — "컨테이너는 커널을 공유한다"는 것 — 을 정면으로 건드리기 때문입니다.

커널 공유는 성능의 원천이자 **격리의 한계**입니다. 커널에 구멍이 하나 나면 그 위의 모든 컨테이너가 영향을 받으니까요. 그래서 신뢰할 수 없는 코드를 돌려야 하는 상황에서는 이 전제 자체를 바꾸는 접근이 나옵니다.

```text
[일반 컨테이너]         [gVisor]                    [Kata]
  앱                     앱                          앱
   │ syscall              │ syscall                   │ syscall
   ▼                      ▼                           ▼
  호스트 커널           Sentry (유저스페이스)        게스트 커널
                          │ 대부분 여기서 처리         │ VM 안에서 처리
                          │ 필요한 것만 제한적으로     │
                          ▼                           ▼
                        호스트 커널                 하이퍼바이저
                                                      ▼
                                                   호스트 커널
```

그림을 읽으실 때 주의할 게 있습니다. gVisor는 시스템 콜을 **걸러서 넘기는 필터가 아닙니다.** Sentry가 **자기가 구현한 커널 기능으로 대부분을 직접 처리**하고, 정말 필요한 것만 제한적으로 호스트에 씁니다. Kata도 마찬가지로 앱의 시스템 콜이 하이퍼바이저로 바로 가는 게 아니라 **게스트 커널이 받아 처리**합니다.

### gVisor — 유저스페이스에 커널을 하나 더

gVisor의 자기 정의는 **"Linux와 유사한 인터페이스를 구현하는 application kernel"**입니다. 구성요소가 셋입니다.

- **runsc** — 진입점. **OCI 런타임 스펙을 구현**하므로 앞에서 본 "갈아 끼우기"가 그대로 됩니다.
- **Sentry** — 커널 역할. 시스템 콜·시그널 전달·메모리 관리와 page fault·스레딩 모델을 **직접 구현**합니다. 핵심은 이 문장입니다 — **"Sentry는 시스템 콜을 호스트 커널로 그대로 통과시키지 않는다."**
- **Gofer** — 파일시스템 접근을 중개합니다. **9P 프로토콜**로 Sentry와 통신하며 한 겹 더 가둡니다.

여기서 가장 중요한 줄은 **"통과시키지 않는다"**입니다. 앱이 커널을 부르면 그 요청을 **gVisor가 받아서 자기가 처리**하고, 정말 필요한 것만 골라 호스트에 전달합니다. 호스트 커널에 노출되는 표면이 확 줄어드는 거죠.

시스템 콜을 가로채는 방식(플랫폼)은 셋인데, 여기 시대성 함정이 있습니다.

| 플랫폼 | 방식 | 상태 |
| --- | --- | --- |
| **systrap** | seccomp trap → 시그널로 gVisor에 전달 | **2023년 중반부터 기본** |
| KVM | 프로세서 가상화 확장 | 베어메탈에서 최적, 중첩 VM에선 저하 |
| ptrace | `PTRACE_SYSEMU` | **지원 종료, 제거 예정** |

오래된 자료가 gVisor를 "ptrace로 syscall을 가로채는 것"이라고 설명하는 걸 자주 보실 겁니다. **지금은 아닙니다.** ptrace는 컨텍스트 스위치 비용이 커서 시스템 콜이 잦은 앱에 불리했고, 그래서 systrap으로 갈아탔습니다.

### Kata Containers — 샌드박스마다 경량 VM

Kata는 접근이 아예 다릅니다. **샌드박스(쿠버네티스에서는 파드)마다 경량 VM을 띄웁니다.** 게스트 커널이 진짜로 하나 더 있는 거예요.

- **"VM의 보안 이점"**을 컨테이너급 관리성과 함께 제공하는 것이 목표
- **OCI 준수 런타임**이라 이미지를 다시 만들 필요가 없고, **CRI로** 쿠버네티스와 붙습니다
- 하이퍼바이저는 **QEMU·Firecracker** 등에서 고를 수 있습니다

여기서 단위를 정확히 해야 합니다. **"컨테이너마다"가 아니라 "샌드박스마다"입니다.** EP3에서 본 PodSandbox 기억하시죠? 쿠버네티스에서 Kata를 쓰면 **파드 하나당 VM 하나**가 뜨고, 그 파드 안의 컨테이너들은 **같은 VM을 공유**합니다. 컨테이너 3개짜리 파드에 VM이 3개 뜨는 게 아니에요. EP3에서 샌드박스를 1급으로 올려 둔 게 여기서 값을 합니다.

앞에서 본 `docker run --runtime io.containerd.kata.v2`가 바로 이겁니다. **위층을 하나도 안 바꾸고 격리 모델만 교체**하는 거죠.

그리고 도입 전에 반드시 확인할 전제가 하나 있습니다. **VM을 띄우려면 하드웨어 가상화가 필요합니다.** 베어메탈에서는 문제없지만, **이미 VM인 클라우드 인스턴스 위에서 Kata를 돌리려면 중첩 가상화(nested virtualization)를 지원하는 인스턴스 타입**이어야 합니다. 지원하지 않는 타입을 골라 놓고 "왜 안 뜨지?"로 시간을 버리는 일이 흔합니다.

### 무엇을 대가로 무엇을 얻나

여기서 정직하게 말씀드릴 것이 있습니다. **이 글에는 성능 수치를 넣지 않습니다.**

gVisor와 Kata의 오버헤드를 숫자로 제시하려면 벤더 중립적인 측정이 필요한데, 이 글을 쓰며 확보하지 못했습니다. 벤더가 자기 제품을 측정한 수치나 조건이 불분명한 벤치마크를 옮기는 건 안 하느니만 못합니다. 그래서 **성질**만 말씀드리겠습니다.

```text
 일반 컨테이너   시작 빠름 · 오버헤드 최소 · 커널 공유(격리 약함)
 gVisor         syscall 이 한 겹 거쳐 감 → syscall 잦은 워크로드에 불리
                커널 기능 호환성 제약 가능
 Kata           VM 부팅 비용 · 메모리 오버헤드
                대신 커널이 분리됨(격리 강함)
```

**여러분 워크로드로 직접 재 보셔야 합니다.** syscall을 얼마나 자주 부르는지, 파일 I/O가 얼마나 많은지에 따라 결과가 크게 달라집니다. 남의 벤치마크로 결정하지 마세요.

수치는 못 드려도 **어디가 아플지**는 구조에서 나옵니다. gVisor는 시스템 콜과 파일 I/O가 한 겹 더 거쳐 가니 **그 둘이 잦은 워크로드**에서 부담이 큽니다(파일 접근은 Gofer를 거칩니다). 그리고 Sentry가 구현하지 않은 커널 기능을 쓰는 앱은 아예 안 돌 수도 있습니다. Kata는 **VM 부팅 시간과 기본 메모리 풋프린트**가 고정 비용으로 붙습니다. 짧게 뜨고 지는 작업을 많이 돌리면 이 시작 비용이 계속 곱해집니다.

> 기억법: **격리를 사면 성능으로 지불한다. 얼마인지는 내 워크로드가 정한다.**

### 격리 강화 ≠ 보안 완성

하나만 더 분명히 하고 넘어가겠습니다. gVisor나 Kata를 넣었다고 **멀티테넌시가 해결되는 게 아닙니다.**

이 도구들이 강화하는 건 **"게스트가 호스트 커널을 건드리는 경로"** 하나입니다. 그 밖에도 지켜야 할 게 남습니다 — 네트워크 격리, 스토리지 접근 범위, 시크릿 노출, 이미지 출처 신뢰(EP2에서 본 그 서명 이야기), seccomp·AppArmor·SELinux 정책, 쿠버네티스라면 RuntimeClass와 네임스페이스 정책까지요.

**한 겹을 두껍게 한 것이지 벽을 완성한 게 아닙니다.**

## 4층 — 빌드 도구: 셋 중 하나는 이제 빼야 합니다

마지막 층입니다. 그리고 **이 편에서 실무적으로 가장 중요한 한 줄**이 여기 있습니다.

### BuildKit

Docker의 현대적 빌더 백엔드이고 **Docker Desktop·Docker Engine의 기본 빌더**입니다(Windows 컨테이너는 레거시 빌더 유지). 개선점이 셋입니다.

- **병렬성** — **"완전 동시적(fully concurrent) build graph solver"**. 독립적인 스테이지를 동시에 돌리고, 최종 결과에 영향 없는 명령은 아예 건너뜁니다.
- **캐싱** — 휴리스틱 대신 **빌드 그래프와 마운트된 콘텐츠의 체크섬을 직접 추적**합니다. 캐시를 레지스트리로 export할 수도 있어서 CI에서 특히 유용합니다.
- **LLB** — 핵심 중간 포맷. **"복잡한 빌드 정의를 조립하는 content-addressable 의존성 그래프"**입니다. EP2에서 본 그 content-addressable이 여기서도 나옵니다. **Frontend**가 Dockerfile을 LLB로 번역하고, frontend 자체가 이미지로 배포돼 버전을 고정할 수 있습니다.

EP1에서 본 `RUN --mount=type=secret`이 BuildKit 기능입니다. 비밀을 레이어에 남기지 않고 빌드할 수 있었던 이유죠.

### Buildah

`containers` 조직의 빌드 전용 도구입니다. **root 없이** Dockerfile 명령을 재현할 수 있고, **Podman이 이미지 빌드에 Buildah의 API를 씁니다.**

Buildah의 특징은 **Dockerfile 없이도 이미지를 조립할 수 있다**는 점입니다. 셸 스크립트로 한 단계씩 쌓아 올릴 수 있어서, Dockerfile 문법에 갇히지 않는 빌드가 가능합니다.

### Kaniko — ⚠ 이제 고르면 안 됩니다

Kaniko는 "Docker 데몬 없이 클러스터 안에서 이미지를 빌드한다"는 목적으로 널리 쓰이던 도구입니다. 각 명령을 유저스페이스에서 실행하고 변경분을 스냅샷해 레이어로 쌓는 방식이었죠.

그런데 **저장소가 아카이브됐습니다.** 리포지터리에 이렇게 적혀 있습니다.

> **"This project is archived and no longer developed or maintained. The code remains available for historic purposes."**
> (이 프로젝트는 아카이브됐으며 더 이상 개발·유지보수되지 않습니다. 코드는 역사적 목적으로만 남아 있습니다.)

마지막 릴리스는 **v1.24.0(2025-05-23)**입니다. 다른 도구들이 2026년에도 릴리스를 내는 것과 대비됩니다. 그러니 **2025년 중반 이전에 쓰인 글**이라면 그때는 맞는 조언이었을 수 있다고 보시면 됩니다.

**이게 왜 중요할까요?** 빌드 도구는 **베이스 이미지와 레지스트리를 다루는 자리**에 있습니다. 유지보수가 멈췄다는 건 새 media type이나 레지스트리 동작 변경에 대응하지 못하고, **보안 패치도 나오지 않는다**는 뜻입니다.

인터넷에는 아직 Kaniko를 권하는 글이 많습니다. 그 글들이 쓰였을 땐 맞는 조언이었어요. **지금 새로 고르실 자리에는 넣지 마세요.**

> 기억법: **아카이브된 도구는 "쓸 수 있다"와 "골라도 된다"가 다르다.**

## 그래서 무엇을 고르나

층을 다 봤으니 이제 상황별로 정리하겠습니다.

| 상황 | 권할 조합 | 이유 |
| --- | --- | --- |
| 로컬 개발, 생태계 우선 | **Docker** | 자료·도구·팀 숙련도가 가장 두텁습니다 |
| 데몬 없이·rootless 기본 | **Podman**(+Buildah) | 유휴 자원이 낮고 권한 모델이 단순합니다 |
| 쿠버네티스 노드 | **containerd** 또는 **CRI-O** | 둘 다 CRI 구현. containerd가 가장 널리 쓰이고, CRI-O는 버전 동조가 장점 |
| 신뢰 못 할 코드 실행 | **gVisor** 또는 **Kata** | 커널 공유를 끊습니다. 단, 이것만으로 끝나지 않습니다 |
| 저수준 런타임 교체 검토 | **crun** 또는 **youki** | runc 자리를 그대로 대체합니다. 언어보다 **패키징·CVE 대응**을 보세요 |
| 클러스터 안에서 빌드 | **BuildKit** 또는 **Buildah** | Kaniko는 아카이브됐습니다 |

여기서 헷갈리기 쉬운 포인트를 마지막으로 짚겠습니다. **이 표는 배타 선택지가 아닙니다.** 한 줄만 고르는 게 아니라 **층마다 한 칸씩** 고르는 겁니다.

<VizComparison2 />

"쿠버네티스 노드에 containerd + 신뢰 못 할 워크로드만 Kata + 빌드는 BuildKit"이 완벽하게 정상적인 조합이에요. 층마다 따로 고르면 **바뀌는 범위가 어디까지인지도 함께 보입니다.**

## 오해하기 쉬운 포인트 정리

**오해 1. "Podman은 Docker의 상위 호환이다."**
층이 같고 설계 철학이 다를 뿐입니다. 데몬리스는 이점이자 제약입니다.

**오해 2. "CRI-O로 로컬 개발을 할 수 있다."**
쿠버네티스 노드용입니다. 사람이 손으로 쓰라고 만든 게 아닙니다.

**오해 3. "gVisor를 쓰면 무조건 안전하다."**
호스트 커널에 노출되는 표면을 **줄이는** 것이지 없애는 게 아닙니다. Sentry 자체도 소프트웨어라 취약점이 있을 수 있고, 격리는 여전히 정도의 문제입니다.

**오해 4. "gVisor는 ptrace로 syscall을 가로챈다."**
2023년 중반부터 기본은 **systrap**이고 ptrace는 지원이 끝났습니다. 오래된 자료의 설명입니다.

**오해 5. "런타임을 바꾸려면 이미지를 다시 만들어야 한다."**
아닙니다. EP2에서 본 대로 이미지 포맷과 런타임은 다른 층입니다. crun도 gVisor도 Kata도 **같은 이미지를 그대로** 씁니다.

**오해 6. "Kata를 쓰면 컨테이너 수만큼 VM이 뜬다."**
쿠버네티스에서는 **파드(샌드박스) 하나당 VM 하나**입니다. 한 파드 안의 컨테이너들은 같은 VM을 공유합니다.

## 직접 해보기

리눅스에서 도커가 돌고 있다면 런타임 교체를 손으로 확인할 수 있습니다.

1. **지금 어떤 런타임이 등록돼 있는지 봅니다.**
   ```bash
   docker info --format '{{json .Runtimes}}' | jq .
   ```
   기대 결과: `runc`가 기본으로 보이고, 설치된 다른 런타임이 있으면 함께 나옵니다.

2. **crun을 설치해 등록합니다.** (배포판 패키지로 설치한 뒤)
   ```json
   // /etc/docker/daemon.json
   {
     "runtimes": {
       "crun": { "path": "/usr/bin/crun" }
     }
   }
   ```
   ```bash
   sudo systemctl reload docker      # 설정만 다시 읽기
   docker info --format '{{json .Runtimes}}' | jq .
   ```
   관찰 포인트: 목록에 `crun`이 늘어납니다. **왜 데몬을 건드려야 하냐면** 이게 `dockerd`의 설정이기 때문입니다 — EP1에서 본 계층에서 런타임 등록은 데몬이 들고 있는 정보예요. 보통은 `reload`로 충분하고, 반영이 안 되면 `restart`를 씁니다.

3. **같은 이미지를 다른 런타임으로 돌려 봅니다.**
   ```bash
   docker run --rm alpine echo hello
   docker run --rm --runtime crun alpine echo hello
   ```
   관찰 포인트: **결과가 똑같습니다.** 이미지를 다시 만들지도, 명령을 바꾸지도 않았는데 그 아래 실행 주체만 달라졌습니다. 이게 EP2에서 본 OCI 런타임 스펙의 실물입니다.

4. **컨테이너 프로세스의 부모를 비교합니다.**
   ```bash
   docker run -d --name a alpine sleep 300
   pstree -aps $(docker inspect -f '{{.State.Pid}}' a)
   ```
   관찰 포인트: EP1에서 본 그 shim이 그대로 보입니다. **런타임을 바꿔도 위층 구조는 그대로**라는 걸 눈으로 확인하실 수 있습니다.

## 스스로 점검하기

1. 동료가 "우리도 Podman으로 갈아타자"고 합니다. 결정 전에 확인해야 할 것 두 가지를 대 보세요.
2. 신뢰할 수 없는 사용자 코드를 실행해야 합니다. gVisor와 Kata 중 무엇을 고르시겠습니까? 그리고 **고르기 전에 무엇을 측정**하시겠습니까?
3. CI에서 클러스터 안 이미지 빌드를 새로 구성합니다. Kaniko를 쓰면 안 되는 이유를 한 문장으로 설명해 보세요.
4. `docker run --runtime crun` 으로 실행했더니 잘 됩니다. 이미지를 다시 빌드하지 않아도 되는 이유는 무엇일까요?

1. ① **도커 데몬을 전제로 만들어진 기존 도구·스크립트**가 있는지(데몬리스라 상태를 중앙에서 관리해 주지 않습니다). ② **부팅 시 자동 시작 등 생명주기 관리**를 systemd 같은 것으로 옮길 준비가 됐는지. 전환 비용 자체는 Docker 호환 CLI·REST API 덕에 낮은 편입니다.

3. **저장소가 아카이브되어 유지보수·보안 패치가 나오지 않기 때문**입니다. 레지스트리·이미지 포맷을 다루는 자리라 대응이 멈추면 위험이 쌓입니다. BuildKit이나 Buildah를 쓰면 됩니다.
4. **이미지 포맷(OCI image-spec)과 런타임(OCI runtime-spec)이 다른 층**이기 때문입니다. 런타임이 받는 건 이미지가 아니라 그것을 변환한 **번들**이고, crun도 runc와 같은 런타임 스펙을 구현합니다.

## 마무리 — 네 편을 한 줄로

한 문장으로 줄이면 이렇습니다.

> **"도커 대신 무엇을"이 아니라 "어느 층을 무엇으로"가 옳은 질문이다.**

<VizFlowchart3 />

그리고 그 질문을 던질 수 있게 된 건 지난 세 편 덕입니다.

- **EP1** — "도커"는 CLI·데몬·containerd·shim·runc·커널이 릴레이하는 **조립품**이다.
- **EP2** — 그 층들이 맞물리는 약속이 **OCI 3대 스펙**이다. 실행하는 법·담는 법·나르는 법.
- **EP3** — 쿠버네티스는 그 위에 **CRI**라는 주문서 양식을 얹는다. 파드는 거기서 1급이 된다.
- **EP4** — 층마다 규격이 있으니 **층마다 갈아 끼울 수 있다.** 대안은 경쟁자가 아니라 부품이다.

처음에 `docker run` 한 줄이 무슨 일을 하는지 물었습니다. 이제는 그 한 줄의 어느 지점에 무엇이 끼어 있고, 그중 무엇을 바꿀 수 있으며, 바꾸면 무엇을 얻고 무엇을 잃는지까지 그리실 수 있게 됐을 겁니다.

기술은 계속 바뀝니다. 이 글에 적은 버전 번호도 몇 달이면 낡을 거예요. 하지만 **층으로 나눠 보는 눈**은 잘 낡지 않습니다. 새 도구가 나왔을 때 "이건 어느 층을 바꾸는 물건인가?"라고 물으실 수 있다면, 그 도구를 훨씬 빨리 이해하시게 됩니다.
