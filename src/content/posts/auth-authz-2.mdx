1편의 마지막에서 약속했습니다. "토큰이 유효한가"와 "이 토큰이 우리를 위한, 이 사용자를 위한 것인가"는 다른 질문이라고. 이제 그 약속을 지킬 차례입니다.

리소스 서버에 JWT 검증 코드를 붙였습니다. `jwt.decode(token)`으로 페이로드를 꺼내 `sub`로 사용자를 식별하고, `exp`가 미래인지 확인했습니다. 테스트도 통과했습니다. 그런데 보안 점검에서 지적을 받습니다 — **"이건 검증이 아니라 디코딩입니다. 서명을 아무도 확인하지 않았어요."** 누구나 base64로 페이로드를 원하는 대로 바꿔 넣어도, 이 코드는 그대로 통과시킵니다.

이 글을 끝까지 읽으시면, **JWT를 '연다'와 '믿는다'가 어떻게 다른지**, 그리고 신뢰의 근거인 **서명을 검증하려면 무엇을 확인해야 하는지**를 실제 토큰과 JWKS를 손에 쥐고 추적할 수 있게 됩니다. `alg`를 `none`으로 바꾼 위조 토큰이, `RS256`을 `HS256`으로 바꾼 공격이 어디서 막히는지도요.

## 들어가며: "디코딩"과 "검증"은 다르다

JWT는 base64url로 인코딩돼 있습니다. **인코딩은 암호화가 아닙니다.** 누구나 페이로드를 디코딩해 내용을 읽을 수 있고, 반대로 원하는 내용을 넣어 다시 인코딩할 수도 있습니다. 그래서 페이로드를 꺼내 읽는 일(디코딩)은 **아무것도 보증하지 않습니다.**

토큰을 신뢰할 수 있게 만드는 유일한 근거는 **서명(signature)**입니다. 발급자가 자기 키로 서명을 만들었고, 그 서명이 페이로드와 맞아떨어질 때에만 "이 내용은 발급자가 보증한 것이고, 중간에 변조되지 않았다"고 말할 수 있습니다. 앞의 사고는 이 서명을 아무도 검사하지 않은 채, 디코딩만으로 "검증했다"고 착각한 것입니다.

그러니 2편의 목표는 분명합니다. **서명을 검증한다는 것이 실제로 무엇을 하는 일인지**, 그리고 서명만으로도 끝이 아니라 `iss`·`aud`·`exp`·`kid`까지 확인해야 비로소 "우리를 위한, 방금 그 발급"임이 보장된다는 것을 실제 데이터로 보이는 것입니다.

## 한눈에 보기: JWT 3파트와 검증 6단계

JWT(JSON Web Token, RFC 7519)는 점 두 개로 나뉜 세 토막입니다.

```text
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImFiYzEyMyJ9   ← ① 헤더 (alg, typ, kid)
.eyJpc3MiOiJodHRwczovL2lkcC5leGFtcGxlLmNvbSIsInN1YiI6Ii4uLiJ9  ← ② 페이로드 (클레임)
.MEUCIQDh8s...서명...                                          ← ③ 서명
```

- **① 헤더(JOSE Header)**: 어떤 알고리즘(`alg`)으로 서명했고, 어떤 키(`kid`)를 썼는지.
- **② 페이로드**: 클레임 집합(`iss`·`sub`·`aud`·`exp`…). **여기에 상태가 담기지만, 암호화되지 않습니다.**
- **③ 서명**: ①과 ②를 발급자 키로 서명한 값. 검증의 유일한 근거.

검증은 다음 여섯 단계입니다. 하나라도 빠지면 구멍이 됩니다.

| # | 단계 | 확인하는 것 |
|---|---|---|
| 1 | **alg 허용목록** | 헤더 `alg`가 우리가 허용한 알고리즘인가 (`none` 금지) |
| 2 | **kid→키 선택** | **신뢰한 JWKS**에서 `kid`로 올바른 공개키를 골랐는가 |
| 3 | **서명 검증** | 그 공개키로 서명이 맞아떨어지는가 |
| 4 | **iss(발급자)** | 우리가 신뢰하는 발급자가 맞는가 |
| 5 | **aud(대상)** | 이 토큰이 **우리를 위해** 발급됐는가 |
| 6 | **exp/nbf(시간)** | 만료되지 않았고, 유효 시작 시각을 지났는가 |

순서가 중요합니다. **서명을 검증하려면 먼저 키를 골라야** 하므로 `kid→키 선택`이 서명 검증보다 앞섭니다. 이 여섯 가지를 이 글에서 하나씩 실제 토큰과 JWKS로 짚고, 마지막 인터랙티브 랩에서 각 단계를 고의로 어겨 보며 "어디서 막히는지"도 관찰하실 수 있습니다. 그리고 6단계는 "이 토큰이 진짜이고 우리 것인가"까지입니다 — 그다음 "이 **행위**를 해도 되는가"(scope·역할로 판단하는 인가)는 별개이며 4편에서 다룹니다.

## 엄밀한 정의: JWT는 서명된 클레임이지 비밀이 아니다

RFC 7519는 JWT를 세 부분(`header.payload.signature`)을 `.`으로 이어 붙이고 각 부분을 **base64url**로 인코딩한 것으로 정의합니다. 실제로 헤더와 페이로드를 디코딩하면 그냥 JSON입니다.

헤더(디코딩 후):

```json
{ "alg": "RS256", "typ": "JWT", "kid": "abc123" }
```

페이로드(디코딩 후, 표준 등록 클레임):

```json
{
  "iss": "https://idp.example.com/realms/demo",
  "sub": "9c85e7a2-1f3b-4d2a-8e11-abc123",
  "aud": "photo-app",
  "exp": 1721650000,
  "nbf": 1721646400,
  "iat": 1721646400,
  "jti": "f5f50c31-5b04-49d6-9cbc-3f01e9989ed1"
}
```

RFC 7519가 정의하는 등록 클레임의 뜻은 이렇습니다.

- **`iss`**(Issuer): 발급 주체. **`aud`**(Audience): 의도된 수신자 — **문자열 하나이거나 문자열 배열**일 수 있습니다.
- **`exp`**(Expiration)·**`nbf`**(Not Before)·**`iat`**(Issued At): 모두 **NumericDate**, 즉 1970-01-01 UTC부터의 **초 단위 숫자**입니다(윤초 무시; 실무에선 보통 정수 epoch). 위 `1721650000` 같은 숫자가 그것입니다.
- **`sub`**(Subject): 주체 식별자. **`jti`**(JWT ID): 토큰의 유일 식별자. RFC 7519는 이를 재생(replay) 방지에 **활용할 수 있다**고 할 뿐입니다 — `jti`가 있다고 재생이 막히는 게 아니라, 검증기가 본 `jti`를 저장소(Redis 등)에 기록·대조해야 비로소 성립합니다(그 순간 stateless 이점과 타협).

여기서 못을 박겠습니다. **흔히 쓰는 signed JWT(JWS 형태)는 암호화가 아닙니다.** (엄밀히 JWT는 JWS일 수도 JWE일 수도 있지만, OAuth·OIDC의 액세스/ID 토큰은 대개 서명만 한 JWS입니다.) JWS(RFC 7515)는 무결성과 진위(변조되지 않았고 발급자가 만들었다)만 보장하며, **페이로드는 그대로 노출됩니다.** 내용을 숨기려면 별도로 JWE(RFC 7516)로 암호화해야 합니다(JWE는 헤더·암호화된 키·IV·암호문·인증 태그 다섯 토막). 그러니 **JWT 페이로드에 비밀번호나 민감정보를 넣지 마십시오** — 누구나 읽습니다.

참고로 서명은 **`base64url(헤더).base64url(페이로드)`** 원본 바이트 그대로에 대해 만들어집니다. 그래서 페이로드를 디코딩했다가 다시 직렬화한 문자열(공백·키 순서가 달라진)로 검증하면 **서명이 깨집니다** — 검증은 반드시 전송받은 원본 문자열로 해야 합니다.

## 핵심 원리: 서명과 공개키 배포(JWS + JWKS)

서명 검증의 핵심은 "어떤 키로 서명했고, 검증자는 그 키를 어떻게 구하느냐"입니다. 여기서 **대칭과 비대칭**이 갈립니다(RFC 7518).

- **대칭(HS256 = HMAC-SHA256)**: 발급자와 검증자가 **같은 비밀키**를 공유합니다. 간단하지만, 검증하려면 비밀키를 나눠 가져야 해서 키가 새면 곧 위조로 이어집니다.
- **비대칭(RS256 = RSA-SHA256, ES256 = ECDSA-P256)**: 발급자는 **개인키로 서명**하고, 검증자는 **공개키로만 검증**합니다. 검증자는 공개키만 있으면 되고, 공개키는 새어도 위조에 쓰이지 않습니다.

비대칭이 이기는 지점이 바로 여기입니다. 공개키는 공개해도 되니, 발급자가 **공개키를 웹에 게시**해 두고 검증자들이 가져가게 할 수 있습니다. 그 게시 형식이 **JWKS(JSON Web Key Set, RFC 7517)**입니다. 발급자의 `jwks_uri`를 GET하면 이런 JSON이 옵니다(RSA 키, 실제 형식):

```json
{
  "keys": [
    {
      "kid": "abc123",
      "kty": "RSA",
      "alg": "RS256",
      "use": "sig",
      "n": "0vx7agoebGcQSuuPiLJXZptN9nndrQmbXEps2aiAFbWhM78...",
      "e": "AQAB",
      "x5c": ["MIICmzCCAYMCBg..."],
      "x5t#S256": "kW8b...SHA-256 지문..."
    }
  ]
}
```

- **`keys`**: 키 배열(RFC 7517은 이 멤버를 필수로 요구). 발급자는 키를 **여러 개** 둘 수 있습니다.
- **`kid`**: 키 식별자. 토큰 헤더의 `kid`와 **대조**해 어느 공개키로 검증할지 고릅니다.
- **`kty`**(키 종류, `RSA`)·**`n`**(모듈러스)·**`e`**(공개 지수, 보통 `AQAB`): RSA 공개키를 이루는 값들.
- **`use: "sig"`**: 이 키는 서명 검증용.

그래서 검증자는 이렇게 움직입니다. 토큰 헤더에서 `kid`를 읽고 → **신뢰한** JWKS에서 같은 `kid`의 공개키를 찾고 → 그 공개키로 서명을 검증합니다.

두 가지를 못 박겠습니다. 첫째, **`kid`는 힌트일 뿐 신뢰의 근거가 아닙니다.** 공격자가 헤더에 아무 값이나 넣을 수 있으니, 검증기는 반드시 **미리 신뢰한 JWKS 안에서만** 후보 키를 찾아야 합니다. 둘째, **JWKS를 어디서 가져오느냐**가 결정적입니다. 토큰 헤더의 `jku`·`x5u`(임의 키 URL)를 따라가면 **SSRF·키 주입**으로 뚫립니다(RFC 8725 경고). 오직 **신뢰한 발급자의 OIDC Discovery(`.well-known/openid-configuration`)에서 얻은 `jwks_uri`**로만 가져와야 합니다.

**키 로테이션**이 자연스러운 이유도 여기 있습니다. 발급자가 새 키로 갈아탈 때 JWKS에 **새 키와 옛 키를 함께** 두면, 옛 키로 서명된(아직 만료 안 된) 토큰도 계속 검증됩니다. 운영에서는 JWKS를 **캐싱**하되(매 요청 GET 금지), 모르는 `kid`가 오면 재조회하고, 이때 **재조회에 최소 간격(rate limit)**을 두어야 합니다 — 그렇지 않으면 공격자가 무작위 `kid`를 쏟아부어 발급 서버로 요청을 유발하는 DoS가 됩니다.

## 실무 시나리오 워크스루: 토큰을 받아 검증하기

이제 실제로 토큰을 받아 검증까지 해보겠습니다. 발급자는 **Keycloak** 기준입니다. (아래 경로·클레임 중 무엇이 OIDC 표준이고 무엇이 Keycloak 특유인지 구분해 표시합니다. Keycloak 17+ 기준이며, 구버전은 경로에 `/auth` 프리픽스가 붙습니다.)

### 1단계 — 토큰을 발급받는다

토큰 엔드포인트에 `application/x-www-form-urlencoded`로 POST합니다(경로 `.../protocol/openid-connect/token`은 **Keycloak 특유**입니다). 아래는 토큰 **형태**를 빨리 보이기 위한 예시입니다:

> ⚠️ **`grant_type=password`(ROPC)는 실무에서 쓰지 마십시오.** OAuth 2.0 Security BCP(RFC 9700)는 이 그랜트를 **MUST NOT**으로 규정합니다(비밀번호가 앱을 거쳐 흐르므로). 여기서는 한 줄로 토큰을 얻어 형태를 보이려는 편의일 뿐이고, 정상 흐름은 3편의 **Authorization Code + PKCE**입니다.

```bash
# ⚠️ 데모용(ROPC, 실무 금지). 실제로는 Authorization Code + PKCE(3편).
curl -X POST 'https://idp.example.com/realms/demo/protocol/openid-connect/token' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'grant_type=password' \
  -d 'client_id=photo-app' \
  -d 'client_secret=<secret>' \
  -d 'username=alice' -d 'password=<pw>' \
  -d 'scope=openid email'
```

응답 JSON(실제 필드명):

```json
{
  "access_token": "eyJ...",
  "expires_in": 300,
  "refresh_expires_in": 1800,
  "refresh_token": "eyJ...",
  "id_token": "eyJ...",
  "token_type": "bearer",
  "not-before-policy": 0,
  "session_state": "7502cf31-...",
  "scope": "openid email"
}
```

`scope`에 `openid`가 있으면 `id_token`이 함께 옵니다(1편의 구분 그대로 — `access_token`은 API 인가용, `id_token`은 로그인 확인용). `expires_in`은 **초**입니다(여기선 5분).

### 2단계 — 액세스 토큰을 디코딩해 본다(아직 검증 아님)

`access_token`의 페이로드를 디코딩하면 Keycloak이 채운 클레임이 보입니다:

```json
{
  "iss": "https://idp.example.com/realms/demo",
  "sub": "9c85e7a2-1f3b-4d2a-8e11-abc123",
  "aud": "account",
  "azp": "photo-app",
  "typ": "Bearer",
  "exp": 1721646700, "iat": 1721646400,
  "jti": "f5f50c31-...",
  "scope": "openid email",
  "realm_access": { "roles": ["offline_access", "default-roles-demo"] },
  "resource_access": { "photo-app": { "roles": ["photo:read"] } },
  "preferred_username": "alice"
}
```

표준(OIDC/RFC)과 Keycloak 특유를 갈라 보겠습니다.

- `iss`·`sub`·`aud`·`exp`·`iat`·`jti`는 RFC 7519 **등록 클레임**. `iss`가 realm URL 형태인 것은 Keycloak 관행입니다.
- **`scope`**는 RFC 7519 등록 클레임이 **아니라** OAuth/OIDC(및 RFC 9068 프로파일) 맥락의 클레임입니다. **`azp`**(authorized party = 이 토큰을 받은 `client_id`)는 OIDC Core가 ID Token 맥락에서 정의한 클레임인데, Keycloak은 액세스 토큰에도 채웁니다.
- **`realm_access.roles` / `resource_access.{client}.roles`**는 **Keycloak 특유**의 역할 표현입니다. 어느 쪽을 권한의 권위 있는 원천으로 삼을지는 **프로젝트의 권한 모델에 따라 정해야** 합니다("무조건 둘 다"가 아니라).
- **`typ: "Bearer"`**(페이로드 클레임) — 이건 지금까지 다뤄온 **① 헤더의 `typ`**과는 **다른 자리의 다른 값**입니다. 헤더 `typ`은 이 토큰에서도 그대로 `"JWT"`이고(앞서 본 헤더 예시대로), 페이로드의 `typ: "Bearer"`는 Keycloak이 액세스·리프레시·ID 토큰을 구분하려고 채우는 **벤더 특유 클레임**입니다. 표준과 갈리는 지점은 따로 있습니다 — RFC 9068(JWT 액세스 토큰 프로파일)을 **채택하면** 리소스 서버가 ID Token 오용을 막기 위해 **헤더의 `typ`**을 **`at+jwt`**로 강제해야 합니다. Keycloak 기본값이 헤더 `typ`을 `JWT`로 두는 것은 그 프로파일을 따르지 않는 **벤더 구현**일 뿐, "RFC 위반"은 아닙니다. 다만 검증기가 헤더 `typ`을 강제한다면 이 차이를 반영해야 합니다.

디코딩으로 여기까지 **읽었을 뿐**입니다. 아직 아무것도 검증하지 않았습니다.

### 3단계 — JWKS를 가져와 서명을 검증한다

토큰 헤더의 `kid`를 확인하고, 발급자의 JWKS(경로 `.../protocol/openid-connect/certs`는 **Keycloak 특유**, `jwks_uri` 필드 자체는 **OIDC Discovery 표준**)를 가져옵니다:

```bash
curl -s 'https://idp.example.com/realms/demo/protocol/openid-connect/certs'
```

헤더 `kid`와 같은 키를 골라 그 공개키(`n`, `e`)로 서명을 검증합니다. 이 검증이 통과해야 비로소 "이 토큰은 발급자가 만들었고 변조되지 않았다"가 성립합니다. 그다음에 `iss`(우리가 아는 발급자인지)·`aud`(우리를 위한 것인지)·`exp`(안 만료됐는지)를 확인하면 **6단계가 완성**됩니다. 시간 검증에는 서버 간 시각 차이를 감안한 **작은 허용 오차(clock skew leeway, 보통 1분 이내)**를 두는 것이 실무 관행입니다.

한 가지 강조. 서명 검증에 성공했다고 끝이 아닙니다. 서명은 **무결성과 진위**(위조·변조가 아니다)의 근거일 뿐, 토큰을 받아들일지는 `iss`·`aud`·`exp`까지 본 **정책 판단**입니다. 앞의 사고(1편)가 그랬듯, **서명이 유효한 남의 토큰**은 `aud`에서 걸러야 합니다. 그리고 이 6단계는 "진짜이고 우리 것"까지입니다 — API가 "이 요청 행위를 허용하는 **scope·역할**이 있는가"까지 확인하는 것은 그다음 인가 단계(4편)입니다.

## 자주 틀리는 포인트

토큰 검증에서 특히 자주 미끄러지는 지점들입니다.

- ❌ **"`jwt.decode()` 했으니 검증했다."** → 디코딩은 검증이 아닙니다. **서명 검증 함수**(`verify`)를 써야 하고, 그 함수에 **공개키와 허용 알고리즘**을 넘겨야 합니다.
- ❌ **"헤더의 `alg`를 믿고 그대로 검증한다."** → 이게 **`alg:none` 공격**입니다. 공격자가 `alg`를 `none`으로 바꾸면 일부 라이브러리는 서명 없이 통과시킵니다. RFC 8725(BCP)는 **호출자가 허용 알고리즘 집합을 지정**하고 그 외는 거부하라고 못 박습니다. `none`은 허용목록에서 빼야 합니다.
- ❌ **"RSA 공개키로 검증하니 안전하다."** → **alg confusion(RS256→HS256)** 공격을 조심하십시오. 공격자가 `alg`를 `HS256`으로 바꾸면, 취약한 라이브러리는 **공개키를 HMAC 비밀키로 사용**해 검증을 시도합니다. 공개키는 누구나 아니까 위조가 가능해집니다. 방어는 **키별로 허용 알고리즘을 고정**(비대칭 키엔 비대칭 알고리즘만)하는 것입니다.
- ❌ **"토큰 헤더의 키 URL(`jku`/`x5u`)에서 공개키를 가져온다."** → 공격자가 넣은 URL을 따라가면 SSRF·키 주입입니다. 키는 **신뢰한 발급자의 `jwks_uri`**에서만 가져오고, `kid`는 그 안에서 후보를 고르는 힌트로만 쓰십시오.
- ❌ **"`aud`는 굳이 안 봐도 된다."** → 1편의 사고가 이것이었습니다. `aud` 없이는 **다른 앱을 위해 발급된 유효한 토큰**이 통과합니다. RFC 8725도 "audience가 없거나 수신자와 맞지 않으면 거부해야 한다"고 규정합니다.
- ❌ **"ID Token으로 API를 인가한다."** → ID Token은 클라이언트가 로그인을 확인하는 용도입니다. API 인가는 **액세스 토큰**으로 하며, `typ`(표준 `at+jwt`)으로 둘을 구분할 수 있어야 합니다.

## 직접 해보기: JWT 서명 검증 랩

앞의 6단계를 손으로 어겨 보겠습니다. `alg`를 바꾸고, `kid`를 없애고, 토큰을 만료시키고, `aud`를 틀리게 만들었을 때 검증이 **어느 단계에서, 왜** 막히는지 관찰해 보십시오. 위조가 통과하는 유일한 경우("취약 검증기")도 켜 볼 수 있습니다.

## opaque 토큰과 sender-constrained 토큰

마지막으로 지도의 나머지 두 조각을 짚겠습니다.

**액세스 토큰이 항상 JWT인 것은 아닙니다.** OAuth 액세스 토큰은 두 형태입니다.

- **JWT 액세스 토큰(RFC 9068)**: 자체 포함형. 리소스 서버가 **로컬에서** 서명·클레임을 검증합니다(네트워크 왕복 없음). 대신 만료 전 폐기 반영이 어렵습니다.
- **opaque 토큰**: 형식 없는 문자열. 리소스 서버가 발급 서버의 **introspection 엔드포인트(RFC 7662)**에 물어봐 검증합니다. 응답의 핵심은 `active`(boolean)이며, 유효하면 `{"active": true, "scope": "...", "client_id": "...", "exp": ...}`, 무효면 `{"active": false}`. 폐기가 즉시 반영되는 대신 매 요청 왕복이 듭니다.

그리고 **Bearer 토큰의 근본 약점** — "가진 자가 곧 행사자"입니다. 토큰만 훔치면 그대로 씁니다. 이를 막는 것이 **sender-constrained(소지 증명) 토큰**입니다.

- **DPoP(RFC 9449)**: 클라이언트가 요청마다 `DPoP` 헤더에 **개인키로 서명한 proof JWT**(`htm`·`htu`·`iat`·`jti`, 토큰 제시 시 `ath`)를 담습니다. 액세스 토큰에는 `cnf.jkt`(클라이언트 공개키 지문)가 박혀, 대응 개인키 없이는 못 씁니다.
- **mTLS-bound(RFC 8705)**: 액세스 토큰에 `cnf.x5t#S256`(클라이언트 인증서 지문)을 박아, mTLS 핸드셰이크로 인증서 소지를 증명해야만 사용할 수 있게 합니다.

둘 다 원리는 같습니다 — **토큰을 특정 키에 묶어, 훔쳐도 못 쓰게** 만드는 것입니다. 상세 적용은 실무편(4편)에서 다룹니다.

## 마무리

이번 편의 핵심을 압축하면 이렇습니다.

- **디코딩 ≠ 검증**이다. base64는 암호화가 아니고, 신뢰의 근거는 오직 **서명**이다.
- 비대칭 서명(RS256)이면 발급자가 **공개키를 JWKS로 게시**하고, 검증자는 **`kid`로 키를 골라** 검증한다.
- 검증은 **여섯 단계**(alg 허용목록 · kid로 키 선택 · 서명 · iss · aud · exp/nbf)이며, 하나라도 빠지면 `alg:none`·alg confusion·audience 우회가 열린다.
- 액세스 토큰은 **JWT(로컬 검증)**이거나 **opaque(introspection)**이며, 탈취 재사용은 **DPoP·mTLS**로 묶어 막는다.

실무 결론 하나만 챙기신다면: **검증 라이브러리에 '허용 알고리즘'과 '올바른 키'를 명시적으로 넘기고, 서명 이후 `iss`·`aud`·`exp`를 반드시 확인하라**는 것입니다. 그런데 이 토큰들은 애초에 **어떻게** 클라이언트 손에 들어올까요? 그 발급 과정 — Authorization Code 흐름과 PKCE, `state`·`nonce`, OIDC 로그인 — 을 다음 3편 「플로우」에서 실제 요청·응답 데이터로 추적합니다.
