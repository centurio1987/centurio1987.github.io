![컨테이너의 해부 2편 표지. OCI의 세 스펙이 각각 무엇을 규정하는지 소개한다.](/images/container-anatomy-2/hero.webp)

지난 편 마지막에 질문 하나를 남겨 뒀습니다. shim이 runc 대신 다른 엔진을 부를 수 있다면, **그 "다른 엔진"은 무엇을 지켜야 자격이 생기는 걸까요?**

오늘은 그 답을 봅니다. 그리고 답을 알고 나면 훨씬 큰 것이 딸려옵니다. 예를 들어 이런 일이 왜 되는지가 설명됩니다.

```text
                  docker build  로 이미지를 만들고
                        ↓
              GitHub Container Registry  에 올린다
                        ↓
            ┌───────────┴───────────┐
            ▼                       ▼
  쿠버네티스 노드의 containerd      로컬의 Podman
  (직접 내려받아 실행)             (직접 내려받아 실행)
```

네 개의 서로 다른 프로그램이, 서로 협의한 적도 없이, 같은 물건을 다룹니다. 심지어 만든 회사도 다릅니다. (containerd와 Podman은 서로 주고받는 게 아니라 **각자 레지스트리에서 독립적으로 내려받습니다** — 둘 사이에 연결선이 없다는 게 오히려 핵심입니다.) 이게 가능한 이유는 딱 하나 — **세 개의 문서**입니다.

이 글을 끝까지 읽으시면 그 세 문서가 각각 무엇을 규정하는지, 그리고 셋이 어디서 맞물리는지를 그리실 수 있게 됩니다. `config.json`이 뭔지, 이미지의 다이제스트가 왜 서로를 가리키는지, 레지스트리가 실은 HTTP API 서버라는 것까지요.

## OCI 표준은 셋으로 나뉩니다

"OCI 표준"은 문서 하나처럼 들리지만 실제로는 **셋입니다.** 그리고 셋이 나뉘어 있다는 사실 자체가 이 이야기의 핵심입니다.

```text
 ┌─ runtime-spec ──────  어떻게 실행하는가   (번들 → 프로세스)
 │
 ├─ image-spec ────────  무엇을 실행하는가   (레이어 + 설정 = 이미지)
 │
 └─ distribution-spec ─  어떻게 주고받는가   (레지스트리 HTTP API)
```

왜 이게 중요할까요? **셋이 독립이라서 층마다 다른 벤더를 꽂을 수 있기 때문**입니다. 이미지는 도커로 만들고, 나르는 건 GitHub 레지스트리가 하고, 실행은 CRI-O가 하는 조합이 성립하는 이유가 여기 있습니다. 하나로 뭉쳐 있었다면 통째로 갈아타야 했겠죠.

> 기억법: **실행·포장·운반. 셋은 따로 버전을 매기되, 정해진 이음매에서만 만난다.**

여기서 정확히 해 둘 게 있습니다. "독립"은 **서로 무관하다**는 뜻이 아닙니다. 셋은 뒤에서 볼 **Descriptor·media type·Conversion**이라는 정해진 접점에서 맞물립니다. 다만 그 접점 밖에서는 서로의 사정을 몰라도 되고, 그래서 각자 버전을 올릴 수 있습니다. **느슨하게 맞물려 있다**는 게 정확한 표현입니다.

## 어쩌다 표준이 생겼나

잠깐 배경을 보고 갈게요. 길지 않습니다.

**2015년 6월 22일**, Docker와 CoreOS를 비롯한 컨테이너 업계가 **Linux Foundation** 산하에 OCI(Open Container Initiative)를 세웠습니다. 그리고 Docker가 자사의 **컨테이너 포맷과 런타임 runC를 기증**했습니다. OCI는 이 기증물을 표준화 노력의 "주춧돌(cornerstone)"이라고 표현합니다.

여기가 중요합니다. **표준이 먼저 있고 구현이 따라온 게 아니라, 이미 널리 쓰이던 구현을 표준으로 승격시킨 것**입니다. 그래서 runc는 "OCI 런타임 스펙의 참조 구현"이면서 동시에 "스펙의 원본"이기도 합니다. EP1에서 본 그 runc가 맞습니다.

지금 기준(2026-07-27 확인)으로 세 스펙의 최신 버전은 이렇습니다.

| 스펙 | 최신 버전 | 릴리스일 |
| --- | --- | --- |
| image-spec | v1.1.1 | 2025-03-03 |
| runtime-spec | v1.3.0 | 2025-11-04 |
| distribution-spec | v1.1.1 | 2025-01-29 |

버전이 제각각인 게 보이시나요? **셋이 따로 버전을 매깁니다.** 독립이라는 말이 빈말이 아닙니다. (다만 image-spec과 distribution-spec의 v1.1.0은 **같은 날 2024-02-15에 함께** 나왔습니다. 이미지 포맷이 바뀌면 나르는 규약도 같이 바뀌어야 하니 이 둘은 서로를 조금 의식합니다.)

## 1. Runtime Spec — 어떻게 실행하는가

첫 번째 문서부터 봅시다. EP1의 질문에 직접 답하는 문서입니다.

### 번들, 실행의 단위

여기서 헷갈리기 쉬운 포인트를 먼저 짚겠습니다. **런타임 스펙의 입력은 "이미지"가 아닙니다.** `runc`에게 `nginx:latest`를 던져 줄 수 없어요. runc는 이미지가 뭔지 모릅니다.

runc가 받는 것은 **filesystem bundle**(파일시스템 번들)입니다. 생김새는 이렇습니다.

```text
 my-bundle/
   ├── config.json    ← 이 이름이어야 한다(MUST)
   └── rootfs/        ← config.json 의 root.path 가 가리키는 디렉터리
         ├── bin/
         ├── etc/
         └── usr/
```

스펙의 요구는 명확합니다. `config.json`은 **번들 디렉터리 루트에 있어야 하고(MUST), 이름이 정확히 `config.json`이어야 합니다(MUST).** 그리고 컨테이너의 root 파일시스템은 `config.json`의 `root.path`가 가리키는 디렉터리입니다.

재미있는 단서가 하나 붙어 있습니다. 이 산출물들은 한 디렉터리 안에 다 있어야 하지만, "**그 디렉터리 자체는 번들의 일부가 아니다**"라는 것. 그래서 번들을 tar로 말면 `my-bundle/`이라는 상위 폴더 없이 `config.json`과 `rootfs/`가 아카이브 루트에 바로 옵니다.

> 기억법: **번들 = 설정 한 장 + 뿌리 한 그루. 담는 바구니는 번들이 아니다.**

### config.json 안에는 무엇이 있나

`config.json`은 "이 컨테이너를 어떻게 세울 것인가"의 전부입니다. 필수 필드부터 봅시다.

```json
{
  "ociVersion": "1.3.0",
  "root": { "path": "rootfs", "readonly": true },
  "process": {
    "cwd": "/",
    "args": ["/bin/sh"],
    "env": ["PATH=/usr/bin:/bin"]
  },
  "hostname": "lab",
  "mounts": [
    { "destination": "/proc", "type": "proc", "source": "proc" }
  ],
  "linux": { }
}
```

- **`ociVersion`** — REQUIRED. 이 번들이 따르는 런타임 스펙 버전이고, **SemVer v2.0.0 형식**이어야 합니다.
- **`root`** — 스키마상으로는 OPTIONAL이지만 실제로는 조건부입니다. 스펙은 **리눅스를 포함한 그 밖의 모든 플랫폼에서 REQUIRED**, Windows Server Container에서도 REQUIRED라고 하면서, **Hyper-V Container에서는 오히려 설정하면 안 된다**(MUST NOT be set)고 정합니다. 격리 방식이 다르면 root 파일시스템을 다루는 주체도 달라지기 때문입니다. 그 안의 `path`는 REQUIRED.
- **`mounts`** — OPTIONAL. 각 항목의 `destination`(컨테이너 안 경로)은 REQUIRED.
- **`process`** — 여기가 흥미롭습니다.

### 실행은 미루고 나머지는 미리 — EP1의 그 분리

여기가 이 절에서 가장 정밀하게 읽어야 할 대목입니다. `process`는 config.json에서 **OPTIONAL**인데, 스펙에 이런 단서가 붙습니다.

> **"This property is REQUIRED when `start` is called."**
> (이 속성은 `start`가 호출될 때는 REQUIRED다.)

그런데 "create 때는 `process`를 통째로 무시한다"고 읽으면 틀립니다. 스펙의 `create` 항목은 훨씬 세밀하게 갈라 놓았습니다.

> `config.json`에 설정된 속성 중 **`process`를 제외한 전부는 적용돼야 한다(MUST)**.
> **`process.args`는 `start` 연산이 촉발하기 전까지 적용돼서는 안 된다(MUST NOT)**.
> **나머지 `process` 속성은 이 연산에서 적용될 수 있다(MAY)**.

여기서 가장 중요한 줄은 가운데입니다. 미뤄지는 것은 **`process` 전체가 아니라 `process.args`** — 즉 "무엇을 실행할 것인가" 딱 하나입니다. 사용자·권한·환경변수 같은 나머지 `process` 속성은 create 시점에 미리 적용될 수 있습니다.

잠깐, 확인 하나만 해 볼까요? **왜 하필 `args`만 미뤘을까요?**

EP1에서 본 `create`와 `start`의 분리가 여기서 되돌아옵니다. 스펙은 다섯 개의 표준 연산을 규정합니다.

| 연산 | 형태 | 하는 일 |
| --- | --- | --- |
| `create` | `create <container-id> <path-to-bundle>` | 컨테이너 환경을 만든다 |
| `start` | `start <container-id>` | 사용자 지정 프로세스를 실행한다 |
| `kill` | `kill <container-id> <signal>` | 시그널을 보낸다 |
| `delete` | `delete <container-id>` | create가 만든 리소스를 제거한다 |
| `state` | — | 상태를 반환해야 한다(MUST) |

그리고 `create` 단계에 대해 스펙은 이렇게 정합니다 — **"사용자 지정 프로그램은 이 시점에 실행돼서는 안 된다(MUST NOT)."**

이게 왜 필요한지 그림으로 보겠습니다.

```text
[Before] args 까지 create 에서 실행해 버린다면
  runc create+start  ─▶  네임스페이스 생성 → 곧바로 nginx 실행
                              ↑
                    네트워크는 언제 붙이지?
                    nginx 가 이미 뛰고 있는데...

[After] args 만 미루면
  runc create   ─▶  네임스페이스·cgroup·마운트 생성
                    process 의 uid·env 등도 여기서 적용 가능
                    단 args(nginx 실행)만 보류
                       ↓
              여기서 hook 들이 순서대로 돌고
              상위 계층이 veth 를 네트워크 네임스페이스에 꽂는다
                       ↓
  runc start    ─▶  이제야 args 를 실행 = nginx 기동
```

**"환경은 다 갖춰졌는데 아직 안 뛰는" 상태가 존재해야 상위 계층이 끼어들 틈이 생깁니다.** 컨테이너에 네트워크 인터페이스를 붙이는 일은 프로세스가 이미 달리는 중에 하기 어렵습니다. 그래서 스펙은 **`args` 하나만 콕 집어 미룬** 것이고, 나머지는 미리 적용해도 되게 열어 뒀습니다.

여기서 가장 중요한 줄은 **`process.args`는 `start`가 촉발하기 전까지 적용돼서는 안 된다(MUST NOT)** 입니다. **이 한 줄이 "컨테이너 생성"과 "프로그램 실행"을 서로 다른 사건으로 분리합니다.** 만약 이게 없었다면 **CNI(Container Network Interface)** 플러그인도 지금 같은 모양으로 존재하기 어려웠을 겁니다. 컨테이너에 네트워크를 붙이는 일을 표준화한 규약인데, 바로 이 "아직 안 뛰는" 틈에서 일합니다.

(이름이 비슷한 **CRI**가 다음 편 주제입니다. **CNI는 네트워크를 붙이는 규약**, **CRI는 쿠버네티스가 런타임에게 일을 시키는 규약** — 글자 하나 차이지만 하는 일이 완전히 다릅니다. 지금 구분해 두시면 다음 편이 편해집니다.)

그 틈에서 무슨 일이 벌어지는지도 스펙이 순서로 정해 뒀습니다. create와 start 사이에 **hook이 네 종류나** 있습니다.

```text
 create
   ├─ prestart        (DEPRECATED — 오래된 글에서 자주 보이는 그것)
   ├─ createRuntime   ← prestart 를 대체
   ├─ createContainer
   ↓
 start
   ├─ startContainer
   ├─ (사용자 프로그램 실행)
   └─ poststart
```

여기서 헷갈리기 쉬운 포인트가 있습니다. 인터넷 자료 상당수가 이 자리를 **`prestart` hook** 하나로 설명합니다. 그런데 `prestart`는 현재 스펙에서 **DEPRECATED로 표시**돼 있고, `createRuntime`·`createContainer`·`startContainer`가 그 역할을 나눠 받았습니다. 오래된 글을 보실 때 이 점만 감안하시면 됩니다.

### state — 실행 중인 컨테이너의 신분증

`state` 연산이 돌려줘야 하는 필드도 정해져 있습니다.

```text
 ociVersion   이 state 가 따르는 스펙 버전
 id           컨테이너 ID — 이 호스트의 모든 컨테이너에 걸쳐 유일해야 함(MUST)
 status       creating | created | running | stopped
 pid          컨테이너 프로세스의 ID
              (리눅스에서 status 가 created 또는 running 이면 REQUIRED,
               그 밖의 플랫폼에서는 OPTIONAL)
 bundle       번들 디렉터리의 절대 경로 (REQUIRED)
 annotations  선택적 메타데이터 맵
```

`pid`의 조건을 눈여겨봐 주세요. **`stopped` 상태에서는 `pid`가 없어도 됩니다.** 당연합니다 — 이미 끝난 프로세스의 번호를 계속 들고 있을 이유가 없으니까요. 스펙은 이런 자잘한 조건까지 상태별로 갈라 둡니다.

`status`의 네 값을 보시면 앞의 이야기가 그대로 담겨 있습니다. `creating`과 `created`가 따로 있죠. **만들어지는 중과 만들어진 뒤가 구분되고, 그 다음에야 `running`이 옵니다.**

그리고 `annotations`. 별것 아닌 것처럼 보이지만, **스펙이 "너희가 필요한 걸 적어 두라"고 비워 둔 칸**입니다. 스펙은 여기에 무엇이 들어가야 하는지 정하지 않습니다.

그리고 실제 생태계는 이 빈칸 위에서 돌아갑니다. EP1에서 같은 쿠버네티스 파드의 컨테이너들이 shim 하나로 묶이던 것 기억하시나요? 그때 기준이 된 `io.kubernetes.cri.sandbox-id`가 이런 종류의 키입니다. 다만 **어떤 키를 어디에 싣느냐는 스펙이 아니라 구현(containerd·CRI)이 정하는 몫**이라는 점은 구분해 두시는 게 좋습니다.

## 2. Image Spec — 무엇을 담는가

두 번째 문서로 갑니다. 아까 "runc는 이미지를 모른다"고 했죠. 그럼 이미지는 누가 아느냐 — 이 문서가 압니다.

### 일곱 조각

이미지 스펙이 정의하는 구성요소는 일곱 개입니다.

| 구성요소 | 무엇인가 |
| --- | --- |
| **Image Manifest** | 이미지를 구성하는 요소들을 기술하는 문서 |
| **Image Index** | 매니페스트들의 주석 달린 목록(보통 플랫폼별) — 아래 참조 |
| **Image Layout** | 이미지 내용을 담는 파일시스템 레이아웃 |
| **Filesystem Layer** | 컨테이너 파일시스템을 기술하는 **changeset** |
| **Image Configuration** | 레이어 순서와 설정 — 런타임 번들로 변환 가능한 형태 |
| **Descriptor** | 타입·메타데이터·**content address**를 담은 참조 |
| **Conversion** | 이미지 → 런타임 번들 변환 지침 |

일곱 개를 외우실 필요는 없습니다. 대신 **이것들이 서로를 어떻게 가리키는지**만 잡으시면 됩니다.

그 전에 Image Index를 조금만 더 보겠습니다. `docker pull alpine`을 M1 맥에서 치든 x86 서버에서 치든 각자 맞는 이미지가 받아지죠. 그 분기가 일어나는 곳이 여기입니다.

```text
 index.json  (Image Index)
   manifests:
     - digest: sha256:aaa...   platform: { os: linux, architecture: amd64 }
     - digest: sha256:bbb...   platform: { os: linux, architecture: arm64 }
     - digest: sha256:ccc...   platform: { os: linux, architecture: arm, variant: v7 }
```

각 항목에 `platform`이 붙어 있고, 클라이언트가 **자기 OS·아키텍처에 맞는 항목을 골라** 그 매니페스트를 받습니다. `arm`처럼 세대가 갈리는 경우를 위해 `variant`까지 둡니다. **고르는 주체는 레지스트리가 아니라 받는 쪽**이라는 점이 중요합니다 — 그래서 같은 태그가 모든 플랫폼에서 통합니다.

### 다이제스트 사슬

핵심은 이겁니다. **모든 조각이 내용의 해시로 서로를 가리킵니다.**

```text
 index.json  (Image Index)
     │  "linux/amd64 용은 sha256:aaa... 를 봐라"
     ▼
 manifest  (sha256:aaa...)
     ├─ config: sha256:bbb...  ─────┐
     └─ layers:                     │
          sha256:ccc...             │
          sha256:ddd...             │
                                    ▼
                              Image Configuration
                              (Env, Cmd, WorkingDir,
                               레이어 순서 ...)
```

실제 매니페스트는 이렇게 생겼습니다.

```json
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "digest": "sha256:b5b2b2c507a0944348e0303114d8d93aaaa081732b86451d9bce1f432a537bc7",
    "size": 7023
  },
  "layers": [
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "digest": "sha256:9834876dcfb05cb167a5c24953eba58c4ac89b1adf57f28f2f9d09af107ee8f0",
      "size": 32654
    }
  ]
}
```

`config`와 `layers`의 각 항목이 똑같은 모양인 게 보이시나요? `mediaType` + `digest` + `size`. **이 세 쌍이 바로 Descriptor**입니다. 이미지 스펙 전체에서 "무언가를 가리킨다"는 건 전부 이 모양입니다. 그리고 **Descriptor의 `mediaType`은 REQUIRED**입니다 — 가리키는 쪽이 "이게 무엇인지"를 반드시 밝혀야 한다는 뜻이죠.

여기서 가장 중요한 줄은 **`"digest": "sha256:..."`** 입니다. 이게 이름이 아니라 **내용의 해시**라는 점이 모든 것을 바꿉니다.

### 내용이 주소다 — 그래서 따라오는 것들

`digest`가 내용의 해시라는 사실 하나에서 세 가지가 따라옵니다. 다만 뒤로 갈수록 조건이 붙으니 그것까지 같이 보겠습니다.

**① 무결성 검증이 공짜입니다.** 받은 파일을 해시해서 주소와 비교하면 끝입니다. 전송 중에 깨졌거나 바뀌었는지를 별도 장치 없이 확인할 수 있어요. 실제로 이미지 레이아웃 문서는 이런 검증 예시를 보여 줍니다.

```bash
$ shasum -a 256 ./blobs/sha256/afff3924849e...
afff3924849e...  ./blobs/sha256/afff3924849e...
   ↑ 파일 이름과 해시가 같다
```

**② 중복 제거의 근거가 생깁니다.** 두 이미지가 같은 베이스를 쓰면 그 레이어의 다이제스트가 같습니다. 같은 주소면 같은 물건이니 하나만 저장하면 되죠. (실제로 얼마나 아끼는지는 레지스트리의 저장 백엔드·GC 정책에 달렸습니다. 다이제스트는 **가능하게 해 줄 뿐** 자동으로 해 주지는 않습니다.)

**③ 캐시가 강해집니다.** 다이제스트로 요청했는데 이미 갖고 있다면 내려받을 이유가 없습니다. 내용이 바뀌면 주소도 바뀌니 stale 캐시 걱정도 없고요. 반대로 **태그로 요청하면** 그 태그가 여전히 같은 걸 가리키는지 매번 확인해야 하므로 이 이점이 약해집니다.

#### 다이제스트가 두 종류라는 것

여기서 한 겹 더 들어가겠습니다. 조금 헷갈리는 대목이지만 알고 나면 개운합니다.

매니페스트의 `layers[].digest`는 **전송되는 파일(보통 gzip으로 압축된 tar)의 해시**입니다. 그런데 이미지 설정(Image Configuration) 안에는 `rootfs.diff_ids`라는 별도 목록이 있고, 여기 담긴 값은 **압축을 푼 tar의 해시**입니다. 이걸 **DiffID**라고 부릅니다.

```text
 layers[].digest   =  sha256( layer.tar.gz )   ← 나를 때 쓰는 주소
 rootfs.diff_ids   =  sha256( layer.tar )      ← 풀어서 쌓을 때 쓰는 신원
```

왜 둘로 나눴을까요? **압축 방식이 바뀌어도 내용물의 신원은 그대로여야 하기 때문**입니다. 같은 레이어를 gzip 대신 zstd로 다시 압축하면 전송 파일의 해시는 달라지지만, 풀어 놓은 결과는 똑같으니 DiffID는 그대로입니다. 그래서 **"이 레이어 이미 갖고 있나?"를 판단할 때는 DiffID를 봅니다.**

앞서 media type에 `+gzip`과 `+zstd` 두 갈래가 있던 걸 기억하시나요? 그 선택지가 존재할 수 있는 이유가 바로 이 분리입니다.

> 기억법: **이름으로 부르면 바뀔 수 있고, 내용으로 부르면 바뀔 수 없다.**

그래서 실무에서는 태그(`nginx:latest`)가 아니라 다이제스트(`nginx@sha256:...`)로 배포를 고정합니다. 태그는 **가리키는 대상이 바뀔 수 있는 이름표**지만, 다이제스트는 정의상 그 내용 자체이기 때문입니다.

### 여기서 반드시 선을 그어야 합니다 — 다이제스트는 서명이 아닙니다

앞의 ①을 "다이제스트가 있으니 보안이 해결됐다"로 읽으면 **위험합니다.** 다이제스트가 보장하는 것과 보장하지 않는 것을 갈라 두겠습니다.

```text
 다이제스트가 보장하는 것 (무결성)
   ✔ 내가 받은 바이트가 기대한 바이트와 같은가
   ✔ 전송 중 변조·손상이 없었는가

 다이제스트가 보장하지 않는 것 (출처·신뢰)
   ✘ 이걸 누가 만들었는가
   ✘ 믿을 만한 빌드 파이프라인에서 나왔는가
   ✘ 배포자가 이 버전을 승인했는가
   ✘ 안에 악성 코드가 없는가
```

공격자가 자기 이미지를 올리고 그 다이제스트를 알려 주면, 여러분은 **"받은 게 그것이 맞다"는 것만 완벽하게 검증**하게 됩니다. 그 "그것"이 안전한지는 전혀 다른 문제죠.

출처와 신뢰는 **서명·증명 체계가 따로** 담당합니다 — Sigstore/cosign 같은 이미지 서명, SBOM(Software Bill of Materials) 첨부, 빌드 출처 증명(provenance attestation) 같은 것들입니다. 앞에서 본 `referrers` API가 바로 그런 부속물을 이미지에 매다는 통로고요.

> 기억법: **다이제스트는 "그것이 맞다"를 말하지, "그것이 안전하다"를 말하지 않는다.**

### 디스크 위의 모습 — Image Layout

이미지를 파일시스템에 풀어 놓으면 이렇게 생겼습니다.

```text
 ./index.json                    ← 진입점
 ./oci-layout                    ← imageLayoutVersion 필드를 담아야 함(MUST)
 ./blobs/
     └── sha256/
           ├── 3588d0254223...   ← 파일 이름 = 내용의 해시
           ├── 4b0bc1c4050b...
           └── 7968321274dc...
```

`blobs/` 아래는 **해시 알고리즘별로 디렉터리를 두고 그 안에 실제 내용을 담습니다.** 그래서 `sha256/` 폴더가 있는 것이고, 나중에 다른 알고리즘이 필요해지면 폴더가 하나 더 생기면 그만입니다.

여기서 헷갈리기 쉬운 포인트가 있습니다. **`blobs/` 안의 파일들은 종류가 섞여 있습니다.** 매니페스트도, 설정도, 레이어 tar도 전부 같은 디렉터리에 해시 이름으로 누워 있어요. 파일만 봐서는 뭐가 뭔지 알 수 없습니다. **무엇인지는 그 파일을 "가리키는 쪽"의 Descriptor `mediaType`이 알려줍니다.** 앞서 본 대로 Descriptor의 `mediaType`이 REQUIRED인 이유가 이것입니다 — 그게 없으면 해시 이름 파일 더미 앞에서 아무것도 해석할 수 없습니다.

정확한 media type 문자열은 이렇습니다.

```text
application/vnd.oci.image.index.v1+json      ← 인덱스
application/vnd.oci.image.manifest.v1+json   ← 매니페스트
application/vnd.oci.image.config.v1+json     ← 설정
application/vnd.oci.image.layer.v1.tar       ← 레이어(비압축)
application/vnd.oci.image.layer.v1.tar+gzip  ← 레이어(gzip)
application/vnd.oci.image.layer.v1.tar+zstd  ← 레이어(zstd)
```

## 3. Distribution Spec — 어떻게 나르는가

마지막 문서입니다. 그리고 아마 가장 김이 빠지실 겁니다. **레지스트리는 HTTP API 서버입니다.** 마법 상자가 아니라 GET·POST·PATCH·PUT·DELETE의 조합이에요.

다만 "정적 파일 서버처럼 단순하다"는 뜻은 아닙니다. 실제 호환성을 떠받치는 건 media type 협상(`Accept` 헤더), 베어러 토큰 인증, 리다이렉트, 청크 업로드, Range 요청, `Docker-Content-Digest` 헤더, 정해진 에러 코드 같은 **계약들**입니다. 잠시 뒤 실습에서 이 계약들을 직접 만나시게 됩니다.

### `/v2/` 하나로 시작한다

모든 연산이 `/v2/` 접두사를 씁니다. 레지스트리인지 확인하는 첫걸음도 여기입니다.

```text
 GET /v2/
   ├─ 200 OK    → 인증 없이 쓸 수 있는 레지스트리
   └─ 401       → 레지스트리는 맞는데 인증이 필요하다
                  응답의 WWW-Authenticate 헤더가
                  "어디서 토큰을 받아 오라"고 알려준다
```

여기서 헷갈리기 쉬운 포인트를 미리 짚겠습니다. **`401`은 실패가 아닙니다.** 잠시 뒤 실습에서 Docker Hub에 요청하면 `401`이 오는데, 이건 "레지스트리가 아니다"가 아니라 "맞다, 그런데 신분을 밝혀라"라는 정상 응답입니다. 공개 이미지를 받을 때조차 익명 토큰을 한 번 받아야 하는 이유가 이것입니다.

### pull은 요청 두 번이면 시작된다

이미지를 받는 과정은 이렇게 생겼습니다.

```text
 ① 매니페스트를 받는다
    GET /v2/<name>/manifests/<tag-or-digest>
    → 200 + 매니페스트 JSON + Docker-Content-Digest 헤더

 ② 매니페스트에 적힌 다이제스트로 blob 을 받는다
    GET /v2/<name>/blobs/<digest>      ← config
    GET /v2/<name>/blobs/<digest>      ← layer 1
    GET /v2/<name>/blobs/<digest>      ← layer 2
    ...
```

**①에서 받은 문서가 ②에서 무엇을 받을지 알려줍니다.** 앞 절에서 본 다이제스트 사슬이 그대로 네트워크 요청 순서가 되는 거예요. 이미지 스펙과 배포 스펙이 만나는 지점이 여기입니다.

blob 요청은 HTTP Range 요청을 지원합니다(RFC 9110). 그래서 큰 레이어를 받다 끊겨도 이어받을 수 있습니다.

### push는 세션을 연다

올리는 쪽은 조금 더 복잡합니다. 큰 파일을 다루니까요.

```text
 ① 업로드 세션 시작
    POST /v2/<name>/blobs/uploads/
    → 202 Accepted + Location: <업로드 주소>

 ② 그 주소로 내용을 보낸다
    PUT <location>?digest=<digest>
    → 201 Created

    (큰 파일이면 나눠서)
    PATCH <location>  → 202   ← 청크마다
    PATCH <location>  → 202
    PUT   <location>?digest=<digest>  → 201

 ③ 마지막에 매니페스트를 올린다
    PUT /v2/<name>/manifests/<tag-or-digest>
    → 201 Created
```

순서를 눈여겨봐 주세요. **매니페스트가 마지막입니다.** 당연합니다 — 매니페스트는 blob들을 가리키는 문서인데, 가리킬 대상이 아직 없는데 먼저 올릴 수는 없죠. 그래서 push는 **잎에서 뿌리 방향**으로, pull은 **뿌리에서 잎 방향**으로 갑니다.

> 기억법: **받을 땐 지도부터, 보낼 땐 짐부터.**

### 교차 저장소 마운트 — 다이제스트가 벌어 준 것

배포 스펙에 이런 요청이 있습니다.

```text
 POST /v2/<name>/blobs/uploads/?mount=<digest>&from=<other_name>
 → 201 Created
```

무슨 뜻일까요? "**이 다이제스트, 저쪽 저장소에 이미 있으니 거기서 가져다 쓰세요**"라는 요청입니다. 성공하면 `201`이 오고, 업로드는 아예 일어나지 않습니다.

이게 왜 가능한지 생각해 보시면 앞 절의 이야기가 되돌아옵니다. **내용이 곧 주소이기 때문**입니다. `myapp/backend`의 `sha256:abc...`와 `myapp/frontend`의 `sha256:abc...`는 같은 주소니 같은 물건일 수밖에 없습니다. 그러니 다시 올릴 이유가 없죠.

같은 베이스 이미지를 공유하는 저장소가 수십 개일 때, 이 한 줄이 수 GB의 전송을 없앱니다.

### 그 밖에

- **태그 목록**: `GET /v2/<name>/tags/list` — 페이지네이션은 `?n=&last=`, 응답의 `Link` 헤더로 다음 쪽을 알려줍니다.
- **referrers**: `GET /v2/<name>/referrers/<digest>` — "이 이미지를 가리키는 다른 아티팩트(서명·SBOM 등)를 찾아 달라"는 요청입니다. v1.1에서 들어온 비교적 새 기능입니다.
- **삭제**: 태그·매니페스트·blob 모두 `DELETE`로 지우며 `202 Accepted`가 옵니다. 레지스트리가 삭제를 막아 뒀으면 `400` 또는 `405`가 오고요.

  여기에 단서 두 개가 붙습니다. 첫째, 태그 삭제와 매니페스트 삭제는 **같은 `/manifests/` 경로**를 쓰지만 뒤에 태그를 주느냐 다이제스트를 주느냐에 따라 의미가 다릅니다(이름표 하나를 떼는 것 vs 그 매니페스트 자체를 지우는 것). 둘째, **`202`가 왔다고 디스크가 즉시 비지 않습니다.** 실제 blob 회수는 레지스트리의 GC 정책이 따로 담당합니다. "지웠는데 용량이 그대로"인 이유가 대개 이것입니다.

이름 규칙도 정해져 있습니다. 태그는 `[a-zA-Z0-9_][a-zA-Z0-9._-]{0,127}` — **최대 128자**이고 첫 글자에 `-`나 `.`을 쓸 수 없습니다.

## 세 스펙이 만나는 지점

이제 셋을 이어 붙일 차례입니다. 아까 이미지 스펙의 일곱 조각 중 마지막이 **Conversion**이었죠. 그게 이음매입니다.

```text
 [image-spec]                      [distribution-spec]
  Image Index                        GET /v2/.../manifests/...
      ↓                              GET /v2/.../blobs/...
  Image Manifest  ←─────────────────  이 경로로 실어 나른다
      ↓
  Config + Layers
      │
      │  Conversion — 레이어를 풀어 rootfs 를 만들고
      │               Config 의 Env·Cmd·WorkingDir 를
      │               config.json 의 process 로 옮긴다
      ▼
 [runtime-spec]
  번들 = config.json + rootfs/
      ↓
  create → start → running
```

<VizFlowchart4 />

**이미지 설정(Image Configuration)의 정의 자체가 "런타임 번들로 변환하기 적합한 형태"입니다.** 스펙이 처음부터 이 변환을 염두에 두고 설계된 거예요.

그리고 이 그림에서 EP1의 질문에 대한 답이 나옵니다. shim이 부를 수 있는 "다른 엔진"의 자격은 — **번들을 받아 runtime-spec의 다섯 연산을 구현하는 것**입니다. 이미지를 이해할 필요도, 레지스트리와 통신할 필요도 없습니다. 그 위층이 이미 다 해서 번들로 만들어 주니까요. 그래서 crun도 youki도 gVisor의 runsc도 자리를 바꿔 낄 수 있습니다.

## 오해하기 쉬운 포인트

**오해 1. "OCI 이미지와 도커 이미지는 완전히 같다"(또는 "완전히 다르다").**
양쪽 다 부정확합니다. 정확히는 **혈연이 있고 상호운용되지만 같지는 않습니다.** OCI Image Spec은 Docker Image Manifest V2 Schema 2에서 출발했고 구조가 거의 겹칩니다. 그래서 실무에서 서로 오갑니다.

다른 점은 세 층위입니다.

```text
 ① media type 문자열
    application/vnd.docker.distribution.manifest.v2+json
    application/vnd.oci.image.manifest.v1+json

 ② 여러 플랫폼을 묶는 상위 문서의 이름
    Docker: manifest list      OCI: image index

 ③ OCI 쪽에만 있는 것
    artifactType, subject, referrers  (서명·SBOM 같은 부속물 매달기)
```

그래서 실무에서는 **레지스트리와 런타임이 양쪽 타입을 모두 받아 주고 필요하면 변환하는** 방식으로 굴러갑니다. 앞의 실습에서 `Accept` 헤더를 두 줄 넣은 게 바로 그 현실을 반영한 것이고요. "포맷이 하나다"라고 외우기보다 "**두 계보가 서로를 받아 준다**"로 이해하시는 편이 실무에서 덜 당황합니다.

**오해 2. "번들이 곧 이미지다."**
아닙니다. 이미지는 **레이어들이 압축된 채 다이제스트로 묶인 것**이고, 번들은 **그걸 풀어서 실행 직전 상태로 만든 것**입니다. 이미지는 나르기 위한 형태, 번들은 실행하기 위한 형태예요. 둘 사이에 Conversion이 있습니다.

**오해 3. "레지스트리는 특별한 서버다."**
`/v2/`로 시작하는 HTTP API를 구현하면 그게 레지스트리입니다. 인증·저장·GC 같은 실무 요소가 붙어서 복잡해 보일 뿐, 스펙 자체는 GET·POST·PATCH·PUT·DELETE의 조합입니다.

**오해 4. "태그로 배포를 고정할 수 있다."**
태그는 **다시 가리킬 수 있는 이름표**입니다. 같은 `v1.2.3` 태그가 어제와 오늘 다른 이미지를 가리킬 수 있어요. 고정이 필요하면 다이제스트(`image@sha256:...`)를 쓰셔야 합니다.

## 직접 해보기

레지스트리가 정말 평범한 HTTP인지 손으로 확인해 봅시다. 도커 없이 `curl`과 `jq`만 있으면 됩니다.

1. **레지스트리인지 확인합니다.**
   ```bash
   curl -sI https://registry-1.docker.io/v2/ | head -3
   ```
   기대 결과: `401`이 옵니다. **인증이 필요하다는 뜻이지 없다는 뜻이 아닙니다** — `Www-Authenticate` 헤더가 어디서 토큰을 받아야 하는지 알려 줍니다.

2. **익명 토큰을 받습니다.**
   ```bash
   TOKEN=$(curl -s "https://auth.docker.io/token?service=registry.docker.io&scope=repository:library/alpine:pull" | jq -r .token)
   ```

3. **매니페스트를 받습니다.** (Accept 헤더로 어떤 media type을 원하는지 알려야 합니다)
   ```bash
   curl -s -H "Authorization: Bearer $TOKEN" \
     -H "Accept: application/vnd.oci.image.index.v1+json" \
     -H "Accept: application/vnd.docker.distribution.manifest.list.v2+json" \
     https://registry-1.docker.io/v2/library/alpine/manifests/latest | jq .
   ```
   관찰 포인트: **인덱스**가 옵니다. 플랫폼별 매니페스트 목록이 보이실 거예요. 각 항목의 `digest`와 `platform`을 확인해 보세요.

4. **플랫폼 하나를 골라 매니페스트를 받습니다.**
   ```bash
   DIGEST=<위에서 고른 linux/amd64 의 digest>
   curl -s -H "Authorization: Bearer $TOKEN" \
     -H "Accept: application/vnd.oci.image.manifest.v1+json" \
     -H "Accept: application/vnd.docker.distribution.manifest.v2+json" \
     "https://registry-1.docker.io/v2/library/alpine/manifests/$DIGEST" | jq .
   ```
   관찰 포인트: `config`와 `layers`가 보입니다. **본문에서 본 Descriptor 모양(mediaType + digest + size) 그대로**입니다.

   `Accept`를 **두 줄** 넣은 걸 눈여겨봐 주세요. Docker Hub의 이미지 상당수는 하위 매니페스트가 아직 Docker Schema 2 타입으로 저장돼 있습니다. OCI 타입만 요구하면 레지스트리가 줄 게 없다고 답할 수 있어요. **이게 앞서 말한 "media type 협상"이 실제로 필요한 순간**입니다.

5. **레이어 하나를 받아 다이제스트를 검증합니다.**
   ```bash
   LAYER=<layers[0].digest>
   curl -sL -H "Authorization: Bearer $TOKEN" \
     "https://registry-1.docker.io/v2/library/alpine/blobs/$LAYER" \
     | shasum -a 256
   ```
   관찰 포인트: 출력된 해시가 `$LAYER`의 `sha256:` 뒤 부분과 **일치**합니다. 내용이 곧 주소라는 걸 손으로 확인하는 순간입니다.

한 문장으로 줄이면 이렇습니다 — **이미지를 받는다는 건 다이제스트 사슬을 따라 HTTP GET을 몇 번 하는 일이다.**

## 스스로 점검하기

1. `runc`에게 `nginx:latest`를 그대로 넘길 수 없는 이유를 한 문장으로 설명해 보세요.
2. `config.json`의 `process`가 OPTIONAL인데도 `start` 시점에는 REQUIRED인 이유는 무엇일까요?
3. push할 때 매니페스트를 **마지막에** 올리는 이유는 무엇일까요?
4. 팀에서 "배포는 `v1.2.3` 태그로 고정한다"고 정했습니다. 이 방식의 위험은 무엇이고, 어떻게 바꾸면 될까요?

<details>
<summary>답 확인</summary>

1. runc의 입력은 이미지가 아니라 **번들**(`config.json` + `rootfs/`)이기 때문입니다. 이미지를 번들로 바꾸는 Conversion은 상위 계층의 일입니다.
2. `create`와 `start`를 분리해 **"만들어졌지만 아직 안 뛰는" 창**을 열어 두기 위해서입니다. 그 창에서 상위 계층이 네트워크를 붙이거나 hook을 실행합니다. 실행 시점에는 무엇을 실행할지 반드시 알아야 하므로 그때는 REQUIRED가 됩니다.
3. 매니페스트는 blob들을 **가리키는** 문서라서, 가리킬 대상이 레지스트리에 먼저 존재해야 합니다. 그래서 push는 잎(blob)에서 뿌리(매니페스트) 방향입니다.
4. 태그는 **다시 가리킬 수 있는 이름표**라 같은 `v1.2.3`이 다른 이미지를 가리키도록 덮어써질 수 있습니다. 재현 가능한 배포가 필요하면 다이제스트(`image@sha256:...`)로 고정하면 됩니다.

</details>

## 마무리 — 핵심 다시 짚기

한 문장으로 줄이면 이렇습니다.

> **OCI는 컨테이너를 셋으로 쪼갰고, 그 덕에 층마다 다른 도구를 꽂을 수 있게 됐다.**

- **runtime-spec** — 입력은 이미지가 아니라 **번들**(`config.json` + `rootfs/`). 연산은 create·start·kill·delete·state 다섯 개. **create/start 분리**가 상위 계층이 끼어들 틈을 만든다.
- **image-spec** — Index → Manifest → Config + Layers가 **다이제스트로 서로를 가리킨다.** 내용이 주소라서 검증·중복 제거·캐시가 공짜로 따라온다.
- **distribution-spec** — `/v2/` 하나로 시작하는 **평범한 HTTP**. pull은 뿌리에서 잎으로, push는 잎에서 뿌리로.
- **Conversion**이 이미지와 번들을 잇는다. 그래서 저수준 런타임은 이미지를 몰라도 자기 일을 할 수 있다.

이제 EP1의 질문에는 답했습니다. 그런데 새 질문이 생깁니다.

지금까지 본 건 **컨테이너 하나**를 만들고 나르고 실행하는 이야기였습니다. 그런데 쿠버네티스는 컨테이너를 하나씩 다루지 않죠. **파드**라는 단위로 묶어 다루고, 노드마다 수십 개를 띄웁니다. 그리고 OCI 어디에도 "파드"라는 말은 없습니다.

그럼 쿠버네티스는 런타임에게 **무슨 말로** 지시를 내릴까요? 다음 편에서는 kubelet과 런타임 사이의 계약, **CRI**(Container Runtime Interface)를 봅니다. 2022년에 "쿠버네티스가 도커를 버렸다"는 말이 돌았던 그 사건의 정체도 거기서 밝혀집니다.
