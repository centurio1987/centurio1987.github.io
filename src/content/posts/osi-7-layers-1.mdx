주소창에 도메인을 치고 Enter를 누릅니다. 잠시 뒤 화면이 뜹니다. 그 짧은 사이에 무슨 일이 벌어졌을까요.

여러분이 친 문자열은 암호화되고 잘게 나뉘어집니다. 거기에 주소표가 붙고 프레임에 실린 뒤, 마지막에는 구리선의 전압이나 광섬유의 빛, 안테나의 전파가 되어 날아가죠. 받는 쪽 종단에서는 그 포장을 역순으로 벗겨냅니다.

문제는 그 화면이 끝내 뜨지 않을 때입니다.

> "인터넷이 안 돼요."

그 말 뒤에는 여러 가지 사정이 있을 수 있습니다. 케이블이 죽었을 수도 있고, 라우팅이 어긋났을 수도 있고, 인증서가 만료됐을 수도 있죠. 원인은 서로 아무 관계가 없는데 증상을 전하는 말은 저 한마디뿐입니다. 무작정 브라우저를 재시작하고 DNS를 8.8.8.8로 바꿔 보는 사람이 있는가 하면, 어디서 막혔는지 한 계단씩 좁혀 물어 내려가는 사람이 있죠. 둘을 가르는 것은 지식의 양이 아닙니다. 질문의 순서입니다.

이 글은 그 순서를 따라가는 여정입니다. 끝까지 읽으시면 머릿속에 데이터의 여행 전체가 한 장으로 펼쳐지고, 지금 어느 책임이 제 몫을 못 했는지를 아래에서 위로 짚어 올라갈 수 있게 됩니다. 계층 이름 일곱 개를 외우자는 이야기가 아닙니다. 그 질문을 던질 수 있게 되는 것, 그것이 이 글의 목표입니다.

## 먼저 바로잡기: OSI는 인터넷의 설계도가 아니다

네트워크를 배우기 시작하면 거의 예외 없이 이런 설명과 마주치게 됩니다.

> 인터넷은 OSI 7계층으로 동작한다.

외우기에는 편한 문장이지만, 엄밀히 따지고 들면 사실이 아닙니다.

ISO/IEC 7498-1이 정의하는 OSI(Open Systems Interconnection) 모델은 참조 모델이어서, 서로 다른 표준을 한자리에 놓고 견주어 보거나 기존 표준이 전체 구조의 어디쯤에 놓이는지 설명하려고 만든 좌표계에 가깝습니다. 운영체제가 어떤 함수를 어떤 순서로 부르는지, 패킷의 바이트가 실제로 어떻게 늘어서는지까지 강제하지는 않습니다.

오늘날 인터넷 프로토콜 모음은 보통 Link, Internet, Transport, Application의 네 층으로 설명하는데, RFC 1122가 쓰는 구조가 바로 이것이고, 여기서는 인터넷의 Application 계층이 OSI의 Application과 Presentation 기능을 사실상 함께 떠맡습니다. 교재에 따라서는 Link를 Physical과 Data Link로 한 번 더 쪼개 5계층으로 가르치기도 하는데, 경계를 어디에 긋느냐의 차이일 뿐이죠.

그래서 TLS는 무조건 L6, HTTP는 무조건 L7이라고 못 박는 분류는 학습용 근사에 지나지 않습니다. 실제 구현에서는 경계가 겹치고, 터널링처럼 한 계층의 프로토콜이 통째로 다른 계층의 payload가 되어 실려 가기도 하니까요.

그렇다면 OSI는 왜 아직도 배울 값이 있을까요. 책임의 경계와 관찰 지점을 알려 주기 때문입니다. 케이블이 끊긴 사고와 DNS 이름 해석 실패를 같은 방식으로 다루지 않도록 막아 주죠. 지도는 땅이 아닙니다. 그래도 길을 찾을 때 우리는 지도를 폅니다.

## 한눈에 보는 일곱 책임

| 계층 | 핵심 질문 | 대표 기능·프로토콜 | 흔히 보는 전송 단위 |
| --- | --- | --- | --- |
| L7 Application | 사용자가 원하는 네트워크 기능은 무엇인가? | HTTP, DNS, SMTP, SSH | Data/Message |
| L6 Presentation | 데이터를 어떤 형식으로 표현·보호할까? | TLS, UTF-8, JSON, JPEG | Data |
| L5 Session | 대화의 시작·유지·복구 상태를 누가 관리할까? | RPC 세션, 체크포인트, 애플리케이션 세션 | Data |
| L4 Transport | 어느 프로세스까지, 어떤 신뢰도로 전달할까? | TCP, UDP, QUIC의 전송 기능 | Segment/Datagram |
| L3 Network | 여러 네트워크를 건너 목적지까지 어떻게 갈까? | IPv4, IPv6, ICMP, IPsec | Packet |
| L2 Data Link | 같은 링크에서 다음 장치까지 어떻게 보낼까? | Ethernet, Wi-Fi MAC, VLAN, ARP/ND 인접 처리 | Frame |
| L1 Physical | 비트를 매체 위 신호로 어떻게 바꿀까? | 1000BASE-T, 광 이더넷, 무선 PHY | Bits/Symbols |

표를 통째로 외우실 필요는 없습니다. PDU(Protocol Data Unit) 이름은 문헌과 문맥에 따라 조금씩 달라지고, 시험이 아닌 다음에야 그 이름을 물어보는 사람도 없으니까요. 정작 눈여겨보셔야 할 것은 각 계층이 어떤 메타데이터를 덧붙이고 어디까지 책임을 지는가입니다.

한 가지만 더 짚고 넘어가겠습니다. 참조 모델을 헤더 붙이는 일곱 단계로만 읽으면 절반밖에 못 본 것인데, OSI에는 문법이 셋 있기 때문입니다.

- 각 계층은 바로 위 계층에 service(서비스)를 제공한다.
- 그 경계는 interface(인터페이스)로 정의된다.
- 같은 계층끼리는(예: 양쪽 호스트의 TCP) 보이지 않는 peer(대등) 관계로 protocol을 주고받는다.

그래서 내 TCP는 상대편 TCP와 직접 말을 주고받는 것처럼 동작하지만, 실제 바이트는 아래 계층의 service를 빌려 내려갔다 다시 올라옵니다. 캡슐화란 이 구조가 물리적으로 남긴 흔적일 뿐이죠.

## 핵심 원리: 캡슐화는 책임을 겹겹이 포장하는 일이다

말로 풀기 전에 먼저 보여 드리겠습니다. 송신 애플리케이션이 만든 데이터가 아래로 내려가는 모습입니다.

```text
HTTP message
  -> [TCP header | HTTP message]
  -> [IP header | TCP header | HTTP message]
  -> [Ethernet header | IP header | TCP header | HTTP message | FCS]
  -> 물리 매체의 신호
```

한 계단 내려갈 때마다 그 계층이 제 일을 하는 데 필요한 header가 덧붙고, 경우에 따라서는 trailer까지 따라붙습니다.

![캡슐화: 계층을 내려갈 때마다 헤더가 덧붙고, 맨 아래에서 신호가 된다](/images/osi-7-layers-1/encapsulation.webp)

받는 쪽에서는 이 계단을 거꾸로 밟아 올라갑니다. Ethernet 인터페이스가 frame을 검사해 payload인 IP packet을 위로 넘기면, IP는 목적지와 상위 프로토콜 번호를 보고 그것을 TCP에 건네고, TCP는 port를 근거로 올바른 프로세스의 socket에 byte stream을 부어 줍니다. 마지막으로 HTTP 구현이 그 message의 의미를 해석해 냅니다.

이 구조가 안정적으로 돌아가는 바탕에는 인접한 두 계층이 맺어 둔 계약이 있습니다. L3는 그 안에 JSON이 들었는지 이미지가 들었는지 전혀 몰라도 packet을 옮기고, L7은 Ethernet FCS를 어떻게 계산하는지 몰라도 요청을 띄웁니다. 서로 모릅니다. 그래서 한쪽이 바뀌어도 다른 쪽은 그대로 있을 수 있습니다.

시뮬레이터를 송신 방향에 두고 L7에서 L1까지 차례로 눌러 보십시오. 상위 계층이 담은 뜻은 그대로 보존되는 대신 각 홉과 종단이 처리해야 할 정보가 겹겹이 덧붙는 모습이 보이는데, L6에서 압축이나 암호화를 거치고 나면 실제 바이트 표현까지 달라집니다. 이번에는 수신 방향으로 돌려 보십시오. 각 계층이 제 몫의 정보만 꺼내 쓰고 나머지를 위로 넘기는 과정이 그대로 드러납니다.

## L1 Physical: 비트가 실제 세계를 만나는 곳

현장에는 오래된 농담이 하나 있습니다. 장애의 절반은 케이블이라는 것이죠. 과장이 섞였지만 방향만큼은 맞습니다. 아무리 정교한 프로토콜을 얹어 놓아도 L1이 죽어 버리면 한 글자도 내보내지 못하니까요.

L1은 0과 1을 물리 신호로 바꿔 내보내는 계층입니다. 구리선의 전압 변화, 광섬유의 빛, 무선의 전자기파. connector 형태, 주파수, 변조·부호화 방식, bit rate, 전송 거리가 모두 여기 속합니다. IEEE 802.3 Ethernet 표준도 Physical Layer가 frame을 매체에 맞는 modulation으로 encode하고 수신 신호를 다시 decode한다고 규정하고 있죠.

여기 속하는 물건은 cable, 광 transceiver 부품(SFP/SFP+), media converter, 그리고 repeater·hub입니다. SFP/SFP+는 독립된 장비라기보다 인터페이스 슬롯에 꽂아 쓰는 L1 부품으로 보는 편이 정확하고요. hub는 현대 유선망에서 거의 자취를 감췄는데도 교육용으로는 여전히 쓸모가 남아 있습니다. 들어온 신호를 그저 다른 port로 되풀이해 내보낼 뿐, MAC 주소를 읽어 목적지를 고르는 일은 하지 않으니까요. 그래서 hub에 물린 모든 port가 충돌 영역 하나를 나눠 쓰게 됩니다. L1과 L2의 차이를 이보다 선명하게 보여 주는 예는 없습니다.

정작 실무에서 자주 손대게 되는 L1 요소는 따로 있습니다. 광 transceiver와 media converter, 그리고 거기서 읽어 내는 광 power와 온도 지표죠.

**관찰할 것** — link LED와 interface의 up/down 상태, 그리고 광 power를 봅니다. 간헐적으로 끊긴다면 symbol·alignment·carrier error가 얼마나 늘어나고 있는지 확인해야 하고요. frame 단위의 FCS/CRC 오류는 엄밀히 L2 책임이라 이 칸에서는 세지 않습니다.

## L2 Data Link: 같은 링크의 다음 한 걸음

질문을 하나 드리겠습니다.

> 서울에서 미국에 있는 웹 서버로 요청을 보낼 때, Ethernet frame의 목적지 MAC 주소 자리에는 무엇이 들어갈까요?

그 서버의 MAC 주소라고 답하셨다면 여기서 한 번 걸리신 겁니다. 실제로 그 자리를 차지하는 것은 여러분 쪽 기본 gateway이고, 집이라면 책상 옆에 놓인 공유기죠.

L2는 하나의 link 또는 broadcast domain 안에서만 frame을 옮겨 주는 계층입니다. Ethernet frame에는 출발지와 목적지 MAC 주소, 상위 protocol을 가리키는 EtherType, 오류를 검출하는 FCS(Frame Check Sequence)가 실립니다. switch와 bridge는 오가는 frame의 source MAC을 학습해 forwarding table을 채운 뒤, destination MAC에 맞는 port로만 그것을 흘려보내죠.

목적지가 다른 IP network에 있으면 host는 기본 gateway의 L2 주소로 frame을 띄웁니다. IP destination은 원격 서버 그대로 유지되는 반면 Ethernet destination은 첫 번째 router interface로 바뀌고, router를 한 번 지날 때마다 L2 frame은 통째로 새로 만들어집니다. 여행 내내 지고 가는 것과 한 구간마다 갈아타는 것. 이 둘을 갈라 볼 수 있게 되는 순간 L2와 L3가 머릿속에서 분리됩니다.

관련 기술은 다음과 같습니다.

- **Ethernet(IEEE 802.3)**: 유선 LAN의 frame과 여러 PHY 규격을 정의합니다.
- **Wi-Fi(IEEE 802.11)**: 무선 매체 접근과 frame 전달을 정의합니다. Ethernet과 같은 L2로 묶어 설명하지만 frame 형식과 매체에 접근하는 방식은 다릅니다.
- **VLAN(IEEE 802.1Q)**: 하나의 물리 switch 인프라를 여러 논리 broadcast domain으로 갈라 씁니다.
- **ARP(Address Resolution Protocol) / Neighbor Discovery**: IPv4 주소에 대응하는 같은 링크의 MAC 주소를 알아냅니다. IPv6에서는 ICMPv6 기반 Neighbor Discovery(ND)가 이 역할을 넘겨받았고요. 엄밀히 따지면 L3 주소를 L2 주소로 잇는 다리라서 ARP를 흔히 L2.5라 부르고, ND는 ICMPv6(L3) 위에서 도는 동작으로 봅니다. 계층 번호를 놓고 다투기보다 같은 링크 안에서 주소를 해석하는 책임으로 묶어 두는 편이 실용적이죠.
- **STP(Spanning Tree Protocol) 계열**: L2 loop가 만들어 내는 broadcast storm을 막으려고 일부 경로를 논리적으로 끊어 둡니다.

**관찰할 것** — 인터페이스 상태와 이웃 주소 해석 결과, 그리고 switch의 MAC address table을 봅니다.

```bash
ip link
ip neigh          # 또는 arp -a
```

VLAN tag가 어긋나 있지는 않은지, interface CRC error가 올라가고 있지는 않은지도 함께 확인합니다.

## L3 Network: 여러 링크를 건너는 경로

IPv6 명세를 펼치면 packet의 정의가 놀랄 만큼 간단하게 적혀 있습니다. IPv6 header에 payload를 더한 것. 그리고 header의 `Next Header` 필드가 뒤따라오는 extension header나 TCP·UDP 같은 upper-layer protocol을 가리키죠. 캡슐화가 교과서 속 그림이 아니라 실제 bit field였다는 증거입니다.

L3는 서로 다른 network 사이로 packet을 실어 나릅니다. IP address가 interface의 논리적 위치를 나타내면, router는 destination prefix와 routing table을 맞춰 보며 다음 hop을 정하죠. RFC 8200은 router를 자신에게 명시적으로 향하지 않은 IPv6 packet을 forwarding하는 node로 정의하고 있습니다.

여기서 잘못 이해하기 쉬운 부분을 하나 짚고 넘어가겠습니다. router는 Ethernet frame을 그대로 통과시키지 않습니다. 입력된 L2 frame을 벗겨 내고 IP header를 검사한 다음 Hop Limit을 하나 줄이고서, 출력 interface에 맞는 새 L2 frame으로 다시 감싸 내보냅니다. 그래서 평범한 routed path에서 MAC 주소는 hop마다 갈아 끼워지는데 IP source와 destination은 종단까지 그대로 살아남죠. 물론 NAT(Network Address Translation)가 끼어들면 IP와 port마저 바뀝니다. 예외는 언제나 있습니다.

**관찰할 것** — 내 주소와 route가 목적지를 향하고 있는지, 그리고 그 경로가 실제로 살아 있는지 봅니다.

```bash
ip addr
ip route
traceroute 1.1.1.1    # 또는 tracepath
```

packet capture에서 IP header의 TTL(Hop Limit)과 ICMP 오류까지 함께 읽어 내면 그림이 완성됩니다.

## L4 Transport: host가 아니라 process까지

많은 입문서가 port를 이렇게 소개합니다.

> port 하나가 곧 프로세스 하나다.

편의를 위한 단순화라서, 실무에 들어서면 가장 먼저 손봐야 하는 문장이기도 합니다.

IP가 packet을 목적 host까지 옮겨 놓았다면, 이제 그 데이터를 올바른 application process에 배달하는 것이 L4의 몫입니다. port number가 multiplexing과 demultiplexing의 열쇠인 것은 맞지만, 실제 demultiplexing은 포트 하나가 아니라 protocol과 출발지 IP:port, 목적지 IP:port를 한데 묶은 socket 단위로 일어납니다. 그래서 같은 목적지 443 port에 수천 개의 connection이 아무 탈 없이 공존합니다. 여기에 `SO_REUSEPORT`나 로드밸런서, container network namespace까지 끼어들면 포트와 프로세스를 일대일로 세는 셈법은 더더욱 성립하지 않죠.

TCP는 connection-oriented byte stream을 제공합니다. sequence number, acknowledgment, retransmission, flow control, congestion control을 동원해 손실·중복·순서 뒤바뀜이 예사로 일어나는 IP 위에서 신뢰할 수 있는 stream을 만들어 냅니다. 반면 UDP는 connection 설정도 재전송도 기본으로 제공하지 않는 datagram service여서, overhead와 지연이 작은 대신 필요한 신뢰성 정책을 application이 직접 골라 얹어야 합니다.

다만 UDP에는 신뢰성이 없다는 문장에서 멈추면 절반만 아신 겁니다. QUIC은 UDP 위에 connection과 reliable stream, congestion control, TLS 보안을 한꺼번에 올려 구현해 냈으니까요. 계층 모델이 구현을 가로막는 벽이 아니라 책임을 설명하는 도구라는 사실을 이보다 잘 보여 주는 사례도 드뭅니다.

**관찰할 것** — listen 중인 소켓 목록과 TCP state를 봅니다. retransmission이 쌓이고 있는지, zero window가 뜨고 있는지도 함께 살핍니다.

```bash
ss -lntup
```

방화벽 규칙을 들여다볼 때는 port 하나가 아니라 5-tuple 전체를 맞춰 봐야 합니다.

## L5 Session: 대화의 생명주기

L5가 유독 흐릿하게 느껴지신다면 그건 여러분 탓이 아닙니다. 원래부터 윤곽이 흐린 계층이니까요.

L5가 맡은 일은 통신 dialog를 열고 유지하고 닫으며, 중간에 끊어진 대화를 어디서부터 다시 이을지 관리하는 것입니다. 고전 OSI 프로토콜에서는 이 책임이 독립된 계층으로 또렷하게 서 있었지만, 현대 인터넷 application에서는 library와 application protocol 안으로 녹아들어 버렸죠. 우연이 아니라 인터넷 설계 철학인 end-to-end argument가 낳은 결과입니다. 세션이나 표현 같은 기능은 중간 네트워크보다 양 끝의 application이 훨씬 잘 처리하니, 굳이 독립 계층으로 못 박지 않고 끝단에 맡겨 둔 것이죠.

로그인 session cookie, RPC connection 상태, SOCKS proxy 세션, database session, 긴 작업의 checkpoint. 모두 대화가 얼마나 오래 이어지는가라는 L5의 눈으로 뜯어볼 수 있습니다. 다만 cookie는 그 자체로 독립된 프로토콜이 아니라 HTTP(L7) 헤더에 실려 다니는 상태 관리 장치라는 점은 분명히 해 두겠습니다. session을 다루니 곧 L5 프로토콜이라는 식으로 실제 protocol suite의 계층과 OSI의 책임 분류를 일대일로 맞붙이려 드는 순간 설명이 어긋나기 시작하니까요.

**관찰할 것** — session ID가 언제 생기고 언제 만료되며 어떻게 재발급되는지 따라가 봅니다. reconnect 정책과 idempotency 보장 여부도 함께 확인하고요. 대화가 끊어졌을 때 어디서부터 다시 시작하는지가 마지막 질문입니다.

## L6 Presentation: 같은 뜻을 같은 bytes로

L6는 데이터를 어떻게 표현하느냐에서 생기는 차이를 흡수해 주는 계층입니다. character encoding, serialization, compression, encryption이 여기 속하는 대표적인 책임이고, UTF-8 text와 JSON document, JPEG image, TLS record를 떠올리시면 됩니다.

TLS를 L6의 대표 protocol로 외워 두는 설명은 교육적으로는 편합니다. 구현을 들여다보면 TLS는 application과 transport 사이에 놓이고 TCP가 아닌 다른 transport와 짝을 이루기도 하지만요. 중요한 것은 번호가 아니라, 상대가 같은 바이트를 같은 뜻으로 읽어 낼 수 있도록 표현하고 보호하는 책임입니다.

**관찰할 것** — charset과 content type이 맞아떨어지는지, serialization schema 버전이 같은지 봅니다. certificate chain과 cipher 협상 결과도 확인하고요. 압축 방식이 어긋나는 경우도 이 칸의 단골입니다.

## L7 Application: 사용자가 원하는 네트워크 기능

TCP connection은 멀쩡히 섰는데 화면에는 `503`이 떴다고 해 봅시다. 이걸 네트워크 문제라고 부를 수 있을까요?

부를 수 없습니다. 아래 계층의 전달은 전부 성공했고, 어긋난 것은 application이 주고받기로 한 의미이기 때문입니다. L7 장애가 네트워크가 안 된다는 말로 뭉뚱그려지는 이유가 여기 있죠. TCP가 붙고 난 뒤에도 HTTP `503`이나 DNS `SERVFAIL`, TLS hostname mismatch는 얼마든지 터져 나올 수 있으니까요.

L7은 user나 application에 network service를 직접 제공하는 계층입니다. HTTP는 resource를 요청하고 응답하는 규칙을, DNS는 이름과 record를 조회하는 규칙을 정의하고, SMTP는 mail transfer를, SSH는 secure remote login이라는 의미를 각각 떠맡습니다.

**관찰할 것** — `curl -v`의 전 과정을 먼저 훑습니다. DNS response code가 정상인지, HTTP status·header·body가 기대와 맞아떨어지는지 봅니다. application log에서는 authentication·authorization 실패와 upstream timeout이 단골로 잡힙니다.

## 장비는 한 계층에만 갇히지 않는다

| 장비 | 주로 보는 정보 | 실제 동작에서의 주의점 |
| --- | --- | --- |
| Repeater/Hub | signal·bit | 목적지 주소를 해석하지 않는다. |
| L2 Switch/Bridge | Ethernet frame, MAC, VLAN | 관리 UI, ACL, routing 기능이 있으면 상위 계층도 사용한다. |
| Router | IP packet, routing table | 출력할 때 L2 frame을 새로 만든다. NAT·firewall 기능을 함께 수행할 수 있다. |
| L4 Load Balancer | IP, protocol, port, connection | connection 단위 분산과 health check를 수행한다. |
| L7 Proxy/WAF(Web Application Firewall) | HTTP/TLS 등 application 의미 | TLS 종료, header 변경, authentication, caching까지 수행할 수 있다. |
| NIC | PHY와 frame 송수신 | checksum offload, segmentation offload 때문에 capture가 wire의 모습과 다를 수 있다. |

switch는 L2, router는 L3라는 말은 주된 기능을 부르는 약칭일 뿐입니다. 현대 장비는 여러 계층을 동시에 처리하니까요. 그러니 장비 이름을 묻는 대신, 그 장비가 지금 이 순간 어떤 header와 어떤 상태를 근거로 결정을 내리고 있는지를 물으셔야 합니다. 장비 이름은 그 장비가 실제로 하는 일을 다 담아내지 못하지만, forwarding decision은 그 순간의 사정을 그대로 알려 줍니다.

## 실무 워크스루: 웹사이트가 열리지 않는다

계층 모델의 진가는 장애 앞에서 드러납니다. 지금부터는 앞에서 쌓아 온 일곱 책임을 실제로 두드려 볼 수 있는 명령어로 바꿔 보겠습니다.

원칙은 하나입니다. 아래에서 위로 좁혀 올라갑니다. 신호가 죽어 있는데 HTTP status를 들여다보고 있어 봐야 시간만 버리니까요. 물론 경험이 쌓이면 증상과 변경 이력에 따라 위에서부터 훑어 내려오는 편이 빠를 때도 있고, 어제까지 멀쩡하던 기준점과 대조해 보는 쪽이 가장 빠를 때도 있습니다. 아래 순서는 길을 잃지 않도록 도와주는 학습용 기본값으로 삼으시면 됩니다.

증상 버튼은 관찰된 현상, 의심 계층, 확인 명령을 한 줄로 이어 줍니다. 아래에서는 같은 흐름을 단계별로 더 깊이 따라가면서 정상 출력과 이상 출력을 어떻게 읽어 내는지까지 짚어 보겠습니다. 명령 예시는 전부 Linux 기준입니다. macOS는 `ifconfig`·`route -n get`·`dscacheutil`, Windows는 `ipconfig`·`Get-NetNeighbor`·`Test-NetConnection`이 대응하고요.

### 1. L1 — link가 살아 있는가

```bash
ip link show dev eth0
```

- **원리**: 신호가 매체에 실리는지부터 봅니다. carrier가 잡히지 않으면 그 위의 모든 것은 의미를 잃습니다.
- **출력 읽기**: `state UP`과 `LOWER_UP`이 함께 보이면 관리 상태와 carrier는 살아 있습니다. 다만 이건 carrier 지표일 뿐이라 end-to-end 신호 품질이나 Wi-Fi 인증 성공까지 보장해 주지는 않습니다. `NO-CARRIER`나 `state DOWN`이 찍혀 있으면 여기서 멈추십시오.
- **흔한 문제**: 빠진 케이블, 죽은 transceiver, Wi-Fi 미연결, 가상 NIC의 host-side link down.
- **진단·팁**: 간헐적으로 끊어진다면 `ip -s link show dev eth0`로 `errors`와 `carrier` 카운터가 올라가고 있는지 봅니다. 계속 오른다면 물리 매체를 먼저 의심하되, duplex 협상 오류나 드라이버·firmware 문제도 같은 카운터를 올린다는 점은 기억해 두십시오.

### 2. L2 — 같은 link의 gateway에 닿는가

```bash
ip neigh show
```

- **원리**: 다른 network로 나가려면 먼저 기본 gateway의 MAC을 알아내야 합니다. 이것을 구하지 못하면 frame을 어디로도 띄우지 못합니다.
- **출력 읽기**: gateway IP 옆에 `lladdr`과 `REACHABLE`이 붙어 있으면 정상입니다. 계속 `INCOMPLETE`나 `FAILED`로 남아 있다면 ARP(또는 IPv6 Neighbor Discovery)가 응답을 받아 내지 못하고 있는 것이죠.
- **흔한 문제**: VLAN tag 불일치, wireless client isolation, switch port 차단, gateway 자체 다운.
- **진단·팁**: 이 단계에서 DNS를 바꿔 보는 것은 헛다리를 짚는 일입니다. `ip addr`로 내 IP와 prefix가 gateway와 같은 링크(on-link)로 잡히는지부터 확인하십시오. prefix가 어긋나 gateway가 다른 네트워크에 있는 것처럼 보이면 host는 gateway에게 ARP조차 띄우지 않습니다. IPv6의 link-local gateway나 명시적 on-link route 같은 예외도 있으니, 같은 prefix에 있다는 것과 on-link로 닿는다는 것을 같은 말로 단정하지는 마시고요.

### 3. L3 — 주소와 route가 목적지를 향하는가

```bash
ip addr show
ip route show
ping -c 3 1.1.1.1
tracepath 1.1.1.1
```

- **원리**: gateway까지 닿았으니 이제 여러 network를 건너가는 경로가 제대로 잡혀 있는지 봅니다.
- **출력 읽기**: `default via` 뒤에 gateway가 붙은 route가 있어야 합니다. `tracepath`가 hop마다 전진해 나가면 경로는 살아 있는 것이죠. 다만 응답이 멈춘 hop이 곧 장애 지점은 아닙니다. 그 router가 ICMP 응답만 제한해 두었을 뿐 트래픽은 그 너머로 잘 흘러갈 수도 있으니까요. 멈춘 hop은 장애의 위치가 아니라 관찰의 한계로 읽으십시오.
- **흔한 문제**: default route 누락, 잘못 밀어 넣은 static route, NAT 뒤에서 엉켜 버린 source 주소, 나가는 길과 돌아오는 길이 서로 다른 비대칭 경로.
- **진단·팁**: `ping`이 실패했다는 것만으로 서버가 죽었다고 단정하지 마십시오. 많은 곳이 ICMP를 아예 차단해 둡니다. route 정보와 실제 service traffic을 나란히 놓고 교차 검증해야 합니다.

### 3.5 잠깐 — 이름이 IP로 풀리는가 (DNS, 사실은 L7)

`nc example.com 443`이나 `curl`은 포트에 닿기 전에 먼저 DNS로 이름을 IP로 바꿔 옵니다. 그래서 L4가 막힌 것처럼 보이는 장애가 실은 이름 해석 실패인 경우가 흔하죠. 둘을 떼어 놓고 봅니다.

```bash
dig +short example.com        # 이름 → IP (systemd 환경은 resolvectl query example.com)
nc -vz <위에서 나온 IP> 443    # 이름 해석을 빼고 순수 L4만 검사
```

`SERVFAIL`이나 `NXDOMAIN`이 돌아오면 resolver와 zone 쪽 application 문제입니다. 이름은 잘 풀리는데 그 IP의 포트가 열리지 않는다면 그때가 진짜 L4 차례고요. DNS 자체는 application protocol이지만 거의 모든 진단이 지나가는 길목이라 여기서 먼저 끊고 갑니다.

### 4. L4 — service port까지 connection이 서는가

```bash
nc -vz example.com 443
ss -tn state syn-sent
```

- **원리**: host까지 packet이 도착했더라도 원하는 process의 port까지 transport가 이어져야 비로소 통신입니다.
- **출력 읽기**: `Connected`가 뜨면 SYN-ACK를 받아 냈다는 뜻이니 포트는 열려 있습니다. `ss`에 `SYN-SENT`만 쌓여 간다면 SYN을 보내 놓고 응답을 받지 못하고 있는 중이죠.
- **흔한 문제와 결정적 단서**:
  - `Connection refused` → 어딘가에서 명시적인 거절(RST)을 받아 온 것입니다. 대개는 그 port에 listen하는 process가 없는 서버지만, 방화벽의 `REJECT` 정책이나 중간 장비가 RST를 대신 쏘아 주기도 합니다. 그래도 조용한 무응답보다는 한참 진전된 신호죠.
  - `timeout` → 어딘가에서 packet이 소리 없이 사라진 것입니다. firewall drop이 흔한 원인이지만 routing 실패, packet loss, 서버 과부하, 돌아오는 경로 문제도 똑같은 증상을 냅니다. 단정하지 마시고 후보로만 두십시오.
- **진단·팁**: `refused`와 `timeout`은 전혀 다른 이야기입니다. 이 둘을 갈라 보는 것만으로 다음에 어디를 들여다볼지가 정해집니다.

### 5. L6~L7 — TLS와 HTTP 의미가 맞는가

```bash
curl -v https://example.com/
```

- **원리**: 여기까지 왔다면 packet은 이미 잘 오갔습니다. 이제 양쪽이 바이트를 같은 뜻으로 읽고 보호하고 있는지, application이 기대한 응답을 돌려주는지가 문제죠.
- **출력 읽기**: `SSL certificate verify ok` 뒤에 `HTTP/2 200`이 따라오면 정상입니다. 실패는 책임별로 갈라집니다. 앞에서 이야기했듯 TLS는 L6과 L7 경계에 걸쳐 있으니 번호 자체에 매달리실 필요는 없습니다.
  - certificate expired, unknown CA, 체인 끊김 → 데이터를 표현하고 보호하는 쪽이 어긋난 것입니다. 인증서 체인이나 cipher 협상, 아니면 로컬 시계를 봅니다.
  - hostname mismatch, SNI(Server Name Indication) 불일치 → 바이트는 보호됐지만 이 이름이 맞는지 따지는 검증 정책이 어긋난 것이라 L6과 L7 사이에 걸칩니다.
  - `301`/`302` redirect loop, `401`, `404`, `503` → application이 주고받기로 한 의미가 어긋난 것입니다. 라우팅, 인증, upstream을 봅니다.
- **진단·팁**: 인증서가 만료됐거나 아직 유효하지 않은 것으로 보이면 서버를 의심하기 전에 `date`로 내 시계부터 확인하십시오. 시계가 틀어져 있으면 멀쩡한 인증서도 무효로 보입니다. 네트워크 문제라는 한마디로 뭉뚱그리는 대신, 정확히 어느 책임이 어긋났는지 짚어 말할 수 있어야 합니다.

### 또 다른 시나리오 1: ping은 되는데 큰 응답에서 멈춘다 (MTU/MSS 블랙홀)

페이지가 거의 다 열리다 특정 시점에 멈춰 서고, `ping`은 멀쩡하며 작은 API 호출만 성공한다면 전형적인 MTU 블랙홀입니다.

**원리.** 경로 중간 링크의 MTU(Maximum Transmission Unit)가 작은데(예: VPN·PPPoE 터널로 1500이 1400으로 줄어든 경우) 큰 packet에 `Don't Fragment`가 붙어 있으면, router는 그 packet을 버리고 "Fragmentation Needed" ICMP를 돌려보내야 합니다. 여기서 IPv4와 IPv6가 갈라집니다. IPv4에는 DF 비트와 경로상 fragmentation 개념이 있는 반면, IPv6 router는 절대 fragment하지 않습니다. IPv6에서 분할이 필요하면 송신 host가 Fragment 확장 헤더를 붙여 직접 쪼개고, 중간 router는 "Packet Too Big" ICMPv6로 알려 줄 뿐이죠. 다만 IPv6는 모든 링크가 최소 1280 byte MTU를 보장하므로 그 아래로 쪼갤 일은 없습니다.

**흔한 문제.** 그 ICMP를 방화벽이 차단해 버리면 송신 측은 크기를 줄여야 한다는 신호를 받지 못합니다. 그래서 작은 packet(handshake와 ping)은 통과하는데 데이터가 실린 큰 packet만 소리 없이 사라지죠. 연결은 성립하는데 전송이 멈춰 버리는 기묘한 증상이 이렇게 만들어집니다.

**진단.** packet 크기를 키워 가며 어디서 끊어지는지 봅니다. IPv4 기준이고, `-4`로 주소군을 고정해 두지 않으면 호스트가 IPv6로 풀려 header 크기가 달라집니다.

```bash
ping -4 -M do -s 1472 example.com   # 페이로드 1472 + IP 20 + ICMP 8 = 1500 (IPv4)
ping -4 -M do -s 1372 example.com   # 더 작은 크기는 되는지
tracepath example.com               # 경로상 pmtu 변화를 보여줌
```

큰 크기에서만 실패한다면 MTU 문제일 가능성이 높습니다. 다만 rate limiting이나 경로별(ECMP, Equal-Cost Multi-Path) 차이, 장비 정책도 크기에 따라 갈리는 실패를 만들어 내니 단정하기 전에 한 번 더 확인하십시오.

**해결·팁.** 경로 MTU에 맞춰 인터페이스 MTU를 낮추거나, 라우터에서 MSS(Maximum Segment Size) clamping(`TCPMSS --clamp-mss-to-pmtu`)을 걸어 둡니다. 단 MSS clamping은 TCP 전용이고, PMTU 정보가 틀렸거나 경로가 비대칭이면 어긋날 수 있는 우회책입니다. QUIC 같은 UDP 위 transport는 ICMP에 기대지 않고 프로브 기반 DPLPMTUD(Datagram Packetization Layer Path MTU Discovery, RFC 8899. QUIC은 RFC 9000 §14에서 채택)로 크기를 스스로 찾아냅니다. 어느 쪽이든 근본 해결은 방화벽이 PMTUD용 ICMP를 통과시키게 만드는 것입니다. IPv4는 `ICMP Type 3 Code 4`, IPv6는 `ICMPv6 Type 2`. 이 메시지를 막아 버리면 ICMP 기반 Path MTU Discovery 자체가 돌아가지 못합니다.

### 또 다른 시나리오 2: 특정 사이트만 인증서 오류가 난다

다른 사이트는 멀쩡한데 한 도메인만 TLS에서 막힌다면 L6에 집중합니다.

**원리.** 서버는 SNI로 받은 hostname에 맞는 인증서를 골라 내려보냅니다. 클라이언트는 그 인증서의 이름·체인·유효기간을 검증하고요.

**흔한 문제.** 가상 호스팅 설정이 잘못돼 SNI와 다른 인증서가 돌아오거나, 중간 CA(intermediate) 인증서가 빠져 체인이 끊어지거나, 클라이언트 신뢰 저장소에 없는 사설 CA를 쓰고 있는 경우입니다.

**진단.**

```bash
curl -v https://target.example/ 2>&1 | grep -Ei 'subject|issuer|SSL|verify'
openssl s_client -connect target.example:443 -servername target.example </dev/null
```

`openssl`은 서버가 실제로 내려보낸 체인 전체를 펼쳐 보여 주므로 체인 누락과 SNI 불일치를 갈라냅니다.

**해결·팁.** 체인이 끊어졌다면 서버에 intermediate를 함께 설치합니다. 브라우저에서는 잘 열리는데 `curl`이나 서버 간 호출에서만 실패하는 인증서 오류의 흔한 원인이 바로 이 intermediate 누락이죠. 브라우저는 과거에 받아 둔 intermediate를 캐시해 두거나 AIA(Authority Information Access)로 직접 가져오는 등 검증 경로가 달라서 문제가 가려집니다. 물론 trust store 차이와 TLS 가로채기도 같은 증상을 냅니다. 시계나 지원 cipher·버전 차이도 마찬가지니 `openssl` 출력으로 원인을 좁혀 들어가십시오.

### packet capture는 계층을 한 화면에 겹쳐 보여준다

앞의 단계들이 어느 계층을 의심할지 좁혀 준다면, capture는 그 계층들을 한 화면에 겹쳐 놓고 실제 바이트로 확인시켜 줍니다.

```bash
sudo tcpdump -ni any -w osi-lab.pcap 'host example.com and port 443'
```

Wireshark로 열면 한 줄에 Ethernet, IP, TCP, TLS가 중첩된 구조로 보입니다. 각 계층의 header를 펼치는 순간, 이 글에서 이야기한 캡슐화가 그림이 아니라 실제 field였다는 사실이 눈으로 들어옵니다.

함정은 둘입니다. Linux에서 `-i any`로 잡으면 진짜 Ethernet header 대신 Linux cooked capture(SLL) 헤더가 보이므로, Ethernet frame 자체를 뜯어보려면 `-i eth0`처럼 실제 interface를 지정해야 합니다. 그리고 NIC의 checksum·segmentation offload 때문에 host에서 관찰한 checksum이나 segment 크기가 실제 wire와 달라 보일 수 있습니다. 관찰하는 도구도 관찰하는 위치의 영향을 받습니다.

## 자주 틀리는 일곱 가지

1. **"OSI 계층은 packet이 물리적으로 통과하는 일곱 개 프로그램이다."** 참조 모델의 책임 분리일 뿐입니다. 구현은 합쳐지기도 하고 나뉘기도 합니다.
2. **"각 계층에는 protocol 하나만 있다."** 계층은 책임의 범위이고, 그 안에 여러 protocol과 기술이 함께 삽니다.
3. **"switch는 언제나 L2, load balancer는 언제나 L4다."** 제품 이름이 아니라 forwarding decision에 쓰는 정보로 판단해야 합니다.
4. **"MAC 주소는 원격 server까지 유지된다."** routed hop을 지날 때마다 L2 frame과 source/destination MAC이 새로 갈립니다.
5. **"ping이 되면 application도 정상이다."** L3 reachability의 일부만 확인한 것입니다. TCP와 TLS, application semantics는 별개로 확인해야 합니다.
6. **"`Connection refused`나 `timeout`이나 결국 연결 안 되는 건 같다."** 정반대 단서입니다. refused는 명시적인 거절이고 timeout은 조용한 무응답이라, 다음에 볼 곳이 갈라집니다.
7. **"연결만 되면 packet 크기는 상관없다."** MTU가 작은 경로에서 "Fragmentation Needed" ICMP가 막히면 작은 packet만 통과하고 큰 packet은 사라져 버립니다.

## 직접 해보기: 한 요청을 계층별로 해부한다

**목표**: `curl` 한 번이 DNS, TCP, TLS, HTTP로 이어지는 증거를 손으로 찾아냅니다.

1. terminal에서 `curl -v https://example.com/`을 실행하고 DNS 결과, 연결 IP, TLS handshake, HTTP status를 적어 둡니다.
2. 다른 terminal에서 `sudo tcpdump -ni eth0 'host example.com or port 53'`을 실행합니다. 실제 interface를 지정해야 Ethernet header까지 보이고, `port 53`을 함께 걸어야 DNS 질의도 잡힙니다. domain filter는 capture 도중 재해석 문제를 만들 수 있으니 먼저 `dig`로 IP를 확인해 `host <IP>`로 거는 편이 안전합니다.
3. capture에서 TCP three-way handshake의 SYN, SYN-ACK, ACK를 찾아냅니다. `curl`은 기본적으로 TCP 위로 붙으므로 handshake가 보이는 것이 정상이고, 보이지 않는다면 interface와 filter를 먼저 의심하십시오. 일부러 `--http3`을 쓰거나 브라우저가 Alt-Svc 캐시로 HTTP/3에 붙었다면 TCP 대신 UDP/443 위의 QUIC이 보입니다. 이때 TCP 3-way handshake는 없지만, QUIC은 연결 수립과 TLS 1.3 키 교환을 1-RTT(또는 0-RTT)에 묶은 자체 handshake를 치릅니다. handshake가 없는 것이 아니라 TCP의 그것이 아닐 뿐이죠.
4. IP header의 TTL(Hop Limit)과 TCP source/destination port를 확인합니다.
5. 같은 LAN의 gateway를 `ip neigh`로 찾아, packet의 원격 IP와 frame의 다음-hop MAC이 왜 서로 다른지 직접 설명해 보십시오.

성공 기준은 명령을 실행해 봤다는 데 있지 않습니다. 하나의 application 요청에서 계층마다 다른 identifier와 상태를 짚어낼 수 있게 되면 성공입니다.

## 마무리: 번호보다 질문을 기억하라

OSI 7계층을 이해했다는 말은 "Please Do Not Throw Sausage Pizza Away" 같은 암기 문장을 외워 두었다는 뜻이 아닙니다. 다음 여섯 질문을 순서대로 던질 수 있게 되었다는 뜻입니다.

- signal과 link는 살아 있는가?
- 같은 link의 next hop까지 frame이 가는가?
- IP route는 destination을 향하는가?
- 원하는 process의 port까지 transport가 연결되는가?
- session과 data representation이 양쪽에서 합의됐는가?
- application protocol이 기대한 의미로 응답하는가?

실무에서 권해 드리는 기본값은 아래에서 위입니다. 신호부터 확인하고 한 칸씩 올라오면 아무리 늦어도 여섯 번째 질문 안에서 원인을 만나게 되니까요. 위에서 아래로 내려오는 방식이 더 빠를 때도 있지만, 그건 무엇이 바뀌었는지 이미 알고 있을 때의 이야기입니다. 아무 단서도 손에 쥐지 못한 채 top-down으로 시작하면 대개 애먼 곳을 파다 시간을 흘려보내게 되죠.

계층은 현실을 정확히 잘라 내는 칼이 아닙니다. 복잡한 현실을 디버깅할 수 있는 크기로 나눠 주는 지도입니다. 그러니 다음에 인터넷이 안 된다는 말을 들으시거든 증상을 한 덩어리로 뭉뚱그리지 마시고, 이 사다리의 어느 칸에서 걸렸는지부터 갈라 보십시오. 진단의 절반은 거기서 끝납니다. 그 습관 하나만은 꼭 몸에 붙이시길 당부드립니다.

이 글은 전체 지도를 그려 보였을 뿐입니다. switch 학습과 flooding, IP 라우팅과 ICMP, TCP 연결 수립과 종료. 그리고 TLS 1.3·QUIC·DNS·HTTP/2의 깊은 동작. 이 모두를 시리즈 뒤편에서 한 계층씩 해부해 나가겠습니다. 다음 편에서는 L1과 L2를 한 묶음으로 다룹니다. Ethernet frame, switch 학습, VLAN, ARP/Neighbor Discovery가 한 LAN 안에서 어떻게 맞물려 도는지 packet 단위로 뜯어보겠습니다.
