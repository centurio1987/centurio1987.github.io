![VPN의 해부 EP5 — WireGuard: 선택지를 없애서 얻은 148바이트. 협상을 지운 자리에서 고정 크기가 태어난다.](/images/vpn-anatomy-5/hero.webp)

[4편](/posts/vpn-anatomy-4/)까지 두 편에 걸쳐 IPsec을 봤습니다. 협상을 맡는 IKEv2, 데이터를 나르는 ESP, NAT을 넘기 위한 UDP 캡슐화, 그리고 그 오버헤드가 만드는 MTU 블랙홀까지 — 부품이 많았습니다. 기능은 충분하지만 손이 많이 가는 물건이라는 인상도 함께 남았을 겁니다.

그런데 WireGuard 설정을 처음 써 보면 정반대의 불안이 찾아옵니다. **너무 짧아서 뭔가 빠뜨린 것 같은** 불안입니다. 고를 암호 알고리즘이 없습니다. phase 1과 phase 2가 없습니다. NAT-T를 켜는 스위치도 없습니다. 피어마다 적는 것은 공개키 한 줄과 IP 주소 몇 개가 전부입니다. IPsec의 `swanctl.conf`를 한참 만지다 온 사람이라면 "이게 정말 다야?" 하고 되묻게 됩니다.

이 짧음은 게으름이 아니라 **설계입니다.** WireGuard는 IPsec이 협상하던 것들을 하나씩 지웠고, 지운 자리마다 다른 성질이 들어섰습니다. 이 글을 끝까지 읽으시면, 왜 WireGuard 핸드셰이크 메시지가 **정확히 148바이트로 고정되는지**, 공개키 한 줄이 어떻게 라우팅과 인증을 동시에 해내는지, 그리고 "빠르다"는 평판의 구체적인 근거가 어느 바이트에 있는지를 실제 캡처를 짚어 가며 설명할 수 있게 됩니다.

> **읽기 전 약속 둘.** 이 글의 크기 숫자 148·92·32는 별도 언급이 없으면 **WireGuard 메시지 자체의 길이(= UDP 페이로드)** 이지 이더넷 프레임이나 IP 패킷 길이가 아닙니다. 프레임과의 차이 42바이트는 **Ethernet II 14 + 옵션 없는 IPv4 20 + UDP 8**을 더한 값이라, VLAN 태그·IP 옵션·IPv6가 끼면 이 42는 달라집니다. 그리고 여기 나오는 필드 배치는 **백서 스펙**이고, 그것이 실제 바이트로 어떻게 나타나는지는 랩에서 뜬 캡처로 대조합니다.

## 한눈에 보기: 크기가 곧 설계다

먼저 이번 편의 주인공인 크기표부터 봅니다. 아래는 랩에서 뜬 캡처를 메시지 종류별로 집계한 것입니다.

```text
# ~/blog-research/raws/captures/vpn-anatomy-5/wg-sizes.txt (발췌)
# tshark -r wg.pcap -T fields -e wg.type -e udp.length -e frame.len

  type  이름                    WG메시지(=UDP페이로드)  UDP전체  이더넷프레임
  ----  ----------------------  ----------------------  -------  ------------
  1     Handshake Initiation    148                     156      190
  2     Handshake Response      92                      100      134
  4     Transport Data          128                     136      170
  4     Transport Data(keepalive) 32                    40       74
```

읽는 법이 중요합니다. 맨 왼쪽 "WG메시지" 열이 백서 §5.4가 말하는 148·92라는 숫자와 대조할 값입니다. 그 오른쪽 두 열은 여기에 **UDP 헤더 8바이트**, 그리고 **이더넷·IP·UDP 헤더 합 42바이트**가 차례로 더해진 것입니다. 자기 환경에서 `wg.type==1`을 잡았는데 프레임 길이가 190으로 찍히더라도 당황할 필요가 없습니다 — WireGuard 메시지는 그중 148바이트일 뿐입니다. 이 계층 구분을 놓치면 "백서는 148이라는데 내 캡처는 190이네" 하는 흔한 혼선이 생깁니다.

여기서 눈여겨볼 것은 **핸드셰이크 두 종류의 크기가 딱 하나로 고정**된다는 점입니다. IKEv2에서는 Proposal과 Transform이 가변 길이라 같은 교환이라도 협상 내용에 따라 메시지 크기가 달라졌습니다([3편](/posts/vpn-anatomy-3/)에서 다룬 SA/Proposal/Transform 구조가 그것입니다). WireGuard에는 협상할 것이 없으니 필드 수도, 각 필드의 크기도 고정입니다. 크기가 하나로 정해진다는 사실 자체가 "이 프로토콜은 아무것도 협상하지 않는다"는 설계의 그림자입니다.

## 먼저 초점: WireGuard의 진짜 발명은 Cryptokey Routing입니다

WireGuard를 "IKEv2의 복잡한 협상을 걷어내고 암호 알고리즘을 하나로 박아 넣은 IPsec" 정도로 요약하는 설명을 자주 봅니다. 암호군을 고정했다는 부분은 맞습니다. 다만 이 요약만으로는 **가장 중요한 발명이 보이지 않습니다.**

암호군 고정은 결과이지 핵심이 아닙니다. WireGuard의 진짜 발명은 **Cryptokey Routing** — 공개키 하나로 "누구에게 보낼지(라우팅)"와 "누구에게서 온 것인지(인증)"를 동시에 결정하는 구조입니다. IPsec은 이 둘을 서로 다른 데이터베이스로 나눠 관리합니다. 어떤 트래픽을 터널로 보낼지는 SPD(Security Policy Database)가, 실제 키와 SA(Security Association)는 SAD(Security Association Database)가 맡고, 피어의 신원은 또 IKEv2가 인증서나 PSK로 따로 확인합니다. WireGuard는 이 셋을 **공개키를 열쇠로 삼는 표 하나**로 합쳤습니다.

그래서 WireGuard를 **"신원·라우팅·키를 한 표로 통합해 협상이 필요 없어진 프로토콜"**로 요약해 두면, 뒤에 나올 148바이트가 훨씬 빨리 이해됩니다. 협상이 사라진 것은 이 통합의 자연스러운 귀결입니다. 이제 그 표부터 해부하겠습니다.

## Cryptokey Routing: 공개키 한 줄이 인증이 되는 이유

WireGuard에서 피어는 오직 하나로 식별됩니다 — **32바이트 Curve25519 공개키**입니다. 백서는 이렇게 정합니다.

> "The fundamental principle of a secure VPN is an association between peers and the IP addresses each is allowed to use as source IPs. In WireGuard, peers are identified strictly by their public key, a 32-byte Curve25519 point."
> — WireGuard 백서 §2

설정은 이 원칙을 그대로 옮긴 표입니다. 인터페이스에 자기 개인키와 포트를 적고, 피어마다 **공개키와 그 피어가 쓸 수 있는 소스 IP 목록(Allowed IPs)**을 적습니다.

```text
# 인터페이스 (백서 Configuration 1a 재구성)
PrivateKey = yAnz...fBmk        ListenPort = 41414

# 피어 A
PublicKey  = xTIB...p8Dg        AllowedIPs = 10.192.122.3/32, 10.192.124.0/24
# 피어 B
PublicKey  = TrMv...WXX0        AllowedIPs = 10.192.122.4/32, 192.168.0.0/16
```

이 표 하나가 양방향으로 동작합니다. 전제 하나만 짚고 갑니다 — 이 표가 도는 것은 커널의 일반 라우팅 테이블이 그 패킷을 먼저 `wg0` 인터페이스로 보낸 다음입니다. WireGuard 인터페이스로 들어온 패킷에 한해 아래 조회가 일어납니다.

- **나가는 패킷**: 목적지 IP로 표를 조회합니다. `10.192.124.7`로 가는 패킷이라면 피어 A의 `10.192.124.0/24`에 걸리니, 그 패킷은 **피어 A와의 세션 키로 암호화**해 피어 A의 엔드포인트로 보냅니다. 공개키 자체가 패킷을 암호화하는 것은 아닙니다 — 공개키는 어느 피어인지, 그리고 [2편](/posts/vpn-anatomy-2/)의 키교환으로 어떤 대칭 세션 키를 쓸지를 고르는 열쇠이고, 실제 암호화는 그렇게 도출된 세션 키가 맡습니다. 조회는 일반 라우팅 테이블처럼 longest-prefix match로 가장 구체적인 항목을 고릅니다.
- **들어오는 패킷**: 먼저 복호합니다. 어떤 세션 키로 풀렸는지가 곧 **어느 피어인지**를 말해 줍니다. 그다음이 결정적입니다 — 복호된 원본 패킷의 **소스 IP가 그 피어에 매핑된 Allowed IP 범위 안에 있어야만 수락**합니다. 없으면 버립니다.

백서의 표현이 이 대목을 정확히 짚습니다.

> "it will only accept it if its source IP resolves in the table to the public key used in the secure session for decrypting it."
> — WireGuard 백서 §2

두 번째 방향이 왜 "인증"이 되는지 곱씹어 볼 가치가 있습니다. 여기에는 성질이 다른 두 겹이 포개져 있습니다. 하나는 **암호학적** 겹입니다 — 패킷이 그 피어의 세션 키로 복호·검증되었다는 것은, 그 세션 키를 쥔 피어가 아니면 만들 수 없었다는 뜻입니다. 다른 하나는 **정책** 겹입니다 — 그렇게 신원이 확인된 피어에게, 이 소스 IP를 쓸 권한을 로컬 설정(Allowed IPs)이 부여했는가를 검사합니다. 그러니 "IP가 암호로 서명된다"기보다, **피어는 암호로 인증하고 그 피어가 주장하는 소스 IP는 로컬 정책으로 허가**하는 것입니다. 두 겹이 포개지면 "이 IP에서 온 것처럼 보이는 패킷"이 아니라 "이 피어가 이 IP를 쓸 자격이 있는가"를 layer 3에서 함께 판정하게 됩니다. 백서는 이 성질을 IPsec과 대비해 이렇게 씁니다.

> "Unlike some common VPN protocols, like L2TP/IPsec, using authenticated identification of peers at a layer 3 level enforces a much cleaner network design."
> — WireGuard 백서 §2

말보다 손이 빠릅니다. 아래에서 나가는 패킷과 들어오는 패킷을 직접 던져 보며, 같은 표가 어떻게 라우팅 판정과 수락/폐기 판정을 함께 내리는지 확인해 보십시오.

들어오는 패킷 모드에서, **피어 B로 복호되었는데 소스 IP를 `10.192.122.3`(피어 A의 몫)으로 위장**한 경우를 눌러 보십시오. 복호는 성공했어도 소스 IP가 피어 B의 Allowed IP에 없으니 폐기됩니다. 이것이 한 피어가 다른 피어의 IP를 사칭하지 못하게 막는 장치입니다. IPsec에서라면 트래픽 셀렉터와 정책을 따로 맞춰야 얻는 성질을, WireGuard는 표 하나로 공짜처럼 얻습니다.

다만 한 표가 라우팅과 수신 필터를 겸한다는 것은 **운영상 위험도 함께 진다**는 뜻입니다. Allowed IPs를 `0.0.0.0/0`으로 열면 그 피어 하나가 모든 목적지의 라우팅과 모든 소스 IP의 수신을 통째로 가져가고, 여러 피어의 범위가 겹치면 longest-prefix match가 의도와 다른 피어를 고를 수 있습니다. 편리한 통합인 만큼, 이 표를 짤 때는 "어디로 보낼까"와 "어디서 온 걸 받을까"를 **동시에** 적고 있다는 사실을 잊지 말아야 합니다.

한 가지 시각화의 흐름으로도 정리해 두겠습니다.

## 네 종류 메시지, 그리고 1-RTT

WireGuard의 메시지는 **딱 네 종류**입니다. 이 좁은 어휘가 프로토콜 전체를 이룹니다.

<OneRttFlow />

핵심은 **1-RTT**입니다. 개시자가 Initiation을 보내고 응답자가 Response를 돌려주면, 그 한 번의 왕복만으로 양쪽이 같은 세션 키를 도출합니다. 개시자는 Response를 받는 즉시 데이터를 실어 보낼 수 있습니다. IKEv2가 IKE_SA_INIT과 IKE_AUTH라는 두 번의 왕복을 거쳐 SA를 세우던 것과 비교하면, 세우는 절차 자체가 한 왕복으로 압축되어 있습니다.

다만 여기에 한 가지 비대칭이 있습니다. 응답자는 Response를 보냈다고 곧바로 그 새 세션으로 데이터를 먼저 밀어 넣지 않습니다 — **개시자로부터 그 세션 키로 인증된 첫 트랜스포트 패킷을 받아, 키가 실제로 합의됐음을 확인(key confirmation)한 뒤에야** 자기도 그 세션으로 보냅니다. 그래서 핸드셰이크 직후 개시자가 보낼 데이터가 없더라도, 개시자 쪽에서 빈 트랜스포트 패킷 하나를 먼저 내보내 응답자에게 키 확인을 건네는 일이 흔합니다. 잠시 뒤 캡처로 볼 keepalive가 바로 그 역할을 겸합니다.

이제 이 메시지들을 실제 캡처의 바이트로 하나씩 열겠습니다. 아래 캡처는 모두 개시자 시점(NAT 라우터 이전)에서, 커널 WireGuard 모듈이 실제로 내보낸 프레임입니다 — 유저스페이스 구현이 아닙니다.

## Handshake Initiation: 148바이트를 한 바이트씩

먼저 tshark가 디섹션한 개시 메시지입니다.

```text
# wg-handshake.txt (발췌) — tshark -r wg.pcap -O wg -V -Y "wg.type==1"
WireGuard Protocol
    Type: Handshake Initiation (1)
    Reserved: 000000
    Sender: 0x5179ef23
    Ephemeral: cfyWER83qYbnkIPvtW/9/s+ne29yFe9oTzmfMU/j0kA=
        [Has Private Key: False]
    Encrypted Static
    Encrypted Timestamp
    mac1: d8c6a69933dd9205ca884eacf85ab876
    mac2: 00000000000000000000000000000000
```

이 디섹션이 실제 바이트로 어떻게 놓이는지, 캡처의 hex 오프셋 그대로 펼치면 다음과 같습니다.

```text
오프셋  크기  필드                        값 / 의미
  0      1   type = 0x01                 Handshake Initiation
  1      3   reserved = 00 00 00         정렬용 0 (아래 참조)
  4      4   sender = 23 ef 79 51        I_i = 0x5179ef23 (little-endian)
  8     32   ephemeral                   평문 Curve25519 임시 공개키
 40     48   encrypted static            32B 정적 공개키 + 16B 인증 태그
 88     28   encrypted timestamp         12B TAI64N + 16B 인증 태그
116     16   mac1 = d8c6a6…f85ab876      Keyed-BLAKE2s
132     16   mac2 = 00…00                쿠키 없음 → 0
                                         합계 148바이트
```

`48 = 32+16`, `28 = 12+16`. 백서의 표기로는 정적 키 필드를 "32♭"로 적는데, ♭ 기호가 "Poly1305 태그 16바이트를 더한다"는 뜻입니다. AEAD(Authenticated Encryption with Associated Data, [2편](/posts/vpn-anatomy-2/)에서 본 암호화·인증 통합 방식)로 감싸면 항상 이 태그 16바이트가 붙습니다. 이제 각 필드가 왜 그 크기, 그 자리인지 봅니다.

**임시 키(ephemeral)는 평문입니다.** 32바이트 Curve25519 공개키가 암호화 없이 그대로 실립니다. 당연합니다 — 상대가 이 임시 공개키를 봐야 자기 개인키와 곱해 공유 비밀을 만들 수 있으니까요([2편](/posts/vpn-anatomy-2/)의 X25519 키교환이 이 곱셈입니다). 매 핸드셰이크마다 새로 생성되는 이 임시 키 쌍이 전진 비밀성(PFS)의 뿌리입니다.

**정적 키(static)는 암호화됩니다.** 여기가 WireGuard의 조용한 강점입니다. `static`은 개시자의 **영구 공개키**, 즉 개시자의 신원입니다. 이것을 평문으로 두면 수동적 도청자가 "누가 이 서버에 접속하는가"를 훤히 알 수 있습니다. 개시자는 이것을 첫 메시지부터 암호화해 숨기는데, 그럴 수 있는 이유가 곧 뒤에서 볼 이름 `IK`의 `K`입니다 — 개시자는 응답자의 정적 공개키를 미리 알고 있어, 방금 보낸 자기 임시 키와 그 응답자 정적 키로 공유 비밀을 곧바로 계산할 수 있습니다. 그 비밀로 자기 정적 키를 AEAD 암호화해 실으니, **신원이 수동 관찰자로부터 가려집니다.** 그래서 이 필드가 32가 아니라 48바이트입니다 — 숨기는 값 32에 인증 태그 16이 붙은 것입니다.

**타임스탬프(timestamp)는 재전송 공격을 막습니다.** 12바이트 TAI64N 값을 역시 암호화해 싣습니다(이 필드는 암호문이라 캡처에서는 자리와 크기만 보이고 값은 열리지 않습니다). 구조만 짚으면, 앞 8바이트가 초, 뒤 4바이트가 나노초인데 — 초 필드는 평범한 유닉스 시각이 아니라 TAI64 라벨(`2^62` 오프셋에 초를 더한 big-endian 정수)이라, 단순한 1970 기준 카운트로 오해하지 않아야 합니다. 응답자는 각 피어에 대해 지금까지 본 가장 큰 타임스탬프를 기억해 두고, 그보다 크지 않은 개시 메시지는 거부합니다. [4편](/posts/vpn-anatomy-4/)의 ESP 시퀀스 번호가 데이터 패킷의 재전송을 막았다면, 이 타임스탬프는 **핸드셰이크 자체의 재전송**을 막는 별개의 장치입니다.

**mac1과 mac2는 마지막 32바이트입니다.** mac1은 앞의 모든 필드에 대한 Keyed-BLAKE2s MAC(Message Authentication Code, 메시지 인증 코드)인데, 그 키가 **라벨 문자열 `"mac1----"`에 응답자의 정적 공개키를 이어 붙여 BLAKE2s로 해시한 값**입니다. 그래서 응답자의 공개키를 모르는 쪽이 보낸 메시지는 mac1부터 틀리고, 응답자는 복호나 키교환에 들어가기도 전에 비용이 작은 MAC 검증만으로 아무 데서나 날아온 패킷을 버립니다. 다만 여기서 오해하기 쉬운 지점이 있습니다 — **공개키는 비밀이 아니므로, mac1은 "강한 신원 인증"이 아니라 DoS 완화용 비용이 작은 1차 필터**입니다. 진짜 피어 인증은 뒤이은 정적 키 DH와 AEAD 검증이 맡습니다. mac2는 평소에는 0이고, 응답자가 부하 상태일 때만 쓰이는 쿠키 자리입니다(잠시 뒤 Cookie Reply에서 다룹니다). 캡처에서 mac2가 `00…00`인 것은 이 핸드셰이크가 부하 없는 정상 상황이라는 뜻입니다.

여기서 앞서 미뤄 둔 **reserved 3바이트**를 짚겠습니다. type 1바이트 바로 뒤에 0 세 개가 왜 있을까요? 두 가지입니다. 첫째, `type(1) + reserved(3) = 4바이트`가 되어 뒤따르는 `sender`(4바이트)가 자연스럽게 4바이트 경계에 정렬됩니다. 둘째, 백서가 직접 밝히듯 이 덕분에 **처음 4바이트를 little-endian 정수 하나로 한 번에 읽을 수 있습니다.** 3바이트를 버리는 대신 얻는 것은 정렬과 단일 로드 — "선택지를 없애 빨라진다"는 이 프로토콜의 철학이 헤더 맨 앞 3바이트에서부터 작동하는 셈입니다.

## Handshake Response: 왜 개시 메시지보다 작아야 하는가

응답 메시지입니다. 캡처에서 이 메시지의 `receiver`가 방금 본 개시 메시지의 `sender`와 같다는 점을 눈여겨보십시오.

```text
# wg-handshake.txt (발췌) — wg.type==2
WireGuard Protocol
    Type: Handshake Response (2)
    Reserved: 000000
    Sender: 0x1116714d
    Receiver: 0x5179ef23        ← 개시 메시지의 Sender
    Ephemeral: C2+iY3tI79PFCSo50/erADr+cN/4MtyBUas30IrE6RU=
    Encrypted Empty
    mac1: f7a5b6f5455fc8c8f78f4ae8b55bbb34
    mac2: 00000000000000000000000000000000
```

바이트 배치는 이렇습니다.

```text
오프셋  크기  필드                        값 / 의미
  0      1   type = 0x02                 Handshake Response
  1      3   reserved = 00 00 00
  4      4   sender = 4d 71 16 11        I_r = 0x1116714d (응답자가 고른 인덱스)
  8      4   receiver = 23 ef 79 51      I_i = 0x5179ef23 (개시자의 인덱스)
 12     32   ephemeral                   평문 Curve25519 임시 공개키
 44     16   encrypted empty             빈 페이로드의 16B 인증 태그뿐
 60     16   mac1 = f7a5b6…b55bbb34
 76     16   mac2 = 00…00
                                         합계 92바이트
```

두 인덱스가 눈에 들어옵니다. `sender`와 `receiver`는 각각 4바이트짜리 **세션 인덱스**로, 백서 스스로 "IPsec의 SPI에 해당한다"고 설명합니다([4편](/posts/vpn-anatomy-4/)에서 방향마다 다르던 그 SPI입니다). 개시자가 자기 인덱스 `I_i`를 정해 개시 메시지에 실으면, 응답자는 응답 메시지에서 그 값을 `receiver`에 되돌려 주고 자기 인덱스 `I_r`을 새로 실어 보냅니다. 이후 개시자가 보내는 데이터에는 `receiver = I_r`이 붙어, 응답자가 매 패킷마다 무거운 키 조회 없이 인덱스만으로 세션을 곧장 찾습니다.

이제 크기입니다. 응답은 **92바이트로, 개시의 148바이트보다 작습니다.** 이것은 우연이 아니라 의도된 설계입니다. 백서가 직접 이유를 밝힙니다.

> "Note that this handshake response message is smaller than the handshake initiation message, preventing amplification attacks."
> — WireGuard 백서 §5.4.3

증폭 공격(amplification attack)이란, 공격자가 피해자의 IP로 출발지를 위조해 작은 요청을 던지고, 서버가 그보다 훨씬 큰 응답을 피해자에게 쏟아붓게 만드는 수법입니다. 응답이 요청보다 크면 공격자는 적은 대역폭으로 큰 트래픽을 증폭할 수 있습니다. WireGuard는 **응답을 요청보다 작게 만들어** 이 증폭비를 1 미만으로 눌러, 프로토콜을 반사 증폭의 도구로 쓰지 못하게 했습니다. 크기 하나에도 방어가 새겨져 있는 것입니다.

그런데 응답이 어떻게 개시보다 작을 수 있을까요? 개시 메시지에는 정적 키(48)와 타임스탬프(28)가 실렸지만, 응답 메시지에서 대응하는 자리는 **"빈 페이로드"의 인증 태그 16바이트뿐**입니다. 응답 단계에서는 더 실어 보낼 신원 정보가 없습니다 — 개시자의 신원은 이미 개시 메시지의 암호화된 정적 키로 전달됐고, 응답자의 신원은 이 핸드셰이크의 정적 키 DH(Diffie-Hellman 키교환)와 AEAD 검증이 증명하니까요(mac1이 아니라). 실을 것이 없으니 필드가 비고, 필드가 비니 메시지가 작아지고, 작아지니 증폭 방어가 따라옵니다. 필요가 크기를 정하고, 크기가 안전을 정하는 연쇄입니다.

## Transport Data: "정확히 16바이트"라는 약속

핸드셰이크가 끝나면 실제 데이터가 흐릅니다. 아래는 캡처에 잡힌 **keepalive**(빈 데이터) 트랜스포트 메시지입니다.

```text
# wg-transport.txt (발췌) — wg.type==4
WireGuard Protocol
    Type: Transport Data (4)
    Reserved: 000000
    Receiver: 0x1116714d        ← 응답 메시지의 Sender
    Counter: 0
    Encrypted Packet
        [Expert Info: This is a Keepalive message]
```

바이트 배치입니다.

```text
오프셋  크기  필드                        값 / 의미
  0      1   type = 0x04                 Transport Data
  1      3   reserved = 00 00 00
  4      4   receiver = 4d 71 16 11      I_r = 0x1116714d
  8      8   counter = 00…00 (0)         nonce 겸 재전송 카운터
 16      *   encrypted packet            AEAD 암호문 (keepalive면 태그 16B뿐)
                                         헤더 정확히 16바이트
```

앞 16바이트 — `type(1) + reserved(3) + receiver(4) + counter(8)` — 가 헤더이고, 그 뒤부터 암호문입니다. 백서가 이 16이라는 숫자를 특별히 강조합니다.

> "Prior to msg.packet, there are exactly 16 bytes of header fields."
> — WireGuard 백서 §5.4.6

왜 하필 16일까요? 두 가지 이유를 백서가 함께 댑니다. 첫째, 헤더가 정확히 16바이트이면 그 뒤에 오는 암호문이 **자연스러운 메모리 정렬을 유지**합니다. 그래서 커널이 받은 패킷을 별도 버퍼로 복사하지 않고 **제자리에서(in-place) 복호**할 수 있고, 이 무-복사 경로가 하드웨어 구현과 처리량에 유리합니다. 둘째, 앞 필드에 3바이트 reserved zero가 있어 — 개시 메시지에서 본 그 정렬 트릭이 여기서도 — 처음 4바이트를 정수 하나로 읽을 수 있습니다. "WireGuard가 빠르다"는 평판의 구체적 근거 하나가 바로 이 16이라는 헤더 크기에 있습니다. 성능이 추상적 구호가 아니라 **바이트 배치의 결과**로 제시된다는 점이 이 프로토콜의 특징입니다.

`counter`는 8바이트입니다. 그리고 이 한 필드가 두 가지 일을 합니다 — **AEAD(ChaCha20-Poly1305) nonce의 재료이면서, 동시에 재전송 방지 카운터로도** 쓰입니다. 정확히는, ChaCha20-Poly1305의 nonce는 12바이트(96비트)인데 WireGuard는 이 8바이트 counter를 little-endian으로 놓고 **앞에 0 4바이트를 붙여** 12바이트를 채웁니다 — 그러니 counter가 nonce의 전부는 아니고, nonce의 하위 64비트입니다. 매 데이터 패킷마다 1씩 오르므로 nonce가 재사용되지 않고([2편](/posts/vpn-anatomy-2/)에서 nonce 재사용이 왜 치명적인지 봤습니다), 수신자는 같은 값으로 이미 본 패킷을 걸러냅니다. 재전송 방지 방식으로 백서는 **RFC 4303 부록 C** 또는 **RFC 6479** 중 하나를 지목하는데, 바로 [4편](/posts/vpn-anatomy-4/)에서 anti-replay 윈도우를 이야기하며 다뤘던 그 RFC 6479의 순환 버퍼 방식입니다. 프로토콜이 달라도 재전송 방지라는 숙제의 답지는 같다는 것을, WireGuard가 그 RFC를 그대로 지목함으로써 다시 확인하게 됩니다.

참고로 앞 크기표의 128바이트 트랜스포트 메시지는 고정 크기가 아닙니다 — 실제 데이터 메시지는 내부 IP 패킷을 **16바이트 배수로 패딩**한 뒤 암호화하므로, 그날 흘린 특정 패킷 크기에 따라 값이 달라집니다. 헤더 16과 마찬가지로 이 16바이트 정렬도 앞서 본 성능 설계의 연장선입니다.

마지막으로 이 **keepalive**의 정체입니다. 캡처의 이 메시지는 평문이 비어 있어 암호문이 인증 태그 16바이트뿐이고, 그래서 전체가 `16(헤더) + 16(태그) = 32바이트`입니다. 앞의 크기표에서 본 그 32바이트 트랜스포트 메시지가 이것입니다. 이것은 **passive keepalive**입니다 — WireGuard는 데이터를 받았지만 10초(Keepalive-Timeout, 뒤에서 다룹니다) 동안 돌려보낼 것이 없으면 이런 빈 패킷을 하나 보내, 방금 본 key confirmation을 겸해 "잘 받았다"를 알립니다. 다만 이걸 NAT 유지 장치와 혼동하지 말아야 합니다. 아무 트래픽도 오가지 않는 유휴 터널의 NAT 매핑을 능동적으로 살려 두는 것은 이 자동 10초 keepalive가 아니라, 사용자가 설정에 명시하는 **`PersistentKeepalive`(흔히 25초 권장)**의 몫입니다 — 받은 것이 있어야 반응하는 passive keepalive와 달리, 이쪽은 아무것도 없어도 주기적으로 빈 패킷을 밀어 냅니다. IPsec이 NAT-T에서 1바이트 `0xFF` keepalive를 쓰던 것과 목적은 같되, WireGuard는 별도 포맷 없이 빈 트랜스포트 메시지 하나로 처리합니다.

> **복호에 관한 정직한 한계.** 이 트랜스포트 페이로드의 내용은 열지 않습니다. 커널 WireGuard는 세션마다 바뀌는 임시 개인키를 노출하지 않아, 정적 키만으로는 트랜스포트를 복호할 수 없습니다. 핸드셰이크의 필드·크기와 트랜스포트의 헤더·크기는 이렇게 그대로 보이지만, 데이터 본문은 암호문으로 남습니다. `wireguard-go`(유저스페이스 구현)로 갈아타면 계측할 수 있으나, 그 순간 "실제 커널 구현이 내보낸 패킷"이라는 이 시리즈의 전제가 성립하지 않으므로 하지 않습니다 — [4편](/posts/vpn-anatomy-4/)에서 ESP를 복호하고 OpenVPN을 열지 않았던 것과 같은 기준입니다.

## Noise_IKpsk2: 이름 하나가 곧 스펙이다

WireGuard의 핸드셰이크는 맨땅에서 발명된 것이 아니라 **Noise Protocol Framework**의 한 패턴을 골라 쓴 것입니다. 그 패턴의 이름이 곧 이 핸드셰이크의 명세서입니다. 백서가 적는 정확한 구성 문자열은 이렇습니다.

```text
Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s
```

한 토막씩 읽으면 이 글에서 본 모든 것이 이름 안에 들어 있습니다.

- **IK** — 메시지 패턴입니다. 첫 글자 `I`는 개시자(Initiator)의 정적 키가 **즉시(Immediately)** 전송된다는 뜻이고(개시 메시지의 그 암호화된 정적 키), 둘째 글자 `K`는 응답자의 정적 키가 개시자에게 **미리 알려져(Known)** 있다는 뜻입니다. 그래서 개시자는 첫 메시지부터 자기 정적 키를 응답자용으로 암호화해 실을 수 있었던 것입니다(앞의 정적 키 절에서 본 그 즉시 DH).
- **psk2** — 사전 공유 키(pre-shared key)를 **두 번째 메시지 단계에서** 선택적으로 섞을 수 있다는 뜻입니다. 이 PSK는 인증 수단이 아니라 대칭 방어층입니다 — 고엔트로피 PSK가 안전하게 배포·보관된다는 전제에서, 미래의 양자 컴퓨터가 Curve25519를 깨더라도 뚫어야 할 대칭 비밀을 하나 더 얹습니다. **완전한 양자 내성 키교환(PQ)을 제공하는 것은 아니고**, 그날이 오기까지 벌어 두는 보강 옵션입니다.
- **25519 / ChaChaPoly / BLAKE2s** — 협상하지 않는, 고정된 세 프리미티브입니다. 키교환은 Curve25519([2편](/posts/vpn-anatomy-2/)의 X25519), AEAD는 ChaCha20-Poly1305, 해시·MAC은 BLAKE2s. 고를 것이 없으니 이름에 박아 둘 수 있고, 이름에 박혀 있으니 다운그레이드 협상 공격의 표적이 될 여지도 없습니다.

> **한 가지 각주.** 백서(2017년 작성)는 ChaCha20-Poly1305를 "RFC 7539"로 표기합니다. 이 RFC는 이후 **RFC 8439로 대체**되었습니다 — 알고리즘 자체는 같고 명세 문서의 번호만 갱신된 것이니, 오늘 기준으로 인용할 때는 RFC 8439를 씁니다.

IKEv2가 SA·Proposal·Transform이라는 가변 구조로 "무엇을 쓸지"를 왕복해 가며 정하던 자리를, WireGuard는 **문자열 한 줄로 정했습니다.** 이름이 스펙이 되면, 협상 메시지가 사라지고, 협상 메시지가 사라지면 메시지 크기가 고정되고, 크기가 고정되면 파서가 단순해지고 공격면이 줄어듭니다. 앞에서 본 148·92·32라는 숫자들은 결국 이 이름 하나에서 흘러나온 것입니다.

물론 공짜는 아닙니다. 암호 민첩성(crypto agility)을 포기했다는 것은, 언젠가 이 프리미티브 중 하나가 깨지거나 양자 내성 알고리즘으로 갈아타야 할 때 **프로토콜과 구현 자체를 새 버전으로 올려야** 한다는 뜻입니다 — 협상 필드로 그 자리에서 알고리즘을 바꿔 끼울 수가 없으니까요. WireGuard의 답은 "그럴 때는 `Noise_IKpsk2_25519_...`가 아닌 새 construction 문자열을 쓰는, 명시적으로 다른 버전이 된다"입니다. 다운그레이드 협상의 위험을 없앤 대가로 유연성을 내준, 의도된 맞바꿈입니다.

## 타이머 일곱 개로 완결되는 상태 기계

WireGuard에는 세션 관리를 위한 별도의 제어 프로토콜이 없습니다. IKEv2라면 CREATE_CHILD_SA 교환으로 정책에 따라 키를 교체하고 DELETE로 세션을 닫았지만, WireGuard는 그 모든 것을 **일곱 개의 상수**로 대신합니다.

| 심볼 | 값 | 역할 |
|---|---|---|
| Rekey-After-Messages | 2^60 메시지 | 이만큼 보냈으면 새 키로 |
| Reject-After-Messages | 2^64 − 2^13 − 1 메시지 | 이후로는 전송 거부 |
| **Rekey-After-Time** | **120초** | 세션이 이만큼 지나면 개시자가 새 핸드셰이크 |
| **Reject-After-Time** | **180초** | 이후로는 그 세션으로 전송 거부 |
| Rekey-Attempt-Time | 90초 | 재시도를 이 시간 안에서만 |
| Rekey-Timeout | 5초 | 응답 없으면 이 간격으로 재시도 |
| Keepalive-Timeout | 10초 | 받고도 보낼 게 없으면 빈 패킷 |

이 일곱 개가 맞물려 하나의 상태 기계를 이룹니다. 세션이 **Rekey-After-Time(120초)**을 넘긴 뒤 **보낼 데이터가 생기면**, 개시자가 조용히 새 핸드셰이크를 시작해 키를 갈아탑니다. 여기서 "보낼 데이터가 생기면"이 중요합니다 — 아무것도 오가지 않는 유휴 터널은 120초가 지나도 굳이 핸드셰이크를 쏘지 않고, 다음 패킷을 보내려는 순간에 시각을 확인해 rekey를 유발합니다. 사람이 rekey 정책을 짤 필요도, 명령을 내릴 필요도 없습니다 — 트래픽이 흐르는 한 약 2분마다 전진 비밀성이 자동으로 갱신됩니다. **Reject-After-Time(180초)**이 지난 낡은 세션으로는 아예 전송을 거부하고, 응답이 없으면 **Rekey-Timeout(5초)** 간격으로 **Rekey-Attempt-Time(90초)** 동안만 재시도합니다. 데이터를 받았지만 돌려보낼 것이 없을 때 **Keepalive-Timeout(10초)** 뒤에 나가는 빈 패킷이, 앞에서 캡처로 본 그 32바이트 keepalive입니다. 그리고 새 세션이 `Reject-After-Time × 3`(=540초) 동안 서지 않으면 모든 세션 상태를 지우고 0으로 밀어, 유휴 피어가 메모리와 키를 붙들고 있지 않게 합니다.

IKEv2의 유연한 rekey 정책과 비교하면 선택의 여지가 좁습니다. 그러나 그 좁음이 곧 예측 가능성입니다 — 어느 WireGuard 구현이든 같은 상수를 쓰므로, 상호운용을 위해 rekey 타이밍을 맞추는 협상이 필요 없습니다. 여기서도 "선택지를 없앤다"는 원칙이 상태 관리 계층까지 관통합니다.

## 단일 UDP 포트와 로밍: NAT-T가 없는 이유

[4편](/posts/vpn-anatomy-4/)에서 IPsec은 NAT을 감지하면 UDP 500에서 4500으로 포트를 갈아타며 ESP를 UDP로 감쌌습니다. WireGuard에는 그런 전환이 **아예 없습니다.** WireGuard는 처음부터 끝까지 **하나의 UDP 소켓** 위에서만 돕니다. 핸드셰이크든 데이터든 전부 같은 UDP 위에 실리니, NAT을 넘기 위해 따로 옷을 갈아입을 일이 없습니다 — 애초에 UDP를 입고 태어났기 때문입니다. 이번 캡처에서 출발지·목적지 포트가 양방향 모두 51820으로 찍힌 것은 **NAT 라우터를 지나기 전(개시자 쪽) 지점**에서 떴고 양쪽 `ListenPort`를 같은 값으로 둔 랩 조건이라서입니다. 실제 NAT 뒤에서는 바깥에서 관측되는 개시자의 출발지 포트가 임의 포트로 바뀝니다 — "단일 포트"가 뜻하는 것은 "프로토콜이 UDP 소켓 하나만 쓴다"이지 "51820↔51820이 끝까지 유지된다"가 아닙니다.

그렇다면 NAT 뒤에서의 로밍은 어떻게 처리할까요? WireGuard의 답은 **엔드포인트 자동 갱신**입니다. 피어의 외부 IP:포트는 설정에 미리 적어 둘 수도 있지만, 그러지 않아도 **인증에 성공한 패킷의 실제 소스 주소로 피어의 엔드포인트를 갱신**합니다. 백서는 이를 Mosh(모바일 셸)에 비유합니다 — 클라이언트가 Wi-Fi에서 LTE로 넘어가 IP가 바뀌어도, **로밍한 쪽이 새 주소에서 유효한 패킷을 한 번 보내면** 서버가 그 소스로 엔드포인트를 갱신해 이후 응답을 돌려보냅니다. 핸드셰이크를 다시 하거나 세션을 새로 세울 필요가 없습니다. 반대로 서버가 먼저 보내야 하는 상황이라면, 서버는 아직 옛 주소를 알고 있으니 로밍한 쪽이 먼저 한마디 건네야 길이 뚫립니다(여기서도 앞의 `PersistentKeepalive`가 쓸모가 있습니다).

여기서 앞서 본 Cryptokey Routing이 다시 빛납니다. 엔드포인트를 아무 패킷의 소스로나 갱신하면 위험하겠지만, WireGuard는 **인증(복호 성공 + 유효한 카운터)을 통과한 패킷의 소스로만** 갱신합니다. 신원이 IP가 아니라 공개키에 묶여 있으니, IP가 아무리 바뀌어도 같은 피어임을 알아볼 수 있는 것입니다. NAT-T라는 별도 기계 장치 없이 로밍이 되는 것은, 신원과 주소를 분리한 이 설계의 배당금입니다.

## Cookie Reply: 스펙에는 있으나 이 캡처에는 없는 것

네 번째 메시지 type 3, **Cookie Reply**는 이번 캡처에 나타나지 않습니다. 부하나 DoS 상황에서만 발생하는데, 랩은 정상 상황이었기 때문입니다. 그래서 이 절은 **백서 스펙만으로** 서술하고, 실제 캡처가 있는 척하지 않겠습니다 — 이 시리즈가 스펙과 실측을 섞지 않는다는 규약 그대로입니다.

구조는 64바이트입니다: `type(1) + reserved(3) + receiver(4) + nonce(24) + cookie(16+16)`. 쓰임은 이렇습니다. 앞서 개시·응답 메시지의 mac2 자리가 평소 0이라고 했습니다. 응답자가 부하에 시달릴 때, 개시 메시지의 mac2가 유효한 쿠키로 채워져 있지 않으면 응답자는 비용이 큰 키교환에 들어가는 대신 이 Cookie Reply를 돌려줍니다. 그 안의 쿠키는 개시자의 소스 IP에 묶여 있고, 개시자는 이 쿠키를 다음 개시 메시지의 mac2에 실어 자기가 그 IP에서 실제로 응답을 받을 수 있는 존재임을 증명합니다. 출발지를 위조한 공격자는 응답을 받지 못하니 유효한 쿠키를 얻을 수 없고, 따라서 부하 상황에서 응답자의 CPU를 태우지 못합니다. mac1이 "응답자를 아는가"를 적은 비용으로 걸렀다면, mac2와 Cookie Reply는 "이 소스 IP가 진짜인가"를 부하 상황에서만 추가로 거르는 2차 방어선인 셈입니다.

## 실무 시나리오: "핸드셰이크는 섰는데 데이터가 안 흐른다"

WireGuard에서 가장 흔한 신고가 이것입니다. `wg show`에는 `latest handshake`가 방금으로 찍히는데 `ping`이 안 나갑니다. 여기서 지금까지 해부한 사실 하나가 진단의 칼이 됩니다 — **핸드셰이크(type 1·2)와 데이터(type 4)는 서로 다른 메시지**라, 핸드셰이크가 섰다는 것이 데이터가 흐른다는 뜻은 아닙니다.

1. **핸드셰이크와 전송량을 분리한다.**
   ```bash
   wg show wg0
   ```
   - **원리**: `latest handshake`는 type 1·2가 오갔다는 뜻이고, `transfer: X received, Y sent`가 실제 type 4(데이터)의 바이트입니다.
   - **읽기**: 핸드셰이크는 최신인데 `received`가 0이면 **들어오는 방향만** 죽은 것입니다. 트랜스포트 패킷이 상대에 닿지 않았거나, 닿았어도 Cryptokey Routing의 소스 IP 검사에서 조용히 폐기됐을 수 있습니다.

2. **AllowedIPs를 양쪽에서 대조한다.**
   ```bash
   wg show wg0 allowed-ips
   ```
   - **원리**: 나가는 패킷은 목적지 IP가 상대 AllowedIPs에 있어야 그 피어로 라우팅되고, 들어오는 패킷은 복호 후 소스 IP가 그 피어 AllowedIPs에 있어야 수락됩니다.
   - **흔한 문제**: 오버레이 대역을 AllowedIPs에서 빠뜨려 **복호는 되는데 소스 IP 검사에서 버려지는** 경우. 정상 폐기라 로그조차 안 남습니다.
   - **해결**: 양쪽 AllowedIPs가 서로의 오버레이 주소를 덮는지 확인합니다. 커널에 실제 반영된 값을 봐야 하므로 설정 파일이 아니라 위 명령의 출력을 기준으로 삼으십시오.
   - **팁**: 여러 피어의 범위가 겹치면 longest-prefix match가 의도한 피어를 고르는지도 함께 봅니다.

3. **NAT 뒤라면 keepalive를 확인한다.**
   - **원리**: 앞에서 나눈 두 keepalive 중 유휴 NAT 매핑을 능동적으로 살리는 것은 `PersistentKeepalive`입니다.
   - **흔한 문제**: "한동안 잘 되다 조용해지면 끊긴다"는 증상. NAT 매핑이 만료됐는데 되살릴 패킷이 없는 것입니다.
   - **해결**: NAT 뒤 피어 쪽에 `PersistentKeepalive = 25`를 켜, 25초마다 빈 패킷으로 구멍을 열어 둡니다.

4. **큰 전송만 죽으면 MTU다.**
   - **원리**: wg0의 기본 MTU는 1420입니다(물리 1500에서 오버헤드를 뺀 값). 터널 위 트래픽이 경로 MTU를 넘으면 [4편](/posts/vpn-anatomy-4/)에서 본 MTU 블랙홀과 같은 증상 — 작은 건 되고 큰 것만 죽는 모양 — 이 그대로 재현됩니다.
   - **진단**: `ping -M do -s 1400 <오버레이 IP>`처럼 크기를 바꿔 가며 끊기는 경계를 찾습니다.
   - **해결**: wg0 MTU를 낮추거나 MSS clamping을 겁니다. WireGuard 트랜스포트 오버헤드(IPv4 60바이트, IPv6 80바이트)를 물리 MTU에서 빼야 안전합니다.

정리하면 순서가 곧 절단면입니다 — **핸드셰이크/데이터 분리 → AllowedIPs → keepalive → MTU**. 각 단계가 앞에서 해부한 메시지 구조에 정확히 대응하니, 증상만 보고도 어느 바이트가 문제인지를 짚어 갈 수 있습니다.

## 자주 틀리는 다섯 가지

1. **"WireGuard는 암호군만 고정한 IPsec이다."** 핵심은 암호군 고정이 아니라 Cryptokey Routing — 신원·라우팅·키를 표 하나로 통합해, 암호로 인증된 피어에게 로컬 정책이 허용한 소스 IP만 받도록 만든 것입니다. 협상이 사라진 것은 그 통합의 결과입니다.
2. **"148바이트는 프레임 길이다."** 148·92·32는 **WireGuard 메시지(= UDP 페이로드)** 길이입니다. 이더넷 프레임과는 42바이트(L2+L3+L4 헤더), UDP 전체와는 8바이트 차이가 납니다. 계층을 밝히지 않으면 자기 캡처와 대조할 때 반드시 어긋납니다.
3. **"reserved 3바이트는 낭비다."** 이 3바이트가 `type`과 합쳐 4바이트 경계를 만들어 정렬을 맞추고, 처음 4바이트를 정수 하나로 읽게 합니다. 트랜스포트 헤더가 정확히 16바이트인 것도 같은 이유 — in-place 복호를 위한 메모리 정렬입니다.
4. **"응답이 개시보다 작은 건 그냥 그렇게 된 것이다."** 의도된 설계입니다. 응답을 요청보다 작게 만들어 증폭 공격의 도구가 되는 것을 막습니다. 크기 자체가 방어입니다.
5. **"WireGuard도 NAT-T가 필요하다."** 필요 없습니다. 처음부터 단일 UDP로 돌고, 로밍은 인증된 패킷의 소스로 엔드포인트를 자동 갱신해 처리합니다. IPsec의 500→4500 전환에 해당하는 것이 아예 없습니다.

## 직접 해보기: 148이 진짜 나오는지 확인한다

**목표:** 자기 손으로 WireGuard 터널을 세워 핸드셰이크 메시지가 정말 148·92바이트로 찍히는지, 그리고 그 값이 프레임 길이와 어떻게 다른지 확인합니다.

**준비물:** 리눅스 두 노드(네트워크 네임스페이스 두 개면 충분합니다), 커널 WireGuard 모듈과 `wireguard-tools`, `tcpdump`/`tshark`. 랩은 `wg-quick`이 아니라 **`wg setconf` + `ip addr/route`**를 씁니다 — `wg-quick`이 뒤에서 대신 해 주는 일을 직접 드러내 보기 위해서입니다.

> **캡처 전에 offload부터 끄십시오.** veth는 GRO/GSO/TSO가 기본으로 켜져 있어, 그대로 두면 실제 회선보다 큰 합쳐진 패킷이 찍혀 크기 관찰이 통째로 어긋납니다.
>
> ```bash
> ethtool -K <인터페이스> gro off gso off tso off tx off rx off
> ```

1. 각 네임스페이스 **안에서** WireGuard 인터페이스를 만듭니다. 인터페이스는 태어난 네임스페이스를 기억하므로, 밖에서 만들어 옮기면 소켓이 엉뚱한 곳에 남습니다.
   ```bash
   ip netns exec c1 ip link add wg0 type wireguard
   ip netns exec c1 wg setconf wg0 /etc/netns/c1/wg0.conf
   ip netns exec c1 ip addr add 198.51.100.2/24 dev wg0
   ip netns exec c1 ip link set wg0 up
   ```
2. 캡처를 겁니다(개시자 쪽, NAT 이전 지점).
   ```bash
   tcpdump -i c1-r -w wg.pcap 'udp port 51820'
   ```
3. 터널 위로 트래픽을 흘려 핸드셰이크를 유발합니다: `ping -c 3 198.51.100.1`.
4. 크기를 계층별로 집계해 읽습니다.
   ```bash
   tshark -r wg.pcap -T fields -e wg.type -e udp.length -e frame.len
   ```
5. **관찰 포인트**
   - `wg.type==1`이 **148 / 156 / 190**(WG메시지 / UDP전체 / 프레임)으로, `wg.type==2`가 **92 / 100 / 134**로 찍히는가.
   - 개시 메시지의 `Sender`가 응답 메시지의 `Receiver`로 되돌아오는가. 이후 트랜스포트 메시지의 `Receiver`가 응답자의 `Sender`와 같은가.
   - 개시 메시지의 `mac2`가 `00…00`인가(부하 없는 정상 상황이라는 뜻).
   - 조용히 두면 10초쯤 뒤 **32바이트짜리 keepalive**(type 4)가 나타나는가.

값은 실행마다 달라집니다 — 키·임시 키·타임스탬프·세션 인덱스는 매번 새로 생성됩니다. **"이 값이 그대로 나온다"가 아니라 "이 구조와 이 크기가 그대로 나온다"**가 확인해야 할 지점입니다.

## 마무리 — 핵심 다시 짚기

**WireGuard의 크기는 외울 숫자가 아니라 설계의 그림자입니다.** 협상을 지웠더니 필드가 고정되고, 필드가 고정되니 크기가 148·92·32로 정해지고, 크기가 정해지니 파서가 단순해지고 공격면이 줄었습니다.

- **Cryptokey Routing이 진짜 발명입니다.** 공개키 한 줄이 라우팅과 인증을 동시에 맡아, 암호로 인증한 피어에게 허용된 소스 IP만 layer 3에서 받아들입니다.
- **148바이트는 협상 없음의 증거입니다.** `type·reserved·sender·ephemeral·static·timestamp·mac1·mac2`가 전부 고정 크기라 합이 하나로 정해집니다. 응답 92바이트가 그보다 작은 것은 증폭 공격 방어입니다.
- **트랜스포트 헤더 16바이트는 성능 설계입니다.** in-place 복호를 위한 정렬이 "빠르다"는 평판의 구체적 근거이고, 8바이트 counter는 96비트 nonce의 하위 64비트이자 재전송 카운터를 겸합니다(RFC 6479 재사용).
- **Noise_IKpsk2라는 이름이 명세서입니다.** 메시지 패턴·PSK 옵션·세 프리미티브가 이름 한 줄에 박혀 있어 다운그레이드 협상의 여지가 없습니다.
- **타이머 일곱 개가 세션 관리를 대신합니다.** 120초 rekey가 사람 개입 없이 전진 비밀성을 갱신하고, 로밍은 단일 UDP 위에서 엔드포인트 자동 갱신으로 처리합니다.

여기까지가 IPsec과 WireGuard입니다. 한쪽은 협상하고 다른 쪽은 협상을 지웠지만, 둘 다 자기만의 프로토콜로 IP 계층 전체를 감쌌습니다. 그런데 세상에는 **아예 새 프로토콜을 만드는 대신, 웹 브라우저가 이미 쓰는 TLS를 그대로 빌려 VPN을 만드는** 길도 있습니다. 방화벽이 봐도 평범한 HTTPS처럼 보이는, 그래서 검열과 차단을 넘는 데 강한 계열입니다. [6편](/posts/vpn-anatomy-6/)에서 OpenVPN과 TLS 기반 VPN을 해부하겠습니다.
