![인증·인가 해부 4편 — 실무 베스트 프랙티스](/images/auth-authz-4/hero.webp)

여기까지 오시느라 고생하셨습니다. 우리는 인증·인가의 **지형**(1편)을 그리고, 토큰을 **검증**하고(2편), 토큰을 안전하게 **얻는**(3편) 법을 익혔습니다. 이제 마지막 질문이 남았습니다 — 이 모든 것을 **실제 시스템에 어떻게 얹는가?**

한 팀의 이야기로 시작하겠습니다. 그들은 nginx 뒤에 인증을 붙였습니다. 로그인한 사용자만 백엔드에 닿게 했고, nginx가 인증된 사용자명을 `X-User` 헤더로 백엔드에 넘겼습니다. 완벽해 보였습니다. 그런데 모의해킹에서 두 가지가 뚫립니다. 첫째, 공격자가 요청에 `X-User: admin`을 **직접 넣자** 백엔드가 그대로 믿었습니다(nginx가 그 헤더를 지우지 않았으니까요). 둘째, 공격자가 nginx를 건너뛰고 **백엔드에 직접** 요청하자 인증이 통째로 사라졌습니다.

이 글을 끝까지 읽으시면, 그 사고들이 왜 필연이었고 어떻게 막는지 — 그리고 시리즈 내내 쌓아 온 원칙들을 **하나의 베스트 프랙티스 체크리스트**로 꿰어 실제 설정과 코드로 옮길 수 있게 됩니다.

## 들어가며: 이론에서 시스템으로

지금까지가 "무엇을·왜"였다면, 이번 편은 "**어떻게**"입니다. 그리고 실무의 진실은 이렇습니다 — **보안은 한 곳이 아니라 여러 겹에서** 이뤄집니다(defense in depth). 리버스 프록시가 인증을 검사하고, 세션 저장소가 상태를 쥐고, 리소스 서버가 인가를 집행하고, 브라우저는 토큰을 아예 만지지 않게 합니다. 한 겹이 뚫려도 다음 겹이 막도록.

이 편은 그 겹들을 순서대로 얹습니다. 먼저 체크리스트로 전체를 조망한 뒤, nginx·Redis·BFF·인가 집행을 실제 설정으로 하나씩 세웁니다.

## 한눈에 보기: 베스트 프랙티스 체크리스트

시리즈 전체를 관통하는 실무 원칙을 한 장으로 모았습니다.

| 영역 | ✅ 해야 할 것 | ❌ 하지 말 것 |
|---|---|---|
| **흐름** | Authorization Code + PKCE(S256), state·nonce·redirect 정확매칭 | Implicit·ROPC·`plain` |
| **클라이언트 인증** | confidential은 인증(비대칭 private_key_jwt·mTLS 선호) | SPA에 secret, 약한 secret |
| **토큰 저장** | BFF(서버측) + HttpOnly 세션 쿠키 | 브라우저 `localStorage` |
| **토큰 수명** | 짧은 access token + refresh **회전** | 긴 수명, 회전 없는 refresh |
| **검증** | alg·서명·iss·aud·exp·typ (kid로 키 선택, 2편) | 디코딩만, `alg` 무검증 |
| **세션** | Redis 서버측 + 로그인 시 ID 회전 | 클라이언트에 상태 저장 |
| **인가** | 리소스 서버에서 scope+RBAC/ABAC, **deny-by-default** | 엣지에서만, 토큰=권한 착각 |
| **프록시** | `auth_request` + 헤더 sanitize + 직접접근 차단 | `X-User` 맹신, 백엔드 노출 |
| **전송/운영** | HTTPS everywhere, 키 회전, 접근 실패 로깅 | 평문, 로깅 부재 |

이 표가 4편의 목차입니다. 이제 핵심 몇 개를 실제 설정으로 세웁니다.

## 실습 1: nginx `auth_request` — 인증을 위임하되 경계를 지킨다

nginx의 `ngx_http_auth_request_module`(1.5.4+)은 **각 요청마다 인증 서버에 서브리퀘스트를 보내** 그 결과로 통과 여부를 정합니다. 규칙은 단순합니다 — **응답이 2xx면 허용, 401·403이면 거부**, 그 외는 에러.

```nginx
# 보호할 경로
location /private/ {
    auth_request /auth;
    error_page 401 = @login;   # 미인증이면 로그인으로 리다이렉트
    # 인증 서버가 돌려준 사용자명을 변수에 담는다
    auth_request_set $user $upstream_http_x_auth_request_user;
    # 클라이언트가 보낸 X-User는 무시하고, 인증 결과($user)로만 덮어쓴다
    proxy_set_header X-User $user;
    proxy_pass http://backend;
}

# 서브리퀘스트 전용(외부 직접 접근 불가)
location = /auth {
    internal;
    proxy_pass              http://auth-server/oauth2/auth;
    proxy_pass_request_body off;
    proxy_set_header        Content-Length "";
    proxy_set_header        X-Original-URI $request_uri;
}
```

여기서 앞의 팀이 놓친 **두 가지 경계**가 보입니다.

- **헤더 sanitize**: `X-User`는 인증 서버가 정하는 값입니다. 그런데 클라이언트도 요청에 `X-User: admin`을 넣을 수 있습니다. 여기서 nginx 동작을 정확히 알아야 합니다 — `proxy_set_header X-User $user;` **한 줄이면 클라이언트가 보낸 `X-User`를 인증 결과(`$user`)로 강제로 덮어씁니다**(같은 헤더에 `proxy_set_header`를 두 번 쓰면 마지막 줄만 적용되니, "빈 값으로 지운 뒤 다시 설정"처럼 두 줄을 쓸 필요가 없습니다). 핵심은 **클라이언트가 준 신원 헤더를 절대 그대로 통과시키지 않는 것**입니다. 같은 원리로 `X-Forwarded-*`도 nginx 변수로 재설정합니다.
- **직접 접근 차단**: `auth_request`는 **엣지를 지나는 요청에만** 적용됩니다. 백엔드가 외부에 노출돼 있으면 공격자가 nginx를 건너뛰어 인증을 통째로 우회합니다. 백엔드는 **인터넷에 닫혀 있어야** 하고, 프록시–백엔드 사이를 **mTLS·보안 그룹**으로 제한해야 합니다. 더 튼튼한 방식은 엣지가 넘긴 헤더를 믿는 대신 **백엔드가 액세스 토큰을 직접 검증**(2편)하거나, 엣지가 서명한 **내부 JWT**를 발급해 위변조를 막는 것입니다(신뢰를 헤더 한 줄에 걸지 않기).

그리고 원칙 하나. **`auth_request`는 "로그인했는가"(인증)를 검사하기 좋은 프리미티브이지, "이 리소스에 권한이 있는가"(세밀한 인가)를 대신하지 못합니다.** 웹 보안 표준을 정리하는 비영리 커뮤니티 OWASP(Open Web Application Security Project)도 인가를 게이트웨이(거친 단위)·서비스·비즈니스 코드의 여러 계층으로 나눕니다. 엣지는 인증된 신원을 다운스트림에 넘기고, **진짜 인가는 리소스 서버가** 합니다(뒤에서 상술).

## 실습 2: 세션과 BFF — 상태는 서버가, 토큰은 브라우저에서 치운다

인증이 끝나면 상태를 어딘가 둬야 합니다. 두 원칙이 있습니다.

**세션은 서버가 쥔다.** 브라우저에는 **불투명한 세션 ID**만 쿠키로 주고, 실제 상태(누구·권한·만료)는 **Redis** 같은 서버측 저장소에 둡니다. OWASP 기준을 그대로 옮기면:

- 세션 ID는 **의미 없는 난수**여야 하고(내용을 디코드해 정보를 캐낼 수 없게), **CSPRNG(암호학적으로 안전한 난수 생성기, Cryptographically Secure Pseudo-Random Number Generator)**로 생성합니다. OWASP는 최소 **64비트 엔트로피**를 요구하며, 브루트포스 여유를 위해 통상 **128비트 이상 길이**를 씁니다.
- 쿠키는 `HttpOnly`(JS 접근 차단)·`Secure`(HTTPS 전용)·`SameSite`를 답니다. `SameSite=None`을 `Secure` 없이 쓰지 마십시오. 가능하면 **`__Host-` 접두사**(+`Path=/`, `Domain` 미설정)로 쿠키 범위를 현재 호스트로 좁힙니다(서브도메인 공격면 축소).
- **로그인 시 세션 ID를 반드시 재발급(회전)**합니다 — 세션 고정(fixation) 공격을 막는 필수 조치입니다.
- **절대 만료**(활동과 무관한 최대 수명)와 **유휴 만료**(무활동 시 만료)를 두고, 로그아웃 시 서버측 세션을 **삭제**합니다.

```http
Set-Cookie: __Host-SID=9vY3...불투명난수; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=1800
```

Redis 자체도 잠급니다 — **AUTH/ACL·TLS·네트워크 격리**, 세션 키에 **TTL**을 걸어 만료를 강제합니다(민감정보를 값에 그대로 두지 않기).

**토큰은 브라우저에서 치운다(BFF).** SPA가 액세스·리프레시 토큰을 `localStorage`에 두면, XSS 한 번에 털립니다 — 악성 JS는 정상 앱 코드와 **같은 권한**을 가지니까요. 이를 근본적으로 막는 패턴이 **BFF(Backend-for-Frontend)**입니다(IETF "OAuth 2.0 for Browser-Based Apps" 초안이 민감한 앱에 강력 권장하지만, 아직 Internet-Draft 단계입니다).

- BFF(서버측)가 **confidential 클라이언트**로 OAuth를 수행하고, **액세스·리프레시 토큰을 서버측 세션 안에** 보관합니다.
- 브라우저에는 **HttpOnly 세션 쿠키만** 줍니다. 토큰은 브라우저에 **도달하지 않습니다**.
- 브라우저가 API를 호출하면 BFF가 요청을 리소스 서버로 **프록시하며 액세스 토큰을 덧붙입니다**.

토큰이 브라우저에 도달하지 않으니, **토큰을 훔치는 경로**는 사라집니다. 다만 오해는 말아야 합니다 — BFF가 XSS를 **없애지는 못합니다.** 악성 JS가 여전히 사용자의 세션 쿠키를 타고 BFF에 **정상처럼 요청**을 보낼 수 있으니, CSP·입력 정제 같은 **XSS 대응은 그대로 필수**입니다. BFF는 "토큰 유출"을 막을 뿐입니다.

### 리프레시 토큰 회전과 재사용 감지

액세스 토큰은 **짧게**(예: 5분) 두고, 만료되면 리프레시 토큰으로 갱신합니다. RFC 9700은 **public 클라이언트의 리프레시 토큰은 sender-constrained이거나 회전(rotation)**이어야 한다고 **MUST**로 요구합니다. BFF는 confidential 클라이언트라 이 MUST의 직접 대상은 아니지만, **회전+재사용 감지는 BFF에도 권장되는 방어**입니다.

회전은 이렇게 동작합니다. **토큰을 갱신할 때마다 새 리프레시 토큰을 발급하고, 옛 것을 무효화**합니다. 유출된 옛 리프레시 토큰이 다시 쓰이면(공격자와 정상 클라이언트가 같은 토큰을 쓰면), 둘 중 하나가 **무효화된 토큰을 제시**하게 되어 서버가 침해를 감지하고, **활성 리프레시 토큰을 폐기**해 흐름을 끊습니다(업계에서는 흔히 "토큰 패밀리 폐기"라 부릅니다). 단, 동시 요청이 많은 환경에서는 정상 클라이언트가 갱신 도중 **옛 토큰을 잠깐 겹쳐 제시**해 오탐될 수 있으니, 짧은 **grace period**(옛 토큰을 즉시 폐기하지 않고 유예를 두는 기간)나 분산 락으로 완화합니다.

## 인가 집행: 토큰이 유효해도 권한은 별개다

이제 시리즈에서 가장 자주 새는 지점입니다. **액세스 토큰이 유효하다 ≠ 이 행위를 해도 된다.** 2편의 6단계로 토큰이 "진짜이고 우리 것"임을 확인했더라도, 리소스 서버는 **인가를 별도로 집행**해야 합니다.

- **scope 검증**: 토큰에 이 API가 요구하는 scope가 있는가.
- **RBAC/ABAC**(역할/속성 기반 접근제어, 1편): 토큰의 역할(표준 `scope`, 또는 Keycloak 예의 `realm_access.roles`)이나 속성으로 이 행위가 허용되는가.
- **deny-by-default**: 공개 리소스가 아니면 **기본은 거부**. 명시적으로 허용된 것만.
- **소유권(record ownership)**: "이 주문을 볼 수 있는가"는 토큰이 아니라 **이 주문이 이 사용자 것인가**로 판단합니다.

이걸 빠뜨리는 것이 OWASP Top 10:2025 **1위 A01(Broken Access Control)**입니다. 대표 유형이 **IDOR**(식별자만 바꿔 남의 레코드 접근)와 **함수 레벨 접근제어 누락**(POST/PUT/DELETE에 권한 검사 부재)입니다.

```text
❌  GET /api/orders/12345          # 토큰만 유효하면 통과 → 남의 주문도 보임(IDOR)
✅  GET /api/orders/12345
    → 토큰 검증(2편) 후: order.owner == token.sub 인지 확인, 아니면 403
```

그리고 1편·3편의 원칙을 다시 못 박습니다 — **ID Token으로 API를 인가하지 마십시오.** ID Token의 `aud`는 클라이언트를 가리킵니다. API 인가는 **액세스 토큰**의 scope·역할·audience로 합니다. 접근 실패는 **로깅하고, 반복되면 경보**를 울립니다(이상 탐지).

## 세션 쿠키를 쓰면 따라오는 것: CSRF

BFF·세션 쿠키를 쓰면 편하지만, 쿠키가 **자동 전송**되는 특성 때문에 CSRF 위험이 생깁니다. 방어는 이렇게 겹칩니다.

- **CSRF 토큰**(표준): 서버가 세션당(또는 요청당) 토큰을 발급하고 검증하는 **Synchronizer Token** 패턴. 서버 상태 유지가 어려우면 **Double-Submit Cookie** 대안.
- **`SameSite`**: 1편에서 봤듯 **보조(defense-in-depth)**일 뿐 CSRF 토큰을 대체하지 못합니다(SameSite의 'site' 판정은 등록가능 도메인, Public Suffix List 기준입니다). 함께 씁니다.
- **CORS ≠ CSRF 방어**: CORS는 CSRF를 막지 않습니다. `Access-Control-Allow-Origin`은 **확실히 통제하는 origin만** 화이트리스트로 허용해야 합니다(느슨한 CORS는 오히려 방어를 우회시킵니다).

## 자주 틀리는 포인트

시리즈를 마무리하며, 실무에서 특히 뼈아픈 실수들을 모았습니다.

- ❌ **토큰을 `localStorage`에 둔다.** → XSS 한 번에 끝. **BFF + HttpOnly 세션 쿠키**로.
- ❌ **`X-User` 같은 신원 헤더를 프록시에서 안 덮어쓴다.** → 클라이언트가 위조합니다. **인증 결과(`$user`)로 덮어쓰도록** 설정.
- ❌ **백엔드를 외부에 노출한 채 엣지에서만 인증한다.** → 직접 접근으로 통째 우회. 내부망·mTLS로 막고, 인가는 **앱에서도** 다시.
- ❌ **엣지(게이트웨이)에서 세밀한 인가까지 다 한다.** → 단일 결정점·관리 지옥. 엣지는 거친 인증, 세밀한 인가는 리소스 서버.
- ❌ **리프레시 토큰을 회전 없이 오래 쓴다.** → 유출 시 무한정 악용. **회전 + 재사용 감지**.
- ❌ **토큰이 유효하면 인가된 것으로 본다.** → IDOR·권한 상승의 문. **deny-by-default + 소유권 검증**.
- ❌ **`SameSite`만 걸고 CSRF는 끝이라 여긴다.** → 보조일 뿐. **CSRF 토큰과 함께**.

## 마무리: 네 편을 하나로

긴 여정이었습니다. 시리즈를 한 문장씩으로 압축하면 이렇습니다.

- **1편(지형도)**: 인증(누구인가)과 인가(해도 되는가)는 다른 축이다. OAuth는 위임, OIDC는 인증.
- **2편(토큰과 검증)**: 디코딩은 검증이 아니다. 서명·`iss`·`aud`·`exp`·`kid`까지 봐야 신뢰한다.
- **3편(플로우)**: 토큰은 Authorization Code + PKCE로 얻는다. 프론트채널엔 코드, 백채널엔 토큰.
- **4편(실무)**: 이 모두를 여러 겹으로 얹는다 — 프록시·세션·BFF·리소스 서버 인가.

관통하는 실무 결론 하나만 챙기신다면: **인증과 인가를 여러 겹으로 나누고, 각 겹이 자기 몫만 하게 하라**는 것입니다. 프록시는 인증을 검사하되 헤더를 믿지 말고, 세션은 서버가 쥐고, 토큰은 브라우저에서 치우고, 인가는 리소스 서버가 deny-by-default로 집행합니다. 어느 한 곳도 "여기서 다 끝난다"고 믿지 않는 것 — 그것이 심층 방어의 태도이자, 이 시리즈가 내내 말한 "**토큰이 유효한가와 이 행위를 해도 되는가는 다른 질문**"의 실천입니다.

여기까지 함께해 주셔서 감사합니다. 이제 여러분은 로그인 화면 뒤의 지형 전체를 스스로 그릴 수 있습니다.
