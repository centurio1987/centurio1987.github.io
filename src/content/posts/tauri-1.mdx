"Tauri로 만들면 앱이 몇 MB밖에 안 된다." Tauri를 소개하는 글의 첫 문장은 대개 이 숫자입니다. 인상적인 수치이고, 실제로 사실에 가깝기도 합니다. 다만 이 문장에는 함정이 하나 있습니다. **작은 번들은 원인이 아니라 결과라는 점**입니다.

Tauri가 가벼운 이유를 "가볍게 설계했으니까"라고 답하면 아무것도 설명한 것이 아닙니다. 정확한 답은 이렇습니다. Tauri는 화면을 그리는 렌더러(브라우저 엔진)와 JavaScript 런타임(Node.js)을 **앱 안에 넣지 않습니다.** 대신 운영체제에 이미 깔려 있는 WebView를 빌려 쓰고, 뒷단은 Rust로 짠 작은 코어에 맡깁니다. 번들 크기는 그 설계에서 자연히 따라온 부산물일 뿐입니다.

그래서 이 글은 "몇 MB"라는 결과가 아니라, 그 결과를 만든 **구조**를 거꾸로 파고듭니다. 무엇을 빼서 무엇을 얻고, 그 대가로 무엇을 감수하는가. 이 한 줄을 끝까지 추적하면 Tauri의 런타임 아키텍처, 프런트엔드와 백엔드가 대화하는 IPC, 그리고 v2에서 완전히 새로 짜인 보안 모델까지 한 번에 손에 잡히실 겁니다. 이 글을 다 읽으시면, 팀에서 "우리 앱을 Electron으로 할까 Tauri로 할까"라는 질문이 나왔을 때 숫자가 아니라 구조로 답하실 수 있게 됩니다.

> 이 글은 Tauri **2.x** 공식 문서(v2.tauri.app)를 1순위 근거로 삼았습니다. 2.0 정식 릴리스는 2024년 10월 2일이며, 참고한 공식 문서는 2026년 7월 확인 기준입니다(페이지별 갱신일은 상이). 보안·IPC·번들러는 2.x에서 변화가 잦으니, 실제 도입 시점에는 문서 버전을 한 번 더 확인하시길 권합니다. 또한 이 글은 데스크톱(Windows·macOS·Linux)을 중심으로 구조를 설명합니다. v2는 모바일(iOS·Android)도 지원하지만, 그 세부는 다음 편에서 다룹니다.

## 한눈에 보기

본론에 들어가기 전에 지도를 먼저 펼쳐 두겠습니다. 이 글은 다음 다섯 축을 순서대로 다룹니다.

- **"안 넣어서 얻는다"** — Tauri가 렌더러·Node.js 런타임을 번들하지 않고 OS WebView를 런타임에 빌려 쓰는 설계.
- **런타임 해부** — OS에 대한 전권을 쥔 Rust **Core 프로세스** 하나가, UI를 그리는 **WebView 프로세스**를 오케스트레이션하는 구조.
- **IPC** — 두 세계를 잇는 다리. 요청-응답형 **Command**와 단방향 **Event**, 그리고 대용량용 **Channel**.
- **보안 모델** — v1의 전역 허용목록을 대체한 **permissions · scopes · capabilities** 3요소와, 이를 런타임에 강제하는 Runtime Authority.
- **정직한 트레이드오프** — Electron과의 구조적 차이, 그리고 "OS마다 다른 WebView"가 치르게 하는 비용.

이 지도에서 길을 잃지 않는 열쇠는 하나입니다. **Tauri의 모든 이야기는 "신뢰 경계"로 수렴한다**는 것. 어디까지가 마음껏 시스템을 만질 수 있는 영역이고, 어디부터가 통제된 영역인지 — 그 선을 잡으면 나머지는 자연스럽게 풀립니다.

## "안 넣어서 얻는다" — 동적 링크와 런타임 미번들

전통적인 웹 기반 데스크톱 앱, 즉 Electron은 앱마다 **Chromium(브라우저 엔진)과 Node.js(JavaScript 런타임)를 통째로 동봉**합니다. 어느 컴퓨터에 설치되든 똑같이 동작하는 대신, 앱 하나하나가 브라우저 한 벌을 짊어지는 셈입니다.

Tauri는 정반대 선택을 합니다. 화면 렌더링은 **운영체제에 이미 설치된 WebView**에게 맡깁니다. Windows에서는 WebView2(Chromium 기반의 Edge 엔진), macOS에서는 WKWebView, Linux에서는 webkitgtk가 그 역할을 합니다. 이들은 앱에 번들되는 것이 아니라 **런타임에 동적으로 링크(dynamically linked at runtime)**됩니다. 여기에 더해 백엔드용 JavaScript 런타임인 Node.js도 동봉하지 않습니다. 여기서 한 가지 오해를 막아 두겠습니다. 프런트엔드 코드는 WebView 안에 내장된 JS 엔진(예: WKWebView의 JavaScriptCore)이 실행하므로, "JavaScript가 안 돈다"는 뜻이 아니라 **앱마다 Node.js 런타임을 따로 짊어지지 않는다**는 뜻입니다.

렌더러 한 벌과 Node.js 런타임 한 벌 — 데스크톱 앱 용량의 대부분을 차지하던 두 덩어리가 빠집니다. "몇 MB"라는 숫자는 바로 여기서 나옵니다. 원인은 크기를 줄이려는 노력이 아니라, **애초에 무엇을 넣지 않기로 한 설계 결정**입니다.

다만 예외도 있습니다. Windows에서는 WebView2 런타임이 설치돼 있지 않은 환경을 대비해, 설치 관리자가 부트스트래퍼로 런타임을 내려받게 하거나 고정 버전 런타임을 함께 동봉하도록 설정할 수 있습니다. 이 선택은 번들 크기와 오프라인 설치 전략에 직접 영향을 줍니다. 즉 "무조건 작다"가 아니라 "무엇을 빌리고 무엇을 동봉하느냐"의 문제라는 점을 기억해 두시면 좋습니다.

물론 공짜는 아닙니다. OS가 제공하는 WebView는 종류도 버전도 제각각이라, "내 코드가 모든 플랫폼에서 똑같이 보이는가"를 스스로 책임져야 합니다. 이 대가는 뒤에서 정직하게 짚겠습니다. 먼저 "무엇을 넣지 않았는가"만큼 중요한 것 — **그럼 무엇을 넣었는가**를 볼 차례입니다.

## 런타임 해부 — Core 하나가 WebView를 오케스트레이션한다

Tauri 앱을 실행하면 프로세스가 여럿 뜹니다. 최신 웹 브라우저나 Electron이 그렇듯, Tauri도 **멀티 프로세스** 구조입니다. 공식 문서의 한 문장이 전부를 요약합니다. *"하나의 Core 프로세스가 하나 이상의 WebView 프로세스를 관리한다."*

<TauriRuntimeArchitecture />

이 그림의 층위를 하나씩 뜯어보겠습니다.

**Core 프로세스**는 앱에서 운영체제에 **전권(full access)을 가진 유일한 컴포넌트**입니다. Rust로 작성되며, 창과 시스템 트레이 메뉴와 알림을 만들고, 모든 IPC를 라우팅하고, 설정이나 데이터베이스 커넥션 같은 전역 상태를 관리합니다. 앱의 "두뇌"이자 "손"입니다.

**WebView 프로세스**는 화면을 그립니다. OS의 WebView 라이브러리로 여러분이 작성한 HTML·CSS·JavaScript를 실행합니다. 여기서 흔한 오해를 하나 바로잡겠습니다. WebView가 무력한 것은 아닙니다 — 브라우저가 기본 제공하는 `fetch`, WebSocket, 로컬 스토리지 같은 웹 표준 기능은 그대로 쓸 수 있습니다. 다만 **OS의 파일 시스템이나 네이티브 권한이 필요한 작업**, 곧 Tauri가 노출하는 시스템 커맨드는 직접 부를 수 없고, 반드시 IPC를 거쳐 Core에 요청해야 합니다. 통제되는 것은 '웹'이 아니라 '네이티브 권한으로 가는 문'입니다.

Tauri가 굳이 프로세스를 나눈 데에는 두 가지 이유가 있습니다. 첫째는 **복원력과 격리**입니다. 한 컴포넌트가 죽어도 앱 전체가 함께 무너지지 않고, 개별 프로세스만 재시작할 수 있습니다. 둘째는 **최소 권한 원칙(Principle of Least Privilege)**입니다. 각 프로세스에는 "자기 일을 할 만큼만" 권한을 줍니다. UI를 그리는 데 파일 시스템 전권이 필요하지는 않으니까요.

이 층위 아래에서 실제 일을 하는 것은 몇 개의 Rust 라이브러리입니다. `tauri` 크레이트가 중심 바인딩으로, 컴파일 타임에 `tauri.conf.json`을 읽고 런타임에 스크립트 주입·시스템 API·업데이터를 담당합니다. 화면을 어느 WebView로 그릴지 결정하는 것은 **WRY**(cross-platform WebView rendering library)이고, 창 자체를 만드는 것은 winit에서 갈라져 나온 **TAO**입니다. 플랫폼마다 다른 이 조각들을 하나로 추상화하는 접착층이 `tauri-runtime`입니다. 여기까지가 "무엇을 넣었는가"에 대한 답입니다.

## IPC — 두 세계를 잇는 유일한 다리

앞의 그림에서 가운데 층, IPC(Inter-Process Communication, 프로세스 간 통신) 브리지가 이 아키텍처의 심장입니다. WebView(신뢰할 수 없는 영역)와 Rust Core(전권을 가진 영역)라는 두 신뢰 그룹을 잇는 다리이자, 동시에 **경계**입니다. 정확히 말하면, WebView가 **네이티브 권한(시스템 커맨드)에 접근하는 유일한 통로**가 IPC입니다. 물리적으로는 커스텀 프로토콜과 WebView에 주입된 JS 바인딩을 통해 메시지가 오갑니다.

Tauri의 IPC는 **비동기 메시지 패싱(Asynchronous Message Passing)** 방식입니다. 두 프로세스가 메모리를 직접 공유하는 대신, 직렬화된 요청과 응답을 주고받습니다. 이 방식이 안전한 이유는 명확합니다. 수신하는 쪽이 메시지를 **실행하기 전에 검사하고 거부할 수 있기 때문**입니다. 뒤에 나올 보안 모델 전체가 바로 이 성질 위에 서 있습니다.

통신 수단은 두 가지 기본형으로 나뉩니다.

- **Command** — 요청하고 응답을 받는 방식. 프런트엔드에서 `invoke()`를 부르면, 브라우저의 `fetch`처럼 생긴 이 함수가 Rust 쪽 함수를 인자와 함께 호출하고 결과를 돌려받습니다.
- **Event** — 던지고 잊는(fire-and-forget) 단방향 메시지. 라이프사이클 알림이나 상태 변화를 흘려보낼 때 씁니다. 프런트엔드와 Core **양쪽 모두** 이벤트를 쏠 수 있습니다.

Command가 실제로 어떻게 오가는지, 왕복 흐름을 네 단계로 끊어 보겠습니다.

<InvokeRoundTrip />

코드로 보면 놀랄 만큼 단순합니다. Rust 쪽에서는 함수 위에 `#[tauri::command]` 애트리뷰트를 붙이고, 빌더에 등록만 하면 됩니다.

```rust
#[tauri::command]
fn greet(message: String) -> String {
    format!("Hello: {message}")
}

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .invoke_handler(tauri::generate_handler![greet])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

프런트엔드에서는 이렇게 부릅니다.

```javascript
import { invoke } from '@tauri-apps/api/core';

const reply = await invoke('greet', { message: 'World' });
// reply === "Hello: World"
```

여기서 기억할 제약이 하나 있습니다. **일반 커맨드의 인자와 반환값은 직렬화 가능한 값이어야 합니다.** IPC가 프로세스 경계를 넘는 메시지 패싱인 이상, 복잡한 객체나 핸들을 그대로 건네줄 수는 없습니다(대용량·바이너리를 주고받는 경로는 곧 따로 설명합니다). 커맨드는 `async`로 만들어 논블로킹으로 돌릴 수 있고, 반환 타입을 `Result<T, E>`로 두면 에러가 프런트의 Promise reject로 자연스럽게 전달됩니다.

문제는 데이터가 커질 때입니다. 예전에는 모든 IPC 페이로드가 JSON으로 직렬화·역직렬화됐는데, 수 KB만 넘어가도 이 오버헤드가 눈에 띄었습니다. 그래서 v2는 두 가지 길을 열었습니다. 하나는 바이너리를 그대로 실어 보내는 raw request(예: `ArrayBuffer` 페이로드)이고, 다른 하나는 `tauri::ipc::Channel<T>`이라는 **스트리밍 통로**입니다. 다운로드 진행률, 자식 프로세스의 출력, WebSocket 메시지처럼 조각조각 순서대로 밀어 보내야 하는 데이터는 Channel로 흘려보냅니다. Event가 소량의 데이터를 가볍게 흘려보내는 통신이라면, Channel은 순서를 보장하고 강한 타입을 유지하는 고속 파이프로 이해하시면 됩니다.

## 보안 모델 — permissions · scopes · capabilities

여기서부터가 v2의 진짜 변화입니다. v1에는 **allowlist**라는 전역 스위치가 있었습니다. "이 앱에서 파일 시스템 API를 켠다/끈다"를 앱 전체 단위로 정하는 방식이었죠. 편하지만 거칠었습니다. 창이 여러 개일 때, 신뢰도가 다른 화면들에 똑같은 권한이 일괄로 주어지는 것을 막기 어려웠습니다.

v2는 이것을 세 개의 개념으로 쪼갰습니다.

- **Permission(퍼미션)** — 개별 커맨드에 대한 켬/끔 정의입니다(`commands.allow`/`deny`, 그리고 아래 스코프까지 포함하는 접근 제어 항목). "이 커맨드를 호출할 수 있다/없다"를 정합니다.
- **Scope(스코프)** — 커맨드에 넘기는 인자를 검증합니다. 예컨대 "파일 읽기는 되지만, `~/Documents` 아래만"처럼 허용·거부 경로를 못박습니다.
- **Capability(케이퍼빌리티)** — 위 퍼미션과 스코프를 **특정 창(Window)이나 WebView에 부착**합니다. "메인 창은 이 권한 묶음을 갖는다"를 선언하는 단위입니다.

퍼미션의 식별자는 `<플러그인>:<커맨드>` 꼴을 따릅니다. 예를 들어 `fs:read-files`는 파일 시스템 플러그인의 `read-files` 퍼미션을 가리키고, `<이름>:default`는 그 플러그인의 기본 퍼미션 묶음을 뜻합니다. 여러 퍼미션을 하나의 새 식별자로 묶은 **퍼미션 세트(permission set)**를 만들어 재사용할 수도 있습니다.

케이퍼빌리티는 `src-tauri/capabilities/` 아래에 JSON(또는 TOML)으로 둡니다. 실제 파일은 이렇게 생겼습니다.

```json
{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "main-capability",
  "description": "메인 창에 부여하는 권한 묶음",
  "windows": ["main"],
  "permissions": [
    "core:path:default",
    "core:event:default",
    "core:window:default",
    "core:app:default",
    "core:window:allow-set-title"
  ]
}
```

`windows`가 이 권한을 받을 창을 지정하고, `permissions` 배열이 허용할 커맨드를 나열합니다. `platforms` 필드로 특정 OS(linux·macOS·windows·iOS·android)에만 적용하거나, `remote` 필드로 허용할 원격 도메인을 못박을 수도 있습니다.

한 가지 짚을 점이 있습니다. 여러분이 `#[tauri::command]`로 **직접 만든 앱 커맨드**는 기본적으로 창에서 호출할 수 있습니다. 케이퍼빌리티가 촘촘히 통제하는 주된 대상은 코어와 플러그인이 노출하는 **시스템 커맨드**(`core:`, `fs:`, `shell:` 같은 접두사)입니다. 즉 뒤에서 말할 "기본 차단"은 위험한 네이티브 권한에 대한 이야기이지, 여러분이 짠 모든 함수가 케이퍼빌리티 없이는 막힌다는 뜻은 아닙니다.

그렇다면 이 선언들은 언제 강제될까요? 정답은 **런타임**입니다. 케이퍼빌리티는 컴파일 타임에 설정에서 취합되어 바이너리에 구워지고, 실행 중에는 **Runtime Authority**라는 관문이 그 표를 손에 쥡니다. WebView에서 커맨드 호출이 들어오면, Runtime Authority가 "이 요청을 보낸 창(origin)이 정말 이 커맨드를 쓸 자격이 있는가"를 확인하고, 정의된 스코프를 주입한 뒤에야 통과시킵니다. 한 가지 뉘앙스는, 스코프의 최종 해석까지 관문이 자동으로 끝내는 것은 아니라는 점입니다. 관문이 스코프를 주입하면 **커맨드 구현이 그 스코프를 읽어** "어느 경로까지 허용할지" 같은 세밀한 판단을 내립니다. 앞서 IPC가 "실행 전에 거부할 수 있다"고 했던 그 성질이, 여기서 구체적인 인가 게이트로 실체화됩니다.

정리하면 신뢰 경계는 이렇게 그어집니다. **Rust 코어와 플러그인 코드는 시스템 자원에 무제약으로 접근**합니다. 반면 **WebView의 코드는 IPC로 명시적으로 노출된 시스템 커맨드에만 접근**할 수 있고, 그 접근조차 케이퍼빌리티로 창별로 좁혀집니다. 기본이 "차단"이고, 필요한 것만 골라 여는 구조입니다. 다만 케이퍼빌리티가 보안의 전부는 아닙니다. WebView에서 XSS(Cross-Site Scripting)가 터지면 이미 허용된 케이퍼빌리티 범위 안에서는 피해가 가능하므로, 콘텐츠 보안 정책(CSP), 원격 콘텐츠 최소화, "비밀 값을 WebView에 두지 않기" 같은 원칙이 함께 가야 합니다.

## 설정과 사이드카 — tauri.conf.json 지도

이 모든 것을 묶는 설정 파일이 `tauri.conf.json`입니다. 최상위 키만 훑어도 앱의 뼈대가 보입니다. `identifier`(역방향 도메인 표기, 필수), `productName`, `version`, 그리고 세 개의 큰 블록 — `build`, `app`, `bundle` — 과 `plugins`입니다.

`app` 블록에는 `windows`(창 설정)와 `security`가 들어갑니다. 보안 항목에는 콘텐츠 보안 정책 `csp`, 그리고 방금 본 `capabilities`가 자리합니다. `bundle` 블록은 배포물의 모양을 정합니다. 어떤 인스톨러를 만들지(`targets`: deb·nsis·dmg 등), 어떤 파일을 함께 묶을지(`resources`), 아이콘은 무엇인지(`icon`)를 지정합니다.

`bundle` 안에서 눈여겨볼 것이 `externalBin`, 곧 **사이드카(sidecar)**입니다. 사이드카는 앱에 임베드하는 외부 실행 파일입니다. 사용자가 별도로 무언가를 설치하지 않아도 되도록, 이를테면 `pyinstaller`로 묶은 Python CLI나 API 서버를 앱과 함께 배포할 때 씁니다. 이때 사이드카는 런타임 의존성까지 포함한 **단일 실행 파일**로 빌드돼 있어야 사용자 환경에서 그대로 동작합니다. 다만 규칙이 하나 더 있습니다. 각 바이너리 이름 뒤에 **타깃 트리플(target triple) 접미사**를 붙여야 합니다. 예컨대 `my-sidecar`는 Linux에서 `my-sidecar-x86_64-unknown-linux-gnu`, Apple Silicon macOS에서 `my-sidecar-aarch64-apple-darwin`으로 존재해야 합니다. 자기 플랫폼의 트리플은 `rustc -vV`의 `host:` 항목(또는 `tauri info`)에서 확인할 수 있습니다.

호출은 shell 플러그인을 통합니다. 프런트엔드에서는 `Command.sidecar('binaries/my-sidecar').execute()`로 실행하며, 물론 이 동작도 케이퍼빌리티에서 `shell:allow-execute` 같은 퍼미션으로 허용해 두어야 합니다. 보안 모델은 사이드카에도 예외 없이 적용됩니다.

## Tauri vs Electron — 정직한 트레이드오프

이제 가장 많이 나오는 질문으로 돌아오겠습니다. Electron과 무엇이 다른가. 표면의 숫자가 아니라 구조로 나란히 놓아 보겠습니다.

<TauriVsElectron />

세 축으로 요약됩니다. **렌더러**: Electron은 Chromium을 번들해 어디서나 똑같이 그리고, Tauri는 OS WebView를 빌려 써서 가벼운 대신 엔진이 플랫폼마다 다릅니다. **백엔드**: Electron은 Node.js, Tauri는 메모리 안전성과 성능을 노린 Rust 코어입니다. **보안 기본값**: 공정하게 말하면 Electron도 근래 버전(12+)은 `contextIsolation: true`·`nodeIntegration: false`를 기본값으로 강화해 왔습니다. 다만 여전히 개발자가 preload 스크립트로 노출 경계를 직접 설계·관리하는 모델인 반면, Tauri는 기본이 차단이고 capabilities로 창마다 명시해 여는 쪽입니다.

여기서 Tauri의 단점을 정직하게 말해야 공정합니다. **"OS마다 다른 WebView"는 곧 렌더링과 기능의 파편화를 뜻합니다.** WebView2·WKWebView·webkitgtk는 엔진도 버전도 제각각이라, 한 곳에서 멀쩡하던 CSS나 최신 웹 API가 다른 OS에서는 다르게 동작하거나 아예 빠져 있을 수 있습니다. 특히 Linux의 webkitgtk가 가장 거친 지점입니다 — 배포판마다 WebKitGTK 버전과 미디어 코덱 지원, 의존 라이브러리가 달라 실제 배포에서 가장 손이 많이 갑니다. Electron이 "Chromium 고정 = 일관성"으로 사는 값을, Tauri는 "가벼움"의 대가로 **직접 테스트할 책임**으로 치릅니다. 어느 쪽이 옳은 선택인지는 앱의 성격이 정합니다. 이것이 트레이드오프의 실체입니다.

## 수치로 보기 — 대표값이 아니라 예시 측정

그렇다면 그 "가벼움"은 실제로 얼마나 될까요. 여기서 조심할 것이 있습니다. **번들 크기와 메모리는 앱 구성과 측정 환경에 따라 크게 달라져서, "Tauri 앱은 무조건 X MB"라고 단정할 수 없습니다.** 그래서 절대치가 아니라, 방법론이 공개된 한 벤치마크의 **예시 측정 한 건**을 그대로 인용하겠습니다.

이 측정은 최소 템플릿 앱으로 창 여섯 개를 열어 재본 것으로, 저자 스스로 "단일 실행이니 가려서 보라"고 면책을 답니다. 그럼에도 방향은 분명합니다. 번들에서는 수십 배 차이가, 메모리에서도 두 배 넘는 차이가 관찰됩니다. 업계에 널리 인용되는 대표 범위로 넓혀 보면 Tauri 인스톨러는 대략 수 MB대, Electron은 80~200MB대로 이야기됩니다만, 이 역시 통설일 뿐 여러분의 앱에 그대로 대입할 수치는 아닙니다. 왜 차이가 나는가에 대한 답은 처음에 이미 나왔습니다. Electron은 Chromium과 Node.js를 동봉하고, Tauri는 OS WebView를 빌리며 Node.js 런타임을 동봉하지 않기 때문입니다. 숫자는 여기서도 원인이 아니라 결과입니다.

## 실무에서 부딪히는 벽 — 구조가 만드는 두 가지 함정

지금까지 그린 구조는 실제 개발에서 특정한 방식으로 발목을 잡습니다. 아직 예시 프로젝트를 만들기 전이지만, "이 구조를 알면 어떤 증상을 어떻게 읽어야 하는가"만 미리 잡아 두겠습니다. 다음 편에서 코드를 짤 때 그대로 쓰이는 진단 감각입니다.

### 함정 1: `invoke`를 불렀는데 "command not found"가 뜬다

1. **원리** — 프런트의 `invoke('greet')`는 Core에 "greet 커맨드를 실행해 달라"는 메시지를 보냅니다. Core는 `generate_handler!`에 **등록된** 커맨드만 알고, 시스템 커맨드라면 그 위에서 케이퍼빌리티까지 확인합니다.
2. **흔한 문제** — 커맨드 함수는 만들었는데 `tauri::generate_handler![...]` 목록에 이름을 빠뜨렸거나, 플러그인 커맨드를 부르면서 케이퍼빌리티에 해당 퍼미션을 넣지 않은 경우입니다.
3. **진단·해결** — 먼저 WebView 개발자 콘솔의 에러 메시지를 봅니다. "command greet not found"라면 등록 누락이니 `generate_handler!` 목록에 이름을 추가합니다. 반대로 "not allowed"/권한 관련 메시지라면 `src-tauri/capabilities/`의 해당 창 케이퍼빌리티에 `fs:...`·`shell:...` 같은 퍼미션을 더합니다.
4. **팁** — 두 원인은 에러 문구로 갈립니다. "없다(not found)"는 **등록** 문제, "안 된다(not allowed)"는 **권한** 문제로 나눠 접근하면 헤매지 않습니다.

### 함정 2: macOS에선 멀쩡하던 화면이 Windows에서 깨진다

1. **원리** — Tauri는 OS의 WebView를 빌려 쓰므로, 같은 코드라도 macOS의 WKWebView와 Windows의 WebView2는 **엔진과 버전이 다릅니다.** 브라우저 호환성 문제가 그대로 데스크톱 앱으로 옮겨 온 것입니다.
2. **흔한 문제** — 개발은 한 OS에서만 하다가, 최신 CSS나 특정 웹 API가 다른 OS의 WebView에서 지원되지 않아 레이아웃이나 기능이 어긋납니다. Linux의 webkitgtk에서 미디어 코덱이 빠져 재생이 안 되는 경우도 여기 속합니다.
3. **진단·해결** — 증상이 나온 OS의 WebView 엔진과 버전을 먼저 확인하고, 문제되는 기능을 [caniuse](https://caniuse.com) 같은 표에서 해당 엔진 기준으로 대조합니다. 필요하면 폴리필을 넣거나, 그 기능을 쓰지 않는 대안으로 우회합니다.
4. **팁** — "한 곳에서 됐으니 다 된다"는 가정이 가장 위험합니다. 최소한 배포 대상 OS마다 한 번씩은 실제 WebView로 확인하는 것을 배포 절차에 넣어 두십시오.

## 자주 오해하는 점

마지막으로, 입문자는 물론 경험자도 자주 헛디디는 지점 세 가지를 짚겠습니다.

- **"Tauri는 서버가 필요 없다"** — 아닙니다. Tauri는 데스크톱 런타임일 뿐, 여러분의 앱이 원격 API를 부르거나 데이터를 동기화한다면 백엔드 서버는 여전히 필요합니다. "네이티브 백엔드가 Rust"라는 말과 "서버가 없다"는 말은 전혀 다릅니다.
- **"Tauri 앱은 무조건 몇 MB다"** — 대표 범위일 뿐입니다. 무거운 프런트엔드 자산, 사이드카로 묶은 외부 바이너리, 번들한 리소스가 더해지면 크기는 얼마든 커집니다. 단일 절대치로 약속하지 마십시오.
- **"프런트엔드는 Rust를 몰라도 되니 Rust는 배울 필요 없다"** — 절반만 맞습니다. 간단한 앱은 기본 커맨드만으로 갈 수 있지만, 시스템을 깊이 다루는 커맨드를 직접 만들거나 성능을 손보려면 결국 Rust 코어를 만지게 됩니다. Tauri의 힘은 그 경계 너머에 있습니다.

## 마무리 — 구조를 알면 숫자가 보인다

처음의 문장으로 돌아가겠습니다. "Tauri 앱은 가볍다." 이제 이 문장은 결론이 아니라 **출발점**입니다. Tauri는 렌더러와 Node.js 런타임을 번들에서 빼고 OS WebView를 빌려 쓰며, 전권을 가진 Rust Core 하나가 통제된 WebView를 오케스트레이션합니다. 둘 사이는 네이티브 권한으로 갈 때 오직 IPC로만 대화하고, 그 통로는 permissions·scopes·capabilities와 Runtime Authority로 창마다 좁혀집니다. 작은 번들은 이 설계에서 따라온 결과이며, 그 대가로 "OS마다 다른 WebView"라는 파편화를 감수합니다.

그러니 "Electron이냐 Tauri냐"라는 질문에는 이렇게 답하실 수 있습니다. **일관된 렌더링과 성숙한 생태계가 절실하면 Electron이, 가벼움과 촘촘한 보안 경계가 절실하면 Tauri가 유리합니다.** 숫자가 아니라 구조로 고르는 것 — 그것이 이 글의 목표였습니다.

다음 편에서는 이 개념들을 실제로 손에 쥐어 보겠습니다. 커맨드와 이벤트, 케이퍼빌리티, 사이드카를 두루 쓰는 **예시 프로젝트를 처음부터 구현**하면서, 오늘 그린 구조가 코드에서 어떻게 살아 움직이는지 추적할 예정입니다. 구조를 알았으니, 이제 만들 차례입니다.
