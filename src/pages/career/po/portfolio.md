# 포트폴리오 — PO

> 엔지니어의 시야로 *기술 자산·역량·비용 추정*까지 포함한 실행 계획을 만드는 PO. 전략 분석부터 제품화 전략까지 직접 수행.

## 방법론·역량 한눈에

- **전략 분석 파이프라인**: PESTEL → 3C / 5Forces / SWOT → STP → Value Chain
- **제품 발견**: Contextual Inquiry · Data Synthesis · VOC 3pager · 결제권자·사용자 분리 분석
- **제품 정의·제품화 전략**: PMF 정렬 · 솔루션·시나리오·IA · 세일즈·프라이싱
- **팀·프로세스**: Product Engineer 육성 · 컨센서스 리뷰 · Notion 단일 지식·자동화 · ProdOps
- **엔지니어링 시야 (보조)**: DDD · Plugin 아키텍처 · NestJS · Vue 3 · Kubernetes · IaC

## 1. 풀무간 — '진짜 LCA 분석'을 돕는 제품 발견 (2025.06 – 2025.12)

> 결제권자와 사용자의 가치 비대칭을 해소하기 위해 PO 역할을 인수해 컨설팅 중심으로 제품 전략을 재정의한 제품 발견 프로젝트.

[시각 자료]
- 전략 분석 파이프라인 (PESTEL → 3C / 5F / SWOT → STP → Value Chain)
- As-Is / To-Be 워크플로우 (LCA 솔루션 → 컨설팅 중심 제품)
- 솔루션 컨셉 (레이어·작업 공간)
- 결제권자·사용자 가치 비대칭 도식

### 진단

| 축 | 실무자 | 결제권자 |
|----|--------|----------|
| LCA 제품 평가 | 높음 | 무관심 |
| 데이터 수집 페인 | 큼 | — |
| 가치 인식 | 분석 도구 | 보고서 신뢰성 |
| 결과 | **계약 성사율 저조** | |

### 선택지 비교

| 옵션 | 단기 영향 | 장기 영향 |
|------|----------|----------|
| 기능 추가로 계약율 개선 | 즉시 가능 | 결제권자 무관심 미해결 |
| 가격·세일즈 전술 변경 | 단기 계약율↑ | 제품 정의 흔들림 |
| **PO 역할 인수, 제품 제로부터 재정의** | 큰 정치적·시간 비용 | *제품·전략·세일즈 일관 정렬* |

### 핵심 결정

> "결제권자와 사용자가 다르고 *원하는 것도 다르다.* 그러면 제품 가치 명제 자체를 재정의해야 한다."

대표·이사와 담판해 PO 권한 확보. 합리성·전문성으로 경영진 설득.

### 실행 파이프라인

```
전면 진단
  └─▶ VOC 3pager 작성·교육
        └─▶ 전략 분석 (PESTEL · 3C · 5F · STP · Value Chain)
              └─▶ Contextual Inquiry (내부 컨설팅팀 관찰·인터뷰)
                    └─▶ Data Synthesis (3대 핵심 문제 영역 도출)
                          └─▶ 결론: "신뢰할 수 있는 결과물을 빠르게 제공하는 컨설팅"
                                └─▶ 솔루션·시나리오·IA·제품화 전략 (컨설팅 앞세운 세일즈, 저가 프라이싱)
```

### 변화

단발성 MVP 반복 → *전략적 제품 활동* 정착. 데이터를 인사이트로 전환해 다음 제품으로 이음.

## 2. LynC — PMF 없는 시장에서 도메인 자체를 자산화 (2023.06 –)

> "지금 만든 제품이 이후 PMF를 찾았을 때 *엔진으로 재사용 가능*해야 한다."

[시각 자료]
- PMF 없는 시장의 제품 자산화 도식 (시장 ↔ 도메인 ↔ 제품)
- 단계별 의도적 아키텍처 분기 (Prototype Next.js / MVP DDD / 운영 Plugin)

### PO 시각의 핵심

- LCA 시장은 형성되지 않아 PMF에 기댈 수 없는 상태.
- *어떤 자산이 시장의 표면 변화에도 흔들리지 않는가* → **도메인 자체** (ISO 14040·14044 이론적 기반).
- 4주 프로토타입(시장 검증·판촉)과 본 제품 MVP(도메인 자산화)를 의도적으로 다르게 설계.

### 단계별 의도적 분기

| 단계 | 목적 | 아키텍처 | PO 관점 결정 기준 |
|------|------|----------|------------------|
| Prototype (4주) | 시장 검증·판촉 | Next.js 올인원 | 영속성·도메인 부담 제거, 빠른 검증 |
| 본 제품 MVP (3개월) | 도메인 자산화 | DDD·레이어드 | PMF 찾았을 때 *엔진으로 재사용 가능* |
| 운영·업데이트 (1.5년+) | 고객사 커스텀 대응 | 헥사고날 + Plugin | 코어 동결, 확장 격리 |

## 3. ProdOps — 제품팀 개발 환경 혁신 (2024.01 – 2024.03)

> "방임과 자유는 다르다 — 조직은 구성원이 일에 집중할 환경을 제공해야 한다."

[시각 자료]
- ProdOps 4축 (지식 관리 / Ways of Working / 프로세스 / 인력)
- Notion 트리거 자동화 흐름
- 회고 체크리스트 템플릿

### 진단

경영진 아이디어 즉시 MVP 구현 방식 → 개인 역량 의존도 과다 → 전략·기획 부재 → 비용 증가·품질 저하·지속가능성 악화.

### 실행 — 4축

| 축 | 구성 |
|----|------|
| **지식 관리** | Notion 단일 지식 + 트리거 기반 워크플로우 자동화 + Artifact 템플릿 |
| **Ways of Working** | 가독성·모듈성·SoC·코드 가이드·Git 전략 · "설명할 수 있는 디자인" |
| **프로세스** | 스크럼 테일러링 + 필수 QA + 프로토타입 중심 합의 + 회고 기반 체크리스트 |
| **인력** | (병행) Product Engineer 육성 |

### 변화

표준은 디테일하게 자주 조정하되 **맥락·근거를 동반**하고 코드 리뷰에서 다뤄, 팀원 부담은 낮으면서 일정한 품질을 내는 체계.

## 4. Product Engineer 육성 — 분산된 책임 + 중앙화된 일관성 (2023.05 – 2025.12)

> 한 사람이 기획부터 엔지니어링까지 *all-in-one*으로 담당. 컨센서스 리뷰로 제품 일관성 유지.

[시각 자료]
- Product Engineer all-in-one 모형
- 컨센서스 리뷰 흐름 (개인 결정 → 사전 공유 → 합의 → 실행)

### 핵심 구조

- **all-in-one 책임**: 기획·디자인 협업·구현·운영을 한 사람이 담당.
- **PM 소양 교육**: 필요한 PM 소양을 직접 정의·교육·멘토링.
- **컨센서스 리뷰**: 각자가 PM으로서 내린 결정은 실행 전 공유해 합의 도출 → 제품 일관성 유지.

### 병행 운영

| 영역 | 구성 |
|------|------|
| 성장 관리 | 밸류업 스터디·기술 세미나 · 취약성 기반 신뢰 위의 원인 분석형 피드백 |
| Inspiration 관리 | 선제적 1on1 |
| 프로세스 QA | 자가검진 체크리스트·넛지 |
| 크로스팀 소통 | 리더십 회의·인터뷰·라포 |

### 변화

파편화된 요구 속에서도 팀원 각자가 독립적으로 프로젝트를 끌고 가는 동시에, 중앙화된 전략으로 제품의 코어 정체성·일관성 유지.
