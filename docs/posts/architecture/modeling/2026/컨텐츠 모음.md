- DDD를 도입 했을 때, RDB Schema 설계 패턴
  - Aggregate -> 테이블, 1:1 대응
    - 밸류는 식별성이 없으므로 하나의 테이블에 플래트닝한다.
    - 1:n인 경우, 여전히 플래트닝 한다. 하지만, 밸류 리스트의 수가 많은 경우, 다음의 패턴을 사용한다.
      - json을 사용한다. json 사용 시, 모델링과 영속화 하는 것은 쉬워 진다. 하지만, 쿼리가 복잡해 진다. 리스트 단위로 불러 와서 programmable하게 처리 하는 것도 방법. view 테이블을 만드는 것도 방법.
      - 별도의 테이블로 분리 한다. 단, value는 여전히 id가 없는 것이 논리적으로나 관리 측면에서나 바람직하다. 변경이 발생하는 경우, 부모 id를 참조하는 레코드를 전부 지우고 다시 삽입한다.
        - 최적화를 위해 변경이 발생 했을 경우에만 delete & insert를 수행한다. 변경 여부를 판단하기 위해 리스트를 hashing하여 부모 테이블 컬럼에서 관리하는 것도 방법
  - 상속이나 composite가 있을 경우
    - 속성의 편차가 작을 경우, 하나의 테이블로 처리하는 접근법도 있다. 상위 개념을 쿼리에서 더 자주 사용 하는 경우, 성능에서도 유리하다. 하지만, table이 sparse 해 진다는 근원적인 문제점이 있다.
  - Aggregate가 거대한 경우
    - 포함하는 모델 자체가 많은 경우, 특히 소속 Entity가 많은 경우에는 설계 관점에서 다시 생각해 본다. 특히, composition 관계가 아닌 경우를 주의 깊게 살펴보면 좋다.
    - 불가피한 경우에는, Lazy Loading 패턴을 사용한다.
      - 1:1인데 속성 자체가 많은 경우, Value 패턴을 고려하여 Root를 재구성하고 테이블을 분화한다. Value는 프록시나 데코레이터를 사용하여, 값에 접근하는 시점에 로딩하도록 구현한다.
      - collection이 문제가 되는 경우, 역시 테이블을 별도로 구성하여 위와 같이 구현한다.
- DDD에서 Composition과 Aggregation
  - Composition으로 연관된 모델은 의존적 생명주기를 가지므로, Aggregate에 소속된다.
  - Aggregation이란 결국은 '참조'다. DB에서는 참조 가능한 Aggregate의 key 칼럼을 포함한다. 하지만, 도메인에서까지 드러낼 필요는 없다. 참조의 목적이 기능 수행 시, 데이터가 필요한 것이라고 한다면, 키를 DAO로 구하여 참조 Aggregate의 정보를 가져와 도메인 메서드의 파라메터로 전달하는 방법을 쓸 수 있다.
  - Aggregation은 연관되는 모델의 생명 주기가 연관을 가지는 Aggregate 바깥에서 발생한다.
- 상속이냐 composite냐
  - 대부분은 composite 관점에서 설계하는게 좋다.
    - 상속은 더 강한 관계성을 가지고 있고, 실 사례에서는 그렇게 깔끔하게 맞아 떨어지는 상속 관계는 잘 나타나지 않는다. 따라서, evolving 과정에서 관계에 변형이 생기는 경우가 많다. composite로 구현 한 경우, 해당 모델을 배제할 수 있어서 관리가 편하다. 또한, composite은 Value의 형태로 나타난다. value의 구현 사항과 독립적으로 변경이 발생할 공산이 크다. 상속의 경우, super를 참조 하게 되는 경우, 변경에 대한 고려사항이 커진다.
    - 제네릭 타입을 사용 하는 경우에도, 상속의 경우, depth가 나타나서 구현 상의 어려움이 있다.
  - 기능 집약적 로직에서는 추상화가 가지는 의미적 절대성이 더 크기 때문에 상속에 대한 고려에 조금 더 가중치를 줄 수 있다.
  - evolving 관점에서는 비슷한 비용을 치룬다.
    - A class가 target인 경우, method 구현 규모가 크다면, 상속이 단시간에 확장할 수 있는 이점을 가져다 준다.
    - 이미 사용하고 있던 Root를 부모 클래스로 사용하도록 확장 하는 경우
      - 구상 클래스를 확장한다는 접근법 자체가 그다지 권장할만 하지 않다.
        - Root는 이미 컨텍스트에 등장하는 별도의 Entity다. 코드 상에서나 DB 상에서나 독립적인 바운더리와 생명주기를 가지고 있다.
      - 상속 개념 자체가 혼란을 야기한다. 컨텍스트 상에서는 OOP 관점의 상속 관계는 존재하지 않는 관계적 개념이다. 실제로는 컨텍스트 상에서 서로 상호 작용 하는지만 관측하면 된다.
      - 상속이 필요하다면, 문맥 레이어가 아닌, 코드 구조의 관점에서 고려해야 한다.
      - 공통의 개념을 추상화 하여 별도로 빼고, Root도 해당 추상 개념을 상속 받도록 구현한다.
      - Composite의 경우에도, 공통 Value를 정의하고, 기존 Root가 Value를
      - 상위 개념을 사용해서 로직을 전개 해야 하는 경우 때문에 설계에 대한 접근을 복잡하게 고려할 필요는 없다. 하위 개념을 각각 사용하는 경우는 필수지만, 상위 개념은 그렇지 않다. 따라서, 하위 개념 기준으로 설계 하되, 상위 개념에 대한 사용 시나리오가 나타나면 확장적으로 고려하면 된다. 이를 테면, Aggregate 단위 관계일때는 도메인 서비스에서 다형성을 사용, Aggregate 하위 엔티티 단위 관계일 때는, root의 도메인 메서드에서 다형성 사용한다. Composite의 경우, Value를 사용하는 공통적 로직을 각각 구현하되, 그에 대한 인터페이스를 정의한다.
